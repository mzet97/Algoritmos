# Aula 8 - Tratamento de erros e excecoes em Python

---

## Objetivo da Aula

Entender o modelo de erros em Python, diferenciar erro de sintaxe de excecao em runtime, usar `try`, `except`, `else`, `finally` e `raise`, criar excecoes proprias e aprender a desenhar fluxo de erro de forma legivel, segura e manutenivel.

Ao final, você deverá: capturar exceções específicas, encadear com `raise ... from`, usar `finally`/`else`, definir exceções próprias, e distinguir erro recuperável de bug.
Mediremos com níveis de proficiência:
- **Nível 1 — Recordar:** `definir exceção, `try/except/else/finally` e encadeamento`;
- **Nível 2 — Aplicar:** `diagnosticar `except` genérico que esconde bug e corrigir`;
- **Nível 3 — Projetar:** `projetar hierarquia de exceções justificando granularidade`.

---

## 1. Por que tratamento de erros importa?

Programas reais falham.

Eles falham por varios motivos:

- entrada invalida;
- arquivo inexistente;
- rede fora;
- permissao negada;
- divisao por zero;
- estado interno inconsistente.

Se o programa nao tratar isso direito, ele pode:

- cair abruptamente;
- esconder causa real;
- corromper fluxo;
- deixar recurso aberto;
- gerar bugs intermitentes.

Tratamento de erros existe para tornar falha um comportamento explicito, legivel e controlado.

---

## 2. Erro de sintaxe vs excecao

### 2.1 Erro de sintaxe

```python
if True
    print("erro")
```

Aqui o codigo nem chega a rodar direito. O parser encontra uma estrutura invalida.

- **Parser**: componente que le o codigo-fonte e verifica se ele obedece as regras sintaticas da linguagem.

### 2.2 Excecao em runtime

```python
print(10 / 0)
```

Isso produz `ZeroDivisionError` durante a execucao.

- **Excecao**: objeto que representa uma condicao de erro ou evento excepcional durante runtime.

**Comparacao:**

- C costuma sinalizar erro por codigos de retorno, `errno` ou falha brutal.
- C++ usa excecoes.
- Rust usa fortemente `Result<T, E>` e `Option<T>`.
- Python adota excecoes como mecanismo principal de sinalizacao de erro em muitas APIs.

---

## 3. Hierarquia de excecoes

Excecoes em Python sao classes.

Exemplo parcial da hierarquia:

- `BaseException`
- `Exception`
- `ValueError`
- `TypeError`
- `KeyError`
- `IndexError`
- `FileNotFoundError`
- `ZeroDivisionError`

Isso importa porque voce pode capturar:

- algo bem especifico;
- ou uma classe-base mais ampla.

**Regra pratica:** capture o mais especifico que fizer sentido.

---

## 4. `try` e `except`

### 4.1 Exemplo basico

```python
try:
    numero = int("abc")
except ValueError:
    print("Nao foi possivel converter para inteiro")
```

O bloco `try` contem a operacao que pode falhar.

O bloco `except` define o tratamento para o tipo de erro esperado.

### 4.2 Multiplos `except`

```python
try:
    dados = {"nome": "Ana"}
    print(dados["idade"])
except KeyError:
    print("Chave inexistente")
except TypeError:
    print("Tipo invalido")
```

### 4.3 Capturando o objeto da excecao

```python
try:
    x = int("abc")
except ValueError as e:
    print("Erro:", e)
```

`e` e a instancia da excecao.

---

## 5. `else` e `finally`

### 5.1 `else`

O `else` roda se nenhuma excecao ocorreu.

```python
try:
    numero = int("123")
except ValueError:
    print("Falhou")
else:
    print("Sucesso:", numero)
```

Isso ajuda a separar claramente:

- o caminho de falha;
- o caminho de sucesso.

### 5.2 `finally`

`finally` roda independentemente de ter havido erro ou nao.

```python
try:
    print("Abrindo recurso")
    x = 10 / 2
except ZeroDivisionError:
    print("Falhou")
finally:
    print("Fechando recurso")
```

`finally` existe para limpeza garantida.

Exemplos comuns:

- fechar arquivo;
- liberar conexao;
- soltar lock;
- remover arquivo temporario.

---

## 6. `raise`

Voce tambem pode gerar uma excecao explicitamente.

```python
idade = -5

if idade < 0:
    raise ValueError("idade nao pode ser negativa")
```

- **`raise`**: instrucao que cria ou propaga uma excecao.

Isso e importante quando voce quer impedir que o programa continue com estado invalido.

### 6.1 Re-raise

```python
try:
    x = int("abc")
except ValueError:
    print("Vou propagar de novo")
    raise
```

`raise` sem argumento dentro do `except` relanca a excecao atual.

---

## 7. Nao esconda erros

Este e um anti-padrao serio:

```python
try:
    fazer_algo()
except:
    pass
```

Problemas:

- captura quase tudo;
- esconde bug real;
- dificulta diagnostico;
- gera comportamento silencioso e perigoso.

**Regra pratica:** nunca capture generico sem motivo tecnico muito claro e sem acao apropriada.

Se voce precisar capturar amplo:

```python
try:
    fazer_algo()
except Exception as e:
    logger_erro(e)
    raise
```

Note que normalmente se usa `Exception`, nao `BaseException`, para nao interceptar sinais especiais como `KeyboardInterrupt` e `SystemExit`.

## 8. EAFP vs LBYL

Python tem forte cultura de **EAFP**:

- **EAFP**: *Easier to Ask Forgiveness than Permission*.
- **LBYL**: *Look Before You Leap*.

### 8.1 LBYL

```python
dados = {"nome": "Ana"}

if "idade" in dados:
    print(dados["idade"])
else:
    print("Sem idade")
```

### 8.2 EAFP

```python
dados = {"nome": "Ana"}

try:
    print(dados["idade"])
except KeyError:
    print("Sem idade")
```

Em Python, muitas APIs e estilos idiomaticos favorecem EAFP, porque:

- reduz checagens duplicadas;
- combina bem com o modelo de excecoes;
- evita race conditions em alguns cenarios de recurso externo.

Mas isso nao significa usar excecao para qualquer fluxo banal.

**Bom senso:** excecao para situacao excepcional ou para API cujo contrato ja e orientado a excecoes.

## 9. Excecoes proprias

Voce pode criar suas proprias classes de erro:

```python
class SaldoInsuficienteError(Exception):
    pass
```

Uso:

```python
class Conta:
    def __init__(self, saldo):
        self.saldo = saldo

    def sacar(self, valor):
        if valor > self.saldo:
            raise SaldoInsuficienteError("saldo insuficiente")
        self.saldo -= valor
```

Isso ajuda a expressar dominio de negocio.

Em vez de usar `ValueError` para tudo, voce cria uma semantica melhor.

## 10. Excecao como parte do contrato da API

Quando voce desenha uma funcao, precisa decidir:

- ela retorna valor especial em caso de falha?
- retorna `None`?
- retorna objeto resultado?
- lanca excecao?

Exemplo ruim:

```python
def buscar_usuario(id_):
    # retorna None, False ou dicionario dependendo do humor do autor
    ...
```

Exemplo melhor:

```python
class UsuarioNaoEncontradoError(Exception):
    pass


def buscar_usuario(id_):
    raise UsuarioNaoEncontradoError(f"usuario {id_} nao encontrado")
```

Ou:

```python
def buscar_usuario(id_):
    return None
```

Ambos podem ser validos, desde que o contrato seja claro e consistente.

## 11. Contexto e encadeamento

### 11.1 Encadeando excecoes

```python
try:
    valor = int("abc")
except ValueError as e:
    raise RuntimeError("falha ao processar entrada") from e
```

O `from e` preserva a causa original.

Isso e extremamente util em sistemas maiores.

### 11.2 Quando enriquecer contexto

Se uma camada mais externa precisa adicionar informacao de negocio, encadear erro e muito melhor do que perder a origem.

---

## 12. `assert`

`assert` nao e substituto geral para validacao de entrada de usuario.

```python
def dividir(a, b):
    assert b != 0
    return a / b
```

- **`assert`**: verificacao pensada para garantir invariantes internas do programador durante desenvolvimento.

Nao use `assert` como principal mecanismo de validacao de regra de negocio exposta a usuario ou ambiente externo.

Para isso, prefira:

```python
if b == 0:
    raise ValueError("b nao pode ser zero")
```

## 13. Recursos e limpeza

Sem tratamento correto de erro, recursos podem vazar.

Exemplo manual:

```python
arquivo = open("dados.txt", "r")
try:
    conteudo = arquivo.read()
finally:
    arquivo.close()
```

Isso ainda funciona, mas mais tarde veremos o jeito idiomatico com `with`, que automatiza esse padrao usando context managers.

## 14. Exemplo completo da aula

```python
class SaldoInsuficienteError(Exception):
    pass


class Conta:
    def __init__(self, saldo):
        self.saldo = saldo

    def sacar(self, valor):
        if valor <= 0:
            raise ValueError("valor deve ser positivo")
        if valor > self.saldo:
            raise SaldoInsuficienteError(
                f"saldo atual {self.saldo}, tentativa de saque {valor}"
            )
        self.saldo -= valor
        return self.saldo


def executar():
    conta = Conta(100)

    try:
        novo_saldo = conta.sacar(150)
    except SaldoInsuficienteError as e:
        print("Erro de negocio:", e)
    except ValueError as e:
        print("Entrada invalida:", e)
    else:
        print("Saque realizado. Novo saldo:", novo_saldo)
    finally:
        print("Operacao encerrada")


executar()
```

### Explicacao linha por linha

- `class SaldoInsuficienteError(Exception)`: cria excecao de dominio.
- `raise ValueError(...)`: sinaliza entrada invalida.
- `raise SaldoInsuficienteError(...)`: sinaliza violacao de regra de negocio.
- `except ... as e`: captura tipo especifico e o objeto do erro.
- `else`: executa apenas no caminho de sucesso.
- `finally`: roda sempre, com ou sem falha.

## 16. Erros Comuns e Anti-Padroes

1. **Usar `except:` generico sem necessidade**.
2. **Engolir erro com `pass`** e perder diagnostico.
3. **Capturar excecao ampla demais cedo demais**.
4. **Usar excecao como substituto de fluxo comum banal**.
5. **Usar `assert` para validar entrada externa ou regra de negocio**.
6. **Perder a causa original ao relancar erro sem contexto**.
7. **Nao limpar recurso em caminho de falha**.

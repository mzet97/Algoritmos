# Aula 19 - Boas praticas para backend, automacao e sistemas de producao

---

## Objetivo da Aula

Fechar a trilha com um conjunto de principios de engenharia para usar Python em backend, automacao e ferramentas internas. Consolidar organizacao de projeto, configuracao, observabilidade, tratamento de falhas, empacotamento, ambientes, seguranca basica e manutencao de codigo em producao.

---

## 1. Sair do modo "script solto"

Aprender Python com scripts pequenos esta correto.

Mas software de producao exige mais disciplina.

A transicao principal e esta:

- de arquivo unico para projeto organizado;
- de execucao manual para fluxo repetivel;
- de codigo local para sistema operado;
- de "funciona na minha maquina" para ambiente controlado.

---

## 2. Estrutura de projeto

Projeto Python mais serio tende a separar responsabilidades.

Exemplo:

```text
meu_sistema/
|-- pyproject.toml
|-- README.md
|-- src/
|   `-- app/
|       |-- __init__.py
|       |-- main.py
|       |-- config.py
|       |-- services.py
|       `-- models.py
|-- tests/
`-- .venv/
```

Pontos importantes:

- codigo principal em estrutura clara;
- testes separados;
- configuracao de projeto centralizada;
- dependencia do ambiente isolada.

---

## 3. Ambiente virtual sempre que fizer sentido

Para projeto real, isole dependencias.

```bash
python -m venv .venv
.venv\Scripts\activate
python -m pip install -U pip
```

Isso evita:

- conflito entre projetos;
- dependencia "funciona aqui porque ja estava instalada";
- ambiente global poluido.

---

## 4. `pyproject.toml`

Hoje, `pyproject.toml` e o centro natural de configuracao moderna de projeto Python.

Ele pode centralizar:

- metadados do projeto;
- dependencias;
- configuracao de ferramentas;
- build backend.

Exemplo conceitual:

```toml
[project]
name = "meu-sistema"
version = "0.1.0"
description = "Sistema interno em Python"
requires-python = ">=3.12"
dependencies = [
  "fastapi",
]
```

Mesmo que voce ainda nao publique pacote, aprender a organizar projeto assim ajuda muito.

---

## 5. Configuracao nao deve ficar hardcoded

Nao espalhe isso pelo codigo:

```python
TOKEN = "segredo"
HOST = "producao"
```

Configuracao deve vir de fontes controladas:

- variaveis de ambiente;
- arquivo de configuracao;
- segredos gerenciados adequadamente.

Exemplo:

```python
import os


debug = os.getenv("APP_DEBUG", "false").lower() == "true"
```

**Regra pratica:** codigo e configuracao devem ser separados.

---

## 6. Logging e observabilidade

Sistema em producao precisa contar o que esta acontecendo.

Nao dependa de `print` espalhado.

Use `logging`:

```python
import logging

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)

logger.info("iniciando processo")
```

Idealmente, logs devem ser:

- claros;
- contextualizados;
- consistentes;
- sem vazar segredo.

- **Observabilidade**: capacidade de entender o comportamento do sistema a partir dos sinais que ele emite.

---

## 7. Tratamento de erro em sistemas reais

Em producao, erro precisa ser:

- detectado;
- registrado;
- classificado;
- tratado no nivel certo;
- transformado em resposta apropriada quando necessario.

Nao faca:

```python
try:
    fazer_algo()
except:
    pass
```

Faca algo mais responsavel:

```python
try:
    fazer_algo()
except Exception:
    logger.exception("falha ao executar operacao")
    raise
```

`logger.exception(...)` inclui traceback no log quando usado dentro de `except`.

---

## 8. Backend: fronteiras claras

Em backend, uma boa separacao ajuda muito:

- camada HTTP;
- validacao e serializacao;
- regra de negocio;
- acesso a persistencia;
- integracoes externas.

Mesmo sem framework especifico, este principio vale.

Quando tudo fica misturado:

- teste piora;
- manutencao piora;
- acoplamento cresce;
- erro de uma camada contamina o resto.

---

## 9. Automacao: idempotencia e reexecucao

Ferramentas internas e scripts de automacao devem ser desenhados pensando:

- pode rodar duas vezes?
- se falhar no meio, como retoma?
- como saber o que foi feito?
- ha efeitos colaterais irreversiveis?

- **Idempotencia**: propriedade de executar repetidamente a mesma operacao com mesmo efeito observavel principal.

Isso e muito importante em jobs, ETL, provisionamento e tarefas administrativas.

---

## 10. CLI e ponto de entrada

Muitas ferramentas internas Python vivem como CLI.

Padrao basico:

```python
def main() -> int:
    print("executando")
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

Isso melhora:

- testabilidade;
- clareza de retorno;
- integracao com shell e automacao.

---

## 11. Dependencias e reproducibilidade

Projeto serio precisa controlar versoes.

Isso significa:

- saber o que esta sendo instalado;
- reduzir surpresas em deploy;
- manter compatibilidade conhecida.

Comandos uteis:

```bash
python -m pip install -U pip
python -m pip install -r requirements.txt
```

Ou fluxo moderno com ferramenta que use `pyproject.toml`.

O importante e:

> ambiente precisa ser reproduzivel.

---

## 12. Seguranca basica

Mesmo sistema interno precisa de higiene minima.

Cuidados:

- nunca commitar segredo;
- validar entrada externa;
- limitar privilegios;
- tratar arquivos e caminhos com cuidado;
- registrar falhas sem expor dados sensiveis;
- atualizar dependencias com criterio.

Python facilita muito prototipagem, mas rapidez sem disciplina vira risco rapidamente.

---

## 13. Testes e checks antes de entregar

Fluxo profissional minimo costuma incluir:

```bash
python -m pip install ruff mypy pytest
ruff check .
mypy .
pytest
```

E, se usar formatador:

```bash
python -m pip install black
black .
```

Nao porque ferramenta e moda, mas porque:

- reduz erro bobo;
- melhora consistencia;
- economiza revisao humana para o que realmente importa.

---

## 14. Concorrencia e producao

Depois das aulas de `threading`, `multiprocessing` e `asyncio`, a regra pratica e:

- nao introduza concorrencia so por estilo;
- faca isso quando a carga realmente exigir;
- isole pontos de sincronizacao;
- meca antes e depois;
- trate timeout, cancelamento e falha parcial como cenarios normais.

Sistema de producao falha em bordas reais, nao em slides perfeitos.

---

## 15. Manutencao e evolucao

Codigo bom para producao nao e apenas o que roda hoje.

E o que:

- pode ser lido;
- pode ser testado;
- pode ser depurado;
- pode ser monitorado;
- pode ser alterado sem terror.

Por isso, varios principios da trilha inteira convergem aqui:

- modulos bem organizados;
- contratos claros;
- erros explicitados;
- testes;
- tipagem onde ajuda;
- observabilidade;
- uso criterioso de concorrencia;
- medicao antes de otimizar.

## 16. Exemplo completo da aula

```python
import logging
import os
from pathlib import Path


logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)


def carregar_config() -> dict[str, str]:
    pasta_saida = os.getenv("APP_OUTPUT_DIR", "saida")
    return {"output_dir": pasta_saida}


def gerar_relatorio(config: dict[str, str]) -> Path:
    destino = Path(config["output_dir"])
    destino.mkdir(parents=True, exist_ok=True)
    arquivo = destino / "relatorio.txt"
    arquivo.write_text("relatorio gerado\n", encoding="utf-8")
    return arquivo


def main() -> int:
    try:
        config = carregar_config()
        arquivo = gerar_relatorio(config)
        logger.info("Relatorio criado em %s", arquivo)
        return 0
    except Exception:
        logger.exception("Falha na execucao")
        return 1


if __name__ == "__main__":
    raise SystemExit(main())
```

### Explicacao linha por linha

- `os.getenv(...)`: separa configuracao do codigo.
- `Path(...)`: trata caminho de forma portavel.
- `mkdir(..., exist_ok=True)`: torna a operacao mais robusta em reexecucao.
- `write_text(...)`: grava saida simples com encoding explicito.
- `logger.info(...)`: registra sucesso operacional.
- `logger.exception(...)`: registra falha com traceback.
- `raise SystemExit(main())`: expande claramente o codigo de saida da CLI.

## 18. Erros Comuns e Anti-Padroes

1. **Manter tudo em um arquivo/script unico mesmo com projeto crescendo**.
2. **Misturar configuracao, segredo e codigo**.
3. **Usar `print` como unica estrategia de observabilidade em producao**.
4. **Engolir excecao e esconder traceback**.
5. **Nao pensar em reexecucao, idempotencia e falha parcial em automacao**.
6. **Ignorar reproducibilidade de ambiente e dependencia**.
7. **Adicionar concorrencia sem necessidade ou sem medicao**.
8. **Tratar entrega em producao como se fosse apenas "rodou localmente"**.

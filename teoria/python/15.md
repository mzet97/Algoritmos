# Aula 15 - Concorrencia com `threading` e `multiprocessing`

Thread em Python divide o mesmo interpretador; processo, não. Concorrência com `threading` e `multiprocessing` exige saber qual dos dois o seu problema está pedindo — e o GIL vai opinar sobre a escolha.

---

## Nesta aula

Entender a diferenca entre concorrencia e paralelismo. Aprender quando usar `threading` e quando usar `multiprocessing`, compreender o impacto do GIL em Python e distinguir workloads I/O-bound de CPU-bound. Construir, por fim, um modelo mental correto para escolher a ferramenta certa.

Você vai aprender a usar `threading` para I/O e `multiprocessing` para CPU, explicar o GIL, e prever quando thread não acelera.

---

## 1. O problema que estamos tentando resolver

Programas reais frequentemente precisam lidar com mais de uma atividade ao mesmo tempo:

- atender varias conexoes;
- baixar varios arquivos;
- processar varias tarefas;
- usar mais de um nucleo de CPU;
- manter a interface responsiva enquanto algo acontece ao fundo.

Esse contexto nos leva ao tema de concorrencia.

---

## 2. Concorrencia vs paralelismo

Esses termos sao relacionados, mas nao identicos.

### 2.1 Concorrencia

Capacidade de estruturar varias tarefas com progresso intercalado.

### 2.2 Paralelismo

Execucao real simultanea em mais de uma unidade de processamento.

**Imagem mental simples:**

- concorrencia: lidar com varias coisas;
- paralelismo: fazer varias coisas exatamente ao mesmo tempo.

Um programa pode ser concorrente sem ser paralelo.

---

## 3. `thread`

Uma **thread** e uma linha de execucao dentro de um mesmo processo.

Threads compartilham:

- mesmo espaco de memoria do processo;
- objetos globais;
- recursos do processo pai.

Isso torna comunicacao mais facil, mas tambem aumenta risco de disputa por estado compartilhado.

---

## 4. `process`

Um **processo** e uma instancia de execucao isolada pelo sistema operacional.

Processos normalmente possuem:

- espaco de memoria separado;
- maior isolamento;
- custo maior de criacao e comunicacao.

Em compensacao, conseguem explorar multiprocessamento real sem as mesmas restricoes de threads em CPython para certas cargas.

---

## 5. O que e o GIL?

Aqui esta um conceito central de Python.

**GIL** significa **Global Interpreter Lock**.

Em CPython, ele e um mecanismo que garante que apenas uma thread por vez execute bytecode Python no interpretador.

### 5.1 Por que ele existe?

Historicamente, ele simplificou o gerenciamento interno do runtime e de estruturas de memoria compartilhadas do interpretador.

### 5.2 Consequencia pratica

Para codigo Python puro intensivo em CPU:

- varias threads nao significam necessariamente uso paralelo real de varios nucleos para bytecode Python.

Mas para tarefas de I/O:

- threads ainda podem ser muito uteis, porque enquanto uma espera rede, disco ou socket, outra pode progredir.

**Comparacao:**

- em C/C++ ou Rust, threads podem explorar paralelismo de CPU de forma mais direta, dependendo do codigo e das bibliotecas;
- em Python, o GIL muda essa decisao arquitetural.

---

## 6. I/O-bound vs CPU-bound

### 6.1 I/O-bound

Programa passa muito tempo esperando:

- rede;
- disco;
- banco;
- API externa;
- entrada/saida em geral.

Nesses casos, `threading` pode funcionar bem.

### 6.2 CPU-bound

Programa passa muito tempo calculando:

- loops pesados;
- transformacoes numericas;
- compressao;
- parsing intensivo;
- processamento bruto.

Nesses casos, `multiprocessing` tende a ser mais adequado em Python puro.

Essa distincao e uma das mais importantes da aula.

---

## 7. `threading`

Modulo padrao:

```python
import threading
```

Exemplo:

```python
import threading
import time


def tarefa(nome):
    for i in range(3):
        print(nome, i)
        time.sleep(1)


t1 = threading.Thread(target=tarefa, args=("A",))
t2 = threading.Thread(target=tarefa, args=("B",))

t1.start()
t2.start()

t1.join()
t2.join()
```

### 7.1 Conceitos

- `Thread(...)`: cria thread.
- `start()`: inicia execucao concorrente.
- `join()`: espera a thread terminar.

Sem `join`, a thread principal pode terminar antes do que voce espera ou o fluxo pode seguir sem sincronizacao clara.

---

## 8. Estado compartilhado e race condition

Como threads compartilham memoria, surgem riscos.

Exemplo conceitual perigoso:

```python
contador = 0
```

Se varias threads fazem incremento sem coordenacao, voce pode ter **race condition**.

- **Race condition**: resultado depende da ordem exata e nao controlada de execucao concorrente.

Isso causa bugs intermitentes, dificeis de reproduzir.

---

## 9. `Lock`

Para proteger secao critica:

```python
import threading

contador = 0
lock = threading.Lock()


def incrementar():
    global contador
    for _ in range(100_000):
        with lock:
            contador += 1
```

- **Secao critica**: trecho que acessa estado compartilhado e precisa de exclusao mutua.
- **Exclusao mutua**: garantia de que apenas um executor entra naquela regiao por vez.

### 9.1 Trade-off

Lock aumenta seguranca, mas pode reduzir paralelismo util e introduzir contencao.

- **Contencao**: varios executores disputando o mesmo recurso sincronizado.

---

## 10. `queue.Queue`

Em vez de compartilhar estado arbitrariamente, um padrao melhor costuma ser passar trabalho por fila.

```python
from queue import Queue
import threading


fila = Queue()


def worker():
    while True:
        item = fila.get()
        if item is None:
            break
        print("processando", item)
        fila.task_done()
```

Esse estilo reduz acoplamento entre workers e dados compartilhados.

---

## 11. `multiprocessing`

Quando o problema e CPU-bound, `multiprocessing` pode usar varios processos.

Exemplo:

```python
from multiprocessing import Process


def tarefa(nome):
    print("Executando", nome)


p1 = Process(target=tarefa, args=("P1",))
p2 = Process(target=tarefa, args=("P2",))

p1.start()
p2.start()

p1.join()
p2.join()
```

Cada processo tem memoria propria.

Isso evita alguns problemas de thread compartilhada, mas cria outros:

- serializacao de dados;
- custo de spawn;
- comunicacao mais cara.

---

## 12. `Pool`

Para distribuir trabalho sobre varios processos:

```python
from multiprocessing import Pool


def quadrado(x):
    return x * x


if __name__ == "__main__":
    with Pool() as pool:
        resultado = pool.map(quadrado, [1, 2, 3, 4])
        print(resultado)
```

`Pool` simplifica fan-out de trabalho.

- **Fan-out**: distribuir um conjunto de tarefas para varios executores.

---

## 13. Windows e `if __name__ == "__main__"`

No Windows, isso e especialmente importante com `multiprocessing`.

Sem proteger o ponto de entrada:

```python
if __name__ == "__main__":
    ...
```

voce pode causar reexecucao indesejada do modulo no processo filho.

Como estamos em um ambiente Windows, trate isso como regra obrigatoria para exemplos de `multiprocessing`.

---

## 14. Compartilhamento entre processos

Como processos nao compartilham memoria da mesma forma que threads, a troca de dados costuma exigir mecanismos explicitos:

- `Queue`;
- `Pipe`;
- objetos gerenciados;
- memoria compartilhada em casos especificos.

Isso tem custo e influencia arquitetura.

Muitas vezes, o melhor design e:

- entrada serializada;
- trabalho independente;
- saida agregada ao final.

---

## 15. Escolhendo entre `threading` e `multiprocessing`

Use `threading` quando:

- a carga e I/O-bound;
- o custo principal e espera;
- compartilhar estado faz sentido e sera bem controlado;
- latencia de troca e leve importa.

Use `multiprocessing` quando:

- a carga e CPU-bound;
- voce quer explorar varios nucleos em Python puro;
- o custo de spawn e serializacao compensa;
- o trabalho pode ser particionado.

---

## 16. O que nao fazer

Nao pense assim:

> "Vou colocar thread em tudo e o programa vai ficar rapido."

Desempenho concorrente depende de:

- natureza da carga;
- custo de sincronizacao;
- custo de comunicacao;
- GIL;
- estrutura de dados;
- arquitetura do sistema.

Concorrencia mal aplicada pode piorar tudo:

- mais bugs;
- mais complexidade;
- menos previsibilidade;
- menor desempenho.

## 17. Exemplo completo da aula

```python
import threading
import time
from multiprocessing import Pool


def baixar_simulado(nome: str) -> str:
    print(f"iniciando download de {nome}")
    time.sleep(1)
    print(f"download concluido de {nome}")
    return nome


def quadrado(x: int) -> int:
    return x * x


def exemplo_threads() -> None:
    threads = [
        threading.Thread(target=baixar_simulado, args=("arquivo_a",)),
        threading.Thread(target=baixar_simulado, args=("arquivo_b",)),
    ]

    for t in threads:
        t.start()

    for t in threads:
        t.join()


def exemplo_processos() -> None:
    with Pool() as pool:
        resultado = pool.map(quadrado, [1, 2, 3, 4, 5])
    print("quadrados:", resultado)


if __name__ == "__main__":
    exemplo_threads()
    exemplo_processos()
```

### Explicacao linha por linha

- `threading.Thread(...)`: cria workers leves dentro do mesmo processo.
- `time.sleep(1)`: simula espera de I/O.
- `Pool().map(...)`: distribui trabalho CPU-like entre processos.
- `if __name__ == "__main__"`: protege ponto de entrada, essencial para `multiprocessing` no Windows.
- o exemplo separa claramente caso I/O-bound e caso mais orientado a CPU.

## 19. Erros Comuns e Anti-Padroes

1. **Confundir concorrencia com paralelismo**.
2. **Usar `threading` para carga CPU-bound esperando ganho linear em CPython**.
3. **Ignorar o GIL ao tomar decisao de arquitetura**.
4. **Compartilhar estado entre threads sem sincronizacao adequada**.
5. **Esquecer `join()` e deixar fluxo principal seguir sem coordenacao**.
6. **Usar `multiprocessing` sem `if __name__ == "__main__"` no Windows**.
7. **Superestimar desempenho e subestimar complexidade concorrente**.

## 1. Por que modularizar?

Nos arquivos anteriores, quase todo exemplo cabia em um unico `.py`. Isso e bom para aprender fundamentos, mas programas reais crescem.

Se todo o codigo ficar em um arquivo so, surgem problemas classicos:

- manutencao dificil;
- baixo reuso;
- acoplamento alto;
- testes piores;
- tempo maior para localizar comportamento.

Modularizar existe para dividir responsabilidade.

**Responsabilidade** aqui significa: cada arquivo ou unidade de codigo deve ter um papel coerente e limitado.

---

## 2. O que e um modulo?

Em Python, um **modulo** normalmente e um arquivo `.py`.

Se voce tem um arquivo:

```text
matematica.py
```

entao esse arquivo pode ser importado como um modulo.

Exemplo:

```python
# matematica.py
def soma(a, b):
    return a + b
```

```python
# main.py
import matematica

print(matematica.soma(2, 3))
```

Termos fundamentais:

- **Modulo**: unidade de organizacao de codigo carregavel por `import`.
- **Namespace**: espaco de nomes em que identificadores vivem sem colidir automaticamente com outros.

Quando voce faz `import matematica`, o nome `soma` nao e jogado direto no namespace atual; ele fica dentro de `matematica.soma`.

Isso existe para evitar colisoes entre nomes iguais de origens diferentes.

---

## 3. Formas de import

### 3.1 `import modulo`

```python
import matematica

print(matematica.soma(10, 20))
```

Esta e a forma mais explicita e geralmente a mais clara.

### 3.2 `from modulo import nome`

```python
from matematica import soma

print(soma(10, 20))
```

Aqui `soma` entra diretamente no namespace atual.

### 3.3 `from modulo import nome as alias`

```python
from matematica import soma as somar

print(somar(1, 2))
```

### 3.4 `import modulo as alias`

```python
import matematica as m

print(m.soma(3, 4))
```

### 3.5 `from modulo import *`

Evite isso:

```python
from matematica import *
```

Isso polui o namespace atual e dificulta saber de onde cada nome veio.

**Regra pratica:** em codigo serio, prefira `import modulo` ou `from modulo import nome` de forma explicita.

---

## 4. O que acontece quando o import roda?

Quando voce faz:

```python
import matematica
```

Python, em linhas gerais:

1. localiza o modulo;
2. carrega o arquivo;
3. executa o codigo top-level do modulo;
4. cria um objeto modulo;
5. guarda esse modulo em cache em `sys.modules`.

Isso significa algo importantissimo:

> importar um modulo executa o codigo de topo dele uma vez.

Exemplo:

```python
# teste.py
print("Modulo teste foi carregado")
```

```python
# main.py
import teste
import teste
```

Saida:

```text
Modulo teste foi carregado
```

Nao aparece duas vezes porque o modulo e cacheado.

- **Top-level code**: codigo que esta no corpo principal do modulo, fora de funcoes e classes.
- **Cache de modulos**: mecanismo usado para evitar recarregamento desnecessario e manter identidade consistente do modulo.

## 5. `if __name__ == "__main__"`

Este e um dos trechos mais famosos de Python.

```python
def soma(a, b):
    return a + b


if __name__ == "__main__":
    print(soma(2, 3))
```

### 5.1 O que isso significa?

Quando um arquivo e executado diretamente:

```bash
python matematica.py
```

Python define `__name__` como `"__main__"`.

Quando o arquivo e importado:

```python
import matematica
```

`__name__` passa a ser o nome do modulo, por exemplo `"matematica"`.

Isso permite separar:

- codigo reutilizavel de biblioteca;
- codigo de teste manual/demo local.

**Comparacao com C/C++/Rust:**

- em C/C++ e Rust, o ponto de entrada principal costuma ser um `main`.
- em Python, o arquivo pode servir como modulo ou como script.
- esse `if` decide qual comportamento acontece quando o arquivo e rodado diretamente.

## 6. Organizando um projeto simples

Exemplo de estrutura:

```text
meu_projeto/
|-- main.py
|-- matematica.py
`-- texto.py
```

`matematica.py`:

```python
def soma(a, b):
    return a + b


def dobro(x):
    return x * 2
```

`texto.py`:

```python
def gritar(msg):
    return msg.upper()
```

`main.py`:

```python
import matematica
import texto

valor = matematica.soma(10, 5)
print(texto.gritar(f"resultado: {valor}"))
```

Aqui cada modulo concentra uma responsabilidade pequena.

## 7. Pacotes

Quando um projeto cresce mais, so modulos soltos nao bastam. Surge a ideia de **pacote**.

Pacote e, conceitualmente, um diretorio que agrupa modulos relacionados sob um namespace comum.

Estrutura:

```text
loja/
|-- main.py
`-- pagamentos/
    |-- __init__.py
    |-- cartao.py
    `-- pix.py
```

`cartao.py`:

```python
def pagar(valor):
    return f"Pagamento no cartao: {valor}"
```

`pix.py`:

```python
def pagar(valor):
    return f"Pagamento via PIX: {valor}"
```

`main.py`:

```python
from pagamentos import cartao, pix

print(cartao.pagar(100))
print(pix.pagar(200))
```

### 7.1 O papel de `__init__.py`

Historicamente, `__init__.py` marcava explicitamente um diretorio como pacote.

Hoje, Python suporta tambem certos casos de **namespace packages**, mas para ensino e organizacao clara, usar `__init__.py` ainda e uma escolha muito boa.

`__init__.py` tambem pode:

- expor API publica do pacote;
- executar inicializacao leve;
- facilitar imports mais ergonomicos.

Exemplo:

```python
# pagamentos/__init__.py
from .cartao import pagar as pagar_cartao
from .pix import pagar as pagar_pix
```

Depois:

```python
from pagamentos import pagar_cartao, pagar_pix
```

---

## 8. Imports absolutos e relativos

### 8.1 Absolutos

```python
from pagamentos.cartao import pagar
```

Import absoluto parte da raiz visivel do pacote/projeto.

### 8.2 Relativos

Dentro de um pacote, voce pode ver algo como:

```python
from .cartao import pagar
from . import pix
from ..utils import logger
```

O ponto significa "partir do pacote atual".

**Regra pratica:** para iniciantes e para clareza, imports absolutos costumam ser mais faceis de ler. Relativos sao uteis, mas devem ser usados com criterio.

---

## 9. API publica e underscore

Em Python, convencoes importam muito.

Se um nome comeca com underscore:

```python
def _funcao_interna():
    pass
```

isso sinaliza:

> este simbolo e interno ao modulo e nao faz parte da API publica principal.

- **API publica**: conjunto de nomes que um modulo ou pacote pretende expor para uso externo.

Python nao impede o acesso, mas a convencao comunica intencao arquitetural.

## 10. Arquitetura e acoplamento

Uma boa divisao em modulos ajuda a reduzir **acoplamento**.

- **Acoplamento**: grau de dependencia entre partes do sistema.

Sinais de modulo ruim:

- importa metade do projeto;
- concentra responsabilidades demais;
- tem nomes genericos como `utils.py` para tudo;
- causa dependencia circular.

### 10.1 Dependencia circular

Exemplo de problema:

- `a.py` importa `b.py`
- `b.py` importa `a.py`

Isso pode gerar erro de inicializacao parcial, porque um modulo ainda nao terminou de carregar quando o outro ja tenta usar seus nomes.

**Como evitar:**

- extrair dependencia comum para terceiro modulo;
- reorganizar responsabilidades;
- mover import para escopo mais interno so quando realmente fizer sentido tecnico.

## 11. Exemplo completo da aula

Estrutura:

```text
app/
|-- main.py
|-- calculo.py
`-- formatacao.py
```

`calculo.py`:

```python
def imposto(valor, taxa):
    return valor * taxa
```

`formatacao.py`:

```python
def moeda(valor):
    return f"R$ {valor:.2f}"
```

`main.py`:

```python
import calculo
import formatacao


def main():
    preco = 100.0
    taxa = 0.15
    valor_imposto = calculo.imposto(preco, taxa)
    total = preco + valor_imposto

    print(f"Preco base: {formatacao.moeda(preco)}")
    print(f"Imposto: {formatacao.moeda(valor_imposto)}")
    print(f"Total: {formatacao.moeda(total)}")


if __name__ == "__main__":
    main()
```

### Explicacao linha por linha

- `import calculo`: carrega o modulo de regra numerica.
- `import formatacao`: carrega o modulo de apresentacao textual.
- `def main()`: concentra o fluxo principal do script.
- `if __name__ == "__main__":`: faz o arquivo funcionar bem tanto como script quanto como modulo importavel.

## 13. Erros Comuns e Anti-Padroes

1. **Colocar tudo em um unico arquivo**: isso escala mal.
2. **Usar `from modulo import *`**: polui namespace e reduz clareza.
3. **Esquecer que import executa codigo top-level**: isso gera efeitos colaterais inesperados.
4. **Nao usar `if __name__ == "__main__"` em scripts reutilizaveis**.
5. **Criar dependencia circular entre modulos**.
6. **Usar `utils.py` como deposito de tudo**: isso vira um modulo sem fronteira clara.
7. **Esconder API do sistema em imports dinamicos confusos sem necessidade real**.

# Aula 14 - Testes, debug e qualidade de codigo

---

## Nesta aula

Entender por que testar importa e como escrever testes automatizados em Python. Aprender como depurar comportamento incorreto, pensar observabilidade local com logs e asserts, e usar ferramentas para manter qualidade de codigo de forma profissional e sustentavel.

Você vai aprender a escrever testes com `pytest` (fixtures, parametrização), depurar com `pdb`/logging, medir cobertura, e distinguir teste que passa de teste que prova.

---

## 1. Por que testar?

Sem testes, voce fica dependente de:

- execucao manual repetitiva;
- memoria humana;
- sorte;
- feedback tardio do usuario;
- medo de refatorar.

Teste automatizado existe para transformar expectativa de comportamento em algo executavel e repetivel.

Isso reduz regressao.

- **Regressao**: bug introduzido em algo que antes funcionava.

**Comparacao:**

- em C/C++ e Rust, testes ajudam a conter efeitos de mudancas em codigo compilado;
- em Python, como a linguagem e dinamica e muitos erros aparecem em runtime, testes ganham ainda mais valor pratico.

---

## 2. Tipos de teste

### 2.1 Teste unitario

Valida uma unidade pequena e isolada.

Exemplo:

- uma funcao;
- uma classe pequena;
- uma regra de negocio.

### 2.2 Teste de integracao

Valida a interacao entre partes.

Exemplo:

- modulo + banco;
- funcao + arquivo;
- API + camada de servico.

### 2.3 Teste ponta a ponta

Valida fluxo mais proximo do uso real.

Exemplo:

- usuario faz requisicao;
- sistema processa;
- resultado final aparece.

Nao existe um unico tipo "melhor". Cada um responde perguntas diferentes.

---

## 3. O que testar?

Priorize:

- regras de negocio;
- transformacoes importantes;
- pontos com historico de bug;
- codigo com custo alto de falha;
- interfaces publicas.

Nao vale testar cegamente cada linha sem criterio.

Teste bom reduz risco real, nao ruido.

---

## 4. `assert`

A forma mais simples de verificar expectativa em Python e `assert`.

```python
def soma(a, b):
    return a + b


assert soma(2, 3) == 5
```

Mas uma coisa importante:

- `assert` e excelente em testes;
- `assert` tambem pode ajudar em invariantes internas;
- `assert` nao substitui toda validacao de entrada externa em codigo de producao.

---

## 5. `unittest`

Python traz `unittest` na biblioteca padrao.

Exemplo de codigo sob teste:

```python
def eh_par(x):
    return x % 2 == 0
```

Teste:

```python
import unittest


def eh_par(x):
    return x % 2 == 0


class TestEhPar(unittest.TestCase):
    def test_numero_par(self):
        self.assertTrue(eh_par(4))

    def test_numero_impar(self):
        self.assertFalse(eh_par(3))


if __name__ == "__main__":
    unittest.main()
```

Executar:

```bash
python arquivo_teste.py
```

Ou descobrir automaticamente:

```bash
python -m unittest
```

---

## 6. `pytest`

Embora `unittest` seja importante por estar na biblioteca padrao, muita gente em Python usa `pytest`.

Por que ele e popular?

- sintaxe mais simples;
- asserts mais ergonomicos;
- fixtures poderosas;
- ecossistema forte.

Exemplo:

```python
def soma(a, b):
    return a + b


def test_soma():
    assert soma(2, 3) == 5
```

Executar:

```bash
python -m pip install pytest
pytest
```

Para esta aula, o importante e entender a ideia. Nao precisa decorar ferramenta agora.

## 7. Estrutura de testes

Projeto tipico:

```text
meu_projeto/
|-- src/
|   `-- calculo.py
`-- tests/
    `-- test_calculo.py
```

Separar testes do codigo principal ajuda organizacao, descoberta automatica e manutencao.

---

## 8. Testes e determinismo

Teste bom precisa ser repetivel.

- **Deterministico**: produz mesmo resultado sob mesmas condicoes.

Se o teste depende de:

- hora atual;
- rede real;
- arquivo do ambiente do usuario;
- ordem aleatoria;
- concorrencia sem controle;

ele pode virar teste instavel.

- **Teste instavel**: teste que passa e falha sem mudanca real relevante no codigo.

Esse tipo de teste desgasta confianca no suite.

---

## 9. `mock` e isolamento

As vezes queremos testar logica sem acessar recurso real.

Exemplo:

- nao chamar API real;
- nao escrever no disco de verdade;
- nao mandar email.

Nesses casos, podemos usar **mock**.

- **Mock**: substituto controlado de dependencia para observacao ou isolamento em testes.

Exemplo conceitual com `unittest.mock`:

```python
from unittest.mock import Mock


enviador = Mock()
enviador.enviar("mensagem")
enviador.enviar.assert_called_once_with("mensagem")
```

Mock e poderoso, mas em excesso pode produzir testes artificiais demais.

---

## 10. Debug

Quando algo falha, testar ajuda a detectar. Depurar ajuda a entender.

Ferramentas mentais de debug:

- reproduzir o bug;
- reduzir o caso;
- inspecionar estado;
- verificar suposicoes;
- localizar a primeira divergencia, nao apenas o ultimo sintoma.

### 10.1 `print`

Sim, `print` ainda serve.

```python
print("valor atual:", valor)
```

Mas use com criterio.

### 10.2 `breakpoint()`

Python moderno oferece:

```python
breakpoint()
```

Quando a execucao chega ali, voce entra em depuracao interativa.

Isso permite:

- inspecionar variaveis;
- avancar passo a passo;
- entender fluxo real.

---

## 11. Traceback

Quando uma excecao nao tratada acontece, Python mostra **traceback**.

- **Traceback**: trilha de chamadas que levou ao ponto da falha.

Aprender a ler traceback e habilidade essencial.

Exemplo mental:

- olhe o tipo da excecao;
- veja a mensagem;
- identifique a linha real do erro;
- suba a pilha para entender como chegou ali.

Nao leia traceback so pela ultima linha textual; leia o caminho.

---

## 12. Logging

`print` ajuda em debug local, mas em sistemas reais usamos `logging`.

```python
import logging

logging.basicConfig(level=logging.INFO)

logging.info("iniciando processamento")
logging.warning("arquivo ausente, usando valor padrao")
logging.error("falha ao abrir conexao")
```

Vantagens:

- niveis de severidade;
- saida configuravel;
- integracao melhor com execucao real.

Niveis comuns:

- `DEBUG`
- `INFO`
- `WARNING`
- `ERROR`
- `CRITICAL`

## 13. Qualidade automatica

Qualidade de codigo nao depende so de testes.

Ferramentas uteis:

- formatador;
- linter;
- verificador de tipos;
- testes automatizados.

Fluxo moderno comum:

- `black` para formatacao;
- `ruff` para lint;
- `mypy` ou `pyright` para tipos;
- `pytest` para testes.

Exemplo:

```bash
python -m pip install black ruff mypy pytest
black .
ruff check .
mypy .
pytest
```

Cada ferramenta enxerga uma classe diferente de problema.

## 14. TDD e realidade

Voce pode ouvir falar de **TDD**:

- **TDD**: *Test-Driven Development*, pratica de escrever teste antes da implementacao.

Isso pode ser util para:

- pensar contrato antes da solucao;
- evitar escopo excessivo;
- manter foco.

Mas nao transforme isso em religiao.

O importante e manter ciclos curtos de feedback e cobertura inteligente.

## 15. Exemplo completo da aula

```python
import logging
import unittest


logging.basicConfig(level=logging.INFO)


def dividir(a: float, b: float) -> float:
    logging.info("Dividindo %s por %s", a, b)
    if b == 0:
        raise ValueError("divisor nao pode ser zero")
    return a / b


class TestDividir(unittest.TestCase):
    def test_divisao_normal(self) -> None:
        self.assertEqual(dividir(10, 2), 5)

    def test_divisao_por_zero(self) -> None:
        with self.assertRaises(ValueError):
            dividir(10, 0)


if __name__ == "__main__":
    unittest.main()
```

### Explicacao linha por linha

- `logging.basicConfig(...)`: configura log basico.
- `dividir(...)`: funcao simples de regra de negocio.
- `raise ValueError(...)`: deixa o contrato de erro explicito.
- `self.assertEqual(...)`: verifica resultado esperado.
- `self.assertRaises(...)`: verifica caminho de falha esperado.
- `unittest.main()`: executa a suite de testes do arquivo.

## 17. Erros Comuns e Anti-Padroes

1. **Depender so de teste manual**.
2. **Escrever testes acoplados demais a detalhes internos**, dificultando refatoracao.
3. **Criar testes instaveis dependentes do ambiente**.
4. **Usar mock em excesso e testar o mock, nao a logica real**.
5. **Ignorar traceback e tentar adivinhar o bug sem evidencias**.
6. **Usar `print` como unica estrategia permanente de observabilidade**.
7. **Nao rodar linter, formatter e checagem de tipos em codigo de equipe**.

# Aula 23 - Observabilidade e operacao de servicos Python

---

## Nesta aula

Entender como observar e operar servicos Python em producao com logs, metricas, tracing e configuracao de runtime, e por que diagnostico operacional nao pode ser improvisado. Você vai aprender a instrumentar com logs/métricas/traces, definir SLOs, responder a incidentes, e distinguir sinal de ruído.
---

## 1. Ponte com as aulas anteriores

Nas Aulas 20 a 22, montamos:

- API;
- persistencia;
- jobs em background.

Agora aparece a pergunta inevitavel:

- como descobrir o que esse sistema esta fazendo quando algo da errado?

---

## 2. Observabilidade nao e `print`

`print` ajuda em teste pequeno.

Mas servico real precisa responder perguntas como:

- quantas requests por segundo entram?;
- qual rota esta lenta?;
- quantos jobs falham?;
- qual dependencia externa esta degradando?;
- qual request atravessou quais etapas?;

---

## 3. Tres pilares

### 3.1 Logs

Servem bem para:

- eventos;
- contexto textual;
- erro pontual.

### 3.2 Metricas

Servem bem para:

- contagem;
- taxa;
- latencia;
- distribuicao.

### 3.3 Tracing

Serve bem para:

- fluxo causal;
- correlacao entre etapas;
- latencia ponta a ponta.

---

## 4. O que logar?

Log bom tende a responder:

- o que aconteceu?;
- onde?;
- com qual identificador?;
- com qual resultado?;

Log ruim tende a ser:

- verboso demais;
- sem contexto;
- sem consistencia;
- caro no hot path.

---

## 5. Metrica sem semantica vira ruido

Metricas uteis para backend pequeno:

- requests totais;
- requests por rota;
- erros por tipo;
- latencia por operacao;
- jobs em fila;
- jobs falhos;
- conexoes abertas.

---

## 6. Exemplo completo da aula

```python
import logging
import time
from collections import defaultdict
from contextlib import contextmanager


logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s level=%(levelname)s request_id=%(request_id)s message=%(message)s",
)


class RequestAdapter(logging.LoggerAdapter):
    def process(self, msg, kwargs):
        extra = kwargs.setdefault("extra", {})
        extra.setdefault("request_id", self.extra["request_id"])
        return msg, kwargs


class Metrics:
    def __init__(self) -> None:
        self.counters = defaultdict(int)
        self.latencies_ms = defaultdict(list)

    def inc(self, name: str, value: int = 1) -> None:
        self.counters[name] += value

    def observe_ms(self, name: str, value: float) -> None:
        self.latencies_ms[name].append(value)


metrics = Metrics()


@contextmanager
def span(name: str, logger: RequestAdapter):
    start = time.perf_counter()
    logger.info(f"span_start={name}")
    try:
        yield
    finally:
        elapsed_ms = (time.perf_counter() - start) * 1000.0
        metrics.observe_ms(f"{name}.latency_ms", elapsed_ms)
        logger.info(f"span_end={name} elapsed_ms={elapsed_ms:.2f}")


def process_request(request_id: str, should_fail: bool) -> None:
    logger = RequestAdapter(logging.getLogger("app"), {"request_id": request_id})
    metrics.inc("http.requests_total")

    with span("request", logger):
        with span("load_user", logger):
            time.sleep(0.01)

        with span("call_dependency", logger):
            time.sleep(0.02)
            if should_fail:
                metrics.inc("http.errors_total")
                logger.error("dependency_failed")
                return

        logger.info("request_ok")


def main() -> None:
    process_request("req-1", should_fail=False)
    process_request("req-2", should_fail=True)
    print(dict(metrics.counters))


if __name__ == "__main__":
    main()
```

---

## 7. O que esse exemplo ensina?

### 7.1 `request_id`

Ajuda a:

- correlacionar logs.

### 7.2 `Metrics`

Ajuda a:

- registrar comportamento agregado.

### 7.3 `span`

Ajuda a:

- medir etapas especificas do fluxo.

### 7.4 `LoggerAdapter`

Ajuda a:

- carregar contexto sem repetir tudo manualmente.

---

## 8. Cardinalidade e custo

Erro classico:

- criar metrica por usuario, email ou request individual.

Isso explode cardinalidade.

Pioras tipicas:

- custo de armazenamento;
- consulta ruim;
- observabilidade inutil.

---

## 9. Operacao tambem e contrato

Servico saudavel precisa definir:

- como sobe;
- como recebe configuracao;
- como expoe health;
- como loga;
- como mede;
- como falha.

Sem isso, "rodar em producao" vira improviso operacional.

---

## 10. Comparacao com C, C++ e Rust

- Em C e C++, observabilidade costuma exigir mais cuidado manual para manter overhead sob controle.
- Em Rust, ecossistema moderno ajuda bastante a tipar contexto e spans.
- Em Python, a instrumentacao pode ser muito rapida de escrever, mas isso aumenta o risco de fazer logging caro ou inconsistente.

## 12. Erros Comuns e Anti-Padroes

1. **Usar `print` como unica estrategia de observabilidade**.
2. **Logar demais sem semantica nem correlacao**.
3. **Criar metrica com cardinalidade explosiva**.
4. **Nao medir latencia de etapas importantes**.
5. **Achar que tracing substitui logs ou metricas**.

# Aula 22 - Filas, workers, retries e idempotencia

---

## Objetivo da Aula

Entender como modelar trabalho em background em sistemas Python, quais problemas filas e workers resolvem, e por que retries, idempotencia e falha parcial sao parte central da engenharia real. Ao final, voce deve conseguir distinguir codigo que "processa tarefa" de sistema que processa tarefa de forma operavel e robusta.

## 2. Por que fila existe?

Fila ajuda a:

- desacoplar produtor e consumidor;
- absorver rajada;
- mover trabalho pesado para depois;
- controlar concorrencia;
- aumentar resiliencia.

### 2.1 Fila nao e magia

Ela nao elimina:

- erro;
- duplicacao;
- atraso;
- saturacao;
- backpressure.

---

## 3. Worker

- **Worker**: processo ou tarefa que consome jobs de uma fila e executa o trabalho real.

Em sistema serio, um worker precisa pensar em:

- timeout;
- retry;
- idempotencia;
- observabilidade;
- poison message;
- shutdown previsivel.

---

## 4. Retry

- **Retry**: tentar novamente uma operacao que falhou.

Retry faz sentido quando a falha e:

- temporaria;
- intermitente;
- externa.

Retry nao faz sentido se a falha e:

- bug deterministico;
- entrada invalida;
- contrato quebrado.

---

## 5. Idempotencia

- **Idempotencia**: executar a mesma operacao mais de uma vez sem corromper o resultado final esperado.

Exemplo:

- marcar pedido como "email enviado" usando chave unica de envio.

Sem idempotencia:

- retry pode gerar duplicacao de efeito.

---

## 6. Exemplo completo da aula

```python
from dataclasses import dataclass
from queue import Queue, Empty
from threading import Event, Thread
import time


@dataclass
class Job:
    job_id: str
    recipient: str
    subject: str
    attempts: int = 0


processed_jobs: set[str] = set()


def send_email(job: Job) -> None:
    if job.job_id in processed_jobs:
        print(f"[skip] duplicate job {job.job_id}")
        return

    if job.attempts < 1:
        raise RuntimeError("temporary smtp failure")

    print(f"[send] to={job.recipient} subject={job.subject}")
    processed_jobs.add(job.job_id)


def worker_loop(name: str, jobs: Queue[Job], stop: Event) -> None:
    while not stop.is_set():
        try:
            job = jobs.get(timeout=0.2)
        except Empty:
            continue

        try:
            send_email(job)
        except RuntimeError as exc:
            job.attempts += 1
            print(f"[{name}] retry job={job.job_id} error={exc}")
            if job.attempts <= 3:
                time.sleep(0.2)
                jobs.put(job)
            else:
                print(f"[{name}] dead-letter job={job.job_id}")
        finally:
            jobs.task_done()


def main() -> None:
    jobs: Queue[Job] = Queue()
    stop = Event()

    thread = Thread(target=worker_loop, args=("worker-1", jobs, stop), daemon=True)
    thread.start()

    jobs.put(Job(job_id="email-1", recipient="ana@example.com", subject="Boas-vindas"))
    jobs.put(Job(job_id="email-1", recipient="ana@example.com", subject="Boas-vindas"))

    jobs.join()
    stop.set()
    thread.join(timeout=1)


if __name__ == "__main__":
    main()
```

---

## 7. O que esse exemplo ensina?

### 7.1 `job_id`

Ajuda a modelar:

- idempotencia.

### 7.2 `attempts`

Ajuda a controlar:

- retry.

### 7.3 `Queue`

Ajuda a desacoplar:

- producao e consumo.

### 7.4 Dead-letter conceitual

Quando o job falha repetidamente, precisamos decidir:

- reprocessar depois;
- isolar;
- registrar;
- inspecionar.

---

## 8. Retry sem criterio piora sistema

Se voce reexecuta tudo cegamente:

- amplifica carga;
- piora cascata de falhas;
- duplica efeitos;
- mascara bug real.

Retry bom precisa de:

- limite;
- atraso;
- classificacao de erro;
- idempotencia.

---

## 9. Worker nao e "thread rodando qualquer coisa"

Worker de producao precisa pensar em:

- visibilidade do que falhou;
- quantos jobs estao enfileirados;
- shutdown;
- concorrencia maxima;
- saturacao da dependencia externa.

---

## 10. Comparacao com C, C++ e Rust

- Em C e C++, muito desse desenho aparece em filas internas, brokers e servicos com controle mais manual de threads e memoria.
- Em Rust, tipos ajudam bastante a modelar estado de job e falha, mas idempotencia continua sendo problema de negocio e sistema.
- Em Python, a produtividade e alta para orquestracao, mas isso nao elimina necessidade de criterio operacional.

## 12. Erros Comuns e Anti-Padroes

1. **Fazer retry de qualquer erro sem classificar causa**.
2. **Nao ter identificador idempotente para trabalho repetivel**.
3. **Executar trabalho lento dentro da request quando deveria ir para fila**.
4. **Nao pensar em poison message ou falha repetida**.
5. **Achar que fila resolve arquitetura ruim automaticamente**.

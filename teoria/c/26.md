# Aula 26 - Strings, buffers e builders eficientes em C

---

## Nesta aula

Você vai aprender a montar um builder com `len`/`cap` e crescimento amortizado; demonstrar o custo quadratico da concatenacao ingenua com numero; e explicar por que `realloc` pode invalidar ponteiros internos (e como o builder sobrevive).


---

Na aula 24, vimos:

- heap real;
- fragmentacao;
- custo de `malloc` e `free`;
- crescimento amortizado.

Na aula 25, estudamos:

Agora vamos aplicar esse raciocinio a um dos problemas mais comuns do software real:

Isso aparece em:

- parser;

- gerador de JSON;
- serializacao;
- montagem de resposta de protocolo;
- leitura incremental de arquivo ou socket.

## 2. String em C nao e "texto magico"

Em C, string normalmente significa:

- sequencia de `char`;
- terminada por `'\0'`.

### 2.1 O que isso implica?

Implica que o programa precisa cuidar de:

- onde os bytes estao;
- quantos bytes validos existem;
- se existe espaco para o terminador;
- se houve overflow;
- quem e dono do buffer.

### 2.2 Por que isso importa?

Porque, em software real, tratar string como abstracao sem custo leva a:

- copia excessiva;
- leitura fora do limite;
- montagem lenta;
- bugs de lifetime.

---

## 3. Tamanho logico vs capacidade

Esse e o ponto central da aula.

Quando montamos um buffer dinamico, precisamos separar:

- **len**: quantidade de bytes realmente usados;
- **cap**: quantidade de bytes reservados;

e, se for string C tradicional:

- reservar espaco para `'\0'`.

### 3.1 Modelo mental

Se `len == 12` e `cap == 32`, isso significa:

- 12 bytes contem dado util;
- 20 bytes ainda estao disponiveis;
- o buffer pode crescer sem realocar imediatamente.

---

## 4. O custo da concatenacao ingenua

Considere uma estrategia ruim:

1. string atual tem tamanho `n`;
2. chega novo pedaco;
3. aloca buffer novo de tamanho exato;
4. copia string antiga;
5. copia pedaco novo;
6. libera antigo;
7. repete para cada append.

### 4.1 O problema

Esse modelo:

- realoca demais;
- copia demais;
- pressiona allocator;
- pode degradar para custo quadratico.

### 4.2 Exemplo de falha: nao copiar nem executar isoladamente

O trecho abaixo e **conceitual e inseguro**. Alem de ser lento em um loop, ele nao verifica se a soma dos tamanhos transborda `size_t` nem se `malloc` retornou `NULL`. Nesses casos, `strcpy` pode escrever fora da alocacao ou acessar um ponteiro nulo. Ele tambem pressupoe que `atual` e `parte` sejam strings terminadas em `\0` validas. Nao o use como implementacao de um builder.

```c
/* exemplo de falha: nao use este codigo */
novo = malloc(strlen(atual) + strlen(parte) + 1);
strcpy(novo, atual);
strcat(novo, parte);
free(atual);
atual = novo;
```

Mesmo quando os tamanhos cabem e a alocacao funciona, repetir essa operacao em um hot path faz o custo crescer rapidamente. Uma versao correta precisa calcular e validar o tamanho antes de alocar, verificar o retorno da alocacao e copiar somente dentro da capacidade conhecida.

---

## 5. Builder de string

- **String builder**: estrutura que mantem buffer, tamanho logico e capacidade para permitir montagem incremental com custo melhor.

### 5.1 O que ele compra?

- menos realocacoes;
- menos copia total;
- append mais previsivel;
- modelo mais seguro do que concatenar cegamente.

### 5.2 O que ele nao compra automaticamente?

- limites corretos;
- tratamento de erro;
- ownership claro;
- protecao contra uso errado.

Essas partes continuam responsabilidade do programador.

---

## 6. Buffers binarios vs strings textuais

Nem todo buffer e string.

### 6.1 Buffer binario

- trabalha com bytes arbitrarios;
- pode conter `'\0'` no meio;
- depende de `len`, nao de terminador.

### 6.2 String textual em C

- normalmente usa bytes textuais;
- termina em `'\0'`;
- muitas APIs da libc esperam esse contrato.

### 6.3 Consequencia pratica

Um builder pode servir aos dois casos, mas voce precisa decidir:

- se quer manter terminador sempre valido;
- se o contrato e textual ou binario.

---

## 7. `strlen` nao e gratis

Esse detalhe e frequentemente ignorado.

`strlen` precisa:

- percorrer a memoria ate achar `'\0'`.

### 7.1 Consequencia

Se voce chama `strlen` o tempo todo durante montagem incremental, pode introduzir custo repetido desnecessario.

### 7.2 Regra pratica

Se voce ja controla `len`, use `len`.

Nao redescubra o tamanho toda hora.

---

## 8. Crescimento amortizado

Aqui voltamos ao que vimos na aula 24.

Em vez de crescer exatamente para o tamanho pedido a cada append, o builder costuma:

- reservar folga;
- aumentar capacidade por fator;
- reduzir numero de realocacoes.

### 8.1 Exemplo comum

- capacidade inicial 16;
- depois 32;
- depois 64;
- depois 128.

### 8.2 Trade-off

Voce aceita:

- alguma memoria extra;

para ganhar:

- menos `realloc`;
- menos copia;
- menor pressao no allocator.

---

## 9. `strcpy`, `strcat` e o problema do limite

Essas funcoes aparecem muito em codigo legado.

### 9.1 O risco

Se o destino nao tiver espaco suficiente:

- overflow;
- corrupcao de memoria;
- comportamento indefinido.

### 9.2 O erro conceitual

O problema nao e apenas "a funcao ser velha".

O problema e:

- operar sem contrato claro de capacidade.

### 9.3 Regra pratica

Sempre pense em:

- quantos bytes tenho;
- quantos bytes vou escrever;
- onde fica o terminador;
- qual e o limite total.

---

## 10. Builder simples da aula

Vamos montar uma struct pequena:

```c
typedef struct {
    char *data;
    size_t len;
    size_t cap;
} StrBuilder;
```

### 10.1 Invariantes desejadas

- `data` aponta para buffer valido enquanto o builder estiver vivo;
- `len <= cap - 1` quando tratado como string textual;
- `data[len] == '\0'`;
- `cap` inclui espaco para o terminador.

Esses invariantes ajudam muito a manter o raciocinio correto.

---

## 11. Exemplo completo da aula

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

typedef struct {
    char *data;
    size_t len;
    size_t cap;
} StrBuilder;

int sb_init(StrBuilder *sb, size_t initial_cap) {
    if (initial_cap < 2) {
        initial_cap = 2;
    }

    sb->data = malloc(initial_cap);
    if (sb->data == NULL) {
        return -1;
    }

    sb->data[0] = '\0';
    sb->len = 0;
    sb->cap = initial_cap;
    return 0;
}

int sb_reserve(StrBuilder *sb, size_t extra) {
    size_t needed = sb->len + extra + 1;
    if (needed <= sb->cap) {
        return 0;
    }

    size_t new_cap = sb->cap;
    while (new_cap < needed) {
        new_cap *= 2;
    }

    char *tmp = realloc(sb->data, new_cap);
    if (tmp == NULL) {
        return -1;
    }

    sb->data = tmp;
    sb->cap = new_cap;
    return 0;
}

int sb_append_n(StrBuilder *sb, const char *src, size_t n) {
    if (sb_reserve(sb, n) != 0) {
        return -1;
    }

    memcpy(sb->data + sb->len, src, n);
    sb->len += n;
    sb->data[sb->len] = '\0';
    return 0;
}

int sb_append_cstr(StrBuilder *sb, const char *src) {
    return sb_append_n(sb, src, strlen(src));
}

void sb_destroy(StrBuilder *sb) {
    free(sb->data);
    sb->data = NULL;
    sb->len = 0;
    sb->cap = 0;
}

int main(void) {
    StrBuilder sb;
    if (sb_init(&sb, 8) != 0) {
        fprintf(stderr, "falha ao inicializar builder\n");
        return 1;
    }

    if (sb_append_cstr(&sb, "GET ") != 0 ||
        sb_append_cstr(&sb, "/api/v1/usuarios") != 0 ||
        sb_append_cstr(&sb, " HTTP/1.1\r\n") != 0 ||
        sb_append_cstr(&sb, "Host: exemplo.local\r\n") != 0 ||
        sb_append_cstr(&sb, "\r\n") != 0) {
        fprintf(stderr, "falha ao montar string\n");
        sb_destroy(&sb);
        return 1;
    }

    printf("len=%zu cap=%zu\n", sb.len, sb.cap);
    printf("%s", sb.data);

    sb_destroy(&sb);
    return 0;
}
```

### 11.1 O que esse exemplo mostra?

- separacao entre `len` e `cap`;
- terminador nulo mantido sempre consistente;
- crescimento amortizado;
- `memcpy` usando tamanho conhecido;
- append incremental sem reconstruir tudo a cada etapa.

### 11.2 O que ele ainda nao resolve?

- escrita formatada tipo `printf`;
- buffer binario com `'\0'` no meio;
- concorrencia;
- pools de builders;
- limites globais de consumo por request.

---

## 12. O que acontece em memoria nesse exemplo?

Conceitualmente:

- a struct `StrBuilder` vive na stack;
- `data` aponta para um bloco no heap;
- `len` cresce a cada append;
- `cap` pode crescer em saltos;
- `realloc` pode mover o bloco;
- `data[len] = '\0'` garante compatibilidade com APIs textuais de C.

O ponto central e:

- texto montado incrementalmente nao precisa ser remontado do zero toda vez.

---

## 13. Builder binario

O mesmo padrao pode servir para payload binario.

Nesse caso:

- `'\0'` deixa de ser semantica central;
- `len` vira a verdade absoluta;
- APIs de string C podem deixar de ser apropriadas.

### 13.1 Exemplo de uso

- serializacao de protocolo;
- montagem de pacote;
- leitura de arquivo em blocos;
- payload de IPC.

### 13.2 Regra pratica

Se o dado pode conter byte zero, trate como:

- buffer binario;

nao como:

- string C textual.

---

## 14. `snprintf` e escrita formatada

`snprintf` pode ser muito util porque:

- respeita limite de buffer;
- ajuda a montar texto formatado;
- devolve informacao sobre tamanho necessario.

### 14.1 Mas nao e solucao magica

Se usada ingenuamente em loop, ainda pode:

- reformatar demais;
- recalcular demais;
- exigir reserva ruim;
- complicar append incremental.

### 14.2 Onde ela entra bem?

- escrever trecho formatado dentro de builder;
- calcular tamanho de output;
- produzir string final em buffer conhecido.

---

## 15. Evitando copias desnecessarias

Pergunta central:

- realmente preciso copiar esse pedaco agora?

### 15.1 Casos em que a copia faz sentido

- consolidar resposta final;
- ownership precisa ficar local;
- origem vai desaparecer;
- API seguinte exige contiguidade.

### 15.2 Casos em que talvez nao precise

- fatias logicas podem apontar para buffer maior;
- protocolo aceita scatter/gather em outra camada;
- dado ainda esta em buffer compartilhado valido.

Mas cuidado:

- menos copia muitas vezes significa mais complexidade de lifetime.

---

## 16. Strings em loop frequente

Esse e um lugar onde bugs de desempenho nascem rapido.

Exemplo de padrao ruim:

- chamar `strcat` repetidamente num loop;
- usar `strlen` toda vez;
- crescer buffer exatamente ao necessario;
- reformatar blocos inteiros a cada iteracao.

### 16.1 Melhor abordagem

- manter builder com `len`;
- reservar capacidade de forma amortizada;
- copiar apenas o trecho novo;
- evitar varrer string inteira repetidamente.

---

## 17. Erros de seguranca mais comuns

1. esquecer espaco para `'\0'`;
2. confiar em `strcpy` sem validar capacidade;
3. confundir tamanho de dado util com tamanho do buffer;
4. usar string textual para dado binario;
5. esquecer que `realloc` pode mover o bloco;
6. manter ponteiros antigos para dentro do buffer apos crescimento.

### 17.1 Esse ultimo ponto e muito importante

Se voce guarda:

- ponteiro para dentro de `sb.data`;

e depois o builder cresce com `realloc`, esse ponteiro interno pode ficar invalido.

## 19. Comparacao com C++, Rust, Go e Python

- Em C++, `std::string` e `std::vector<char>` escondem boa parte dessa mecanica, mas crescimento, capacidade e copia continuam existindo.
- Em Rust, `String` e `Vec<u8>` tornam esse modelo bem explicito e mais seguro, mas o trade-off fisico continua o mesmo.
- Em Go, `strings.Builder`, `bytes.Buffer` e slices reduzem bastante a friccao, mas seguem a mesma logica de capacidade e crescimento.
- Em Python, concatenacao pode parecer simples, mas o runtime ainda precisa lidar com alocacao e copia por baixo.

Em C, voce ve essa realidade diretamente:

- string boa e gestao de buffer bem pensada;
- string ruim e custo ou bug esperando acontecer.

---

## 20. Erros Comuns e Anti-Padroes

1. **Concatenar em loop com realocacao exata a cada passo**.
2. **Esquecer o byte do terminador nulo**.
3. **Usar `strlen` repetidamente quando `len` ja existe**.
4. **Tratar buffer binario como string textual**.
5. **Guardar ponteiro interno e esquecer que `realloc` pode invalidar tudo**.
6. **Assumir que `strcat` sabe o limite do destino**.

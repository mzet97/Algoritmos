# Aula 15 - Sockets, rede e programacao de sistemas Unix-like

---

## Objetivo da Aula

Entender o modelo basico de programacao de rede em C com sockets, incluindo endereco, porta, `bind`, `listen`, `accept`, `connect`, `send`, `recv` e fluxo de bytes. Ao final, voce deve conseguir montar o modelo mental de cliente e servidor TCP em C, ligando processos, descritores e rede a uma interface classica de sistemas Unix-like.

---

## 1. Ponte com a aula anterior

Na aula 14, vimos concorrencia dentro de um processo.

Agora vamos abrir a fronteira entre processos e maquinas:

- rede.

Em C e sistemas Unix-like, isso aparece fortemente via:

- sockets;
- descritores;
- bytes;
- chamadas de sistema encapsuladas em APIs classicas.

---

## 2. O que e um socket?

- **Socket**: endpoint de comunicacao entre processos, frequentemente usado para rede, tratado pelo sistema operacional como um recurso manipulavel por um descritor.

### 2.1 Modelo mental

Pense no socket como:

- um canal para enviar e receber bytes;
- associado a um protocolo e a um endereco;
- controlado pelo kernel.

---

## 3. TCP

- **TCP**: protocolo orientado a conexao, fluxo de bytes, confiavel, com entrega ordenada.

### 3.1 Por que comecar por TCP?

Porque ele simplifica o modelo inicial:

- conexao explicita;
- bytes entregues em ordem;
- menor foco em perda e reorder no codigo da aula.

---

## 4. Etapas de um servidor TCP

Fluxo classico:

1. `socket`
2. `bind`
3. `listen`
4. `accept`
5. `recv` e `send`
6. `close`

### 4.1 O que cada etapa faz?

- `socket`: cria endpoint.
- `bind`: associa endereco e porta.
- `listen`: marca como socket passivo de escuta.
- `accept`: aceita nova conexao de cliente.
- `recv`/`send`: troca bytes.
- `close`: fecha recurso.

---

## 5. Etapas de um cliente TCP

Fluxo classico:

1. `socket`
2. `connect`
3. `send`
4. `recv`
5. `close`

### 5.1 O ponto central

Cliente e servidor usam primitives parecidas, mas em papeis diferentes.

---

## 6. Estruturas importantes

Headers classicos:

```c
#include <sys/types.h>
#include <sys/socket.h>
#include <netinet/in.h>
#include <arpa/inet.h>
#include <unistd.h>
```

Estrutura comum:

```c
struct sockaddr_in addr;
```

### 6.1 O que ela carrega?

- familia de enderecos;
- porta;
- endereco IPv4.

---

## 7. `bind`, `listen` e `accept`

Exemplo conceitual:

```c
int server_fd = socket(AF_INET, SOCK_STREAM, 0);
bind(server_fd, (struct sockaddr *)&addr, sizeof(addr));
listen(server_fd, 16);
int client_fd = accept(server_fd, NULL, NULL);
```

### 7.1 `SOCK_STREAM`

Indica socket orientado a fluxo, tipicamente TCP.

### 7.2 `AF_INET`

Indica IPv4.

---

## 8. `connect`

No cliente:

```c
int fd = socket(AF_INET, SOCK_STREAM, 0);
connect(fd, (struct sockaddr *)&addr, sizeof(addr));
```

### 8.1 O que `connect` faz?

Pede ao kernel para estabelecer conexao com o endpoint remoto.

---

## 9. `send` e `recv`

Exemplo:

```c
send(fd, msg, len, 0);
recv(fd, buffer, sizeof(buffer), 0);
```

### 9.1 Regra importantissima

TCP e fluxo de bytes.

Nao existe garantia de que uma chamada:

- envie tudo de uma vez;
- receba tudo de uma vez;
- preserve "mensagens" do jeito que voce imaginou.

Isso e crucial.

### 9.2 Consequencia pratica

Protocolos reais precisam definir:

- framing;
- delimitacao;
- tamanho;
- estrategia de leitura.

---

## 10. Exemplo completo da aula

Servidor TCP simples:

```c
#include <arpa/inet.h>
#include <netinet/in.h>
#include <stdio.h>
#include <string.h>
#include <sys/socket.h>
#include <sys/types.h>
#include <unistd.h>

int main(void) {
    int server_fd = socket(AF_INET, SOCK_STREAM, 0);
    if (server_fd < 0) {
        perror("socket");
        return 1;
    }

    struct sockaddr_in addr;
    memset(&addr, 0, sizeof(addr));
    addr.sin_family = AF_INET;
    addr.sin_port = htons(8080);
    addr.sin_addr.s_addr = htonl(INADDR_ANY);

    if (bind(server_fd, (struct sockaddr *)&addr, sizeof(addr)) < 0) {
        perror("bind");
        close(server_fd);
        return 1;
    }

    if (listen(server_fd, 16) < 0) {
        perror("listen");
        close(server_fd);
        return 1;
    }

    printf("escutando na porta 8080\n");

    int client_fd = accept(server_fd, NULL, NULL);
    if (client_fd < 0) {
        perror("accept");
        close(server_fd);
        return 1;
    }

    char buffer[256];
    ssize_t n = recv(client_fd, buffer, sizeof(buffer) - 1, 0);
    if (n < 0) {
        perror("recv");
        close(client_fd);
        close(server_fd);
        return 1;
    }

    buffer[n] = '\0';
    printf("recebido: %s\n", buffer);

    const char *resp = "ok\n";
    if (send(client_fd, resp, strlen(resp), 0) < 0) {
        perror("send");
    }

    close(client_fd);
    close(server_fd);
    return 0;
}
```

### 10.1 Explicacao linha por linha

- `socket(AF_INET, SOCK_STREAM, 0)`: cria socket TCP IPv4.
- `memset(&addr, 0, sizeof(addr))`: zera a struct de endereco.
- `htons(8080)`: converte porta para ordem de bytes de rede.
- `htonl(INADDR_ANY)`: aceita conexoes em qualquer interface local.
- `bind`: liga o socket a endereco e porta.
- `listen`: torna o socket passivo.
- `accept`: aceita um cliente.
- `recv`: le bytes.
- `send`: envia bytes de resposta.
- `close`: libera descritores.

---

## 11. O que acontece em memoria e no kernel?

Conceitualmente:

- `server_fd` e `client_fd` sao inteiros locais na stack;
- esses inteiros sao descritores que referenciam objetos de socket mantidos pelo kernel;
- buffers locais como `buffer[256]` vivem na stack;
- `recv` copia bytes do kernel para o buffer do processo;
- `send` copia bytes do processo para buffers do kernel.

O ponto central:

- socket nao e "a conexao em si" dentro do seu endereco virtual;
- e um handle para recurso controlado pelo sistema operacional.

---

## 12. Byte order de rede

Funcoes classicas:

- `htons`
- `htonl`
- `ntohs`
- `ntohl`

### 12.1 Por que isso existe?

Porque a rede usa convencao de ordem de bytes e as maquinas podem ter representacoes internas diferentes.

Isso e outro exemplo forte de fronteira entre:

- logica do programa;
- representacao fisica.

---

## 13. Limites do exemplo simples

Este servidor e didatico.

Ele ainda nao trata bem:

- varios clientes;
- loop de `accept`;
- leituras parciais robustas;
- timeouts;
- multiplexacao com `select` ou `poll`;
- framing de protocolo;
- shutdown gracioso.

Mas ele te entrega o modelo mental essencial.

## 15. Comparacao com C++, Rust, Go e Python

- Em C++, bibliotecas e wrappers podem tornar a API menos crua, mas os conceitos basicos continuam.
- Em Rust, crates de rede encapsulam muito melhor ownership e erros.
- Em Go, `net` e `net/http` elevam muito o nivel da programacao de rede.
- Em Python, sockets e frameworks escondem parte da dureza inicial.

Em C, a API classica te deixa muito proximo do modelo do SO.

## 16. Erros Comuns e Anti-Padroes

1. **Assumir que `send` e `recv` lidam com a mensagem inteira sempre**.
2. **Esquecer conversao de byte order para porta e endereco**.
3. **Nao checar retorno de `socket`, `bind`, `listen`, `accept`, `recv` e `send`**.
4. **Achar que descritor e o recurso em si, e nao um handle**.
5. **Esquecer de fechar sockets**.
6. **Escrever protocolo sem framing claro sobre TCP**.

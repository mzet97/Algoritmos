# Aula 27 - Mini runtime de containers e APIs reutilizaveis

---

## Objetivo da Aula

Ao final, voce devera: entregar um vetor dinamico generico com contrato de ownership escrito; parametrizar comportamento com callback sem quebrar o contrato; e explicar onde genericidade com `void *` ajuda e onde so esconde o tipo.

### Como ler esta aula (tres niveis)

- **Fundamental:** vetor com `len`/`cap`, `void *` como carga, dono declarado.
- **Intermediario:** callback, fila simples, contrato de API previsivel.
- **Aprofundamento (opcional):** mapa simples e o custo da genericidade (aula 31 usa em producao).

Na aula 25, estudamos:

- arenas;

Agora chegamos a uma pergunta natural:

Essa e a porta de entrada para um mini runtime local de containers.

---

## 2. O que significa "mini runtime" neste contexto?

Nao estamos falando de runtime de linguagem no sentido de:

- garbage collector;
- scheduler;
- VM.

Aqui, "mini runtime" significa:

- um pequeno conjunto de estruturas e contratos reutilizaveis;
- para armazenar, mover, destruir e iterar dados;
- sem reescrever a mesma infraestrutura em cada modulo.

Exemplos:

- vetor dinamico;
- fila;
- lista de ponteiros;
- mapa simples;
- callbacks de comparacao ou destruicao.

---

## 3. Por que isso importa em C?

Porque C te da:

- liberdade enorme;
- mas pouca infraestrutura padrao de container generico.

Sem estrategia, o resultado costuma ser:

- cada modulo inventa seu proprio vetor;
- ownership muda de um lugar para outro;
- callbacks sao inconsistentes;
- destruicao de elementos vira fonte de bug;
- APIs nao se encaixam entre si.

### 3.1 O objetivo aqui

Nao e copiar STL, Rust `std` ou Go slices.

E aprender a desenhar:

- containers pequenos;
- contratos claros;
- custos explicitamente visiveis;
- ownership previsivel.

---

## 4. Tres perguntas obrigatorias de qualquer API de container

Antes de implementar qualquer estrutura, responda:

1. o container guarda bytes, ponteiros ou objetos por valor?
2. quem e dono do elemento armazenado?
3. quem destroi o elemento quando ele sai do container?

### 4.1 Sem essas respostas

Voce acaba com:

- leaks;
- double free;
- destruicao esquecida;
- ponteiros pendurados;
- API confusa.

---

## 5. Estrategias de genericidade em C

As mais comuns sao:

- macro;
- `void *`;
- callback;
- armazenar bytes crus com `elem_size`.

Nesta aula, vamos focar principalmente em:

- `void *` para ponteiros genericos;
- callbacks para comparacao e destruicao;
- vetor dinamico como base.

---

## 6. `void *`: poder e perigo

- **`void *`**: ponteiro generico sem tipo concreto associado no ponto da API.

### 6.1 O que ele compra?

- flexibilidade;
- capacidade de guardar referencias para varios tipos;
- API unica para diferentes payloads.

### 6.2 O que ele cobra?

- menos verificacao pelo compilador;
- mais responsabilidade do chamador;
- cast correto em pontos de uso;
- risco maior de erro de contrato.

### 6.3 Regra pratica

`void *` funciona melhor quando a API documenta com clareza:

- o que o ponteiro representa;
- quem e dono;
- quem destroi;
- qual callback espera qual tipo concreto.

---

## 7. Vetor dinamico de ponteiros

Comecaremos pelo container mais util.

Modelo:

```c
typedef struct {
    void **items;
    size_t len;
    size_t cap;
} PtrVec;
```

### 7.1 O que isso representa?

- `items`: array de ponteiros genericos;
- `len`: numero de elementos ocupados;
- `cap`: capacidade atual do vetor.

### 7.2 O que isso nao faz automaticamente?

- destruir payload apontado;
- copiar profundamente os objetos;
- verificar tipo.

Essas decisoes pertencem ao contrato da API.

---

## 8. Callback de destruicao

Um padrao muito util:

```c
typedef void (*destroy_fn)(void *);
```

### 8.1 Por que isso e importante?

Porque o vetor pode saber:

- como destruir cada item;

sem conhecer o tipo concreto.

### 8.2 Casos possiveis

- vetor nao e dono de nada: `destroy_fn == NULL`;
- vetor e dono dos elementos: chama destruidor na limpeza;
- vetor guarda objetos heterogeneos? ai o contrato fica bem mais delicado.

---

## 9. Callback de comparacao

Outro padrao util:

```c
typedef int (*cmp_fn)(const void *, const void *);
```

Isso permite:

- busca;
- ordenacao simples;
- remocao por criterio;
- reuso da mesma estrutura com varios tipos.

### 9.1 Cuidado

Se a API e generica, a comparacao precisa ser:

- coerente;
- bem documentada;
- consistente com o tipo real guardado.

---

## 10. Exemplo completo da aula: vetor generico simples

```c
#include <stdio.h>
#include <stdlib.h>

typedef void (*destroy_fn)(void *);

typedef struct {
    void **items;
    size_t len;
    size_t cap;
    destroy_fn destroy;
} PtrVec;

int ptrvec_init(PtrVec *v, size_t initial_cap, destroy_fn destroy) {
    if (initial_cap < 2) {
        initial_cap = 2;
    }

    v->items = malloc(initial_cap * sizeof(*v->items));
    if (v->items == NULL) {
        return -1;
    }

    v->len = 0;
    v->cap = initial_cap;
    v->destroy = destroy;
    return 0;
}

int ptrvec_push(PtrVec *v, void *item) {
    if (v->len == v->cap) {
        size_t new_cap = v->cap * 2;
        void **tmp = realloc(v->items, new_cap * sizeof(*v->items));
        if (tmp == NULL) {
            return -1;
        }
        v->items = tmp;
        v->cap = new_cap;
    }

    v->items[v->len++] = item;
    return 0;
}

void *ptrvec_get(const PtrVec *v, size_t index) {
    if (index >= v->len) {
        return NULL;
    }
    return v->items[index];
}

void ptrvec_destroy(PtrVec *v) {
    if (v->destroy != NULL) {
        for (size_t i = 0; i < v->len; i++) {
            if (v->items[i] != NULL) {
                v->destroy(v->items[i]);
            }
        }
    }

    free(v->items);
    v->items = NULL;
    v->len = 0;
    v->cap = 0;
    v->destroy = NULL;
}

static void int_destroy(void *ptr) {
    free(ptr);
}

int main(void) {
    PtrVec v;
    if (ptrvec_init(&v, 2, int_destroy) != 0) {
        fprintf(stderr, "falha ao criar vetor\n");
        return 1;
    }

    for (int i = 0; i < 5; i++) {
        int *value = malloc(sizeof(*value));
        if (value == NULL) {
            fprintf(stderr, "falha ao criar inteiro\n");
            ptrvec_destroy(&v);
            return 1;
        }

        *value = i * 10;
        if (ptrvec_push(&v, value) != 0) {
            fprintf(stderr, "falha ao inserir no vetor\n");
            free(value);
            ptrvec_destroy(&v);
            return 1;
        }
    }

    for (size_t i = 0; i < v.len; i++) {
        int *value = ptrvec_get(&v, i);
        printf("v[%zu] = %d\n", i, *value);
    }

    ptrvec_destroy(&v);
    return 0;
}
```

### 10.1 O que esse exemplo mostra?

- container generico de ponteiros;
- crescimento amortizado;
- callback de destruicao;
- ownership explicito do vetor sobre elementos;
- contrato simples e reutilizavel.

### 10.2 O que ele ainda nao resolve?

- remocao;
- insercao no meio;
- iteradores melhores;
- ordenacao;
- thread safety;
- armazenamento por valor.

---

## 11. O que acontece em memoria nesse vetor?

Conceitualmente:

- a struct `PtrVec` vive na stack ou embutida em outro objeto;
- `items` aponta para array dinamico de `void *` no heap;
- cada item pode apontar para outro bloco independente no heap;
- isso cria dois niveis de ownership:
- o ownership do array interno do vetor;
- o ownership dos objetos apontados.

### 11.1 Por que isso importa?

Porque bugs aparecem justamente quando esses dois niveis se confundem.

---

## 12. Dono do container vs dono do payload

Esse e o grande tema da aula.

### 12.1 Caso A: container nao e dono

O vetor so guarda referencias.

Logo:

- destruir o vetor nao deve destruir os elementos.

### 12.2 Caso B: container e dono

O vetor passa a ser responsavel por destruir os elementos.

Logo:

- precisa de callback de destruicao;
- o chamador nao pode dar `free` por fora depois.

### 12.3 Regra pratica

Escolha um dos contratos.

Nao misture silenciosamente.

---

## 13. API reutilizavel precisa de limites claros

Algumas perguntas que a sua API deve responder:

- push aceita `NULL`?
- get fora da faixa retorna o que?
- destroy e idempotente?
- quem libera item removido?
- a ordem de iteracao e estavel?
- o container invalida ponteiros internos ao crescer?

Se isso nao estiver claro, a reutilizacao vira fonte de confusao.

## 14. Fila simples

Outro container muito util e:

- fila FIFO.

Implementacoes comuns:

- lista ligada;
- buffer circular;
- vetor com indices.

### 14.1 Qual usar?

Para previsibilidade e localidade, buffer circular costuma ser muito interessante.

Para simplicidade didatica, lista ligada e facil de visualizar.

### 14.2 O ponto central

Mesmo numa fila simples, as perguntas continuam:

- quem e dono do item?
- quem destroi?
- fila bloqueia? nao bloqueia?
- quando cresce?

---

## 15. Armazenar ponteiro vs armazenar bytes por valor

Esse trade-off e importante.

### 15.1 Guardar ponteiros

Compra:

- API mais simples para tipos grandes;
- menos copia de payload;
- flexibilidade com `void *`.

Cobra:

- mais indirecao;
- mais heap;
- ownership mais delicado.

### 15.2 Guardar bytes por valor

Compra:

- contiguidade;
- melhor localidade;
- menos indirecao.

Cobra:

- `elem_size`;
- copia de bytes;
- custo de mover elementos;
- callbacks mais cuidadosos.

---

## 16. `void *` nao substitui design de tipo

Esse e um alerta importante.

Em C, genericidade por `void *` e util.

Mas se usada sem criterio, produz:

- API opaca demais;
- casts espalhados;
- bugs dificeis;
- baixo apoio do compilador.

### 16.1 Regra pratica

Use `void *` quando:

- a reutilizacao e real;
- o contrato e pequeno;
- callbacks sao suficientes;
- o ganho compensa a perda de verificacao estatica.

Caso contrario, prefira:

- container tipado por dominio;
- API mais simples e especifica.

---

## 17. Callbacks e custo mental

Callback e muito poderoso, mas cobra:

- assinatura correta;
- documentacao clara;
- cuidado com lifetime de dados capturados por contexto externo.

### 17.1 Onde costuma ajudar

- destruir item;
- comparar item;
- visitar item;
- aplicar predicado de busca.

### 17.2 Onde costuma complicar

- quando contrato de tipo fica implicito demais;
- quando callback assume estado global escondido;
- quando ownership do contexto nao esta claro.

## 19. Comparacao com C++, Rust, Go e Python

- Em C++, `std::vector`, templates, iteradores e destrutores automaticos resolvem grande parte dessa infraestrutura com muito mais apoio da linguagem.
- Em Rust, `Vec<T>`, generics e ownership tornam esse desenho muito mais seguro sem perder controle de custo.
- Em Go, slices e interfaces reduzem muito a friccao, embora o modelo de ownership seja bem diferente.
- Em Python, listas e dicionarios prontos escondem quase toda essa camada estrutural do programador comum.

Em C, construir containers reutilizaveis significa encarar diretamente:

- layout;
- lifetime;
- destroy;
- contrato de API;
- custo de indirecao e copia.

---

## 20. Erros Comuns e Anti-Padroes

1. **Nao definir quem e dono do payload**.
2. **Usar `void *` sem documentar o tipo esperado**.
3. **Esquecer callback de destruicao quando o container e dono**.
4. **Misturar ownership compartilhado e ownership unico sem regra clara**.
5. **Fazer API generica demais sem necessidade real**.
6. **Assumir que reutilizacao compensa automaticamente a perda de clareza**.

# Aula 11 - Depuracao com `gdb`, sanitizers e `valgrind`

---

## Objetivo da Aula

Ao final, voce devera: reproduzir um crash e extrair stack trace com `gdb`; explicar o que um relatorio do ASan/UBSan aponta (arquivo, linha, categoria); e montar um fluxo minimo sintoma -> hipotese -> instrumento -> confirmacao para um bug de memoria.

### Como ler esta aula (tres niveis)

- **Fundamental:** compilar com `-g`, rodar sob `gdb`, ler `bt`, rodar sob ASan/UBSan e ler o relatorio.
- **Intermediario:** breakpoint condicional, `watch`, `valgrind` quando sanitizer nao basta.
- **Aprofundamento (opcional):** core dump e depuracao post-mortem (aula 15/18 retomam o contexto).

---

## 1. Ponte com a aula anterior

Na aula 10, vimos que C permite:

- performance alta;
- controle fino;
- e tambem UB, aliasing perigoso e erros sutis.

Agora vem a pergunta inevitavel:

- como descobrir o que esta errado quando o programa quebra?

Essa e a funcao da depuracao.

---

## 2. O problema real

Em C, bugs comuns incluem:

- segmentation fault;
- leitura fora dos limites;
- uso de memoria nao inicializada;
- use-after-free;
- double free;
- resultado incorreto sem crash.

Sem ferramentas, voce fica preso a:

- `printf` espalhado;
- suposicoes;
- tentativa e erro.

Isso nao escala.

---

## 3. O que e `gdb`?

- **`gdb`**: depurador que permite executar o programa passo a passo, inspecionar variaveis, ver stack trace, colocar breakpoints e entender o estado da execucao.

### 3.1 Quando ele ajuda mais?

- crash reproduzivel;
- fluxo logico confuso;
- valor ficando errado;
- necessidade de inspecionar stack frame e chamada.

### 3.2 Requisito importante

Compile com informacao de debug:

```bash
gcc -Wall -Wextra -Wpedantic -O0 -g bug.c -o bug
```

Sem `-g`, o depurador perde muito contexto.

---

## 4. Breakpoint

- **Breakpoint**: ponto em que a execucao para para voce inspecionar o estado do programa.

Comandos classicos no `gdb`:

- `break main`
- `run`
- `next`
- `step`
- `print variavel`
- `bt`
- `continue`

### 4.1 `next` vs `step`

- `next`: executa a linha atual sem entrar em chamada de funcao.
- `step`: entra na funcao chamada naquela linha.

---

## 5. Stack trace

- **Stack trace**: sequencia de chamadas ativas que levou ao ponto atual.

No `gdb`, um comando central e:

```text
bt
```

Isso responde:

- onde estou?
- quem chamou esta funcao?
- qual foi a cadeia de chamadas ate aqui?

---

## 6. Exemplo simples para `gdb`

```c
#include <stdio.h>

int divide(int a, int b) {
    return a / b;
}

int main(void) {
    int x = 10;
    int y = 0;
    int z = divide(x, y);
    printf("%d\n", z);
    return 0;
}
```

### 6.1 Fluxo tipico no `gdb`

```bash
gdb .\bug
```

Dentro do `gdb`:

```text
break main
run
next
print x
print y
step
bt
```

Aqui o objetivo nao e decorar o `gdb` inteiro.

E aprender o modelo:

- parar;
- observar;
- explicar.

---

## 7. Sanitizers

- **Sanitizers**: instrumentacoes do compilador que inserem verificacoes extras para detectar classes especificas de erro em runtime.

Os mais importantes nesta trilha:

- AddressSanitizer
- UndefinedBehaviorSanitizer
- ThreadSanitizer

### 7.1 Por que isso e tao poderoso?

Porque essas ferramentas detectam muitos bugs perto da causa, nao apenas quando os sintomas aparecem longe.

---

## 8. AddressSanitizer

Compilar:

```bash
gcc -Wall -Wextra -Wpedantic -O0 -g -fsanitize=address bug.c -o bug
```

Ele ajuda a detectar:

- buffer overflow;
- use-after-free;
- stack overflow em varios cenarios;
- double free;
- varios acessos invalidos de memoria.

### 8.1 Modelo mental

O binario fica instrumentado para vigiar acessos.

Voce paga overhead, mas ganha sinal de altissimo valor.

---

## 9. UndefinedBehaviorSanitizer

Compilar:

```bash
gcc -Wall -Wextra -Wpedantic -O0 -g -fsanitize=undefined bug.c -o bug
```

Ele ajuda a detectar classes de UB, como:

- overflow inteiro com sinal em varios casos;
- alinhamento invalido;
- certas conversoes problematicas;
- operacoes que violam contratos da linguagem.

### 9.1 Regra pratica

Para estudo e diagnostico:

```bash
gcc -Wall -Wextra -Wpedantic -O0 -g -fsanitize=address -fsanitize=undefined bug.c -o bug
```

e uma combinacao muito forte.

---

## 10. `valgrind`

- **`valgrind`**: ferramenta de instrumentacao em runtime, especialmente forte para detectar leaks, uso de memoria nao inicializada e acessos invalidos em varias plataformas Unix-like.

Uso classico:

```bash
valgrind --leak-check=full ./bug
```

### 10.1 Quando ele ajuda mais?

- vazamento de memoria;
- caminho de alocacao/liberacao confuso;
- analise de heap em programas nao recompilados com sanitizer.

### 10.2 Trade-off

- muito util;
- geralmente mais lento que execucao normal;
- nao substitui completamente sanitizers.

## 11. Exemplo completo da aula

```c
#include <stdio.h>
#include <stdlib.h>

int soma_primeiro_ultimo(const int *v, int n) {
    return v[0] + v[n - 1];
}

int main(void) {
    int *v = malloc(3 * sizeof(int));
    if (v == NULL) {
        fprintf(stderr, "falha em malloc\n");
        return 1;
    }

    v[0] = 10;
    v[1] = 20;
    v[2] = 30;

    printf("resultado = %d\n", soma_primeiro_ultimo(v, 3));

    free(v);
    v = NULL;
    return 0;
}
```

### 11.1 Como usar esse exemplo didaticamente?

Versao limpa:

```bash
gcc -Wall -Wextra -Wpedantic -O0 -g aula11.c -o aula11
```

Versao com ASan e UBSan:

```bash
gcc -Wall -Wextra -Wpedantic -O0 -g -fsanitize=address -fsanitize=undefined aula11.c -o aula11
```

Se voce introduzir propositalmente:

- `v[3] = 99;`

ou

- leitura depois de `free(v);`

o sanitizer passa a mostrar relatorios muito instrutivos.

---

## 12. Fluxo real de investigacao

Fluxo pratico recomendado:

1. reproduza o bug.
2. compile com `-Wall -Wextra -Wpedantic -O0 -g`.
3. rode com sanitizer quando fizer sentido.
4. se houver crash ou valor errado, entre no `gdb`.
5. inspecione stack trace, argumentos e variaveis.
6. reduza o caso ao menor exemplo reproduzivel.

### 12.1 Regra de maturidade

Nao tente "consertar no chute" antes de explicar o bug.

---

## 13. O que acontece em memoria nessas ferramentas?

Conceitualmente:

- `gdb` observa o estado do processo e seus simbolos de debug;
- sanitizers inserem verificacoes extras no binario;
- `valgrind` monitora acessos e alocacoes em runtime.

O ponto central e:

- nao sao "magia";
- sao lentes diferentes sobre execucao, stack e heap.

---

## 14. Comparacao com C++, Rust, Go e Python

- Em C++, essas ferramentas continuam extremamente importantes porque boa parte dos mesmos riscos ainda existe.
- Em Rust, a necessidade muda de perfil porque muitos erros saem do runtime e vao para compilacao, embora `gdb` e sanitizers ainda possam ser uteis em `unsafe`.
- Em Go, `pprof`, race detector e stack traces automaticos ocupam parte desse espaco.
- Em Python, depuracao costuma focar mais em logica e excecao do que em corrupcao de memoria crua.

Em C, essas ferramentas sao parte do fluxo normal, nao luxo.

---

## 15. Erros Comuns e Anti-Padroes

1. **Compilar sem `-g` e depois culpar o depurador**.
2. **Usar so `printf` para bugs complexos de memoria**.
3. **Rodar com otimizacao alta logo no inicio da investigacao**.
4. **Ignorar warnings e partir direto para o `gdb`**.
5. **Confiar em uma unica ferramenta para toda classe de bug**.
6. **Corrigir sem reproduzir e sem explicar a causa raiz**.

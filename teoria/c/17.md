# Aula 17 - Performance tuning, cache, profiling e otimizacao real

---

## Objetivo da Aula

Entender como medir e melhorar desempenho em C sem cair em micro-otimizacao cega, conectando cache, localidade, branch prediction, profiler, layout de dados e custo real de CPU e memoria. Ao final, voce deve conseguir montar um fluxo tecnico de otimizacao baseado em medicao, e nao em supersticao.

Essa aula e sobre custo fisico real.

## 2. Regra zero da performance

Antes de otimizar:

- meca.

Sem medicao, voce nao sabe se o gargalo esta em:

- CPU;
- cache;
- branch;
- alocacao;
- I/O;
- lock;
- syscall;
- algoritmo.

### 2.1 Regra ainda mais importante

Melhor algoritmo ruim medido do que "truque esperto" sem prova.

## 3. Cache e localidade

- **Cache**: memorias menores e mais rapidas entre CPU e RAM principal.

### 3.1 Por que isso domina tanto?

Porque CPU moderna e muito mais rapida do que acesso aleatorio a memoria principal.

### 3.2 Tipos de localidade

- localidade espacial: dados proximos tendem a ser acessados juntos
- localidade temporal: dados acessados recentemente tendem a ser acessados de novo

### 3.3 Consequencia pratica

Array contiguo costuma ser muito melhor para iteracao do que estrutura espalhada no heap.

---

## 4. Layout de dados importa

Ja vimos padding e alinhamento.

Agora o ponto de performance e:

- ordem de campos;
- tamanho do objeto;
- contiguidade;
- arrays de structs vs structs de arrays;
- falso compartilhamento em concorrencia.

### 4.1 Exemplo conceitual

Dois layouts podem ter mesma informacao logica e desempenho bem diferente.

---

## 5. Branch prediction

- **Branch prediction**: mecanismo do processador que tenta adivinhar qual caminho de desvio sera seguido.

### 5.1 Por que importa?

Desvios imprevisiveis podem custar caro.

### 5.2 Regra pratica

Codigo com fluxo simples, dados mais previsiveis e loops limpos geralmente ajuda mais do que "otimizacao exotica".

---

## 6. Profiling

- **Profiling**: medicao de onde o tempo ou outros recursos estao sendo gastos.

Ferramentas comuns em Unix-like:

- `perf`
- `gprof`
- `callgrind`
- `valgrind --tool=callgrind`

### 6.1 O que voce quer descobrir?

- quais funcoes consomem mais tempo;
- onde ha hot path;
- se o gargalo e CPU ou outra coisa;
- se a intuicao bate com a medicao.

---

## 7. Otimizacao do compilador

Flags comuns:

- `-O0`
- `-O2`
- `-O3`

### 7.1 Regra pratica

- `-O0`: aprendizado e debug
- `-O2`: baseline serio de producao em muitos casos
- `-O3`: pode ajudar, mas nem sempre e melhor

### 7.2 Por que `-O3` nem sempre vence?

Porque mais agressividade pode:

- aumentar tamanho de codigo;
- piorar cache de instrucoes;
- gerar trade-offs que nao ajudam seu caso real.

---

## 8. Exemplo simples de localidade

```c
double soma_array(const double *v, size_t n) {
    double s = 0.0;
    for (size_t i = 0; i < n; i++) {
        s += v[i];
    }
    return s;
}
```

Isso tende a ser amigavel a cache porque:

- acesso linear;
- pouca indirecao;
- padrao previsivel.

Agora compare conceitualmente com lista ligada:

- mais ponteiros;
- mais misses;
- menos previsibilidade.

---

## 9. Exemplo completo da aula

```c
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

double soma_array(const double *v, size_t n) {
    double s = 0.0;
    for (size_t i = 0; i < n; i++) {
        s += v[i];
    }
    return s;
}

int main(void) {
    size_t n = 1000000;
    double *v = malloc(n * sizeof(*v));
    if (v == NULL) {
        fprintf(stderr, "falha em malloc\n");
        return 1;
    }

    for (size_t i = 0; i < n; i++) {
        v[i] = (double)i * 0.5;
    }

    clock_t inicio = clock();
    double s = soma_array(v, n);
    clock_t fim = clock();

    double segundos = (double)(fim - inicio) / (double)CLOCKS_PER_SEC;
    printf("soma = %.2f\n", s);
    printf("tempo = %.6f s\n", segundos);

    free(v);
    return 0;
}
```

### 9.1 O que esse exemplo ensina?

- acesso linear;
- custo de iteracao pura;
- medicao simples de CPU;
- relacao entre tamanho de dados e tempo.

### 9.2 O que ele nao te ensina sozinho?

- nao substitui profiler real;
- nao mede latencia de cache diretamente;
- nao explica sozinho gargalos complexos.

## 10. `clock()` nao e profiler

`clock()` serve como medicao simples inicial.

Mas para investigacao seria, voce quer ferramentas que mostrem:

- funcao quente;
- call graph;
- amostragem de CPU;
- hotspots reais.

### 10.1 Exemplo com `gprof`

Compilar:

```bash
gcc -Wall -Wextra -Wpedantic -O2 -pg aula17.c -o aula17
```

Rodar:

```bash
./aula17
gprof ./aula17 gmon.out
```

### 10.2 Exemplo com `perf`

Em Linux:

```bash
gcc -Wall -Wextra -Wpedantic -O2 -g aula17.c -o aula17
perf record ./aula17
perf report
```

## 11. Falso compartilhamento

- **False sharing**: quando threads diferentes escrevem em variaveis distintas que caem na mesma cache line, causando invalidacoes desnecessarias.

### 11.1 Por que isso importa?

Porque voce pode ter:

- pouca contencao logica;
- muito custo fisico.

Esse e o tipo de problema que so aparece quando voce pensa em hardware real.

---

## 12. O que acontece em memoria?

Conceitualmente:

- o array `v` vive contiguamente no heap;
- CPU carrega cache lines contendo varios elementos de uma vez;
- acesso linear aproveita melhor prefetch e localidade;
- ponteiros dispersos no heap tendem a custar mais misses.

Isso conecta diretamente:

- estrutura de dados;
- padrao de acesso;
- desempenho observado.

---

## 13. Comandos exatos

Baseline de debug:

```bash
gcc -Wall -Wextra -Wpedantic -O0 -g aula17.c -o aula17
```

Baseline otimizada:

```bash
gcc -Wall -Wextra -Wpedantic -O2 aula17.c -o aula17
```

Versao mais agressiva:

```bash
gcc -Wall -Wextra -Wpedantic -O3 aula17.c -o aula17
```

### 13.1 Regra pratica

Compare sempre:

- corretude;
- tempo;
- tamanho do binario;
- clareza do codigo.

---

## 14. Comparacao com C++, Rust, Go e Python

- Em C++, o terreno de performance e muito parecido, porque o custo fisico do hardware e o mesmo.
- Em Rust, varias decisoes de layout e iteracao continuam igualmente importantes, mesmo com mais seguranca.
- Em Go, o runtime adiciona outras camadas de custo, mas cache, localidade e alocacao continuam centrais.
- Em Python, a maior parte do custo bruto some atras do runtime, mas ainda existe nas camadas nativas e extensoes.

Em C, performance fica muito nua:

- o que voce desenha, o hardware sente.

---

## 15. Erros Comuns e Anti-Padroes

1. **Otimizar sem medir**.
2. **Achar que `-O3` resolve arquitetura ruim**.
3. **Ignorar localidade de cache**.
4. **Trocar clareza por truque minimo sem ganho comprovado**.
5. **Olhar so tempo total e ignorar hotspot real**.
6. **Confundir benchmark de brinquedo com carga real de producao**.

# Aula 19 - Boas praticas para bibliotecas, CLIs, backend e sistemas de producao em C

---

## Objetivo da Aula

Fechar a trilha principal de C consolidando criterios de engenharia para escrever bibliotecas, CLIs, servicos e sistemas operacionais de forma mais previsivel. Ao final, voce deve conseguir montar um modelo mental de producao em C, ligando API, ownership, erros, build, observabilidade, testes e limites operacionais a software nativo real.

## 2. O que "codigo de producao" significa em C?

Nao significa apenas:

- compilar;
- rodar;
- passar num exemplo pequeno.

Significa tambem:

- falhar de forma previsivel;
- ter ownership claro;
- expor API estavel;
- ser depuravel;
- ser testavel;
- ser observavel o suficiente;
- nao depender de sorte contra UB.

---

## 3. Boas praticas para bibliotecas C

### 3.1 API pequena e chata e uma virtude

Em biblioteca C, prefira:

- poucas funcoes;
- nomes consistentes;
- ownership explicito;
- tipos opacos quando possivel;
- erros com contrato simples;
- documentacao precisa.

### 3.2 Evite expor demais

Nem todo detalhe interno precisa estar no header publico.

Se o consumidor nao precisa conhecer o layout:

- esconda.

Isso reduz acoplamento e protege evolucao.

---

## 4. Contrato de ownership

Perguntas obrigatorias em qualquer API:

- quem cria?
- quem destroi?
- quem pode manter referencia?
- por quanto tempo?
- quem pode modificar?

### 4.1 Nomes ajudam

Padrao saudavel:

- `foo_create`
- `foo_destroy`
- `foo_init`
- `foo_deinit`

Nomes claros reduzem ambiguidade.

---

## 5. Tratamento de erro

C normalmente nao usa excecoes.

Por isso, voce precisa desenhar erro de forma explicita.

Estrategias comuns:

- retorno `0/1`;
- retorno negativo para erro;
- `enum` com codigos;
- parametro de saida para valor;
- `errno` em APIs de baixo nivel;
- mensagem auxiliar quando necessario.

### 5.1 Regra pratica

Nao esconda falha.

API boa em C faz o chamador perceber que algo pode dar errado.

---

## 6. CLIs em C

Boas praticas para utilitarios de linha de comando:

- `exit code` previsivel;
- mensagens de erro em `stderr`;
- ajuda minima de uso;
- parsing de argumentos claro;
- contrato simples para automacao.

### 6.1 O que importa para shell?

- `0` significa sucesso;
- nao `0` significa falha;
- texto humano e maquina precisam coexistir com criterio.

---

## 7. Backend e servicos em C

Se voce for usar C para backend ou infraestrutura, pense em:

- timeouts;
- limites de buffer;
- protocolo bem definido;
- logs uteis;
- controle de concorrencia;
- tratamento robusto de erro;
- shutdown e limpeza de recursos.

### 7.1 O que C nao te da de brinde?

- runtime gerenciado;
- exceptions;
- garbage collector;
- abstracoes de servidor de alto nivel.

Entao disciplina de engenharia precisa subir.

---

## 8. Observabilidade minima

Em C puro, observabilidade pode ser muito mais simples do que em stacks modernas, mas ainda precisa existir.

No minimo:

- logs de erro claros;
- contexto suficiente para diagnostico;
- codigos de retorno coerentes;
- pontos de medicao de latencia ou throughput quando fizer sentido.

### 8.1 O perigo

Sem observabilidade, crash e corrupcao viram misterio.

---

## 9. Testes

Mesmo sem framework sofisticado, voce pode e deve testar:

- funcoes puras;
- estruturas de dados;
- parsing;
- limites;
- erros;
- ownership e limpeza.

### 9.1 Niveis uteis

- testes unitarios simples;
- testes de integracao pequenos;
- execucao com sanitizers;
- casos de borda.

### 9.2 Regra pratica

Em C, rodar testes com sanitizer vale muito mais do que "so passou no caso feliz".

---

## 10. Build saudavel

Checklist minimo de build:

- warnings altos;
- modo debug;
- modo otimizado;
- opcao com sanitizers;
- dependencias claras;
- reproducao simples.

Exemplos:

```bash
gcc -Wall -Wextra -Wpedantic -O0 -g app.c -o app
gcc -Wall -Wextra -Wpedantic -O2 app.c -o app
gcc -Wall -Wextra -Wpedantic -O0 -g -fsanitize=address -fsanitize=undefined app.c -o app
```

### 10.1 Por que isso importa?

Porque "compila na minha maquina" nao e processo de engenharia.

## 11. Exemplo completo da aula

API pequena de biblioteca e CLI consumindo a biblioteca:

`contador.h`

```c
#ifndef CONTADOR_H
#define CONTADOR_H

typedef struct Contador Contador;

Contador *contador_create(void);
void contador_destroy(Contador *c);
int contador_inc(Contador *c);
int contador_get(const Contador *c, int *out);

#endif
```

`contador.c`

```c
#include <stdlib.h>
#include "contador.h"

struct Contador {
    int valor;
};

Contador *contador_create(void) {
    Contador *c = malloc(sizeof(*c));
    if (c == NULL) {
        return NULL;
    }
    c->valor = 0;
    return c;
}

void contador_destroy(Contador *c) {
    free(c);
}

int contador_inc(Contador *c) {
    if (c == NULL) {
        return 0;
    }
    c->valor++;
    return 1;
}

int contador_get(const Contador *c, int *out) {
    if (c == NULL || out == NULL) {
        return 0;
    }
    *out = c->valor;
    return 1;
}
```

`main.c`

```c
#include <stdio.h>
#include "contador.h"

int main(void) {
    Contador *c = contador_create();
    if (c == NULL) {
        fprintf(stderr, "falha ao criar contador\n");
        return 1;
    }

    for (int i = 0; i < 3; i++) {
        if (!contador_inc(c)) {
            fprintf(stderr, "falha ao incrementar contador\n");
            contador_destroy(c);
            return 1;
        }
    }

    int valor;
    if (!contador_get(c, &valor)) {
        fprintf(stderr, "falha ao obter valor\n");
        contador_destroy(c);
        return 1;
    }

    printf("contador=%d\n", valor);
    contador_destroy(c);
    return 0;
}
```

### 11.1 O que esse exemplo resume da trilha?

- tipo opaco;
- ownership explicito;
- tratamento de erro simples;
- biblioteca separada da CLI;
- binario pequeno e previsivel;
- criterio de API.

---

## 12. O que acontece em memoria e na operacao?

Conceitualmente:

- `Contador *` vive como handle no lado chamador;
- o objeto real vive no heap;
- `create` e `destroy` controlam ciclo de vida;
- a CLI traduz sucesso e falha em `stdout`, `stderr` e `exit code`.

Esse e um padrao muito saudavel em C:

- recurso bem delimitado;
- fronteira clara;
- falha tratada cedo.

---

## 13. Checklist de maturidade para C em producao

- warnings fortes sempre;
- sanitizer em debug;
- ownership documentado;
- API pequena;
- erro explicitado;
- limites de buffer claros;
- limpeza de recurso em todos os caminhos;
- diagnostico minimo;
- benchmark e profiling quando performance importar;
- portabilidade pensada desde o inicio.

---

## 14. Comparacao com C++, Rust, Go e Python

- Em C++, varias dessas praticas continuam boas, mas RAII e containers tiram parte da carga manual.
- Em Rust, grande parte da disciplina vira contrato do compilador.
- Em Go, o runtime e a biblioteca padrao levantam o nivel de ergonomia para CLI e backend.
- Em Python, produtividade sobe, mas controle nativo cai.

Em C, a maturidade vem menos de "features da linguagem" e mais de:

- desenho;
- processo;
- criterio;
- repeticao disciplinada.

---

## 15. Erros Comuns e Anti-Padroes

1. **API que nao define ownership**.
2. **Biblioteca que expoe detalhes internos sem necessidade**.
3. **CLI sem `stderr` e sem `exit code` coerente**.
4. **Backend em C sem limites e sem tratamento duro de erro**.
5. **Build sem warnings e sem modo de debug com sanitizer**.
6. **Confiar em "parece funcionar" em vez de contrato e teste**.

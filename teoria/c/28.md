## 2. Cache line

- **Cache line**: unidade de transferencia entre niveis de cache e memoria principal, normalmente com algumas dezenas de bytes, sendo 64 bytes um valor muito comum em CPUs modernas.

### 2.1 Por que isso importa?

Porque a CPU raramente busca:

- um unico byte isolado.

Ela tende a buscar:

- uma linha inteira.

### 2.2 Consequencia pratica

Se voce acessa:

- um elemento de array;

o hardware frequentemente traz para cache:

- varios elementos vizinhos junto.

E aqui nasce a grande vantagem da contiguidade.

---

## 3. Localidade espacial revisitada em nivel fisico

Quando os dados estao proximos, uma unica cache line pode alimentar varios acessos consecutivos.

Exemplo:

```c
for (size_t i = 0; i < n; i++) {
    soma += v[i];
}
```

### 3.1 O que o hardware gosta aqui?

- acesso sequencial;
- stride pequeno e regular;
- proximo elemento previsivel;
- pouca indirecao.

### 3.2 O que o hardware nao gosta?

- ponteiros espalhados;
- saltos imprevisiveis;
- stride irregular;
- estruturas grandes com campos inutilizados no meio.

---

## 4. Arrays de structs vs structs de arrays

Esse e um ponto classico de performance.

### 4.1 Array de structs

```c
typedef struct {
    float x;
    float y;
    float z;
    float w;
} Point;

Point pts[n];
```

### 4.2 Struct de arrays

```c
typedef struct {
    float x[n];
    float y[n];
    float z[n];
    float w[n];
} Points;
```

### 4.3 Qual e melhor?

Depende do padrao de acesso.

Se voce sempre usa:

- `x`, `y`, `z`, `w` juntos;

array de structs pode fazer sentido.

Se voce processa:

- so `x`;

struct de arrays pode reduzir leitura inutil e melhorar vetorizacao.

### 4.4 Regra pratica

O melhor layout e o que melhor combina com:

- o hot path;
- os campos realmente usados juntos;
- a forma como a CPU puxa cache lines.

---

## 5. Prefetch

- **Prefetch**: mecanismo pelo qual o hardware tenta trazer dados para cache antes que a CPU precise deles explicitamente.

### 5.1 Quando ele funciona bem?

- acesso sequencial;
- stride regular;
- loops previsiveis;
- pouca indirecao.

### 5.2 Quando ele falha mais?

- lista ligada;
- grafo espalhado;
- acesso pseudo-aleatorio;
- saltos grandes e imprevisiveis.

### 5.3 O ponto central

Voce nao "liga o prefetch" por pensamento positivo.

Voce ajuda o prefetch quando desenha:

- dados contiguos;
- acessos previsiveis;
- loops simples.

---

## 6. Miss de cache

- **Cache miss**: quando o dado necessario nao esta no nivel de cache consultado e precisa ser buscado em nivel mais lento.

### 6.1 Por que isso doi tanto?

Porque a diferenca de custo entre:

- registrador;
- L1;
- L2;
- L3;
- RAM;

pode ser enorme.

### 6.2 Consequencia

Um algoritmo teoricamente bom pode perder para outro pior em teoria, mas melhor em:

- localidade;
- contiguidade;
- previsibilidade de acesso.

---

## 7. Branch prediction em profundidade

- **Branch prediction**: tentativa do processador de prever o resultado de um desvio antes que a condicao esteja totalmente resolvida.

### 7.1 Por que isso existe?

Porque pipelines modernas querem continuar trabalhando sem parar a cada `if`.

### 7.2 Quando o predictor acerta bastante?

- padroes repetitivos;
- dados previsiveis;
- condicoes fortemente tendenciosas;
- loops estaveis.

### 7.3 Quando ele erra mais?

- dados aleatorios;
- desvios muito misturados;
- fluxo irregular;
- hot path cheio de condicoes imprevisiveis.

### 7.4 O custo da falha

Quando o predictor erra, o pipeline pode precisar:

- descartar trabalho especulativo;
- recarregar caminho correto;
- perder ciclos.

---

## 8. Exemplo conceitual de branch previsivel vs imprevisivel

Caso mais previsivel:

```c
if (x >= 0) {
    positivos++;
}
```

quando a maioria dos valores segue padrao estavel.

Caso mais imprevisivel:

```c
if (valores[i] & 1) {
    a++;
} else {
    b++;
}
```

com dados pseudo-aleatorios.

### 8.1 Regra pratica

Nao tente "enganar" branch predictor com supersticao.

Primeiro entenda:

- o padrao dos dados;
- o fluxo real do programa;
- onde o desvio esta no hot path.

## 9. Exemplo completo da aula

```c
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

typedef struct {
    int value;
    char padding[60];
} PaddedInt;

static double elapsed(clock_t start, clock_t end) {
    return (double)(end - start) / (double)CLOCKS_PER_SEC;
}

int main(void) {
    const size_t n = 1000000;

    int *linear = malloc(n * sizeof(*linear));
    PaddedInt *padded = malloc(n * sizeof(*padded));
    if (linear == NULL || padded == NULL) {
        fprintf(stderr, "falha em malloc\n");
        free(linear);
        free(padded);
        return 1;
    }

    for (size_t i = 0; i < n; i++) {
        linear[i] = (int)i;
        padded[i].value = (int)i;
    }

    long long sum1 = 0;
    clock_t t1 = clock();
    for (size_t i = 0; i < n; i++) {
        sum1 += linear[i];
    }
    clock_t t2 = clock();

    long long sum2 = 0;
    clock_t t3 = clock();
    for (size_t i = 0; i < n; i++) {
        sum2 += padded[i].value;
    }
    clock_t t4 = clock();

    printf("linear sum=%lld tempo=%.6f s\n", sum1, elapsed(t1, t2));
    printf("padded sum=%lld tempo=%.6f s\n", sum2, elapsed(t3, t4));

    free(linear);
    free(padded);
    return 0;
}
```

### 9.1 O que esse exemplo mostra?

- dois dados logicamente semelhantes;
- layouts fisicamente muito diferentes;
- uma versao contigua e enxuta;
- outra versao com stride enorme e cache desperdicada.

### 9.2 O que esperar conceitualmente?

Em geral:

- `linear` tende a usar melhor cache e prefetch;
- `padded` tende a puxar mais memoria do que o dado util exige.

## 10. False sharing

- **False sharing**: situacao em que threads diferentes escrevem em variaveis distintas, mas que caem na mesma cache line, causando invalidacoes e trafego desnecessario de coerencia.

### 10.1 O erro conceitual

Logicamente, as variaveis sao separadas.

Fisicamente, a cache line e compartilhada.

### 10.2 Consequencia

Mesmo sem lock logico forte, o custo pode explodir porque:

- uma thread invalida a linha da outra;
- a linha fica "ping-pongando" entre nucleos.

---

## 11. Exemplo conceitual de false sharing

```c
typedef struct {
    long long a;
    long long b;
} Counters;
```

Se:

- thread 1 incrementa `a`;
- thread 2 incrementa `b`;

essas variaveis podem cair na mesma linha.

### 11.1 Possivel mitigacao

Separar com padding ou layout mais cuidadoso:

```c
typedef struct {
    long long a;
    char pad1[56];
    long long b;
    char pad2[56];
} CountersSeparated;
```

### 11.2 Cuidado importante

Isso e apenas modelo didatico.

O valor exato depende de:

- cache line da arquitetura;
- alinhamento;
- compilador;
- layout final real.

---

## 12. Estruturas pequenas demais ou grandes demais

Existe um equilibrio.

### 12.1 Estrutura pequena e boa quando

- campos usados juntos cabem bem em poucas linhas;
- acesso e denso;
- pouca leitura inutil ocorre.

### 12.2 Estrutura ruim quando

- muitos campos raramente usados ficam juntos;
- cada acesso puxa bytes desnecessarios;
- stride fica grande e localidade piora.

### 12.3 Regra pratica

Layout ideal depende de:

- quais campos o hot path toca;
- em que ordem;
- com que frequencia;
- em qual contexto de thread.

---

## 13. Concorrencia e cache line

Quando voce pensa em threads, nao pense apenas em:

- lock;
- race;
- atomic.

Pense tambem em:

- topologia fisica dos dados;
- escrita frequente em campos vizinhos;
- counters por thread;
- agregacao posterior.

### 13.1 Estrategia comum

Em vez de varios threads atualizarem um contador compartilhado central, use:

- contador por thread;
- consolidacao posterior.

Isso reduz:

- contencao logica;
- false sharing;
- trafego de coerencia.

---

## 14. O que o profiler nao te conta sozinho

Um profiler pode mostrar:

- funcao quente.

Mas sozinho talvez nao mostre claramente:

- se o problema e cache miss;
- se o layout esta ruim;
- se ha false sharing;
- se a branch prediction esta sofrendo.

### 14.1 Por isso esta aula existe

Voce precisa juntar:

- medicao;
- modelo mental de hardware;
- leitura de layout e acesso.

---

## 15. Sintomas de problema de microarquitetura

Sinais comuns:

- throughput pior do que o algoritmo sugeria;
- pequena mudanca de layout muda muito o desempenho;
- lista ligada perde feio para array;
- multithreading nao escala como esperado;
- hot path parece simples, mas o tempo continua alto;
- counters compartilhados pioram com mais threads.

---

## 16. O que acontece em memoria e hardware?

Conceitualmente:

- CPU busca cache lines, nao apenas o campo logico que voce imaginou;
- prefetch tenta adiantar linhas futuras quando o padrao ajuda;
- branch predictor tenta adivinhar o fluxo;
- protocolo de coerencia entre nucleos reage a escritas concorrentes;
- false sharing aparece quando layout e concorrencia se chocam.

Esse e o ponto central da aula:

- o hardware enxerga linhas, padroes e coerencia;
- nao "conceitos bonitos" da sua struct.

## 18. Comparacao com C++, Rust, Go e Python

- Em C++, os mesmos principios fisicos valem integralmente; a diferenca e que templates e containers podem facilitar ou esconder certas decisoes de layout.
- Em Rust, a seguranca de tipos ajuda muito, mas cache line, localidade e false sharing continuam sendo problemas fisicos identicos.
- Em Go, o runtime muda parte do jogo, mas estruturas de dados, cache e contencao de hardware continuam existindo.
- Em Python, a maior parte dessas decisoes fica enterrada no runtime e no C subjacente, mas extensoes nativas e hot loops ainda sofrem exatamente do mesmo mundo fisico.

Em C, tudo isso fica muito visivel:

- layout ruim cobra caro;
- layout bom ajuda o hardware a trabalhar a seu favor.

## 19. Erros Comuns e Anti-Padroes

1. **Achar que algoritmo bom basta sem olhar localidade**.
2. **Ignorar stride e tamanho real da struct**.
3. **Assumir que threads independentes logicamente nao compartilham custo fisico**.
4. **Introduzir padding sem medir se o problema real era false sharing**.
5. **Otimizar branch manualmente sem entender o padrao dos dados**.
6. **Usar listas e ponteiros espalhados onde array contiguo resolveria melhor**.

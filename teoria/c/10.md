# Aula 10 - Undefined behavior, aliasing, alignment, padding e armadilhas classicas

---

## Objetivo da Aula

Entender por que C permite programas extremamente rapidos, mas ao mesmo tempo perigosos, estudando undefined behavior, aliasing, alignment, padding e erros classicos de acesso invalido ou interpretacao incorreta de memoria. Ao final, voce deve conseguir reconhecer fronteiras em que o compilador deixa de te proteger e onde disciplina tecnica passa a ser obrigatoria.

---

## 1. Esta aula muda sua relacao com C

Se nas aulas anteriores voce viu o poder da linguagem, agora precisa ver o custo.

O ponto central e:

- C te da liberdade;
- o compilador assume que voce respeita o contrato;
- se voce quebra esse contrato, o resultado pode ser qualquer coisa.

---

## 2. O que e undefined behavior?

- **Undefined behavior (UB)**: situacao em que o padrao da linguagem nao define o comportamento do programa.

Isso nao significa apenas:

- "dara erro bonitinho"

Pode significar:

- parecer funcionar;
- funcionar hoje e falhar amanha;
- falhar so com otimizacao;
- produzir resultado absurdo;
- abrir brecha de seguranca.

---

## 3. Exemplos classicos de UB

### 3.1 Acesso fora dos limites

```c
int v[3] = {1, 2, 3};
printf("%d\n", v[10]);
```

### 3.2 Uso de ponteiro invalido

```c
int *p = NULL;
*p = 10;
```

### 3.3 Use-after-free

```c
int *p = malloc(sizeof(int));
free(p);
printf("%d\n", *p);
```

### 3.4 Variavel nao inicializada

```c
int x;
printf("%d\n", x);
```

---

## 4. Por que o compilador trata isso com tanta liberdade?

Porque o padrao de C prioriza:

- desempenho;
- portabilidade da implementacao;
- baixa imposicao sobre compiladores e hardware.

Se o programa entra em UB, o compilador pode assumir:

- "isso nao deveria acontecer"

e otimizar em cima dessa premissa.

---

## 5. Alignment

- **Alignment**: restricao ou preferencia de que certos tipos sejam armazenados em enderecos multiplos de determinado valor.

Exemplo conceitual:

- `int` frequentemente prefere alinhamento de 4 bytes;
- `double` frequentemente prefere alinhamento de 8 bytes.

### 5.1 O que acontece se voce quebrar isso?

Depende da arquitetura:

- pode funcionar com custo maior;
- pode gerar excecao;
- pode produzir comportamento incorreto.

---

## 6. Padding

Ja vimos padding em `struct`.

Agora o ponto importante e:

- padding faz parte do layout fisico;
- nao faz parte do "valor logico" dos campos;
- nao deve ser presumido como dado significativo.

### 6.1 Consequencia

Comparar `struct` inteira com `memcmp` nem sempre e semanticamente correto.

---

## 7. Aliasing

- **Aliasing**: situacao em que dois ponteiros ou referencias acessam a mesma regiao de memoria.

Isso por si so nao e erro.

Mas em C existem regras sutis sobre como tipos diferentes podem aliasar a mesma memoria.

### 7.1 Strict aliasing

O compilador pode assumir que certos ponteiros de tipos diferentes:

- nao apontam para o mesmo objeto

e otimizar com base nisso.

Se voce viola essas regras sem criterio, pode ter bugs muito dificeis.

---

## 8. Exemplo conceitual perigoso

```c
float f = 1.0f;
int *pi = (int *)&f;
printf("%d\n", *pi);
```

Mesmo quando parece "so reinterpretar bytes", isso pode entrar em terreno perigoso do ponto de vista das regras da linguagem.

### 8.1 Regra pratica

Para reinterpretacao bruta de bytes, use tecnicas mais seguras e bem justificadas, como:

- copia por `memcpy`;
- `union` apenas quando houver criterio e entendimento das implicacoes;
- APIs especificas da plataforma quando necessario.

---

## 9. Conversoes perigosas de ponteiro

Exemplo:

```c
char buffer[4];
int *p = (int *)buffer;
```

Problemas possiveis:

- alinhamento inadequado;
- aliasing indevido;
- leitura de bytes sem inicializacao valida do objeto alvo.

Isso mostra como "compilar" nao significa "estar correto".

---

## 10. Overflow inteiro

Outro tema importante:

- overflow de inteiro com sinal pode entrar em UB.

Exemplo:

```c
int x = 2147483647;
x = x + 1;
```

### 10.1 Por que isso importa?

Porque muita gente assume comportamento de complemento de dois como se o padrao garantisse tudo.

O compilador pode otimizar com hipoteses mais fortes.

---

## 11. Exemplo completo da aula

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

struct Exemplo {
    char c;
    int x;
};

int main(void) {
    struct Exemplo e = {'A', 123};

    printf("sizeof(struct Exemplo) = %zu\n", sizeof(struct Exemplo));
    printf("campo c = %c\n", e.c);
    printf("campo x = %d\n", e.x);

    unsigned char bytes[sizeof(struct Exemplo)];
    memcpy(bytes, &e, sizeof(e));

    for (size_t i = 0; i < sizeof(e); i++) {
        printf("byte[%zu] = 0x%02x\n", i, bytes[i]);
    }

    int *p = malloc(sizeof(int));
    if (p == NULL) {
        fprintf(stderr, "falha em malloc\n");
        return 1;
    }

    *p = 42;
    printf("*p = %d\n", *p);
    free(p);
    p = NULL;

    return 0;
}
```

### 11.1 Por que este exemplo e "seguro o suficiente" didaticamente?

Porque:

- evita ler alem dos limites;
- evita aliasing indevido com cast arbitrario;
- usa `memcpy` para observar bytes;
- libera heap corretamente.

---

## 12. O que acontece em memoria?

Para:

```c
struct Exemplo {
    char c;
    int x;
};
```

pode haver layout como:

```text
[c][padding][padding][padding][x x x x]
```

Os bytes copiados por `memcpy` incluem:

- bytes do campo `c`;
- possivel padding;
- bytes de `x`.

Isso reforca:

- layout fisico nao e so "campos um atras do outro sem criterio".

---

## 13. Como se proteger na pratica

Ferramentas e habitos:

- compile com warnings fortes;
- use sanitizers;
- evite cast de ponteiro sem necessidade real;
- respeite limites de arrays;
- inicialize memoria antes de ler;
- prefira clareza a "truque esperto";
- se mexer com bytes crus, documente a intencao.

### 13.1 Comandos uteis

```bash
gcc -Wall -Wextra -Wpedantic -O0 -g -fsanitize=address -fsanitize=undefined aula10.c -o aula10
```

---

## 14. Comparacao com C++, Rust, Go e Python

- Em C++, varios desses riscos ainda existem, embora RAII e tipos mais ricos ajudem em outras frentes.
- Em Rust, grande parte desse terreno perigoso e empurrada para `unsafe`.
- Em Go, o runtime e o sistema de tipos evitam quase todos esses problemas de memoria crua no uso comum.
- Em Python, esse nivel praticamente desaparece do codigo de aplicacao.

Em C, tudo isso esta perto de voce o tempo todo.

---

## 15. Erros Comuns e Anti-Padroes

1. **Achar que UB significa sempre crash imediato**.
2. **Confiar em comportamento observado uma vez como se fosse garantia**.
3. **Fazer cast de ponteiro para "reinterpretar" tudo sem criterio**.
4. **Ignorar alinhamento e padding ao serializar ou comparar memoria**.
5. **Assumir que otimizacao nao muda nada semanticamente em codigo errado**.
6. **Ler memoria nao inicializada "so para teste"**.

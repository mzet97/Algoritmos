# Aula 16 - Syscalls, `mmap`, arquivos grandes e I/O de baixo nivel

Por baixo de cada `fopen` existe uma syscall pedindo serviço ao kernel. `mmap`, arquivos grandes e I/O de baixo nível mostram o sistema operacional sem a maquiagem da biblioteca — onde desempenho e controle de verdade moram.

---

## Nesta aula

Você vai aprender a copiar um arquivo com `read`/`write` tratando retorno parcial; explicar por que `read` pode devolver menos que o pedido sem ser erro; e justificar quando `mmap` substitui I/O por acesso a memoria (e quando nao substitui).

## 2. `stdio` vs I/O de baixo nivel

Ja vimos `FILE *` em `stdio`.

Agora precisamos diferenciar:

- **`stdio`**: camada de biblioteca padrao com buffering e API mais amigavel.
- **I/O de baixo nivel**: chamadas mais proximas do SO, tipicamente baseadas em descritor e syscalls.

### 2.1 Quando `stdio` basta?

- leitura textual comum;
- arquivos pequenos ou medios;
- portabilidade e simplicidade;
- formatacao com `fprintf`, `fgets`, `fread`.

### 2.2 Quando descer de nivel?

- controle fino de descritor;
- integracao com `poll`, `select`, `epoll`;
- arquivos grandes;
- mapeamento de memoria;
- custo de copia e throughput importando mais.

---

## 3. Descritor de arquivo

- **File descriptor**: inteiro pequeno que referencia um recurso aberto no kernel.

Exemplos:

- arquivo;
- pipe;
- socket;
- terminal.

### 3.1 Modelo mental

O inteiro em si nao e o arquivo.

Ele e um handle que indexa estado mantido pelo kernel.

---

## 4. `open`, `read`, `write`, `close`

Headers classicos:

```c
#include <fcntl.h>
#include <unistd.h>
```

Exemplo:

```c
int fd = open("dados.txt", O_RDONLY);
ssize_t n = read(fd, buffer, sizeof(buffer));
close(fd);
```

### 4.1 Por que `ssize_t`?

Porque leitura e escrita:

- retornam quantidade transferida;
- podem retornar erro com valor negativo.

---

## 5. Leitura parcial

Regra crucial:

- `read` pode ler menos bytes do que voce pediu.

Isso nao implica erro necessariamente.

### 5.1 Consequencia pratica

Em I/O robusto, voce frequentemente precisa:

- loop de leitura;
- acumular bytes;
- detectar EOF;
- tratar `EINTR` e outros erros.

---

## 6. `lseek`

Exemplo:

```c
off_t pos = lseek(fd, 0, SEEK_END);
```

### 6.1 Para que serve?

- mover offset atual;
- medir tamanho em varios casos;
- reposicionar leitura e escrita.

### 6.2 Cuidado

Nem todo descritor aceita seek.

Sockets e pipes, por exemplo, nao seguem esse modelo.

---

## 7. `mmap`

- **`mmap`**: mecanismo que mapeia um arquivo ou outra regiao no espaco de enderecamento do processo.

Exemplo conceitual:

```c
void *p = mmap(NULL, tamanho, PROT_READ, MAP_PRIVATE, fd, 0);
```

### 7.1 O que isso muda?

Em vez de chamar `read` para copiar bytes explicitamente para um buffer seu, voce passa a enxergar o conteudo mapeado como memoria do processo.

### 7.2 Isso elimina toda copia sempre?

Nao trate `mmap` como slogan.

Ele muda o modelo, mas ainda ha:

- page faults;
- page cache;
- interacao com o kernel;
- custo de TLB e mapeamento;
- dependencia forte de padrao de acesso.

---

## 8. `mmap` e page cache

- **Page cache**: cache de paginas de arquivo mantido pelo kernel para acelerar I/O.

### 8.1 Por que isso importa?

Porque benchmark de leitura de arquivo pode estar medindo:

- RAM;
- cache do kernel;
- e nao disco real.

### 8.2 Regra pratica

Nao conclua sobre desempenho de arquivo grande sem entender:

- se os dados vieram de disco ou cache;
- padrao de acesso;
- custo de faltas de pagina.

---

## 9. Exemplo com `read`

```c
#include <fcntl.h>
#include <stdio.h>
#include <unistd.h>

int main(void) {
    int fd = open("entrada.txt", O_RDONLY);
    if (fd < 0) {
        perror("open");
        return 1;
    }

    char buffer[128];
    ssize_t n;
    while ((n = read(fd, buffer, sizeof(buffer))) > 0) {
        ssize_t written = write(STDOUT_FILENO, buffer, (size_t)n);
        if (written < 0) {
            perror("write");
            close(fd);
            return 1;
        }
    }

    if (n < 0) {
        perror("read");
    }

    close(fd);
    return (n < 0) ? 1 : 0;
}
```

### 9.1 O que esse exemplo ensina?

- descritor inteiro em vez de `FILE *`;
- leitura em bloco;
- escrita bruta em `STDOUT_FILENO`;
- controle mais direto do fluxo.

---

## 10. Exemplo conceitual com `mmap`

```c
#include <fcntl.h>
#include <stdio.h>
#include <sys/mman.h>
#include <sys/stat.h>
#include <unistd.h>

int main(void) {
    int fd = open("entrada.txt", O_RDONLY);
    if (fd < 0) {
        perror("open");
        return 1;
    }

    struct stat st;
    if (fstat(fd, &st) < 0) {
        perror("fstat");
        close(fd);
        return 1;
    }

    void *map = mmap(NULL, (size_t)st.st_size, PROT_READ, MAP_PRIVATE, fd, 0);
    if (map == MAP_FAILED) {
        perror("mmap");
        close(fd);
        return 1;
    }

    write(STDOUT_FILENO, map, (size_t)st.st_size);

    munmap(map, (size_t)st.st_size);
    close(fd);
    return 0;
}
```

### 10.1 O que esse exemplo nao te autoriza a concluir?

Nao conclua automaticamente que:

- sempre e mais rapido;
- sempre e mais simples;
- sempre e melhor para qualquer arquivo.

---

## 11. O que acontece em memoria?

Com `read`:

- kernel copia bytes para buffer do processo;
- buffer local vive no seu espaco de usuario.

Com `mmap`:

- paginas do arquivo ficam associadas ao espaco de enderecamento do processo;
- acessos podem disparar faltas de pagina;
- o kernel coordena materializacao e page cache.

O ponto central:

- `mmap` troca parte do modelo de copia explicita por modelo de mapeamento.

## 13. Comparacao com C++, Rust, Go e Python

- Em C++, wrappers podem melhorar ergonomia, mas os conceitos de `open`, `read` e `mmap` continuam os mesmos.
- Em Rust, crates e tipos ajudam muito a reduzir erro de fronteira, embora a ideia fisica do sistema continue igual.
- Em Go, `os.File`, `io.Reader` e bibliotecas de mapeamento escondem parte da dureza da API.
- Em Python, o uso fica muito mais simples, mas custo fisico de copia, cache e pagina continua existindo no sistema.

Em C, a API te obriga a encarar a fronteira com o kernel diretamente.

---

## 14. Erros Comuns e Anti-Padroes

1. **Assumir que `read` sempre entrega tudo o que foi pedido**.
2. **Usar `mmap` sem entender page cache e padrao de acesso**.
3. **Esquecer `munmap`**.
4. **Misturar `FILE *` e descritor cru sem criterio**.
5. **Benchmark de arquivo sem controlar cache e concluir demais**.
6. **Fazer `lseek` em recurso que nao suporta seek**.

# Aula 22 - IPC, pipes, Unix domain sockets e memoria compartilhada

Processos que precisam cooperar sem rede usam pipes, sockets Unix e memória compartilhada. IPC é a conversa local entre processos — rápida, perigosa e cheia de condições de corrida esperando quem não desenha o protocolo.

---

## Nesta aula

Você vai aprender a trocar bytes entre dois processos por pipe e por Unix socket; medir a diferenca de copia entre os dois; e explicar quando memoria compartilhada paga o risco (e quando nao paga).


---

## 1. Ponte com a aula anterior

Na aula 21, comparamos arquiteturas de servidor:

- `thread-per-connection`;
- event-driven;
- modelo hibrido.

Ali o foco era concorrencia entre conexoes e descritores de rede.

Agora vamos para outro problema recorrente em sistemas reais:

- como dois processos na mesma maquina trocam dados de forma eficiente e previsivel?

Essa e a area de IPC.

---

## 2. O que e IPC?

- **IPC**: inter-process communication, ou comunicacao entre processos.

Isso existe porque processos:

- sao isolados pelo sistema operacional;
- possuem espacos de enderecamento separados;
- nao compartilham memoria automaticamente.

Entao, se um processo precisa conversar com outro, o SO precisa oferecer mecanismos para isso.

### 2.1 Casos tipicos

- processo pai conversa com filho;
- worker local recebe tarefas;
- daemon expoe interface local para outros processos;
- componentes separados trocam mensagens sem abrir rede externa;
- dois processos compartilham alto volume de dados na mesma maquina.

---

## 3. Criterio de escolha

Antes de estudar cada mecanismo, precisamos de um criterio.

Perguntas praticas:

- a comunicacao e unidirecional ou bidirecional?
- precisamos de fluxo de bytes ou mensagens?
- o volume de dados e pequeno, medio ou muito alto?
- queremos simplicidade ou throughput maximo?
- precisamos de isolamento forte?
- precisamos de varias conexoes simultaneas?
- precisamos evitar copias sempre que possivel?

Essas perguntas guiam a escolha entre:

- `pipe`;
- Unix domain socket;
- memoria compartilhada.

---

## 4. Pipes

- **Pipe**: canal de comunicacao unidirecional fornecido pelo kernel, representado por dois descritores, um para leitura e outro para escrita.

Exemplo conceitual:

```c
int fd[2];
pipe(fd);
```

Depois disso:

- `fd[0]` costuma ser leitura;
- `fd[1]` costuma ser escrita.

### 4.1 Modelo mental

Um pipe e como um cano:

- um lado escreve bytes;
- o outro lado le bytes na ordem.

### 4.2 Onde ele brilha?

- comunicacao simples entre pai e filho;
- pipelines estilo shell;
- fluxo linear de bytes;
- cenarios pequenos e previsiveis.

### 4.3 Limites

- tipicamente unidirecional;
- nao e um mecanismo naturalmente bom para topologias mais ricas;
- nao representa mensagem por si so, apenas fluxo de bytes;
- ainda envolve copia entre user space e kernel.

---

## 5. Exemplo simples com `pipe` e `fork`

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    int fd[2];
    if (pipe(fd) < 0) {
        perror("pipe");
        return 1;
    }

    pid_t pid = fork();
    if (pid < 0) {
        perror("fork");
        return 1;
    }

    if (pid == 0) {
        close(fd[1]);

        char buffer[64];
        ssize_t n = read(fd[0], buffer, sizeof(buffer) - 1);
        if (n > 0) {
            buffer[n] = '\0';
            printf("filho recebeu: %s\n", buffer);
        }

        close(fd[0]);
        return 0;
    }

    close(fd[0]);
    write(fd[1], "ola do pai", 10);
    close(fd[1]);
    wait(NULL);
    return 0;
}
```

### 5.1 O que esse exemplo mostra?

- o pipe e criado antes do `fork`;
- pai e filho herdam os descritores;
- um lado escreve e o outro le;
- fechar pontas nao usadas importa para o fluxo funcionar corretamente.

---

## 6. `pipe` nao e protocolo

Esse ponto lembra a aula 20.

Pipe tambem e fluxo de bytes.

Logo:

- uma escrita nao significa "mensagem semantica";
- uma leitura pode vir parcial;
- o leitor precisa saber como interpretar fronteiras.

### 6.1 Consequencia

Se voce precisa de mensagens, talvez precise:

- delimitadores;
- tamanho no cabecalho;
- framing explicito.

---

## 7. Unix domain sockets

- **Unix domain socket**: socket local da maquina, usado para comunicacao entre processos sem passar pela rede IP tradicional.

Eles podem ser:

- `SOCK_STREAM`, parecidos com TCP local;
- `SOCK_DGRAM`, orientados a datagrama local.

### 7.1 Por que eles existem?

Porque muitas vezes queremos:

- semantica de socket;
- bidirecionalidade;
- modelo cliente-servidor;
- enderecamento local;
- menor custo e menor complexidade do que sair para a pilha de rede externa.

### 7.2 Onde brilham?

- daemon local;
- proxy local;
- banco ou agente local;
- interface administrativa entre processos;
- comunicacao entre componentes do mesmo host.

---

## 8. Exemplo conceitual de Unix domain socket

```c
int server_fd = socket(AF_UNIX, SOCK_STREAM, 0);
```

Depois:

- definir `sockaddr_un`;
- fazer `bind` em um caminho local;
- `listen`;
- `accept`;
- ler e escrever como em socket de rede.

### 8.1 O que isso compra?

- API familiar se voce ja estudou sockets TCP;
- conexao bidirecional;
- possibilidade de varios clientes;
- arquitetura local mais natural que `pipe` para servidor.

### 8.2 O que ainda continua valendo?

- leitura parcial;
- escrita parcial;
- protocolo de aplicacao;
- controle de erro;
- fechamento correto de descritores.

---

## 9. `pipe` vs Unix domain socket

### 9.1 `pipe`

Bom para:

- pai e filho;
- fluxo simples;
- pouca infraestrutura;
- unidirecionalidade previsivel.

### 9.2 Unix domain socket

Bom para:

- cliente-servidor local;
- bidirecionalidade;
- varios clientes;
- reaproveitar modelo de sockets.

### 9.3 Resumo honesto

Se o problema ja parece "um servico local", Unix domain socket costuma encaixar melhor.

Se o problema e apenas "empurrar bytes simples entre processos relacionados", pipe pode bastar.

---

## 10. Memoria compartilhada

- **Memoria compartilhada**: regiao de memoria visivel para mais de um processo, permitindo troca de dados sem copiar payload inteiro a cada operacao de IPC tradicional.

### 10.1 Por que isso e poderosa?

Porque reduz um custo importante:

- copia repetida de dados entre processos via kernel buffering tradicional.

### 10.2 Por que isso e perigosa?

Porque tira uma protecao conceitual importante:

- agora varios processos acessam os mesmos bytes.

Isso traz:

- sincronizacao;
- protocolo de ownership;
- risco de corrida;
- risco de inconsistencias;
- bugs mais dificeis.

---

## 11. Modelo mental de memoria compartilhada

Com pipe ou socket:

- cada lado pede ao kernel transferencia de bytes;
- a troca e mediada como fluxo de I/O.

Com memoria compartilhada:

- os dois processos enxergam a mesma regiao;
- o problema deixa de ser apenas mover bytes;
- passa a ser coordenar quem le, quem escreve e quando.

### 11.1 Consequencia

Memoria compartilhada e menos sobre "transporte" e mais sobre:

- protocolo;
- sincronizacao;
- layout;
- ownership temporal.

---

## 12. Exemplo conceitual com `mmap`

Em Unix-like, uma forma comum de memoria compartilhada e mapear uma regiao compartilhada:

```c
void *ptr = mmap(NULL, 4096, PROT_READ | PROT_WRITE,
                 MAP_SHARED, fd, 0);
```

Se dois processos mapeiam a mesma regiao compartilhada:

- um pode escrever;
- o outro pode ler os mesmos bytes.

### 12.1 O que isso nao resolve sozinho?

- exclusao mutua;
- ordem de leitura/escrita;
- framing de registros;
- consistencia de estruturas compostas.

---

## 13. Sincronizacao em IPC

Sempre que dois processos compartilham estado ou trocam fluxo, voce precisa pensar em sincronizacao.

### 13.1 Com pipes e sockets

O kernel ja ajuda bastante no transporte.

Mas voce ainda precisa:

- protocolo;
- delimitacao;
- ordem de mensagens;
- backpressure;
- fechamento coerente.

### 13.2 Com memoria compartilhada

Voce frequentemente precisa de mecanismos extras:

- semaforos;
- mutexes entre processos;
- atomics com muito cuidado;
- filas lock-free especializadas;
- contratos muito claros de ownership.

---

## 14. Custo de copia

Esse e um dos eixos mais importantes.

### 14.1 Pipes e sockets locais

Normalmente envolvem:

- escrita do processo A;
- passagem pelo kernel;
- leitura pelo processo B.

Ha custo de copia e de syscall.

### 14.2 Memoria compartilhada

Pode reduzir o custo de mover payload repetidamente.

Mas cobra:

- mais complexidade;
- mais risco;
- mais engenharia de sincronizacao.

### 14.3 Regra pratica

Nao escolha memoria compartilhada so porque "parece mais rapida".

Escolha quando:

- volume de dados justifica;
- medicao mostra gargalo real de copia;
- equipe consegue manter a disciplina necessaria.

---

## 15. Isolamento e debuggabilidade

Pipes e Unix domain sockets mantem separacao conceitual melhor:

- um lado escreve mensagens ou bytes;
- outro lado consome;
- o estado compartilhado e menor.

Memoria compartilhada reduz isolamento:

- bugs podem corromper estrutura compartilhada;
- diagnostico fica mais dificil;
- ordem de eventos fica mais sensivel.

### 15.1 Consequencia pratica

Simplicidade operacional tambem e custo.

Nem sempre o caminho com menos copia e o melhor sistema.

---

## 16. Exemplo comparativo de escolha

### 16.1 Caso A: pai gera linhas e filho processa

Escolha natural:

- `pipe`.

### 16.2 Caso B: daemon local recebe comandos administrativos

Escolha natural:

- Unix domain socket.

### 16.3 Caso C: dois processos compartilham grande buffer de frames ou blocos

Escolha possivel:

- memoria compartilhada + sincronizacao disciplinada.

---

## 17. O que acontece no kernel e na memoria?

### 17.1 Pipe

- kernel mantem buffer do canal;
- processos usam descritores;
- trafego passa por syscalls de leitura e escrita.

### 17.2 Unix domain socket

- kernel mantem semantica de socket local;
- conexoes locais ainda usam descritores e readiness;
- arquitetura se parece com rede, sem sair do host.

### 17.3 Memoria compartilhada

- processos mapeiam a mesma regiao;
- os bytes podem ser vistos por ambos;
- a disciplina de acesso passa a ser problema central do software.

## 19. Comparacao com C++, Rust, Go e Python

- Em C++, as mesmas primitivas existem ou sao encapsuladas por bibliotecas, mas o problema fisico de copia, sincronizacao e fronteira entre processos continua igual.
- Em Rust, o compilador ajuda muito a reduzir erros intra-processo, mas IPC e shared memory continuam exigindo desenho cuidadoso de protocolo e sincronizacao.
- Em Go, channels nao substituem IPC entre processos; quando se cruza fronteira de processo, volta-se ao mundo de socket, pipe e protocolo.
- Em Python, multiprocessing e bibliotecas de IPC escondem parte da mecanica, mas os custos reais continuam existindo por baixo.

Em C, voce ve esses mecanismos quase diretamente como contratos do SO.

---

## 20. Erros Comuns e Anti-Padroes

1. **Usar memoria compartilhada sem estrategia de sincronizacao**.
2. **Achar que `pipe` resolve protocolo por magica**.
3. **Usar Unix domain socket sem pensar em framing ou escrita parcial**.
4. **Escolher shared memory por performance antes de medir o gargalo**.
5. **Nao fechar descritores ou pontas nao usadas de `pipe`**.
6. **Misturar simplicidade de API com simplicidade de sistema**.

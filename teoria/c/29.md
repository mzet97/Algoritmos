# Aula 29 - Profiling de CPU e memoria com `perf`, `callgrind` e counters

---

## Objetivo da Aula

Entender como sair da intuicao e entrar em diagnostico objetivo de desempenho em C, usando `perf`, `callgrind` e counters para descobrir onde o tempo realmente vai, qual funcao esta quente, e quais sinais sugerem gargalo de CPU, branch ou memoria. Ao final, voce deve conseguir olhar para um programa C e montar uma investigacao tecnica baseada em evidencia, e nao em palpite.

Na aula 28, vimos:

- cache lines;

- layout e custo microarquitetural.

Mas ainda faltava um ponto decisivo:

- como provar no mundo real que um gargalo esta em CPU, memoria, branch ou acesso ruim?

## 2. Profiling nao e benchmark simples

- **Benchmark simples**: mede tempo total de uma execucao ou de um trecho.
- **Profiler**: tenta mostrar onde o programa gastou custo e como esse custo se distribui.
- **Counter de hardware**: mede eventos observados pelo processador, como ciclos, instrucoes, branches e misses.

### 2.1 Por que `clock()` sozinho nao basta?

Porque `clock()` pode dizer:

- "ficou lento".

Mas nao responde bem:

- onde ficou lento;
- se o problema e CPU puro;
- se o problema e branch imprevisivel;
- se o problema e cache miss;
- se a culpa esta em uma funcao especifica.

---

## 3. O que queremos descobrir de verdade?

Quando voce investiga performance em C, as perguntas mais uteis sao:

- qual funcao esta no hot path?;
- a maior parte do custo esta em CPU ou em espera por memoria?;
- ha muito branch miss?;
- o layout de dados esta derrotando cache?;
- o compilador ajudou ou a estrutura do codigo continua ruim?;
- a intuicao bate com os dados medidos?

---

## 4. `perf`: amostragem e counters do sistema real

- **`perf`**: conjunto de ferramentas do Linux para observar execucao real com amostragem, call stacks e contadores de hardware.

### 4.1 O que ele faz bem?

- encontrar hotspots reais;
- mostrar funcoes mais quentes;
- coletar counters da CPU;
- operar perto do comportamento real de producao;
- ajudar a correlacionar tempo com eventos de hardware.

### 4.2 O que ele nao faz sozinho?

- nao explica automaticamente o motivo arquitetural sem interpretacao;
- nao substitui leitura de codigo;
- nao garante causalidade so porque algo apareceu no topo do ranking.

---

## 5. `callgrind`: instrumentacao e visao detalhada de chamadas

- **`callgrind`**: ferramenta do ecossistema `valgrind` que instrumenta a execucao para estimar custo por funcao e por relacionamento de chamadas.

### 5.1 O que ele faz bem?

- mostrar call graph com detalhe;
- destacar custo por funcao chamadora e chamada;
- comparar versoes do mesmo programa com bastante precisao relativa;
- estimar instrucoes e, opcionalmente, cache/branch simulados.

### 5.2 O que ele cobra em troca?

- execucao muito mais lenta;
- ambiente menos parecido com producao;
- resultados que precisam ser lidos como diagnostico estrutural, nao como tempo real absoluto.

---

## 6. `perf` vs `callgrind`

Nao sao concorrentes diretos. Eles respondem perguntas ligeiramente diferentes.

### 6.1 Regra pratica

Use `perf` quando quiser:

- observar execucao real;
- achar hotspot rapido;
- olhar counters da CPU;
- medir comportamento proximo do sistema real.

Use `callgrind` quando quiser:

- detalhar call graph;
- comparar caminhos de execucao;
- enxergar distribuicao estrutural de custo;
- estudar relacao entre funcoes com mais calma.

### 6.2 Fluxo tecnico comum

1. Mecha no codigo o minimo possivel.
2. Gere baseline otimizada com simbolos.
3. Rode `perf` para localizar hotspots e counters.
4. Se precisar de anatomia mais detalhada das chamadas, rode `callgrind`.
5. Releia layout, algoritmo e padrao de acesso.
6. Altere uma coisa por vez e meca de novo.

---

## 7. Counters importantes

Os nomes exatos podem variar por CPU, kernel e permissao, mas alguns counters aparecem o tempo todo:

- `cycles`
- `instructions`
- `branches`
- `branch-misses`
- `cache-references`
- `cache-misses`

### 7.1 Como ler sem supersticao?

- muitos `cycles` com poucas `instructions` uteis podem sugerir espera alta;
- `branch-misses` elevados podem sugerir desvio imprevisivel em hot path;
- `cache-misses` elevados podem sugerir localidade ruim, stride ruim ou indirecao cara;
- `instructions` altas com poucos misses podem indicar trabalho computacional puro ou codigo inchado.

### 7.2 Cuidado importante

Counter isolado nao fecha diagnostico.

Voce precisa cruzar:

- counter;
- hotspot;
- codigo;
- layout;
- padrao de dados;
- contexto de compilacao.

## 8. Exemplo completo da aula

O exemplo abaixo foi desenhado para produzir tres tipos de custo:

- iteracao linear amigavel a cache;
- acesso com stride mais hostil a localidade;
- desvio frequente sobre dados pseudo-aleatorios.

```c
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

static double elapsed(clock_t start, clock_t end) {
    return (double)(end - start) / (double)CLOCKS_PER_SEC;
}

static void fill_data(int *v, size_t n) {
    uint32_t x = 2463534242u;

    for (size_t i = 0; i < n; i++) {
        x ^= x << 13;
        x ^= x >> 17;
        x ^= x << 5;
        v[i] = (int)(x & 1023u);
    }
}

static long long sum_linear(const int *v, size_t n) {
    long long sum = 0;

    for (size_t i = 0; i < n; i++) {
        sum += v[i];
    }

    return sum;
}

static long long sum_stride(const int *v, size_t n, size_t stride) {
    long long sum = 0;

    for (size_t i = 0; i < n; i += stride) {
        sum += v[i];
    }

    return sum;
}

static size_t count_branchy(const int *v, size_t n, int limit) {
    size_t count = 0;

    for (size_t i = 0; i < n; i++) {
        if (v[i] < limit) {
            count++;
        }
    }

    return count;
}

int main(void) {
    const size_t n = 20000000;
    const size_t stride = 16;
    int *data = malloc(n * sizeof(*data));
    if (data == NULL) {
        fprintf(stderr, "falha em malloc\n");
        return 1;
    }

    fill_data(data, n);

    clock_t t1 = clock();
    long long a = sum_linear(data, n);
    clock_t t2 = clock();

    clock_t t3 = clock();
    long long b = sum_stride(data, n, stride);
    clock_t t4 = clock();

    clock_t t5 = clock();
    size_t c = count_branchy(data, n, 512);
    clock_t t6 = clock();

    printf("sum_linear  = %lld tempo=%.6f s\n", a, elapsed(t1, t2));
    printf("sum_stride  = %lld tempo=%.6f s\n", b, elapsed(t3, t4));
    printf("branchy_cnt = %zu tempo=%.6f s\n", c, elapsed(t5, t6));

    free(data);
    return 0;
}
```

### 8.1 O que esse programa tenta expor?

- `sum_linear`: acesso sequencial, previsivel e amigavel a cache;
- `sum_stride`: menos elementos processados, mas com pior aproveitamento espacial;
- `count_branchy`: loop simples, mas com desvio frequente sobre dados pouco previsiveis.

### 8.2 O que isso nao garante?

- nao garante que seu hardware reagira igual em todos os detalhes;
- nao substitui carga real;
- nao prova sozinho que um counter alto significa um unico culpado.

---

## 9. Primeira leitura do exemplo

Se voce rodar esse programa, a intuicao inicial pode enganar:

- "menos iteracoes sempre significa mais rapido";
- "loop com um `if` simples sempre e barato";
- "tempo total sozinho basta".

Na pratica, o hardware pode mostrar:

- pior localidade em `sum_stride`;
- branch miss relevante em `count_branchy`;
- hotspots diferentes do que a leitura superficial sugeria.

## 10. Compilacao correta para investigar

Para profiling serio, voce normalmente quer:

- otimizacao razoavel;
- simbolos de debug;
- warnings ligados.

Compilar baseline:

```bash
gcc -Wall -Wextra -Wpedantic -O2 -g aula29.c -o aula29
```

### 10.1 Por que `-O2 -g`?

- `-O2` aproxima do codigo que voce realmente quer analisar;
- `-g` ajuda `perf` e outras ferramentas a mapear funcoes e linhas;
- `-O0` e util para aprendizado ou depuracao, mas pode distorcer o perfil de um programa que seria otimizado.

## 12. `perf stat`: counters globais

Comando:

```bash
perf stat ./aula29
```

Versao mais explicita:

```bash
perf stat -e cycles,instructions,branches,branch-misses,cache-references,cache-misses ./aula29
```

### 12.1 O que voce quer observar?

- total de ciclos;
- total de instrucoes;
- quantidade de branches;
- taxa de branch miss;
- taxa de cache miss.

### 12.2 Leitura conceitual

Se `branch-misses` sobe muito:

- suspeite de dados imprevisiveis ou fluxo ruim.

Se `cache-misses` sobe muito:

- suspeite de localidade ruim;
- stride alto;
- indirecao excessiva;
- working set grande demais para os caches relevantes.

Se `instructions` esta alta sem ganho correspondente:

- suspeite de trabalho inutil;
- codigo mais complexo do que precisava;
- caminho quente inchado.

---

## 13. `perf record` e `perf report`: hotspots reais

Comandos:

```bash
perf record ./aula29
perf report
```

### 13.1 O que esperar?

Voce deve ver algo como:

- `sum_linear`
- `sum_stride`
- `count_branchy`
- possivelmente funcoes de runtime ou inicializacao

### 13.2 Interpretacao

Se `sum_stride` aparece mais quente do que parecia razoavel:

- o padrao de acesso pode estar custando mais que o numero bruto de iteracoes sugere.

Se `count_branchy` aparece muito quente:

- o desvio e o comportamento dos dados podem estar cobrando caro.

### 13.3 Passo extra

Quando fizer sentido:

```bash
perf annotate
```

Isso ajuda a aproximar:

- funcao quente;
- instrucoes geradas;
- efeito do codigo compilado.

## 14. `callgrind`: anatomia estrutural do custo

Comandos:

```bash
valgrind --tool=callgrind ./aula29
callgrind_annotate callgrind.out.*
```

Versao com simulacao adicional:

```bash
valgrind --tool=callgrind --cache-sim=yes --branch-sim=yes ./aula29
callgrind_annotate --auto=yes callgrind.out.*
```

### 14.1 O que ele tende a mostrar bem?

- custo relativo por funcao;
- relacao chamador -> chamada;
- distribuicao de instrucoes;
- impacto estrutural de certas mudancas de codigo.

### 14.2 O que ele mede com menos fidelidade ao mundo real?

- tempo absoluto;
- comportamento identico ao hardware real;
- qualquer conclusao que dependa de escalonamento, ruido do sistema ou detalhes finos do processador.

## 15. `perf` e `callgrind` contam historias diferentes

Esse ponto e importante.

`perf` pode dizer:

- "isso aqui aquece de verdade em execucao real".

`callgrind` pode dizer:

- "esse caminho estrutural consome muito trabalho e chama isso aqui tantas vezes".

Juntos, eles ajudam a separar:

- gargalo real observado;
- anatomia interna do custo.

---

## 16. CPU-bound vs memoria-bound

Voce raramente recebe um rotulo pronto da ferramenta.

Precisa inferir.

### 16.1 Sinais de gargalo mais CPU-bound

- muitas instrucoes uteis;
- pouco sinal de cache miss relevante;
- loop denso de calculo;
- hotspot concentrado em trabalho computacional.

### 16.2 Sinais de gargalo mais memoria-bound

- muitos ciclos em relacao ao trabalho util;
- cache miss alto;
- stride ruim;
- indirecao;
- working set grande;
- layout que derrota localidade.

### 16.3 Sinais de problema de branch

- `branch-misses` relevante;
- dados pouco previsiveis;
- `if` frequente em hot path;
- grande sensibilidade a distribuicao de entrada.

---

## 17. O counter nao substitui o modelo mental

Suponha que voce veja:

- `cache-misses` alto.

Isso ainda nao responde sozinho:

- o problema esta em qual estrutura?;
- qual campo puxa a linha errada?;
- se o stride e artificial ou inevitavel?;
- se o working set cabe em outro arranjo?;
- se o algoritmo esta acessando memoria em ordem ruim?

Por isso a ordem correta e:

1. medir;
2. localizar hotspot;
3. ler counters;
4. reler o codigo;
5. reler layout e padrao de acesso;
6. testar mudanca pequena;
7. medir outra vez.

---

## 18. Erros comuns ao usar profiler

1. **Otimizar o que nao esta quente**.
2. **Olhar apenas tempo total e ignorar call graph**.
3. **Olhar apenas call graph e ignorar counters**.
4. **Usar `-O0` e achar que o perfil representa producao**.
5. **Concluir que cache e o problema sem olhar padrao de acesso**.
6. **Concluir que branch e o problema sem olhar distribuicao dos dados**.
7. **Comparar execucoes diferentes sem controlar minimamente o baseline**.
8. **Alterar varias coisas ao mesmo tempo e perder causalidade**.

---

## 19. Comparacao com C++, Rust, Go e Python

- Em C++, `perf` e `callgrind` continuam extremamente uteis, mas templates, inlining e abstracoes podem dificultar leitura superficial do perfil.
- Em Rust, o diagnostico de performance segue muito parecido no nivel fisico, embora ownership seguro reduza certas classes de erro.
- Em Go, profiler e runtime entregam outras visoes tambem, mas counters de hardware e hotspots nativos continuam valiosos.
- Em Python, a maior parte do tempo pode estar no interpretador ou em extensoes nativas, entao o ponto de observacao muda, mas o mundo fisico por baixo continua o mesmo.

Em C, essa investigacao fica especialmente clara porque:

- funcoes, layout, alocacao e loops estao muito expostos;
- o custo observado costuma refletir mais diretamente o desenho que voce escreveu.

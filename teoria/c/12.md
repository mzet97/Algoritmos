# Aula 12 - Bibliotecas estaticas, dinamicas, linkagem e ABI

Seu programa chama funções que você não escreveu, de bibliotecas que você não compilou. Linkagem estática, dinâmica e ABI são o contrato que torna isso possível — e a origem de uma classe inteira de erros que só aparece quando o programa nasce. Esta aula abre esse contrato.

---

## Nesta aula

Você vai aprender a produzir `.a` e `.so` do mesmo fonte e linkar os dois modos; prever o que quebra ao trocar uma biblioteca sem recompilar o dependente (ABI); e explicar por que mudar layout de tipo publico sem versionar e quebra silenciosa.

## 2. Arquivos objeto

Quando voce compila:

```bash
gcc -c math_utils.c -o math_utils.o
```

voce gera um:

- **arquivo objeto**

Ele contem, de forma simplificada:

- codigo compilado;
- simbolos definidos;
- simbolos ainda nao resolvidos;
- metadados para linkagem.

### 2.1 Ponto central

Arquivo objeto ainda nao e executavel final.

Ele e uma peca.

---

## 3. O que e linkagem?

- **Linkagem**: etapa que resolve referencias entre simbolos definidos e usados por varios objetos e bibliotecas, produzindo um binario final ou outro artefato reutilizavel.

Exemplo conceitual:

- `main.o` chama `soma`
- `math_utils.o` define `soma`
- o linker conecta os dois

Se nao achar o simbolo:

- erro de link

---

## 4. Biblioteca estatica

- **Biblioteca estatica**: arquivo contendo varios objetos agrupados, ligado ao executavel em build time.

Em ambiente Unix-like, extensao comum:

- `.a`

### 4.1 Fluxo tipico

```bash
gcc -c math_utils.c -o math_utils.o
ar rcs libmath_utils.a math_utils.o
gcc main.c libmath_utils.a -o app
```

### 4.2 O que isso significa?

Trechos necessarios da biblioteca sao incorporados ao executavel final.

### 4.3 Consequencias

- executavel mais autonomo;
- menos dependencia externa em runtime;
- possivel aumento de tamanho do binario.

---

## 5. Biblioteca dinamica

- **Biblioteca dinamica**: biblioteca carregada e ligada em runtime ou no carregamento do processo, em vez de ser copiada integralmente para o executavel no build.

Extensoes comuns:

- `.so` em Linux
- `.dll` em Windows
- `.dylib` em macOS

### 5.1 Consequencias

- menor binario final em varios casos;
- possibilidade de compartilhamento entre processos;
- dependencia de runtime e distribuicao correta da biblioteca.

---

## 6. ABI

- **ABI (Application Binary Interface)**: contrato binario que define como codigo compilado conversa em nivel de binario, incluindo convencoes de chamada, layout de tipos, alinhamento, passagem de argumentos, nomes de simbolos e formato de objetos.

### 6.1 Por que isso importa?

Porque dois modulos podem compilar sem erro isoladamente e ainda assim serem incompativeis binariamente.

ABI afeta:

- chamada de funcao;
- tamanho de tipos;
- layout de `struct`;
- ordem e forma de passagem de argumentos;
- interoperabilidade entre linguagens.

---

## 7. API vs ABI

- **API**: contrato em nivel de codigo fonte.
- **ABI**: contrato em nivel binario.

### 7.1 Exemplo simples

Se voce muda a ordem dos campos de uma `struct` publica:

- talvez a API pareca semelhante;
- mas a ABI pode quebrar.

Esse ponto e central em bibliotecas publicas.

---

## 8. Exemplo com biblioteca estatica

`math_utils.h`

```c
#ifndef MATH_UTILS_H
#define MATH_UTILS_H

int soma(int a, int b);
int multiplica(int a, int b);

#endif
```

`math_utils.c`

```c
#include "math_utils.h"

int soma(int a, int b) {
    return a + b;
}

int multiplica(int a, int b) {
    return a * b;
}
```

`main.c`

```c
#include <stdio.h>
#include "math_utils.h"

int main(void) {
    printf("%d\n", soma(2, 3));
    printf("%d\n", multiplica(4, 5));
    return 0;
}
```

### 8.1 Comandos

```bash
gcc -Wall -Wextra -Wpedantic -O0 -g -c math_utils.c -o math_utils.o
ar rcs libmath_utils.a math_utils.o
gcc -Wall -Wextra -Wpedantic -O0 -g main.c libmath_utils.a -o app
```

---

## 9. Exemplo conceitual de biblioteca dinamica

Em ambiente Unix-like, um fluxo simplificado seria:

```bash
gcc -Wall -Wextra -Wpedantic -O0 -g -fPIC -c math_utils.c -o math_utils.o
gcc -shared -o libmath_utils.so math_utils.o
gcc -Wall -Wextra -Wpedantic -O0 -g main.c -L. -lmath_utils -o app
```

### 9.1 O que e `-fPIC`?

- **Position Independent Code**: codigo gerado para funcionar melhor em bibliotecas dinamicas carregadas em enderecos variaveis.

### 9.2 O que e `-L.` e `-lmath_utils`?

- `-L.`: adiciona diretorio atual na busca de bibliotecas
- `-lmath_utils`: pede ao linker a biblioteca `libmath_utils`

## 10. Erros de link comuns

### 10.1 Simbolo indefinido

Voce declarou e usou, mas o linker nao encontrou a definicao.

### 10.2 Simbolo duplicado

Voce definiu a mesma entidade em mais de um lugar.

### 10.3 Ordem de bibliotecas

Em certos fluxos tradicionais, a ordem de argumentos do linker pode influenciar resolucao.

## 11. Exemplo completo da aula

`stack.h`

```c
#ifndef STACK_H
#define STACK_H

typedef struct {
    int *dados;
    int topo;
    int capacidade;
} Stack;

int stack_init(Stack *s, int capacidade);
void stack_destroy(Stack *s);
int stack_push(Stack *s, int valor);
int stack_pop(Stack *s, int *valor);

#endif
```

`stack.c`

```c
#include <stdlib.h>
#include "stack.h"

int stack_init(Stack *s, int capacidade) {
    s->dados = malloc((size_t)capacidade * sizeof(int));
    if (s->dados == NULL) {
        return 0;
    }
    s->topo = 0;
    s->capacidade = capacidade;
    return 1;
}

void stack_destroy(Stack *s) {
    free(s->dados);
    s->dados = NULL;
    s->topo = 0;
    s->capacidade = 0;
}

int stack_push(Stack *s, int valor) {
    if (s->topo >= s->capacidade) {
        return 0;
    }
    s->dados[s->topo++] = valor;
    return 1;
}

int stack_pop(Stack *s, int *valor) {
    if (s->topo <= 0) {
        return 0;
    }
    s->topo--;
    *valor = s->dados[s->topo];
    return 1;
}
```

`main.c`

```c
#include <stdio.h>
#include "stack.h"

int main(void) {
    Stack s;
    if (!stack_init(&s, 4)) {
        return 1;
    }

    stack_push(&s, 10);
    stack_push(&s, 20);

    int valor;
    if (stack_pop(&s, &valor)) {
        printf("pop = %d\n", valor);
    }

    stack_destroy(&s);
    return 0;
}
```

### 11.1 O que esse exemplo ensina?

- header como contrato publico;
- `.c` como implementacao;
- tipo exposto pela interface;
- simbolos resolvidos no link.

---

## 12. O que acontece em memoria e no binario?

Conceitualmente:

- cada `.c` vira objeto separado;
- a biblioteca estatica e um pacote de objetos;
- o linker seleciona e combina o necessario;
- a ABI determina como o executavel chamara funcoes da biblioteca;
- o layout de `Stack` precisa ser conhecido por todos os lados que usam o header.

Se voce mudar `Stack` no header publico:

- muda API e possivelmente ABI.

## 13. Comandos exatos

Compilar objetos:

```bash
gcc -Wall -Wextra -Wpedantic -O0 -g -c stack.c -o stack.o
gcc -Wall -Wextra -Wpedantic -O0 -g -c main.c -o main.o
```

Criar biblioteca estatica:

```bash
ar rcs libstack.a stack.o
```

Linkar executavel:

```bash
gcc main.o libstack.a -o app
```

Rodar:

```bash
.\app
```

## 14. Comparacao com C++, Rust, Go e Python

- Em C++, bibliotecas estaticas e dinamicas seguem base semelhante, mas name mangling, templates e excecoes complicam muito mais a ABI.
- Em Rust, o ecossistema tende a trabalhar mais em nivel de crate e menos em ABI publica estavel tradicional, exceto em fronteiras especificas como `extern "C"`.
- Em Go, a toolchain esconde muito da dor de linkagem tradicional para o caso idiomatico.
- Em Python, extensoes nativas ainda dependem fortemente de ABI, mas o usuario de aplicacao costuma ficar longe disso.

Em C, ABI e linkagem sao parte explicita da engenharia.

---

## 15. Erros Comuns e Anti-Padroes

1. **Confundir API com ABI**.
2. **Expor `struct` publica sem pensar em evolucao binaria**.
3. **Definir simbolo em header comum e gerar duplicacao**.
4. **Achar que biblioteca dinamica e "so um arquivo a mais"**.
5. **Ignorar convencoes de build e distribuicao do alvo**.
6. **Mudar tipo publico sem considerar compatibilidade binaria**.

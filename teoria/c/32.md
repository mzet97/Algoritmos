# Aula 32 - Projeto pratico de biblioteca/CLI de infraestrutura em C

---

## Objetivo da Aula

Ao final, voce devera: entregar biblioteca + CLI com API opaca, ownership e codigos de erro; provar com sanitizer e teste que o contrato segura; e evoluir a implementacao sem quebrar o publico.

### Como ler esta aula (tres niveis)

- **Fundamental:** opaco, erro como codigo, biblioteca + CLI + build.
- **Intermediario:** ownership explicito, sanitizer no fluxo, contrato operacional.
- **Aprofundamento (opcional):** evoluir sem quebrar, versionar simbolo (aula 12 retoma).

### Pre-teste e pos-teste da porta C8

**Pre-teste:** (1) por que tipo opaco? (2) quem libera o que numa biblioteca? **Pos-teste:** (1) mostre sua API que permite trocar a implementacao sem recompilar o cliente; (2) onde o sanitizer entrou no seu fluxo? Gabarito curto: pre -- (1) esconder representacao e preservar liberdade de mudar, (2) contrato escrito, dono nomeado; pos -- (1) cabecalho estavel + simbolo versionado, cliente relinkado sem tocar, (2) em todo teste, verde antes de qualquer medida.

## 2. O que vamos construir?

O projeto sera uma biblioteca pequena de configuracao chave/valor em memoria, com:

- tipo opaco;
- inicializacao e destruicao claras;
- insercao e busca de pares;
- codigos de erro por `enum`;
- CLI que carrega pares via argumentos;
- exibicao de resultado;
- separacao entre biblioteca e aplicacao.

### 2.1 Por que esse exemplo e bom?

Porque ele obriga voce a pensar em:

- fronteira publica vs interna;
- header publico;
- implementacao privada;
- ownership de strings;
- politica de erro;
- contrato de uso;
- build com varios arquivos;
- teste e observabilidade minima.

## 3. Forma do projeto

Organizacao conceitual:

```text
config_store.h
config_store.c
main.c
Makefile
```

### 3.1 Responsabilidade de cada parte

- `config_store.h`: API publica;
- `config_store.c`: implementacao e estruturas internas;
- `main.c`: CLI que usa a biblioteca;
- `Makefile`: build reproduzivel e alvos utilitarios.

Isso parece simples, e deve parecer simples mesmo.

Em C, simplicidade organizacional e uma virtude enorme.

## 4. Tipo opaco

Em vez de expor a struct inteira no header, vamos expor apenas um nome abstrato:

```c
typedef struct ConfigStore ConfigStore;
```

### 4.1 O que isso compra?

- reduz acoplamento;
- protege layout interno;
- permite evoluir implementacao;
- impede o usuario de mexer em campos internos por acidente.

### 4.2 O que isso cobra?

- o usuario precisa passar por funcoes da API;
- mais disciplina na definicao de operacoes publicas;
- menos "atalho facil" para inspecionar internals.

Esse trade-off costuma valer muito a pena em bibliotecas.

---

## 5. Contrato de ownership

Aqui esta uma decisao essencial:

- a biblioteca copiara `key` e `value` recebidos.

Logo:

- o chamador continua dono das strings originais;
- a biblioteca fica dona das copias internas;
- `config_store_destroy()` libera tudo que a biblioteca alocou.

### 5.1 Por que essa decisao e boa?

Porque reduz ambiguidade.

Alternativa ruim:

- "talvez a biblioteca guarde o ponteiro do chamador".

Isso gera lifetime fragil e bugs previsiveis.

### 5.2 Regra pratica

Se uma biblioteca guarda dados para uso futuro, muitas vezes faz sentido:

- copiar;
- documentar;
- destruir internamente depois.

---

## 6. Politica de erro

Em vez de retornar apenas `0` ou `1`, vamos usar um `enum`.

Exemplo:

```c
typedef enum {
    CONFIG_OK = 0,
    CONFIG_ERR_OOM,
    CONFIG_ERR_INVALID,
    CONFIG_ERR_NOT_FOUND
} ConfigStatus;
```

### 6.1 Por que isso melhora a API?

- erro fica nomeado;
- chamador pode tratar casos diferentes;
- debug fica menos nebuloso;
- contrato fica mais legivel.

### 6.2 Ainda precisamos de mensagem humana?

Frequentemente sim.

Por isso e comum adicionar algo como:

- `config_status_str()`

para converter codigo de erro em texto simples.

---

## 7. Estrutura interna

Internamente, a biblioteca pode usar algo bem simples e honesto.

Nao precisamos de hash map sofisticado para ensinar arquitetura.

Modelo:

```c
typedef struct {
    char *key;
    char *value;
} ConfigEntry;

struct ConfigStore {
    ConfigEntry *items;
    size_t len;
    size_t cap;
};
```

### 7.1 Por que esse design funciona didaticamente?

- mostra vetor dinamico;
- mostra ownership das strings;
- mostra crescimento amortizado;
- mostra fronteira entre API publica e detalhe privado.

### 7.2 O que ele nao otimiza?

- busca em grande escala;
- remocao eficiente;
- concorrencia;
- persistencia.

E tudo bem.

Primeiro queremos:

- contrato bom;
- ciclo de vida claro;
- reutilizacao correta.

### 8.2 Implementacao da biblioteca

`config_store.c`

```c
#include "config_store.h"

#include <stdio.h>
#include <stdlib.h>
#include <string.h>

typedef struct {
    char *key;
    char *value;
} ConfigEntry;

struct ConfigStore {
    ConfigEntry *items;
    size_t len;
    size_t cap;
};

static char *dup_cstr(const char *s) {
    size_t len = strlen(s) + 1;
    char *copy = malloc(len);
    if (copy == NULL) {
        return NULL;
    }
    memcpy(copy, s, len);
    return copy;
}

static int ensure_capacity(ConfigStore *store) {
    if (store->len < store->cap) {
        return 0;
    }

    size_t new_cap = store->cap == 0 ? 4 : store->cap * 2;
    ConfigEntry *tmp = realloc(store->items, new_cap * sizeof(*tmp));
    if (tmp == NULL) {
        return -1;
    }

    store->items = tmp;
    store->cap = new_cap;
    return 0;
}

static ConfigEntry *find_entry(ConfigStore *store, const char *key) {
    for (size_t i = 0; i < store->len; i++) {
        if (strcmp(store->items[i].key, key) == 0) {
            return &store->items[i];
        }
    }
    return NULL;
}

static const ConfigEntry *find_entry_const(const ConfigStore *store,
                                           const char *key) {
    for (size_t i = 0; i < store->len; i++) {
        if (strcmp(store->items[i].key, key) == 0) {
            return &store->items[i];
        }
    }
    return NULL;
}

ConfigStore *config_store_create(void) {
    ConfigStore *store = calloc(1, sizeof(*store));
    return store;
}

void config_store_destroy(ConfigStore *store) {
    if (store == NULL) {
        return;
    }

    for (size_t i = 0; i < store->len; i++) {
        free(store->items[i].key);
        free(store->items[i].value);
    }

    free(store->items);
    free(store);
}

ConfigStatus config_store_set(ConfigStore *store,
                              const char *key,
                              const char *value) {
    char *key_copy;
    char *value_copy;
    ConfigEntry *entry;

    if (store == NULL || key == NULL || value == NULL ||
        key[0] == '\0') {
        return CONFIG_ERR_INVALID;
    }

    entry = find_entry(store, key);
    if (entry != NULL) {
        value_copy = dup_cstr(value);
        if (value_copy == NULL) {
            return CONFIG_ERR_OOM;
        }
        free(entry->value);
        entry->value = value_copy;
        return CONFIG_OK;
    }

    if (ensure_capacity(store) != 0) {
        return CONFIG_ERR_OOM;
    }

    key_copy = dup_cstr(key);
    value_copy = dup_cstr(value);
    if (key_copy == NULL || value_copy == NULL) {
        free(key_copy);
        free(value_copy);
        return CONFIG_ERR_OOM;
    }

    store->items[store->len].key = key_copy;
    store->items[store->len].value = value_copy;
    store->len++;
    return CONFIG_OK;
}

ConfigStatus config_store_get(const ConfigStore *store,
                              const char *key,
                              const char **out_value) {
    const ConfigEntry *entry;

    if (store == NULL || key == NULL || out_value == NULL) {
        return CONFIG_ERR_INVALID;
    }

    entry = find_entry_const(store, key);
    if (entry == NULL) {
        return CONFIG_ERR_NOT_FOUND;
    }

    *out_value = entry->value;
    return CONFIG_OK;
}

size_t config_store_len(const ConfigStore *store) {
    if (store == NULL) {
        return 0;
    }
    return store->len;
}

const char *config_status_str(ConfigStatus status) {
    switch (status) {
        case CONFIG_OK:
            return "ok";
        case CONFIG_ERR_OOM:
            return "out of memory";
        case CONFIG_ERR_INVALID:
            return "invalid argument";
        case CONFIG_ERR_NOT_FOUND:
            return "not found";
        default:
            return "unknown error";
    }
}
```

### 8.3 CLI consumindo a biblioteca

`main.c`

```c
#include "config_store.h"

#include <stdio.h>
#include <string.h>

static int parse_pair(const char *arg, const char **key, const char **value) {
    const char *eq = strchr(arg, '=');
    if (eq == NULL || eq == arg || eq[1] == '\0') {
        return 0;
    }

    *key = arg;
    *value = eq + 1;
    return 1;
}

static void print_usage(const char *prog) {
    fprintf(stderr, "uso: %s chave=valor [chave=valor ...] --get chave\n", prog);
}

int main(int argc, char **argv) {
    ConfigStore *store;
    const char *query_key = NULL;
    const char *value = NULL;

    if (argc < 4) {
        print_usage(argv[0]);
        return 2;
    }

    store = config_store_create();
    if (store == NULL) {
        fprintf(stderr, "erro: falha ao criar store\n");
        return 1;
    }

    for (int i = 1; i < argc; i++) {
        if (strcmp(argv[i], "--get") == 0) {
            if (i + 1 >= argc) {
                fprintf(stderr, "erro: faltou chave apos --get\n");
                config_store_destroy(store);
                return 2;
            }
            query_key = argv[i + 1];
            break;
        }

        const char *key;
        const char *val;
        if (!parse_pair(argv[i], &key, &val)) {
            fprintf(stderr, "erro: argumento invalido: %s\n", argv[i]);
            config_store_destroy(store);
            return 2;
        }

        size_t key_len = (size_t)((strchr(argv[i], '=')) - argv[i]);
        char key_buf[128];
        if (key_len >= sizeof(key_buf)) {
            fprintf(stderr, "erro: chave muito longa\n");
            config_store_destroy(store);
            return 2;
        }

        memcpy(key_buf, key, key_len);
        key_buf[key_len] = '\0';

        ConfigStatus st = config_store_set(store, key_buf, val);
        if (st != CONFIG_OK) {
            fprintf(stderr, "erro: %s\n", config_status_str(st));
            config_store_destroy(store);
            return 1;
        }
    }

    if (query_key == NULL) {
        fprintf(stderr, "erro: faltou --get chave\n");
        config_store_destroy(store);
        return 2;
    }

    ConfigStatus st = config_store_get(store, query_key, &value);
    if (st != CONFIG_OK) {
        fprintf(stderr, "erro: %s\n", config_status_str(st));
        config_store_destroy(store);
        return 1;
    }

    printf("%s\n", value);
    config_store_destroy(store);
    return 0;
}
```

### 8.4 Build reproduzivel

`Makefile`

```make
CC = gcc
CFLAGS = -Wall -Wextra -Wpedantic
DBGFLAGS = -O0 -g
RELFLAGS = -O2
SANFLAGS = -fsanitize=address -fsanitize=undefined

.PHONY: all debug release sanitize clean

all: debug

debug: app_debug

release: app_release

sanitize: app_sanitize

app_debug: main.c config_store.c config_store.h
	$(CC) $(CFLAGS) $(DBGFLAGS) main.c config_store.c -o app_debug

app_release: main.c config_store.c config_store.h
	$(CC) $(CFLAGS) $(RELFLAGS) main.c config_store.c -o app_release

app_sanitize: main.c config_store.c config_store.h
	$(CC) $(CFLAGS) $(DBGFLAGS) $(SANFLAGS) main.c config_store.c -o app_sanitize

clean:
	rm -f app_debug app_release app_sanitize
```

## 9. O que esse projeto mostra de importante?

- separacao real entre biblioteca e aplicacao;
- header publico pequeno;
- internals escondidos;
- ownership explicito;
- erro com contrato legivel;
- build com mais de um modo;
- caminho claro para testes e automacao.

### 9.1 O que ele ainda nao resolve?

- persistencia em arquivo;
- parser de configuracao mais complexo;

- concorrencia;
- suporte a thread safety;
- estrutura de busca mais eficiente.

Tudo isso pode vir depois.

Se a base da API estiver ruim, escalar funcionalidade so multiplica problema.

- o que o usuario pode chamar;

### 10.3 Camada 3: interface operacional

`main.c` traduz:

- argumentos de linha de comando;
- mensagens de erro;
- `exit code`;

### 10.4 Camada 4: processo de build

`Makefile` materializa:

- modo debug;
- modo release;
- modo com sanitizer;
- forma repetivel de compilar.

Essa camada faz parte da engenharia, nao e decoracao.

## 11. O que acontece em memoria?

Conceitualmente:

- `ConfigStore *` e um handle para uma estrutura opaca no heap;
- `items` aponta para vetor dinamico de entradas;
- cada `ConfigEntry` possui duas strings alocadas separadamente;
- `config_store_set()` pode crescer o vetor e copiar novas strings;
- `config_store_destroy()` libera tudo em cascata.

### 11.1 O que isso ensina?

- um tipo opaco nao remove custo, ele so organiza responsabilidade;
- ownership bem definido simplifica destrucao;
- copiar dados cedo pode deixar a API mais segura e previsivel;
- vetor dinamico interno conecta design de biblioteca com as aulas de memoria e runtime.

## 12. Contrato operacional minimo da CLI

Uma CLI de infraestrutura precisa ser previsivel.

Neste projeto:

- `stdout` carrega o valor encontrado;
- `stderr` carrega erros e uso;
- `0` significa sucesso;
- `1` significa falha operacional;
- `2` significa uso invalido.

### 12.1 Por que isso importa?

Porque CLIs frequentemente sao usadas por:

- shell scripts;
- automacao;
- pipelines;
- outras ferramentas.

Sem contrato operacional, a CLI fica chata de integrar.

## 13. Testes e sanitizers

Mesmo num projeto pequeno, voce ja deveria pensar em:

- casos validos;
- chave ausente;
- argumento invalido;
- chave vazia;
- valor vazio, se permitido ou nao;
- destruicao repetida de `NULL`;
- crescimento do vetor.

### 13.1 O que os sanitizers ajudam a pegar?

- uso apos `free`;
- overflow de buffer;
- acessos invalidos;
- comportamentos indefinidos comuns.

### 13.2 Regra pratica

Antes de sofisticar a biblioteca:

- estabilize contrato;
- rode sanitizer;
- tente quebrar a API com entradas ruins.

## 16. Comparacao com C++, Rust, Go e Python

- Em C++, esse projeto se beneficiaria de RAII, `std::string`, `std::vector` e excecoes ou `expected`, reduzindo bastante a carga manual.
- Em Rust, ownership e lifetimes fariam varios contratos ficarem mais seguros por construcao, embora a API ainda precise ser bem desenhada.
- Em Go, mapas, slices e a biblioteca padrao deixariam a implementacao mais curta, mas com menos controle fino sobre alocacao e layout.
- Em Python, a mesma ideia seria trivial de escrever, mas perderia a proximidade com a engenharia nativa que estamos treinando aqui.

Em C, esse projeto ensina bem porque deixa visiveis:

- onde memoria nasce;
- quem destroi;
- onde a API protege o usuario;
- como build e contrato operacional entram no desenho.

## 17. Erros comuns e anti-padroes

1. **Expor a struct inteira no header sem necessidade**.
2. **Nao definir quem e dono das strings recebidas pela biblioteca**.
3. **Misturar erro de uso com erro operacional sem codigos claros**.
4. **Fazer a CLI acessar internals da biblioteca diretamente**.
5. **Nao separar `stdout` e `stderr`**.
6. **Ter apenas um modo de build e nunca rodar sanitizer**.
7. **Aumentar funcionalidade antes de estabilizar o contrato da API**.
8. **Achar que biblioteca pequena nao precisa de disciplina de engenharia**.

# Aula 30 - SIMD, vetorizacao e criterio para otimizar loops criticos

## 2. O que e SIMD?

- **SIMD**: Single Instruction, Multiple Data.

Em termos praticos:

- uma unica instrucao opera sobre varios elementos ao mesmo tempo.

Exemplo conceitual:

- somar 4, 8 ou mais valores em paralelo;
- multiplicar varios `float` de uma vez;
- aplicar a mesma operacao a um bloco contiguo de dados.

### 2.1 O ponto central

SIMD nao melhora qualquer codigo magicamente.

Ele ajuda mais quando voce tem:

- muitos dados do mesmo tipo;
- mesma operacao repetida;
- pouco desvio imprevisivel;
- acesso regular;
- layout favoravel.

---

## 3. Vetorizacao

- **Vetorizacao**: transformacao de um loop escalar em execucao vetorial.

Ela pode acontecer de dois jeitos principais:

- automaticamente pelo compilador;
- manualmente pelo programador via intrinsics.

### 3.1 Auto-vetorizacao

O compilador tenta identificar loops que podem ser executados em paralelo por elemento sem quebrar a semantica.

### 3.2 Vetorizacao manual

Voce usa APIs especificas da arquitetura, como intrinsics SSE, AVX ou similares, para controlar mais diretamente as instrucoes vetoriais.

---

## 4. Quando a auto-vetorizacao costuma funcionar melhor?

Loops simples com:

- iteracao linear;
- pouca ou nenhuma dependencia entre iteracoes;
- arrays contiguos;
- tipos numericos simples;
- corpo pequeno e previsivel;
- pouca indirecao;
- sem chamada complicada no meio do hot path.

Exemplo amigavel:

```c
for (size_t i = 0; i < n; i++) {
    c[i] = a[i] + b[i];
}
```

Esse e o tipo de loop que o compilador gosta de analisar.

---

## 5. O que costuma atrapalhar a vetorizacao?

- aliasing incerto;
- ponteiros sobrepostos;
- `if` imprevisivel no miolo do loop;
- chamadas de funcao nao inlineaveis;
- stride irregular;
- indirecao por ponteiros espalhados;
- dependencias entre iteracoes;
- layout ruim;
- alinhamento desfavoravel em alguns casos.

### 5.1 Exemplo de dependencia que bloqueia

```c
for (size_t i = 1; i < n; i++) {
    v[i] = v[i - 1] + 1;
}
```

Aqui cada iteracao depende da anterior.

Isso reduz ou elimina a chance de vetorizacao direta.

---

## 6. `restrict` e aliasing

Ja vimos que aliasing atrapalha tanto corretude mental quanto otimizacao.

Agora o impacto fica ainda mais claro.

- **`restrict`**: promessa feita ao compilador de que, por aquele ponteiro, o acesso nao conflita com outros ponteiros equivalentes no mesmo escopo de uso.

Exemplo:

```c
void sum_arrays(float *restrict dst,
                const float *restrict a,
                const float *restrict b,
                size_t n) {
    for (size_t i = 0; i < n; i++) {
        dst[i] = a[i] + b[i];
    }
}
```

### 6.1 Por que isso ajuda?

Porque o compilador pode raciocinar melhor que:

- ler `a[i]` nao vai invalidar `dst[i]` por alias inesperado;
- ler `b[i]` nao vai esconder escrita em `dst`;
- cada iteracao fica mais independente.

### 6.2 Cuidado

`restrict` nao e enfeite.

Se voce mentir para o compilador, o programa pode entrar em comportamento incorreto.

---

## 7. Layout de dados e vetorizacao

Aula 28 ja apontou isso:

- layout e padrao de acesso determinam muito do custo real.

Para vetorizacao, isso pesa ainda mais.

### 7.1 Struct of arrays costuma ajudar quando

- o hot path opera sobre um ou poucos campos por vez;
- os dados ficam contiguos por coluna;
- o loop processa o mesmo tipo de operacao repetidamente.

### 7.2 Array of structs pode atrapalhar quando

- cada iteracao toca so um campo;
- a struct contem muito lixo para aquele hot path;
- o stride efetivo fica maior do que o dado util.

Exemplo conceitual:

```c
typedef struct {
    float x;
    float y;
    float z;
    float w;
} Point;
```

Se voce quer processar apenas `x`, talvez um layout como:

```c
typedef struct {
    float *x;
    float *y;
    float *z;
    float *w;
} PointsSOA;
```

possa ser melhor para o loop critico.

---

## 8. Alinhamento: importante, mas sem misticismo

- **Alinhamento**: endereco ajustado a multiplos adequados para certos tipos e operacoes.

### 8.1 Por que isso importa?

Dependendo da arquitetura e da geracao de instrucoes:

- dados alinhados podem facilitar certos acessos vetoriais;
- dados desalinhados podem gerar codigo menos ideal ou mais trabalho de ajuste.

### 8.2 Mas qual e a regra pratica?

Primeiro:

- garanta corretude;
- simplifique o loop;
- garanta contiguidade;
- reduza aliasing;
- deixe o compilador trabalhar.

So depois pense em refinamentos de alinhamento mais agressivos.

---

## 9. Branches e vetorizacao

Um loop muito cheio de `if` imprevisivel tende a ser pior para vetorizacao.

Exemplo mais hostil:

```c
for (size_t i = 0; i < n; i++) {
    if (a[i] > limit) {
        out[i] = a[i] * scale;
    } else {
        out[i] = a[i];
    }
}
```

### 9.1 Por que isso incomoda?

- aumenta complexidade do fluxo;
- pode dificultar auto-vetorizacao;
- pode introduzir mascara, blends ou codigo alternativo mais caro;
- ainda pode sofrer com branch prediction ruim dependendo da entrada.

### 9.2 Cuidado com "branchless mania"

Nem todo codigo sem `if` fica melhor.

Trocar branch por algebra obscura sem medir pode:

- piorar legibilidade;
- aumentar instrucoes;
- nao ajudar seu compilador nem sua CPU;
- mascarar o problema real, que talvez fosse layout ou cache.

---

## 10. Exemplo escalar amigavel a auto-vetorizacao

```c
void saxpy_scalar(float *restrict y,
                  const float *restrict x,
                  float a,
                  size_t n) {
    for (size_t i = 0; i < n; i++) {
        y[i] = a * x[i] + y[i];
    }
}
```

### 10.1 Por que esse loop e bom candidato?

- arrays contiguos;
- mesma operacao para todos os elementos;
- sem dependencia entre iteracoes;
- sem branch;
- com `restrict`.

Esse e exatamente o tipo de loop em que voce deve primeiro tentar:

- `-O2` ou `-O3`;
- olhar relatorio do compilador;
- medir antes de escrever intrinsics.

---

## 11. Exemplo manual com intrinsics

O codigo abaixo e apenas didatico, focado em x86 com AVX.

Ele mostra como a versao manual fica mais especifica, menos portavel e mais dificil de manter.

```c
#include <immintrin.h>
#include <stddef.h>

void saxpy_avx(float *restrict y,
               const float *restrict x,
               float a,
               size_t n) {
    size_t i = 0;
    __m256 va = _mm256_set1_ps(a);

    for (; i + 8 <= n; i += 8) {
        __m256 vx = _mm256_loadu_ps(x + i);
        __m256 vy = _mm256_loadu_ps(y + i);
        __m256 vr = _mm256_add_ps(_mm256_mul_ps(va, vx), vy);
        _mm256_storeu_ps(y + i, vr);
    }

    for (; i < n; i++) {
        y[i] = a * x[i] + y[i];
    }
}
```

### 11.1 O que esse exemplo mostra?

- broadcast de um escalar para vetor;
- carga de 8 `float` por iteracao;
- multiplicacao e soma vetoriais;
- tratamento do resto no fim do array.

### 11.2 O que ele tambem cobra?

- dependencia de arquitetura;
- compilacao apropriada;
- maior custo de manutencao;
- mais responsabilidade do programador;
- risco de complexidade sem ganho material.

## 12. Exemplo completo da aula

```c
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

static double elapsed(clock_t start, clock_t end) {
    return (double)(end - start) / (double)CLOCKS_PER_SEC;
}

void saxpy_scalar(float *restrict y,
                  const float *restrict x,
                  float a,
                  size_t n) {
    for (size_t i = 0; i < n; i++) {
        y[i] = a * x[i] + y[i];
    }
}

void saxpy_branchy(float *restrict y,
                   const float *restrict x,
                   float a,
                   size_t n,
                   float limit) {
    for (size_t i = 0; i < n; i++) {
        if (x[i] > limit) {
            y[i] = a * x[i] + y[i];
        } else {
            y[i] = y[i] - 1.0f;
        }
    }
}

int main(void) {
    const size_t n = 20000000;
    float *x = malloc(n * sizeof(*x));
    float *y1 = malloc(n * sizeof(*y1));
    float *y2 = malloc(n * sizeof(*y2));
    if (x == NULL || y1 == NULL || y2 == NULL) {
        fprintf(stderr, "falha em malloc\n");
        free(x);
        free(y1);
        free(y2);
        return 1;
    }

    for (size_t i = 0; i < n; i++) {
        x[i] = (float)(i % 1000) * 0.01f;
        y1[i] = 1.0f;
        y2[i] = 1.0f;
    }

    clock_t t1 = clock();
    saxpy_scalar(y1, x, 2.5f, n);
    clock_t t2 = clock();

    clock_t t3 = clock();
    saxpy_branchy(y2, x, 2.5f, n, 3.0f);
    clock_t t4 = clock();

    printf("scalar  y1[123]=%.3f tempo=%.6f s\n", y1[123], elapsed(t1, t2));
    printf("branchy y2[123]=%.3f tempo=%.6f s\n", y2[123], elapsed(t3, t4));

    free(x);
    free(y1);
    free(y2);
    return 0;
}
```

### 12.1 O que comparar nesse exemplo?

- loop simples vs loop com branch;
- amigavel a auto-vetorizacao vs mais hostil;
- impacto de previsibilidade do fluxo;
- comportamento com `-O2` e `-O3`.

### 12.2 O que essa aula quer que voce veja?

O maior ganho nem sempre vem de escrever intrinsics.

Muitas vezes ele vem de:

- simplificar loop;
- reorganizar layout;
- remover dependencia;
- explicitar aliasing;
- deixar o compilador vetorizar.

## 13. Como investigar vetorizacao de verdade

O fluxo tecnico correto e parecido com o da aula 29.

### 13.1 Passo 1

Descubra se o loop esta realmente quente.

Use:

- `perf stat`;
- `perf record`;
- `perf report`;
- leitura do hot path.

### 13.2 Passo 2

Simplifique o loop antes de sofisticar:

- remova trabalho inutil;
- reduza branches;
- evite chamadas no miolo;
- garanta dados contiguos;
- repense layout.

### 13.3 Passo 3

Peca ajuda ao compilador:

- `-O2`
- `-O3`
- `-march=native` quando apropriado no seu ambiente
- relatorios de vetorizacao

### 13.4 Passo 4

Se ainda houver gargalo real e justificativa concreta:

- considere intrinsics;
- compare com baseline limpo;
- confirme portabilidade exigida pelo projeto.

## 14. Relatorios do compilador

So medir o binario final nao basta se voce quer saber se houve vetorizacao.

Em `gcc`, por exemplo, pode ser util pedir informacao extra ao compilador.

Exemplos:

```bash
gcc -Wall -Wextra -Wpedantic -O3 -march=native -fopt-info-vec aula30.c -o aula30
```

```bash
gcc -Wall -Wextra -Wpedantic -O3 -march=native -fopt-info-vec-missed aula30.c -o aula30
```

### 14.1 O que esses relatorios ajudam a responder?

- o loop foi vetorizado?;
- se nao foi, por que nao?;
- houve dependencia?;
- houve aliasing?;
- houve padrao de acesso ruim?;
- o compilador conseguiu provar seguranca suficiente?

---

## 15. `-O2`, `-O3` e `-march=native`

### 15.1 `-O2`

- bom baseline geral;
- costuma ativar otimizacoes importantes sem agressividade maxima.

### 15.2 `-O3`

- pode ajudar mais em loops numericos;
- pode ativar transformacoes extras;
- nem sempre gera o melhor resultado global.

### 15.3 `-march=native`

- permite gerar codigo ajustado para a CPU local;
- pode habilitar conjuntos de instrucoes mais amplos;
- reduz portabilidade do binario para outras maquinas.

### 15.4 Regra pratica

Nao confunda:

- "ficou vetorizado";

com:

- "ficou melhor no meu caso real".

Sempre meca.

---

## 16. Quando intrinsics valem a pena?

Use intrinsics com mais seriedade quando:

- o loop e comprovadamente quente;
- o compilador nao entrega resultado suficiente;
- a operacao e numericamente regular;
- a arquitetura-alvo e conhecida;
- o ganho potencial justifica perda de clareza;
- voce consegue manter fallback ou estrategia aceitavel para outros ambientes.

### 16.1 Quando provavelmente nao vale?

- loop nem esta no topo do perfil;
- ganho estimado e marginal;
- codigo ficara muito mais fragil;
- a equipe nao quer dependencia forte de arquitetura;
- o problema real era cache, branch ou algoritmo ruim.

---

## 17. Vetorizacao nao corrige modelo ruim de acesso

Esse erro e comum.

Voce pode ter:

- intrinsics bonitas;
- muitas instrucoes vetoriais;
- pouco ganho final.

Por que?

Porque o gargalo real talvez seja:

- cache miss;
- layout ruim;
- stride hostil;
- branch imprevisivel;
- memoria mais lenta do que a CPU consegue consumir.

SIMD acelera trabalho por elemento.

Ela nao apaga automaticamente custo ruim de acesso.

---

## 18. Comparacao com C++, Rust, Go e Python

- Em C++, auto-vetorizacao e intrinsics tambem sao relevantes, mas templates, containers e overloading podem tanto ajudar quanto esconder detalhes.
- Em Rust, iteradores e slices podem compor bem com otimizacao, mas o criterio fisico continua o mesmo: layout, aliasing e hot path importam.
- Em Go, o espaco para controle manual fino e menor, e a estrategia costuma pender mais para desenho de algoritmo e layout visivel ao runtime.
- Em Python, vetorizacao pesada normalmente aparece em bibliotecas nativas como NumPy, nao no loop Python puro.

Em C, esse mundo fica mais direto:

- voce ve o loop;
- voce ve os ponteiros;
- voce consegue aproximar mais claramente codigo, compilador e hardware.

---

## 19. Erros comuns e anti-padroes

1. **Escrever intrinsics antes de provar que o loop esta quente**.
2. **Ignorar aliasing e culpar o compilador cedo demais**.
3. **Achar que `-O3` sempre vence `-O2`**.
4. **Confundir vetorizar com melhorar throughput final**.
5. **Usar branchless trick obscuro sem medir impacto real**.
6. **Tentar vetorizar loop cheio de dependencia entre iteracoes**.
7. **Esquecer que layout de dados pode render mais ganho do que intrinsics**.
8. **Aceitar perda grande de portabilidade sem necessidade real**.

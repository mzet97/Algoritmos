# Aula 21 - Servidores orientados a eventos vs `thread-per-connection`

---

## Objetivo da Aula

Ao final, voce devera: medir o custo de uma thread (stack + contexto) contra o custo de estado explicito por conexao; escolher o modelo para um cenario dado e defender com numeros; e explicar por que sistemas reais terminam hibridos.

### Como ler esta aula (tres niveis)

- **Fundamental:** thread-per-connection vs eventos, custo visivel de cada um.
- **Intermediario:** latencia, heap por conexao, estado explicito que cresce.
- **Aprofundamento (opcional):** hibridos reais e o teto que decide (aula 23f mede).

---

## 1. Ponte com a aula anterior

Na aula 20, vimos:

- `select`;
- `poll`;
- `epoll`;
- readiness;
- event loop;
- I/O nao bloqueante.

Aquilo resolve uma pergunta:

- como observar muitos descritores ao mesmo tempo?

Agora precisamos responder outra:

- qual arquitetura de servidor faz melhor uso disso no mundo real?

As duas familias classicas sao:

- `thread-per-connection`;
- event-driven.

---

## 2. O que e `thread-per-connection`?

- **`Thread-per-connection`**: modelo em que cada conexao aceita pelo servidor ganha sua propria thread para tratar leitura, escrita e logica associada.

Fluxo conceitual:

1. `accept`;
2. criar thread;
3. thread atende aquele cliente;
4. thread termina quando a conexao fecha.

### 2.1 Por que esse modelo e atraente?

Porque ele parece natural.

Cada cliente ganha:

- sua pilha;
- seu fluxo linear;
- sua propria linha de execucao.

Do ponto de vista didatico, ele costuma ser muito facil de entender.

---

## 3. O que e event-driven?

- **Event-driven**: modelo em que um loop central ou um pequeno conjunto de loops observa varios descritores e processa apenas os que estao prontos, mantendo estado por conexao sem precisar de uma thread dedicada para cada cliente.

Fluxo conceitual:

1. registrar descritores;
2. esperar readiness;
3. despachar leitura e escrita;
4. atualizar buffers e estado da conexao;
5. repetir.

### 3.1 Por que esse modelo existe?

Porque o custo de uma thread por conexao cresce rapido quando o numero de conexoes sobe.

---

## 4. Custo de thread

Thread nao e gratis.

Mesmo antes de falar em CPU, uma thread traz:

- stack propria;
- metadados do runtime de threads do SO;
- custo de criacao e destruicao;
- custo de agendamento;
- custo de sincronizacao quando ha estado compartilhado.

### 4.1 O que isso significa na pratica?

Com poucas conexoes:

- pode ser totalmente aceitavel.

Com milhares:

- stacks somam memoria;
- scheduler do SO trabalha mais;
- troca de contexto pesa;
- debugging fica mais dificil.

---

## 5. Custo de event loop

Event-driven tambem nao e gratis.

Ele cobra:

- buffers por conexao;
- maquina de estados explicita;
- cuidado com leitura parcial;
- cuidado com escrita parcial;
- nao bloqueante em pontos criticos;
- mais disciplina no desenho.

### 5.1 O que ele compra?

- menos threads;
- menos stacks;
- menor custo de contexto;
- maior controle sobre muitos sockets ociosos.

---

## 6. Conexoes ociosas e conexoes ativas

Essa distincao e central.

Se voce tem:

- poucas conexoes muito ativas;

o quadro e um.

Se voce tem:

- milhares de conexoes mostly idle;

o quadro muda completamente.

### 6.1 `thread-per-connection` sofre mais quando:

- ha muitas conexoes abertas com pouco trafego;
- cada uma segura stack e recurso;
- o SO precisa administrar muitas threads.

### 6.2 Event-driven brilha mais quando:

- muitas conexoes passam longos periodos sem atividade;
- o servidor quer dormir ate readiness;
- a carga e largamente I/O-bound.

---

## 7. Modelo mental de memoria

### 7.1 `thread-per-connection`

Por conexao, voce tende a ter:

- uma thread;
- uma stack;
- buffers da conexao;
- possivel contexto adicional.

### 7.2 Event-driven

Por conexao, voce tende a ter:

- descritor;
- buffers;
- struct de estado;
- nenhuma thread dedicada.

### 7.3 Consequencia

O modelo event-driven desloca custo de:

- pilhas e scheduling;

para:

- estado explicito e complexidade de I/O parcial.

---

## 8. Custo de contexto

- **Context switch**: troca entre threads ou processos em execucao.

### 8.1 Por que isso importa?

Porque cada troca custa:

- estado de registradores;
- scheduling;
- cache perturbado;
- TLB e efeitos indiretos de execucao.

### 8.2 Regra pratica

Se o servidor cria muitas threads para trabalho quase sempre bloqueado, pode acabar pagando:

- bastante custo de organizacao;
- pouco ganho real.

---

## 9. Latencia e previsibilidade

`Thread-per-connection` pode ser agradavel para:

- logica linear por cliente;
- depuracao conceitual;
- servidor pequeno ou medio.

Mas pode perder previsibilidade sob explosao de conexoes.

Event-driven pode ser muito eficiente em escala, mas:

- uma logica mal desenhada no loop central;
- um handler que bloqueia;
- uma etapa de CPU pesada;

pode prejudicar varias conexoes ao mesmo tempo.

### 9.1 Regra essencial

No modelo event-driven:

- nao bloqueie o loop principal sem um plano.

---

## 10. Exemplo conceitual `thread-per-connection`

```c
for (;;) {
    int client_fd = accept(server_fd, NULL, NULL);
    if (client_fd < 0) {
        continue;
    }

    pthread_t tid;
    pthread_create(&tid, NULL, worker, (void *)(intptr_t)client_fd);
    pthread_detach(tid);
}
```

### 10.1 O que esse esqueleto compra?

- simplicidade de fluxo por conexao;
- codigo de leitura/escrita quase linear;
- facilidade inicial de raciocinio.

### 10.2 O que ele esconde?

- custo de thread;
- custo de stack;
- sincronizacao futura;
- escalabilidade limitada.

---

## 11. Exemplo conceitual event-driven

```c
for (;;) {
    int n = poll(fds, nfds, -1);
    if (n < 0) {
        continue;
    }

    for (int i = 0; i < nfds; i++) {
        if (fds[i].revents & POLLIN) {
            /* aceitar conexao ou ler do cliente */
        }
    }
}
```

### 11.1 O que esse esqueleto compra?

- um loop para muitos descritores;
- menos threads;
- melhor controle do conjunto de conexoes.

### 11.2 O que ele esconde?

- estado por conexao;
- necessidade de buffers;
- partial I/O;
- fairness e backpressure.

---

## 12. Exemplo completo da aula

Comparacao didatica de estruturas de estado:

```c
typedef struct {
    int client_fd;
    char buffer[1024];
} ThreadClientContext;

typedef struct {
    int client_fd;
    char in_buffer[1024];
    size_t in_len;
    char out_buffer[1024];
    size_t out_len;
    int closed;
} EventClientState;
```

### 12.1 Leitura do modelo

No desenho `thread-per-connection`:

- o fluxo da thread carrega boa parte do estado implicitamente na stack e na sequencia linear do codigo.

No desenho event-driven:

- o estado precisa ser mais explicito na heap ou em estruturas geridas pelo loop.

### 12.2 O ponto central

Event-driven frequentemente reduz custo operacional de threads, mas aumenta custo de modelagem do estado.

---

## 13. Quando escolher `thread-per-connection`

Escolha com boa consciencia quando:

- numero de conexoes simultaneas e baixo ou moderado;
- simplicidade do time importa muito;
- logica por cliente e relativamente pesada e isolada;
- ambiente e pequeno o suficiente para o custo por thread ser aceitavel;
- velocidade de desenvolvimento vale mais do que escala extrema.

### 13.1 Casos tipicos

- servidor interno pequeno;
- ferramenta de rede especializada;
- prototipo tecnico;
- sistema com poucos clientes simultaneos.

---

## 14. Quando escolher event-driven

Escolha com boa consciencia quando:

- ha muitas conexoes concorrentes;
- muitas delas ficam ociosas grande parte do tempo;
- o custo de thread por conexao ficaria alto demais;
- a carga e fortemente I/O-bound;
- o time consegue lidar com maior complexidade do estado.

### 14.1 Casos tipicos

- proxy;
- gateway;
- broker;
- servidor com muitas conexoes long-lived;
- frontend TCP com alta cardinalidade de clientes.

---

## 15. Modelo hibrido

Na pratica, muito sistema real acaba hibrido.

Exemplo:

- event loop para rede;
- pool de threads para etapas de CPU ou blocos isolados;
- filas para transferir trabalho.

### 15.1 Por que isso faz sentido?

Porque rede e CPU nem sempre pedem o mesmo modelo.

Essa combinacao evita dois extremos:

- thread demais para tudo;
- loop unico fazendo trabalho pesado demais.

---

## 16. O que acontece em memoria e no SO?

No modelo `thread-per-connection`:

- o kernel agenda muitas threads;
- cada thread tem stack separada;
- o processo acumula mais contexto de execucao.

No modelo event-driven:

- menos threads ficam vivas;
- o kernel sinaliza readiness de descritores;
- o processo administra mais estado explicito por conexao.

O trade-off honesto e:

- menos stack e menos contexto;
- mais complexidade de maquina de estados.

---

## 17. Comandos exatos

Exemplo `thread-per-connection` com pthreads:

```bash
gcc -Wall -Wextra -Wpedantic -O0 -g servidor_threads.c -o servidor_threads -pthread
```

Exemplo event-driven com `poll`:

```bash
gcc -Wall -Wextra -Wpedantic -O0 -g servidor_event_loop.c -o servidor_event_loop
```

Em Linux, para investigar custo de CPU:

```bash
perf record ./servidor_event_loop
perf report
```

### 17.1 O que comparar?

- memoria total;
- numero de threads;
- throughput;
- latencia;
- facilidade de depuracao;
- comportamento sob muitas conexoes ociosas.

---

## 18. Comparacao com C++, Rust, Go e Python

- Em C++, frameworks e abstracoes ajudam, mas o dilema fisico entre threads e event loop continua o mesmo.
- Em Rust, runtimes async empurram muito sistema para modelo parecido com event-driven, com mais ajuda do compilador.
- Em Go, goroutines reduzem brutalmente o custo conceitual de "uma unidade de execucao por conexao", mudando o trade-off.
- Em Python, `asyncio` e threads tambem refletem o mesmo dilema, mas dentro de outro runtime.

Em C, esse trade-off aparece quase cru:

- o que voce economiza em threads, paga em estado explicito;
- o que voce economiza em complexidade, paga em memoria e scheduling.

---

## 19. Erros Comuns e Anti-Padroes

1. **Achar que event-driven e sempre superior por definicao**.
2. **Achar que `thread-per-connection` e sempre inviavel**.
3. **Ignorar custo de stack e contexto sob muitas conexoes**.
4. **Bloquear o loop de eventos com tarefa lenta ou CPU-bound**.
5. **Nao modelar buffers e estado por conexao no desenho event-driven**.
6. **Comparar arquiteturas sem considerar padrao de carga real**.

# Aula 18 - Interoperabilidade com C++, Rust e outras linguagens

---

## Nesta aula

Você vai aprender a expor uma funcao C com tipos simples e chama-la de outra linguagem (ou simular a chamada); explicar quem aloca e quem libera em cada direcao da fronteira; e justificar tipos opacos e codigos de erro em vez de excecao/retorno rico.


---

## 1. Ponte com a aula anterior

Na aula 17, vimos custo fisico de desempenho.

Agora vamos olhar para outra razao pela qual C continua central:

- interoperabilidade.

Muitas linguagens conseguem conversar entre si usando C como contrato comum.

---

## 2. O que e FFI?

- **FFI (Foreign Function Interface)**: mecanismo que permite a uma linguagem chamar codigo escrito em outra linguagem.

### 2.1 Por que C aparece tanto nisso?

Porque:

- ABI de C e relativamente simples;
- convencoes de chamada sao amplamente suportadas;
- praticamente todo ecossistema nativo sabe falar com C;
- headers e simbolos C servem como fronteira comum.

---

## 3. Por que "compatibilidade com C" nao e detalhe

Se voce quer que outro ambiente chame seu codigo, precisa estabilizar:

- assinatura;
- tipos;
- layout;
- ownership;
- forma de erro;
- convencao de alocacao e liberacao.

Sem isso, a integracao quebra.

---

## 4. Interoperando com C++

O problema imediato em C++ nao e apenas sintaxe.

E tambem:

- name mangling;
- excecoes;
- sobrecarga;
- classes e vtables;
- templates.

### 4.1 Solucao comum

Expor fronteira C:

```cpp
extern "C" int soma(int a, int b);
```

### 4.2 O que `extern "C"` faz?

Pede ABI e naming compativeis com C naquela fronteira.

---

## 5. Interoperando com Rust

Em Rust, fronteira comum:

```rust
#[no_mangle]
pub extern "C" fn soma(a: i32, b: i32) -> i32 {
    a + b
}
```

### 5.1 O que isso comunica?

- sem name mangling Rust;
- convencao de chamada C;
- assinatura simples para o mundo externo.

### 5.2 O grande ponto

Rust continua seguro por dentro, mas na fronteira FFI voce precisa pensar como engenheiro de ABI.

---

## 6. Layout de tipos compartilhados

Tipos bons para fronteira C:

- inteiros de largura conhecida;
- ponteiros opacos;
- `structs` simples bem documentadas;
- buffers com tamanho explicito.

Tipos ruins para expor sem cuidado:

- layout dependente de compilador;
- ownership ambiguo;
- `struct` complexa que vai evoluir toda hora;
- tipos que carregam alocadores ou invariantes ocultas.

### 6.1 Regra pratica

Na fronteira binaria, prefira contratos pequenos, chatos e estaveis.

---

## 7. Ownership na fronteira

Perguntas obrigatorias:

- quem aloca?
- quem libera?
- qual funcao libera?
- em qual lado do FFI a memoria nasceu?

### 7.1 Regra fortissima

Se um lado aloca, o melhor desenho muitas vezes e:

- esse mesmo lado fornecer a rotina de destruicao.

Misturar allocators e um caminho classico para desastre.

---

## 8. Strings na fronteira

String e caso classico de problema.

Em C, o mundo espera algo como:

- `char *`
- `const char *`

mas isso nao carrega:

- ownership;
- tamanho;
- encoding;
- lifetime.

### 8.1 Desenhos melhores

- buffer + tamanho;
- ponteiro opaco;
- API com copia controlada;
- funcao de destruicao explicita.

---

## 9. Callbacks entre linguagens

Callbacks sao possiveis, mas perigosos.

Porque entram em jogo:

- lifetime;
- thread;
- panics ou excecoes atravessando fronteira;
- contexto do callback;
- userdata opaco.

### 9.1 Desenho classico

```c
typedef void (*Callback)(int evento, void *userdata);
```

Isso costuma ser mais robusto do que tentar passar contexto escondido.

---

## 10. Exemplo completo da aula

Header C pensado para interoperabilidade:

```c
#ifndef API_H
#define API_H

#include <stddef.h>

typedef struct Calculadora Calculadora;

Calculadora *calculadora_create(void);
void calculadora_destroy(Calculadora *c);

int calculadora_soma(Calculadora *c, int a, int b);
int calculadora_ultimo_resultado(Calculadora *c, int *out);

#endif
```

Implementacao C:

```c
#include <stdlib.h>
#include "api.h"

struct Calculadora {
    int ultimo;
};

Calculadora *calculadora_create(void) {
    Calculadora *c = malloc(sizeof(*c));
    if (c == NULL) {
        return NULL;
    }
    c->ultimo = 0;
    return c;
}

void calculadora_destroy(Calculadora *c) {
    free(c);
}

int calculadora_soma(Calculadora *c, int a, int b) {
    if (c == NULL) {
        return 0;
    }
    c->ultimo = a + b;
    return 1;
}

int calculadora_ultimo_resultado(Calculadora *c, int *out) {
    if (c == NULL || out == NULL) {
        return 0;
    }
    *out = c->ultimo;
    return 1;
}
```

### 10.1 Por que esse desenho e bom para FFI?

- usa ponteiro opaco;
- centraliza ownership;
- expoe poucos tipos;
- nao forca layout interno para o consumidor;
- nao depende de excecao nem template nem generics de outra linguagem.

---

## 11. O que acontece em memoria e no binario?

Conceitualmente:

- o consumidor externo recebe um ponteiro opaco `Calculadora *`;
- o layout real da struct so e conhecido no `.c`;
- o binario exporta simbolos C estaveis;
- a ABI define como parametros e retorno trafegam;
- o contrato de destruicao impede que o lado errado tente liberar memoria.

---

## 12. Erros e fronteira

Nao atravesse FFI com:

- excecao C++;
- `panic` Rust sem criterio;
- ponteiro para objeto temporario;
- referencia para buffer ja morto;
- erro sem convencao clara.

### 12.1 Desenhos classicos de erro

- retorno inteiro `0/1` + parametro de saida;
- codigo de erro enumerado;
- callback de log/erro;
- buffer de erro controlado pelo chamador.

---

## 13. Comandos exatos

Compilar biblioteca objeto:

```bash
gcc -Wall -Wextra -Wpedantic -O0 -g -c api.c -o api.o
```

Gerar biblioteca estatica:

```bash
ar rcs libapi.a api.o
```

Consumir de outro programa C:

```bash
gcc -Wall -Wextra -Wpedantic -O0 -g main.c libapi.a -o app
```

### 13.1 Observacao

Os detalhes exatos de integracao com C++, Rust, Python, Zig, C# ou outra linguagem dependem do ecossistema, mas o contrato base continua sendo:

- ABI;
- ownership;
- tipos simples;
- fronteira pequena.

---

## 14. Comparacao com C++, Rust, Go e Python

- Em C++, muitas vezes a melhor forma de expor biblioteca para o mundo externo e justamente fornecer uma facade C.
- Em Rust, `extern "C"` e tipos `repr(C)` aparecem como ponte para o mundo nativo.
- Em Go, `cgo` depende justamente dessa fronteira C.
- Em Python, extensoes nativas e bindings tambem costumam orbitar APIs C.

O resumo honesto e:

- C continua menos poderosa que varias linguagens modernas em expressividade;
- mas continua fortissima como lingua comum binaria.

---

## 15. Erros Comuns e Anti-Padroes

1. **Expor tipos complexos demais na fronteira**.
2. **Misturar allocators de lados diferentes sem contrato claro**.
3. **Esquecer que string C nao carrega tamanho nem ownership**.
4. **Deixar excecao ou panic atravessar fronteira FFI**.
5. **Assumir ABI estavel sem documentar e versionar**.
6. **Expor layout interno quando ponteiro opaco resolveria melhor**.

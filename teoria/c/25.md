# Aula 25 - Arenas, pools e estrategias customizadas de alocacao

---

## Objetivo da Aula

Entender quando o allocator geral deixa de ser a melhor resposta para um problema em C e como arenas, object pools e estrategias customizadas de alocacao podem reduzir overhead, fragmentacao e custo de gerenciamento. Ao final, voce deve conseguir montar um criterio tecnico para escolher entre `malloc` tradicional e alocacao especializada sem cair em overengineering prematuro.

## 2. Quando `malloc` nao basta?

`malloc` e uma solucao geral.

Isso e uma forca enorme.

Mas ser geral significa tambem:

- atender muitos tamanhos;
- muitos tempos de vida;
- muitos padroes de uso;
- cenarios multithread;
- programas com necessidades muito diferentes.

### 2.1 Sinais de que o allocator geral pode nao ser ideal

- muitas alocacoes pequenas e frequentes;
- objetos com mesmo tamanho repetidos em massa;
- objetos com mesma vida util;
- fragmentacao crescente;
- custo de `malloc`/`free` aparecendo no profiler;
- necessidade de liberar tudo de uma vez.

---

## 3. O que e uma estrategia customizada de alocacao?

- **Estrategia customizada de alocacao**: forma especializada de reservar e liberar memoria adaptada a um padrao especifico do programa.

Isso nao significa necessariamente:

- substituir todo o heap do processo.

Pode significar apenas:

- criar um subsistema local de memoria para certo tipo de objeto;
- reduzir fragmentacao;
- reduzir numero de chamadas ao allocator geral;
- ganhar previsibilidade.

---

## 4. Arena allocator

- **Arena allocator**: estrategia em que o programa reserva um bloco grande e depois distribui partes desse bloco para varios objetos, liberando tudo em lote no final.

### 4.1 Modelo mental

Pense em uma arena como:

- um cursor que avanca dentro de um buffer grande.

Voce faz:

1. aloca a arena;
2. faz varias subalocacoes dentro dela;
3. no fim, libera a arena inteira.

### 4.2 Onde isso brilha?

- parser de requests;
- compiladores;
- AST temporaria;
- processamento por lote;
- workloads em que muitos objetos morrem juntos.

### 4.3 O que ela compra?

- alocacao muito barata;
- quase nenhum `free` individual;
- menos fragmentacao dentro do caso de uso;
- ownership em bloco.

### 4.4 O que ela cobra?

- pouca flexibilidade;
- desperdicio potencial se objetos precisarem viver tempos muito diferentes;
- risco de usar objeto depois de destruir a arena inteira.

---

## 5. Exemplo de arena simples

```c
#include <stddef.h>
#include <stdio.h>
#include <stdlib.h>

typedef struct {
    unsigned char *base;
    size_t used;
    size_t cap;
} Arena;

int arena_init(Arena *a, size_t cap) {
    a->base = malloc(cap);
    if (a->base == NULL) {
        return -1;
    }
    a->used = 0;
    a->cap = cap;
    return 0;
}

void *arena_alloc(Arena *a, size_t size) {
    if (a->used + size > a->cap) {
        return NULL;
    }

    void *ptr = a->base + a->used;
    a->used += size;
    return ptr;
}

void arena_reset(Arena *a) {
    a->used = 0;
}

void arena_destroy(Arena *a) {
    free(a->base);
    a->base = NULL;
    a->used = 0;
    a->cap = 0;
}

int main(void) {
    Arena a;
    if (arena_init(&a, 1024) != 0) {
        fprintf(stderr, "falha ao criar arena\n");
        return 1;
    }

    int *x = arena_alloc(&a, sizeof(*x));
    int *y = arena_alloc(&a, sizeof(*y));

    if (x == NULL || y == NULL) {
        fprintf(stderr, "falha ao alocar na arena\n");
        arena_destroy(&a);
        return 1;
    }

    *x = 10;
    *y = 20;
    printf("x=%d y=%d used=%zu\n", *x, *y, a.used);

    arena_destroy(&a);
    return 0;
}
```

### 5.1 O que esse exemplo ensina?

- subalocacao fica muito simples;
- nao existe `free(x)` e `free(y)` individual;
- a arena inteira define o ownership;
- o custo de alocar dentro dela tende a ser baixo.

### 5.2 O que esse exemplo simplifica demais?

- alinhamento;
- crescimento da arena;
- debugging de lifetime;
- uso concorrente;
- mistura de tamanhos e classes de objeto.

## 6. Pool de objetos

- **Object pool**: estrutura que mantem objetos de mesmo tamanho ou mesma classe prontos para reutilizacao, evitando alocar e liberar no heap geral toda vez.

### 6.1 Modelo mental

Em vez de:

- criar e destruir 100000 objetos iguais no heap;

voce:

- recicla objetos da mesma classe.

### 6.2 Onde isso brilha?

- conexoes;
- buffers fixos;
- nos de lista;
- structs de job;
- eventos de mesmo formato.

### 6.3 O que compra?

- menos `malloc`/`free`;
- menos fragmentacao;
- maior previsibilidade;
- reaproveitamento local.

### 6.4 O que cobra?

- objetos ficam reservados mesmo quando ociosos;
- bugs de reuso sem limpeza adequada;
- risco de pool superdimensionado;
- maior complexidade de bookkeeping.

---

## 7. Exemplo conceitual de pool

```c
typedef struct Node {
    int value;
    struct Node *next;
} Node;

typedef struct {
    Node *free_list;
} NodePool;
```

Fluxo conceitual:

1. pool devolve um `Node` livre;
2. se nao houver, aloca um novo;
3. ao "liberar", o objeto volta para a free list;
4. a memoria continua no pool para futuro reuso.

### 7.1 Diferenca importante para arena

Arena:

- libera tudo junto.

Pool:

- reaproveita objetos individualmente da mesma classe.

---

## 8. Arena vs pool

### 8.1 Arena

Boa quando:

- muitos objetos morrem juntos;
- o fluxo e por fase ou por request;
- reset em lote faz sentido.

### 8.2 Pool

Boa quando:

- muitos objetos iguais entram e saem o tempo todo;
- o programa quer reciclar unidades individuais;
- ha classe de objeto muito frequente.

### 8.3 Regra rapida

Se o criterio dominante e:

- vida util em lote, pense em arena;
- reuso individual de objetos iguais, pense em pool.

---

## 9. Bump allocator

Um caso comum de arena e o:

- **bump allocator**: alocador que apenas avanca um ponteiro.

### 9.1 Por que ele e tao rapido?

Porque a logica de alocacao vira algo parecido com:

- verificar espaco;
- devolver ponteiro atual;
- incrementar cursor.

### 9.2 Por que ele e limitado?

Porque nao sabe:

- liberar objeto individual;
- encaixar blocos arbitrarios;
- reorganizar espaco.

Ele depende muito de:

- reset por fase;
- lifetime agrupado.

---

## 10. Alinhamento em alocadores customizados

Esse ponto e obrigatorio.

Se voce implementa arena ou pool, precisa respeitar alinhamento dos objetos.

Nao basta fazer:

```c
void *ptr = base + used;
```

e assumir que serve para qualquer tipo.

### 10.1 Riscos

- acesso desalinhado;
- UB em algumas arquiteturas;
- desempenho pior;
- bugs sutis.

### 10.2 Consequencia

Allocator customizado exige:

- arredondar offsets;
- respeitar alinhamento do tipo alvo;
- ter modelo claro de layout.

---

## 11. Limpando estado no reuso

Em pools, um erro comum e reciclar objeto sem reset adequado.

Exemplo de risco:

- flags antigas permanecem;
- ponteiros antigos continuam vivos;
- dados sensiveis ficam sobrando;
- lista encadeada reaparece corrompida.

### 11.1 Regra pratica

Ao devolver objeto a um pool, decida explicitamente:

- limpar na devolucao;
- limpar na aquisicao;
- ou manter contrato muito claro de inicializacao posterior.

---

## 12. Ownership fica mais importante, nao menos

Ao introduzir arena ou pool, muita gente acha que ownership fica mais simples automaticamente.

Nem sempre.

Na verdade, ownership muda de forma.

### 12.1 Em arena

Ownership passa a ser:

- "esse objeto pertence a esta fase ou a esta arena".

### 12.2 Em pool

Ownership passa a ser:

- "esse objeto pertence ao pool quando nao esta em uso";
- "e pertence temporariamente ao consumidor enquanto esta alugado".

### 12.3 Consequencia

Voce precisa documentar:

- quem pode devolver;
- quando pode devolver;
- o que invalida um ponteiro;
- se ha reset em lote.

## 13. Exemplo completo da aula: pool simples

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

typedef struct Item {
    int id;
    char name[32];
    struct Item *next;
} Item;

typedef struct {
    Item *free_list;
} ItemPool;

Item *pool_acquire(ItemPool *pool) {
    Item *item;

    if (pool->free_list != NULL) {
        item = pool->free_list;
        pool->free_list = item->next;
    } else {
        item = malloc(sizeof(*item));
        if (item == NULL) {
            return NULL;
        }
    }

    memset(item, 0, sizeof(*item));
    return item;
}

void pool_release(ItemPool *pool, Item *item) {
    item->next = pool->free_list;
    pool->free_list = item;
}

void pool_destroy(ItemPool *pool) {
    Item *cur = pool->free_list;
    while (cur != NULL) {
        Item *next = cur->next;
        free(cur);
        cur = next;
    }
    pool->free_list = NULL;
}

int main(void) {
    ItemPool pool = {0};

    Item *a = pool_acquire(&pool);
    Item *b = pool_acquire(&pool);
    if (a == NULL || b == NULL) {
        fprintf(stderr, "falha ao adquirir itens\n");
        free(a);
        free(b);
        return 1;
    }

    a->id = 1;
    strcpy(a->name, "primeiro");
    b->id = 2;
    strcpy(b->name, "segundo");

    printf("a=%d %s\n", a->id, a->name);
    printf("b=%d %s\n", b->id, b->name);

    pool_release(&pool, a);
    pool_release(&pool, b);

    Item *c = pool_acquire(&pool);
    if (c == NULL) {
        fprintf(stderr, "falha ao readquirir item\n");
        pool_destroy(&pool);
        return 1;
    }

    c->id = 3;
    strcpy(c->name, "reutilizado");
    printf("c=%d %s\n", c->id, c->name);

    pool_release(&pool, c);
    pool_destroy(&pool);
    return 0;
}
```

### 13.1 O que esse exemplo mostra?

- objetos podem ser reciclados;
- `malloc` nao precisa acontecer a cada uso;
- a free list guarda blocos reutilizaveis;
- `memset` ajuda a evitar lixo antigo no reuso.

### 13.2 O que ele nao resolve?

- thread safety;
- limites maximos do pool;
- politicas de crescimento;
- coleta estatistica de uso;
- pools por CPU ou por thread.

## 14. Quando NAO usar estrategia customizada

Nao use arena ou pool so porque parecem sofisticados.

Evite quando:

- o gargalo ainda nao foi medido;
- a taxa de alocacao nao e problema real;
- o padrao de lifetime e irregular demais;
- a equipe ainda nao domina ownership basico;
- a complexidade extra supera o beneficio.

### 14.1 Regra de maturidade

Primeiro:

- codigo correto;
- perfil de uso claro;
- medicao.

Depois:

- especializacao de allocator.

---

## 15. Efeito em depuracao

A customizacao de alocacao muda tambem o debugging.

### 15.1 Possiveis ganhos

- padrao de lifetime mais previsivel;
- menos fragmentacao local;
- menos ruido de milhares de alloc/free.

### 15.2 Possiveis perdas

- bugs fora do padrao esperado ficam mais dificeis;
- ponteiros invalidos podem sobreviver mais tempo de forma enganosa;
- uso apos reset de arena pode ser bem destrutivo;
- ferramentas genericas podem mostrar sintomas menos obvios.

---

## 16. O que acontece em memoria?

### 16.1 Arena

- existe bloco grande base;
- subalocacoes vivem dentro dele;
- nao ha heap separado por objeto visivel ao allocator geral;
- reset descarta todos os objetos de uma vez.

### 16.2 Pool

- existe conjunto de blocos de mesmo tipo;
- parte esta em uso;
- parte fica na free list;
- custo de reuso vira principalmente bookkeeping local.

### 16.3 O ponto central

A customizacao desloca custo de:

- generalidade do allocator;

para:

- disciplina do programador e padrao especifico de uso.

## 18. Comparacao com C++, Rust, Go e Python

- Em C++, PMR, allocators customizados e containers ajudam a integrar estrategias especializadas com RAII e tipos mais ricos.
- Em Rust, arenas e bump allocators aparecem muito em workloads especificos, mas ownership continua exigindo desenho cuidadoso da fronteira de lifetime.
- Em Go, object pooling existe em alguns cenarios, mas sob outra logica de runtime e GC.
- Em Python, esse tipo de controle costuma ficar quase todo escondido no runtime e raramente aparece como ferramenta direta do programador de aplicacao.

Em C, arenas e pools sao ferramentas muito poderosas justamente porque:

- a linguagem quase nao te impede;
- e exatamente por isso pode sair muito certo ou muito errado.

## 19. Erros Comuns e Anti-Padroes

1. **Criar allocator customizado sem medir gargalo real**.
2. **Ignorar alinhamento na arena**.
3. **Reciclar objeto no pool sem limpar estado relevante**.
4. **Misturar objetos com lifetime incompativel na mesma arena**.
5. **Assumir que pool elimina problemas de ownership**.
6. **Introduzir estrategia sofisticada sem documentar contrato de uso**.

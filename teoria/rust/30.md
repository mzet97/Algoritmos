# Aula 30 — Masterpiece A: Construindo um Load Balancer TCP do Zero

## Objetivo da Aula
Bem-vindo ao **Módulo 4: Projetos Práticos (Masterpieces)**!
Nesta aula, não vamos usar *frameworks* de alto nível como o Axum. Vamos usar os conhecimentos que adquirimos de redes, concorrência e chamadas de sistema para construir um **Balanceador de Carga TCP (Load Balancer)** do zero.
Nosso objetivo é criar um serviço extremamente rápido que aceite milhares de conexões de clientes e as redirecione de forma assíncrona (usando `tokio`) para vários servidores de *backend* através do algoritmo *Round-Robin*.

Um **load balancer** existe para distribuir carga entre varios servidores, evitando que um unico backend vire gargalo ou ponto unico de falha.

---

## 1. A Arquitetura do Load Balancer

Um Load Balancer atua como um "proxy reverso".

Um **proxy reverso** e um processo que recebe conexoes em nome dos servidores reais e decide para qual backend encaminhar cada requisicao. Ele existe para centralizar roteamento, observabilidade, TLS, balanceamento e politicas de falha.

O fluxo é:
1. O Cliente (Navegador) conecta na porta `8080` do nosso Load Balancer.
2. Nosso Load Balancer aceita a conexão.
3. O Load Balancer escolhe qual servidor de Backend (ex: `Backend A` na porta `8081` ou `Backend B` na porta `8082`) deve receber a carga.
4. O Load Balancer abre uma *nova* conexão TCP para o Backend escolhido.
5. Ele começa a copiar bytes bidirecionalmente: tudo o que o Cliente envia, vai para o Backend; tudo que o Backend responde, volta para o Cliente.

### O Desafio da Concorrência
Copiar bytes entre dois sockets é uma operação de I/O.

Um **socket** e o endpoint de comunicacao de rede exposto pelo sistema operacional; pense nele como um arquivo especial que envia e recebe bytes pela pilha TCP/IP.

Se fizermos isso de forma síncrona (bloqueante), uma conexão lenta vai travar todo o nosso servidor. Por isso, usaremos o `tokio::net` e o poder do *Event Loop* (epoll/kqueue) para gerenciar o tráfego sem bloquear threads.

Um **event loop** existe para multiplexar milhares de conexoes com poucas threads, acordando trabalho apenas quando o kernel sinaliza que ha algo para ler ou escrever.

### A Lógica do Algoritmo Round-Robin
O *Round-Robin* é um algoritmo simples: se temos 3 servidores, a 1ª requisição vai para o servidor 1, a 2ª para o 2, a 3ª para o 3, e a 4ª volta para o 1. Ele existe porque e a forma mais barata de distribuir carga quando todos os backends sao considerados equivalentes.

Para manter esse índice global de forma segura em concorrência, usaremos um `AtomicUsize`. Um **atômico** e um tipo cujo acesso pode ser atualizado pela CPU de forma indivisivel, sem risco de duas threads sobrescreverem o mesmo contador no meio da operacao.

## 3. O Código Completo (`src/main.rs`)

```rust
use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;
use tokio::io::copy_bidirectional;
use tokio::net::{TcpListener, TcpStream};

// 1. O Estado do nosso Load Balancer
struct BalancerState {
    // Lista de IPs/Portas dos nossos servidores backend
    backends: Vec<String>,
    // O índice atômico para o algoritmo Round-Robin
    current_index: AtomicUsize,
}

impl BalancerState {
    fn new(backends: Vec<String>) -> Self {
        Self {
            backends,
            current_index: AtomicUsize::new(0),
        }
    }

    // Função que decide qual servidor receberá a próxima requisição
    fn get_next_backend(&self) -> String {
        // Incrementa o índice atomicamente (thread-safe, sem Mutex bloqueante!)
        let index = self.current_index.fetch_add(1, Ordering::Relaxed);
        
        // Faz o módulo (%) para voltar a 0 quando chegar no fim da lista
        let selected = index % self.backends.len();
        
        // Clona a string do IP escolhido
        self.backends[selected].clone()
    }
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    // Lista de servidores falsos que nosso Load Balancer vai proteger.
    // (Para testar de verdade, você teria que ter servidores rodando nessas portas).
    let backends = vec![
        "127.0.0.1:8081".to_string(),
        "127.0.0.1:8082".to_string(),
        "127.0.0.1:8083".to_string(),
    ];

    let state = Arc::new(BalancerState::new(backends));

    // Faz o bind do nosso Load Balancer na porta 8080
    let listener = TcpListener::bind("0.0.0.0:8080").await?;
    println!("⚖️ Load Balancer rodando na porta 8080");

    // O Event Loop Principal
    loop {
        // Aceita uma nova conexão do Cliente. Isso NÃO bloqueia o loop inteiro,
        // apenas suspende esta task até um cliente conectar.
        let (mut client_socket, client_addr) = listener.accept().await?;
        println!("Nova conexão de: {}", client_addr);

        // Clona a referência do estado (barato, é um Arc)
        let state_clone = state.clone();

        // 2. Faz o "Spawn" de uma nova Task (Green Thread) para cada cliente.
        // Uma task do Tokio e mais leve que uma thread do SO.
        // Ela existe para termos concorrencia massiva sem custo de milhares de threads nativas.
        // Assim o loop volta instantaneamente a escutar novos clientes.
        tokio::spawn(async move {
            let backend_addr = state_clone.get_next_backend();
            println!("Roteando {} -> {}", client_addr, backend_addr);

            // 3. Conecta no servidor de backend
            match TcpStream::connect(&backend_addr).await {
                Ok(mut backend_socket) => {
                    // 4. A Mágica do Zero-Cost Proxy!
                    // copy_bidirectional é uma função do Tokio altamente otimizada.
                    // Ela cria dois buffers e fica bombeando bytes do Cliente para o Backend
                    // e do Backend para o Cliente simultaneamente.
                    // O await só termina quando um dos dois lados fechar a conexão.
                    match copy_bidirectional(&mut client_socket, &mut backend_socket).await {
                        Ok((bytes_up, bytes_down)) => {
                            println!(
                                "Conexão encerrada. Up: {} bytes, Down: {} bytes",
                                bytes_up, bytes_down
                            );
                        }
                        Err(e) => eprintln!("Erro ao copiar dados: {}", e),
                    }
                }
                Err(e) => {
                    eprintln!("O Backend {} está fora do ar! Erro: {}", backend_addr, e);
                    // Opcional: Se o backend caiu, você poderia mandar um erro HTTP 502
                    // para o client_socket aqui.
                }
            }
        });
    }
}
```

## 5. Arquitetura Avançada (A Fronteira do Splice)

A função `copy_bidirectional` do Tokio é excelente e segura, mas ela copia os bytes do socket do cliente para a memória do User Space do nosso programa Rust, e depois escreve esses bytes no socket do backend.

**Como o NGINX faz?**
Balanceadores de carga *hardcore* no Linux usam uma syscall chamada **`splice`** (ou o mais novo `io_uring`). O `splice` conecta o socket de entrada diretamente no socket de saída *dentro do Kernel Space*.

Os bytes trafegam pela rede e vão para o backend sem nunca passar pela memória do seu programa Rust. Isso se aproxima do ideal de **zero-copy**, ou seja, mover dados sem replicas desnecessarias entre buffers de user space.

Isso economiza cópias de memória e uso brutal de CPU, permitindo atingir limites teóricos do hardware (como a Cloudflare faz no seu projeto *Pingora*).

O Tokio tem suporte experimental para zero-copy via `splice`, que pode ser investigado na documentação avançada de redes do ecossistema.

## Erros Comuns e Anti-Padrões

1.  **Vazamento de File Descriptors (FD Exhaustion):** No Linux, tudo é um arquivo. Cada socket aberto gasta um FD. Um **file descriptor** e o identificador inteiro que o kernel usa para rastrear recursos abertos do processo.

    Se um cliente abrir conexão e não mandar nenhum dado (Slowloris attack), nosso `copy_bidirectional` ficará preso para sempre. **Slowloris** e um ataque em que o cliente mantem muitas conexoes abertas e lentas para esgotar recursos do servidor.

    Se 65.000 clientes fizerem isso, o SO negará novas conexões ("Too many open files"). A solução é sempre usar `tokio::time::timeout` ao redor de operações de I/O de rede.
2.  **Usar `Mutex` em vez de `AtomicUsize` para o índice:** Já discutimos isso, mas vale repetir. Bloquear um Mutex para calcular `index % tamanho` criaria um gargalo terrível onde apenas uma task poderia rotear pacotes por vez.

Se falhar, ela deve marcar o servidor como "morto" no `BalancerState` para que a função `get_next_backend` pule os servidores mortos.

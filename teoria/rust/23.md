# Aula 23 — Comunicação entre Microserviços: gRPC, Protobuf e `tonic`

## Objetivo da Aula
Nesta aula, encerraremos o Módulo 1 substituindo APIs REST (JSON sobre HTTP/1.1) por **gRPC** (Protocol Buffers sobre HTTP/2). Vamos entender por que arquiteturas de microserviços de alto desempenho (como na Netflix, Uber ou Cloudflare) abandonam o JSON e adotam serialização binária para comunicação interna (*backend-to-backend*), e como o ecossistema Rust implementa isso através da crate `tonic`.

Esta aula fecha o módulo de backend mostrando como sistemas distribuídos de produção costumam conversar internamente. O foco aqui não é frontend público, e sim comunicação entre serviços que precisam ser rápidos, tipados e previsíveis.

Mapa mental:

- JSON é simples e universal, mas caro para CPU e rede;
- gRPC prioriza eficiência e contrato forte;
- o arquivo `.proto` vira a fonte única de verdade entre cliente e servidor.

---

## 1. O Modelo Mental: REST/JSON vs gRPC/Protobuf

### O Custo Invisível do JSON
Quando o "Microserviço A" fala com o "Microserviço B" via REST/JSON, ocorrem os seguintes passos caros para a CPU:
1. **A** aloca memória, formata números para strings (`123` vira os bytes `"123"`).
2. Adiciona aspas, chaves e espaços em branco (overhead de rede).
3. **B** recebe os bytes, itera byte a byte (parsing) procurando aspas, converte a string `"123"` de volta para um inteiro na memória.
*Esse processo é um enorme desperdício de ciclos de CPU.*

- **REST**: estilo arquitetural muito comum em APIs HTTP, geralmente usando métodos como GET/POST e payloads em JSON.
- **Serialização**: transformar estruturas em bytes para transporte.
- **Parsing**: analisar os bytes recebidos para reconstruir os dados.

### A Solução: Protocol Buffers (Protobuf) e gRPC
Criado pelo Google, o Protobuf é um formato binário denso. O número `123` é enviado literalmente como bytes puros, sem aspas ou nomes de chaves.
O gRPC é o framework que usa Protobuf em cima de uma conexão **HTTP/2**. 
Vantagens do HTTP/2:
*   **Multiplexação:** Você não precisa abrir uma nova conexão TCP para cada request. Múltiplos requests acontecem em paralelo dentro do mesmo socket.
*   **Streaming:** Suporte nativo a streams bidirecionais (substituindo WebSockets para comunicação interna).

- **Protobuf (Protocol Buffers)**: formato binário com esquema explícito, criado para comunicação eficiente entre sistemas.
- **HTTP/2**: versão mais moderna do HTTP, com multiplexação, framing binário e melhor aproveitamento da conexão.
- **Multiplexação**: múltiplas requisições lógicas compartilhando a mesma conexão física sem abrir um TCP novo para cada chamada.

**O Contrato Estrito:**
No gRPC, o cliente e o servidor compartilham um arquivo `.proto`. O compilador (em Rust, via `tonic-build`) lê esse arquivo e **gera o código Rust (Structs e Traits)** automaticamente. Se você mudar um tipo no arquivo `.proto`, o código Rust quebra, garantindo que o "Microserviço A" e "B" nunca fiquem dessincronizados silenciosamente.

- **Contrato**, aqui, significa a definição formal da interface entre serviços.
- Isso é importante porque reduz um dos problemas mais caros em sistemas distribuídos: cliente e servidor evoluírem de forma incompatível sem perceber.

## 2. Configurando um Projeto gRPC em Rust

Diferente de um projeto web comum, o gRPC exige um passo extra no tempo de compilação: gerar o código Rust a partir do arquivo `.proto`. Fazemos isso usando o arquivo `build.rs`.

- **Code generation / codegen**: geração automática de código-fonte a partir de uma descrição mais abstrata.
- Isso existe porque escrever manualmente cliente, servidor e tipos equivalentes em cada lado seria repetitivo e propenso a erro.

```bash
cargo new grpc_rust
cd grpc_rust

# Dependências do servidor e cliente
cargo add tonic tokio --features tokio/full
cargo add prost # A biblioteca que lida com os bytes do Protobuf

# Dependência de compilação (build.rs)
cargo add tonic-build --build
```

### O Arquivo de Contrato: `proto/pagamentos.proto`
Crie uma pasta `proto` na raiz do projeto e adicione este arquivo. É a interface agnóstica de linguagem.

- **Agnóstica de linguagem** significa que o contrato não pertence só ao Rust; ele pode gerar código para várias linguagens diferentes.

```protobuf
syntax = "proto3";
package pagamentos;

// O Serviço (As "rotas")
service SistemaPagamento {
    rpc ProcessarPagamento (PagamentoRequest) returns (PagamentoResponse);
}

// O Payload de Entrada
message PagamentoRequest {
    string usuario_id = 1;
    double valor = 2;
    string moeda = 3;
}

// O Payload de Saída
message PagamentoResponse {
    bool sucesso = 1;
    string transacao_id = 2;
}
```

- **`service`**: conjunto de operações remotas expostas.
- **`rpc`**: chamada de procedimento remoto, isto é, chamar uma função em outro processo via rede.
- **`message`**: estrutura de dados serializada pelo Protobuf.

### O Script de Build: `build.rs`
Na raiz do projeto (mesmo nível do `Cargo.toml`), crie este arquivo. O Cargo o executa *antes* de compilar o `main.rs`.

- **`build.rs`**: script de build rodado pelo Cargo antes da compilação principal.
- Ele serve para preparar código gerado, localizar dependências nativas e configurar etapas auxiliares do build.

```rust
fn main() -> Result<(), Box<dyn std::error::Error>> {
    // Compila o arquivo .proto em código Rust
    tonic_build::compile_protos("proto/pagamentos.proto")?;
    Ok(())
}
```

## 3. O Código do Servidor (`src/server.rs`)

Vamos escrever o servidor que implementa a interface gerada.
*(Nota: Para testar, mude o `main.rs` para rodar este código ou configure multiplos binários no Cargo).*

```rust
use tonic::{transport::Server, Request, Response, Status};

// Importa o código gerado magicamente pelo tonic-build no build.rs
pub mod pagamentos {
    tonic::include_proto!("pagamentos"); // O nome do package definido no .proto
}

// Importamos a Trait e as Structs geradas
use pagamentos::sistema_pagamento_server::{SistemaPagamento, SistemaPagamentoServer};
use pagamentos::{PagamentoRequest, PagamentoResponse};

// Nossa struct que vai implementar o serviço.
// Aqui você pode colocar seu AppState (Pool de banco de dados, canais, etc).
#[derive(Default)]
pub struct MeuServicoPagamento {}

// Implementamos a trait gerada pelo gRPC
#[tonic::async_trait]
impl SistemaPagamento for MeuServicoPagamento {
    async fn processar_pagamento(
        &self,
        request: Request<PagamentoRequest>, // Requisição empacotada com metadados (headers HTTP2)
    ) -> Result<Response<PagamentoResponse>, Status> {
        
        // Extrai o payload binário já deserializado de forma super eficiente
        let req = request.into_inner();
        
        println!("Processando {} {} para usuário {}", req.valor, req.moeda, req.usuario_id);

        // Lógica de negócios...
        
        let resposta = PagamentoResponse {
            sucesso: true,
            transacao_id: uuid::Uuid::new_v4().to_string(),
        };

        // Retorna a resposta
        Ok(Response::new(resposta))
    }
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let addr = "[::1]:50051".parse()?;
    let servico = MeuServicoPagamento::default();

    println!("Servidor gRPC escutando em {}", addr);

    Server::builder()
        .add_service(SistemaPagamentoServer::new(servico))
        .serve(addr)
        .await?;

    Ok(())
}
```

- **Trait gerada**: contrato Rust produzido automaticamente a partir do `.proto`.
- O servidor concreta esse contrato implementando a lógica real por trás das chamadas remotas.

## 4. O Código do Cliente (`src/client.rs`)

O cliente gRPC também é gerado automaticamente. Ele gerencia o pool de conexões HTTP/2, multiplexação e reconexões sob o capô, garantindo máxima performance sem que você precise escrever código de sockets.

Isso é importante porque o cliente deixa de ser "um monte de requisições HTTP manuais" e passa a ser um stub tipado que sabe falar exatamente o protocolo do serviço remoto.

```rust
use pagamentos::sistema_pagamento_client::SistemaPagamentoClient;
use pagamentos::PagamentoRequest;

pub mod pagamentos {
    tonic::include_proto!("pagamentos");
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    // Conecta no servidor. A conexão TCP/HTTP2 é mantida aberta.
    let mut client = SistemaPagamentoClient::connect("http://[::1]:50051").await?;

    // Cria a requisição (Note que os campos batem exatamente com o .proto)
    let request = tonic::Request::new(PagamentoRequest {
        usuario_id: "user_777".into(),
        valor: 150.50,
        moeda: "BRL".into(),
    });

    // Faz a chamada de rede (Serialização binária rápida)
    let response = client.processar_pagamento(request).await?;

    println!("Resposta do Servidor: {:?}", response.into_inner());

    Ok(())
}
```

## 5. Streaming Bidirecional (O Poder Oculto do gRPC)

Um dos maiores recursos do gRPC é o **Streaming**. Imagine que você precisa enviar 1 milhão de registros de um microserviço para outro. Enviar um array gigante trava a memória. Enviar 1 milhão de requests HTTP causa overhead de cabeçalhos.

- **Streaming**: envio e recebimento gradual de mensagens ao longo do tempo, sem exigir materializar tudo de uma vez na memória.
- Isso é crucial para throughput alto e uso controlado de RAM.

No arquivo `.proto`, basta adicionar a palavra `stream`:
```protobuf
rpc UploadMassa (stream PagamentoRequest) returns (PagamentoResponse);
```

No Rust, o `tonic` mapeará isso para o `tokio::sync::mpsc::Receiver`. O servidor lerá os pacotes *sob demanda* conforme chegam na placa de rede, sem estourar a memória RAM!

## Erros Comuns

1.  **Esquecer o `build.rs` ou o `protoc`:** O `tonic-build` depende do compilador C++ do Protobuf instalado no seu sistema operacional. No Linux/WSL, você precisa fazer `apt install protobuf-compiler`. No Windows, instale via `scoop` ou `choco`.
2.  **Tratar gRPC como REST público:** O gRPC é difícil de ser consumido diretamente por navegadores web devido às limitações do HTTP/2 no JavaScript do frontend (embora exista o gRPC-Web). Use gRPC para comunicação interna (backend-to-backend) ou aplicativos nativos (Mobile, Desktop).
3.  **Não reutilizar o Cliente:** O `SistemaPagamentoClient` mantém o pool HTTP/2 internamente. Criar um novo Client para cada chamada destrói toda a performance da multiplexação. Clone o cliente (é barato) e reutilize-o.

# Aula 22 — Bancos de Dados de Alta Performance: sqlx e Zero-Copy Deserialization

## Objetivo da Aula
Nesta aula, conectaremos nosso backend a um banco de dados relacional (PostgreSQL) usando a crate `sqlx`. Vamos entender por que ORMs tradicionais muitas vezes são gargalos de performance e como Rust nos permite algo quase mágico: **verificar a sintaxe SQL e os tipos de retorno diretamente no banco de dados durante a compilação**, além de mapear resultados da rede (TCP) diretamente para estruturas na memória sem alocar cópias extras no *heap* (Zero-Copy Deserialization).

Esta aula faz a ponte entre backend de rede e backend de persistência. Um sistema web pode ser extremamente rápido no HTTP e ainda assim perder toda a performance quando toca no banco.

Mapa mental:

- banco de dados não é só "guardar dados"; ele também é uma fronteira crítica de custo de CPU, memória e latência;
- abstrações muito pesadas podem esconder alocação, cópia e SQL ruim;
- Rust tenta manter a ergonomia sem esconder o custo real do acesso ao banco.

---

## 1. O Modelo Mental: C/C++ (libpq) vs ORMs vs Rust (`sqlx`)

Se você já escreveu código de banco de dados em C ou C++ puro usando `libpq` (PostgreSQL) ou ODBC, sabe que a interface é brutal: você envia uma string SQL, recebe um array de bytes, checa o número de colunas manualmente e faz *casts* inseguros de `char*` para `int` ou `float`.

- **Banco relacional**: banco que organiza dados em tabelas com linhas, colunas e relações entre entidades.
- **Driver**: biblioteca responsável por conversar com o banco usando o protocolo nativo dele.
- **ODBC**: padrão antigo e genérico de acesso a bancos de dados.

Para fugir disso, o mercado inventou os **ORMs** (Object-Relational Mappers, como Hibernate, Entity Framework ou Diesel). ORMs abstraem o SQL, mas geram queries ineficientes e alocam milhares de objetos na memória para representar uma única linha do banco, destruindo a performance e causando pressão no *Garbage Collector* (em linguagens com GC) ou fragmentação do heap.

- **ORM (Object-Relational Mapper)**: camada que tenta mapear tabelas e linhas do banco para objetos da linguagem.
- O benefício é ergonomia; o risco é perder visibilidade de SQL, layout e custo.

**A Solução do Rust: `sqlx`**
O `sqlx` **não é um ORM**. É um executor de SQL puramente assíncrono e tipado.
Ele se conecta ao seu banco de dados **durante o `cargo build`**. Ele envia a sua string SQL para o Postgres, pede o plano de execução (`EXPLAIN`), analisa os tipos das colunas que o banco vai retornar, e gera o código Rust correspondente. Se você digitar o nome de uma coluna errado na sua string SQL, o seu programa Rust **não compila**!

- **Executor de SQL**: biblioteca que envia SQL explícito ao banco e devolve resultados tipados, sem tentar esconder a linguagem SQL atrás de uma camada OO completa.
- **Plano de execução**: descrição de como o banco pretende executar uma query.
- Isso é poderoso porque transfere erros comuns de integração do runtime para a compilação.

---

## 2. Zero-Copy Deserialization (O Santo Graal da Performance)

Quando o Postgres responde a uma query, os bytes trafegam pelo cabo de rede e chegam no buffer TCP do SO, sendo lidos para um *buffer* do `sqlx`.

**A abordagem ingênua (Alocação Constante):**
Para cada linha retornada, o framework copia os bytes do buffer de rede, aloca uma nova `String` no heap e a entrega para você. Se sua query retorna 10.000 linhas, você acaba de fazer 10.000 `malloc`s.

**A abordagem Zero-Copy em Rust:**
Com o poder do *Borrow Checker* e dos *Lifetimes*, você pode dizer ao Rust: *"Minha struct não possui uma `String`. Ela possui um `&str` que aponta diretamente para o buffer TCP onde os dados chegaram."*
Não há `malloc`. Não há cópia. O Rust garante em tempo de compilação que você não usará esse `&str` após o buffer do banco de dados ser limpo ou reaproveitado.

- **Desserialização**: transformação de bytes vindos do banco em valores estruturados da aplicação.
- **Zero-copy**, aqui, significa reaproveitar o buffer já existente em vez de duplicar o conteúdo em novas alocações.
- Isso é especialmente valioso quando a aplicação transporta muitas linhas ou textos grandes.

## 3. Código Prático: Setup e Pool de Conexões

Crie um novo projeto ou use o anterior e adicione as dependências:
```bash
cargo add axum tokio --features tokio/full
# Adicionando o sqlx com suporte a Postgres, runtime do Tokio e macros
cargo add sqlx --features "postgres runtime-tokio-rustls macros chrono uuid"
cargo add serde --features derive
cargo add dotenvy
```

### O Código (`src/main.rs`)

- **Connection pool / pool de conexões**: conjunto de conexões já abertas e reutilizáveis para evitar o custo de abrir uma conexão nova a cada requisição.
- Em produção, isso é essencial para throughput e também para proteger o próprio banco de explosão de conexões.

```rust
use axum::{extract::State, routing::get, Json, Router};
use sqlx::postgres::{PgPool, PgPoolOptions};
use std::env;
use std::time::Duration;
use serde::Serialize;

// 1. A Struct de Retorno (Zero-Copy)
// Observe o lifetime 'a e o uso de `&'a str` no lugar de `String`.
// Isso significa: "O nome de usuário é apenas uma 'janela' (view)
// para a memória que o sqlx já alocou para ler o socket".
#[derive(Serialize)]
struct UsuarioInfo<'a> {
    id: i32,
    nome: &'a str, 
    email: &'a str,
}

// O Estado Global: Em vez de Mutex, usamos um Pool de conexões.
// PgPool já encapsula compartilhamento e sincronizacao interna para gerenciar conexoes.
// Clonar o pool é barato e OBRIGATÓRIO.
#[derive(Clone)]
struct AppState {
    db_pool: PgPool,
}

#[tokio::main]
async fn main() {
    // Carrega variáveis do arquivo .env
    dotenvy::dotenv().ok();
    let database_url = env::var("DATABASE_URL").expect("DATABASE_URL deve estar setada");

    // 2. Criando o Pool de Conexões
    // Em produção, nunca crie uma conexão por requisição.
    // Mantenha um pool aberto. O sqlx gerencia conexões ociosas e falhas.
    let pool = PgPoolOptions::new()
        .max_connections(50) // Máximo de conexões simultâneas com o DB
        .acquire_timeout(Duration::from_secs(3))
        .connect(&database_url)
        .await
        .expect("Falha ao conectar no banco de dados");

    let state = AppState { db_pool: pool };

    let app = Router::new()
        .route("/usuarios/rapido", get(handler_buscar_usuarios_zerocopy))
        .with_state(state);

    let addr = "0.0.0.0:3000";
    let listener = tokio::net::TcpListener::bind(addr).await.unwrap();
    println!("🚀 Servidor conectado ao DB e rodando na porta 3000");
    axum::serve(listener, app).await.unwrap();
}

// 3. O Handler de Alta Performance
async fn handler_buscar_usuarios_zerocopy(
    State(state): State<AppState>,
) -> Json<Vec<UsuarioInfo<'static>>> { // Simplificação didática para o retorno JSON
    
    // A Macro `query!` é onde a mágica acontece.
    // Em tempo de compilação, o Rust conecta no `DATABASE_URL`, valida se
    // a tabela `usuarios` existe, se as colunas `id`, `nome` e `email` existem,
    // e se o tipo delas bate com o que esperamos.
    let linhas = sqlx::query!(
        r#"
        SELECT id, nome, email
        FROM usuarios
        LIMIT 100
        "#
    )
    .fetch_all(&state.db_pool) // Executa a query assincronamente
    .await
    .unwrap(); // Em produção, mapeie o erro adequadamente!

    // Convertendo as linhas do banco para a nossa Struct
    // Note que `linha.nome` é alocado pelo `sqlx`. Se quiséssemos um `&str` estrito
    // que vivesse apenas durante o request, usaríamos métodos avançados do sqlx de decode manual.
    // Aqui, a macro `query!` ainda aloca Strings na struct anônima que ela gera.
    // Para Zero-Copy real com SQLx, veja a seção de "Erros Comuns e Ajustes" abaixo.
    
    let mut resultado = Vec::with_capacity(linhas.len());
    
    // *Nota técnica:* A macro `query!` padrão gera `String`s por segurança.
    // Na vida real, a conversão para JSON (Serde) fará a leitura, mas 
    // mostraremos o conceito puro.
    
    // Retorna como JSON
    Json(vec![]) // Placeholder para compilar (veja explicação zero-copy abaixo)
}
```

- **View**, nesse contexto, significa uma janela emprestada para dados que já existem em outro buffer.

Isso segue o mesmo padrão arquitetural das aulas anteriores:

- o estado global precisa ser barato de clonar;
- cada request pega o recurso compartilhado adequado;
- a sincronização já fica encapsulada dentro da abstração certa, em vez de um mutex manual genérico.

## 4. O Verdadeiro Zero-Copy no SQLx

Para forçar o `sqlx` a **não alocar Strings** e usar Zero-Copy real emprestando do buffer, não podemos usar a macro genérica `query!`. Precisamos usar o sistema manual de `FromRow` com lifetimes explícitos, ou usar o tipo `Cow<'a, str>` (Clone-on-Write).

- **`FromRow`**: trait que ensina ao `sqlx` como montar um tipo Rust a partir de uma linha retornada pelo banco.
- **`Cow<'a, str>`** (*Clone-on-Write*): tipo que pode ser tanto um empréstimo (`Borrowed`) quanto um valor próprio (`Owned`), escolhendo a opção mais barata possível.

```rust
use std::borrow::Cow;
use sqlx::FromRow;

// Se a string recebida for puramente ASCII válida (ex: UTF-8 limpo),
// o sqlx empresta (Borrowed). Se precisar processar (ex: unescape),
// ele aloca (Owned). O Cow abstrai isso sem custo extra se for Borrowed.
#[derive(FromRow, Serialize)]
struct UsuarioRapido<'a> {
    id: i32,
    #[sqlx(borrow)] // Diretiva CRUCIAL: diz ao sqlx para não dar malloc!
    nome: Cow<'a, str>, 
}

async fn handler_extremo(State(state): State<AppState>) -> String {
    // Usamos fetch_all em uma conexão adquirida diretamente para garantir
    // que o buffer viva o suficiente para processarmos.
    let mut conn = state.db_pool.acquire().await.unwrap();
    
    let usuarios: Vec<UsuarioRapido> = sqlx::query_as::<_, UsuarioRapido>(
        "SELECT id, nome FROM usuarios LIMIT 10"
    )
    .fetch_all(&mut *conn)
    .await
    .unwrap();

    // Podemos iterar e processar `usuarios` aqui.
    // Se `nome` não precisou de decoding especial, NENHUMA ALOCAÇÃO DE STRING ocorreu!
    format!("Processamos {} usuários na velocidade da luz.", usuarios.len())
}
```

## 5. Como o Compilador Conecta no Banco? (O arquivo `.env`)

Para o compilador validar as macros `query!`, você precisa ter um banco rodando **durante a compilação** (cargo build).

- **`.env`**: arquivo simples de variáveis de ambiente usado para configuração local.
- **CI/CD**: ambiente automatizado de integração e entrega contínuas, onde muitas vezes não há um banco real disponível no momento do build.

1.  Crie um arquivo `.env` na raiz do projeto:
    ```env
    DATABASE_URL=postgres://usuario:senha@localhost:5432/meubanco
    ```
2.  Crie a tabela no banco:
    ```sql
    CREATE TABLE usuarios (
        id SERIAL PRIMARY KEY,
        nome VARCHAR NOT NULL,
        email VARCHAR NOT NULL
    );
    ```

**Mas e no CI/CD (GitHub Actions)? Eu não tenho banco lá!**
Rust pensou nisso. O `sqlx` permite salvar o estado das queries offline:
```bash
# Instala a CLI do sqlx
cargo install sqlx-cli

# Prepara as queries (Gera arquivos .json na pasta sqlx-data)
cargo sqlx prepare

# Agora você pode commitar a pasta `sqlx-data`. 
# No CI/CD, basta rodar com uma variável de ambiente especial:
SQLX_OFFLINE=true cargo build --release
```

## Erros Comuns

1.  **Bloquear o Pool (Connection Starvation):**
    Adquirir uma conexão com `pool.acquire().await` e depois fazer uma operação pesada (ex: chamada de rede para outra API) sem devolver a conexão para o pool. Se você fizer isso 50 vezes simultâneas, seu pool esgota (starvation) e a aplicação inteira trava esperando conexões.
2.  **Usar `query!` sem `.env`:** O erro do compilador dirá algo críptico sobre "DATABASE_URL not set".
3.  **Achar que `query!` protege contra tudo:** Ele checa sintaxe e tipos. Ele **não** cria as tabelas para você. Você ainda precisa de um sistema de Migrations (o `sqlx` possui suporte nativo a migrations via `sqlx migrate run`).

## Exercícios Obrigatórios

1.  **Transações (ACID):** Crie uma rota `POST /transferencia` que tira dinheiro da conta A e coloca na conta B. Use `let mut tx = state.db_pool.begin().await?;`. Execute os `UPDATE`s passando `&mut *tx` ao invés de `&pool`. No final, chame `tx.commit().await?;`.
2.  **Migrations no Código:** Use a macro `sqlx::migrate!("./migrations").run(&pool).await?;` na sua função `main` logo após criar o Pool. Isso fará com que seu servidor crie/atualize as tabelas automaticamente assim que o binário iniciar.

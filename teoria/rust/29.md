## 1. O Modelo Mental: O que é eBPF?

### O Problema dos Módulos do Kernel (LKM)
Tradicionalmente, se você queria interceptar pacotes de rede na placa de rede *antes* que o Kernel os processasse (para criar um firewall ultra-rápido ou um balanceador de carga), você precisava escrever um Módulo do Kernel em C (LKM). **LKM** significa *Loadable Kernel Module*, ou modulo carregavel do kernel. Ele existe para adicionar funcionalidade ao Linux sem recompilar o kernel inteiro, mas carrega junto todo o risco de rodar C privilegiado em Ring 0.
O problema: se o seu código C tivesse um pequeno erro de ponteiro (Segmentation Fault), **o sistema inteiro entrava em pânico (Kernel Panic)** e a máquina reiniciava.

### A Revolução eBPF
O eBPF (Extended Berkeley Packet Filter) é uma máquina virtual que roda *dentro* do Kernel do Linux.

Maquina virtual aqui nao significa VirtualBox ou QEMU; significa um ambiente controlado de execucao de bytecode, com instrucoes e restricoes proprias, validado pelo kernel antes de aceitar o programa.

Você escreve um programa, compila para o "assembly" do eBPF (bytecode), e pede para o Linux rodá-lo.

**O Segredo:** Antes de rodar o código, o Linux o passa por um **Verifier** (Verificador). Ele analisa estaticamente as instruções e seus caminhos possíveis para rejeitar acessos inválidos à memória, uso indevido de ponteiros e programas que excedem suas restrições. Ele admite formas de repetição que consegue verificar; não é uma prova geral de que o programa não tem falhas lógicas, não consome recursos em excesso ou não prejudica o serviço.

Se o código for seguro, o Linux o converte para o código de máquina nativo (JIT) e o anexa a eventos do SO (ex: "rode esta função sempre que um pacote TCP chegar na placa de rede eth0"). **JIT** significa *Just-In-Time compilation*: o bytecode e convertido para instrucoes nativas da CPU no momento do carregamento ou da execucao, reduzindo o custo de interpretar instrucoes uma por uma.

### C/C++ vs Rust (`Aya`)
Para escrever eBPF, o padrão de mercado é usar C clang/BCC. 

O ecossistema **Aya** trouxe o eBPF para o Rust. Aya e um framework/ecossistema Rust para criar, carregar e gerenciar programas eBPF sem depender da toolchain classica baseada em clang e libbpf.

O borrow checker verifica propriedades do código Rust antes da compilação para eBPF. O Verifier do Linux faz outra análise, sobre o bytecode gerado, com restrições próprias de acesso, helpers, pilha e fluxo de controle. Passar em uma etapa não garante passar na outra: o carregamento do programa deve ser testado no kernel de destino.

Detalhes do processo de análise constam na [documentação do eBPF Verifier do Linux](https://docs.kernel.org/bpf/verifier.html).

## 2. A Arquitetura de um Projeto eBPF (Aya)

Semelhante ao `rust-gpu`, um projeto Aya possui dois componentes:
1.  **O Programa eBPF (Kernel Space):** O código que será injetado no Kernel. Deve ser `#![no_std]` (pois o kernel não usa a stdlib do usuário).
2.  **O Programa User Space (Host):** Um binário Rust normal (`std`, Tokio, etc.) que carrega o programa eBPF compilado, o envia para o Kernel, e se comunica com ele através de mapas de memória (eBPF Maps).

Essa separacao e obrigatoria porque o codigo eBPF vive em um ambiente extremamente restrito.

Ja o processo em user space faz o trabalho de orquestracao: carregar, anexar, ler estatisticas, logar eventos e encerrar o programa com seguranca.

## 3. O Código Prático: Um Interceptador de Pacotes XDP

*Nota: Programação eBPF exige um sistema Linux recente (Kernel 5.8+). Este código não rodará no Windows ou macOS nativamente.*

Para gerar um projeto Aya correto, usamos o `cargo-generate` (pois o setup manual de dependências é muito complexo):

```bash
cargo install bpf-linker
cargo install cargo-generate
cargo generate https://github.com/aya-rs/aya-template
# Responda as perguntas: nome: "meu_ebpf", tipo: "xdp"
cd meu_ebpf
```

### A) O Programa no Kernel Space (`meu_ebpf-ebpf/src/main.rs`)

O XDP (eXpress Data Path) é um tipo de programa eBPF que roda no nível mais baixo possível da placa de rede, antes mesmo do Kernel alocar memória (sk_buff) para o pacote.

**sk_buff** e a estrutura tradicional do kernel Linux para representar pacotes de rede em memoria. XDP existe justamente para atuar antes desse custo de alocacao e processamento, reduzindo latencia e CPU.

É usado pela Cloudflare para mitigar ataques DDoS na casa dos Terabits por segundo.

```rust
#![no_std]
#![no_main]

use aya_ebpf::{
    bindings::xdp_action,
    macros::xdp,
    programs::XdpContext,
};
use aya_log_ebpf::info;

// O Ponto de entrada do nosso filtro XDP
#[xdp]
pub fn meu_ebpf(ctx: XdpContext) -> u32 {
    // Tenta interceptar o pacote
    match try_meu_ebpf(ctx) {
        Ok(ret) => ret,
        Err(_) => xdp_action::XDP_ABORTED, // Aborta/Derruba o pacote em caso de erro
    }
}

fn try_meu_ebpf(ctx: XdpContext) -> Result<u32, u32> {
    // Loga uma mensagem (o Aya envia isso via canais mágicos para o User Space)
    // Isso roda no caminho XDP do kernel para cada pacote recebido.
    info!(&ctx, "Pacote interceptado na Placa de Rede!");

    // Retorna XDP_PASS para deixar o pacote seguir seu fluxo normal para o SO.
    // Retornar XDP_DROP deletaria o pacote instantaneamente (Firewall de ultra performance).
    Ok(xdp_action::XDP_PASS)
}

// Handler de panic obrigatório para no_std
#[panic_handler]
fn panic(_info: &core::panic::PanicInfo) -> ! {
    unsafe { core::hint::unreachable_unchecked() }
}
```

### B) O Programa User Space (`meu_ebpf/src/main.rs`)

Este é o binário normal que você roda com `sudo`. Ele injeta o código acima no Kernel. Pense nele como o "processo controlador": o código eBPF fica dentro do kernel, mas este binario decide quando carregar, em qual interface anexar e como observar o comportamento do programa.

```rust
use aya::{include_bytes_aligned, Bpf};
use aya::programs::{Xdp, XdpFlags};
use aya_log::BpfLogger;
use std::sync::Arc;
use std::sync::atomic::{AtomicBool, Ordering};

#[tokio::main]
async fn main() -> Result<(), anyhow::Error> {
    // 1. Carrega o bytecode eBPF compilado pelo bpf-linker
    let mut bpf = Bpf::load(include_bytes_aligned!(
        "../../target/bpfel-unknown-none/release/meu_ebpf"
    ))?;

    // 2. Inicializa o Logger (para receber os `info!` do Kernel)
    if let Err(e) = BpfLogger::init(&mut bpf) {
        eprintln!("Falha ao inicializar o logger: {}", e);
    }

    // 3. Extrai o programa "meu_ebpf" do bytecode
    let program: &mut Xdp = bpf.program_mut("meu_ebpf").unwrap().try_into()?;
    
    // 4. Carrega o programa no Kernel
    program.load()?;
    
    // 5. Anexa (Attach) o programa a uma placa de rede (ex: "eth0" ou "lo" para localhost)
    // "Attach" significa registrar esse programa eBPF em um ponto de evento do kernel.
    let placa_rede = "eth0"; // Mude para o nome da sua placa de rede
    program.attach(placa_rede, XdpFlags::default())?;

    println!("Programa XDP carregado na interface {}. Pressione Ctrl+C para sair.", placa_rede);

    // Mantém o programa rodando até o usuário apertar Ctrl+C
    // Quando o binário for fechado, o Aya remove o programa XDP do Kernel automaticamente!
    let rodando = Arc::new(AtomicBool::new(true));
    let r = rodando.clone();
    ctrlc::set_handler(move || {
        r.store(false, Ordering::SeqCst);
    }).expect("Erro no Ctrl+C");

    while rodando.load(Ordering::SeqCst) {
        std::thread::sleep(std::time::Duration::from_millis(100));
    }

    Ok(())
}
```

## 4. O Poder dos Mapas eBPF (Compartilhando Estado)

No código acima, usamos logs. Mas e se quisermos contar quantos pacotes chegaram de um determinado IP?
O eBPF nos fornece os **Maps** (Estruturas de dados como HashMaps, Arrays ou Per-CPU Arrays). Um **mapa eBPF** e uma estrutura de dados gerenciada pelo kernel que pode ser acessada tanto pelo programa eBPF quanto pelo processo em user space.

Ele existe para compartilhar estado entre dois mundos sem precisar inventar um protocolo proprio de comunicacao.

Você cria o Mapa no Kernel (ex: um `HashMap<u32, u64>` onde a chave é o IP e o valor é o contador). O programa XDP incrementa o contador a cada pacote. O programa no User Space lê o mapa a cada 5 segundos e plota um gráfico no terminal.

Tudo isso com sincronizacao gerenciada pelo proprio subsistema eBPF, mantendo desempenho muito proximo da velocidade de hardware.

## Erros Comuns e Anti-Padrões

1.  **Esquecer do Limite de Tamanho:** O *Verifier* do Kernel só aceita programas eBPF pequenos (geralmente até 1 milhão de instruções, mas depende da versão do Kernel). Você não pode escrever um backend inteiro em eBPF. É apenas para lógica rápida de interceptação.
2.  **Achar que eBPF é só para Rede:** XDP é focado em rede, mas o eBPF suporta *Kprobes* (Kerenel Probes) e *Uprobes* (User Probes). Você pode escrever um programa eBPF que é disparado sempre que a função `sys_open` do Kernel é chamada, ou sempre que uma função específica de *outro* binário no sistema é executada. Isso é a base do Sysdig e outras ferramentas de observabilidade extremas.
3.  **Ler memória não checada:** O Verifier rejeitará o seu código se você tentar ler o payload de um pacote de rede sem antes checar se o índice (offset) está dentro dos limites de tamanho do pacote. Em C isso é irritante. Em Rust, o *slice* (`&[u8]`) ajuda muito, mas às vezes você precisa convencer o Verifier com ifs extras.

# Aula 10 — Lifetimes

---

## Nesta aula

Dominar **lifetimes** — o mecanismo que torna o borrow checker possível. Entenderemos o que são lifetimes (não são tempos de vida de objetos, são relações entre referências), a sintaxe `<'a>`, **elisão de lifetimes** (quando o compilador infere), quando precisamos explicitar, lifetimes em structs, enums, funções, traits, e bounds. Você vai aprender a explicar lifetimes como relações entre referências (não tempo de vida de objetos), aplicar elisão nos casos cobertos pelas regras, explicitar `<'a>` quando necessário, e anotar lifetimes em structs e funções.
---

## 1. O Problema que Lifetimes Resolvem

### 1.1 Dangling pointers em C

```c
// C — o clássico dangling pointer
char* gerar_saudacao() {
    char buffer[100];
    sprintf(buffer, "Olá, mundo!");
    return buffer;   // WARN: retorna endereço de variável local
    // buffer é desalocado ao sair da função
    // o ponteiro retornado aponta para memória inválida
}

int main(void) {
    char* msg = gerar_saudacao();
    printf("%s\n", msg);   // UB — lixo de memória
}
```

O compilador C avisa, mas compila. O bug aparece em runtime — se aparecer.

- **Runtime**: momento em que o programa já está executando.
- **Dangling pointer**: ponteiro ou referência que ainda existe, mas aponta para uma região que já saiu de validade.

### 1.2 Rust recusa em compilação

```rust
fn gerar_saudacao() -> &str {
    let buffer = String::from("Olá, mundo!");
    &buffer[0..11]   // ERRO: `buffer` does not live long enough
}   // buffer é dropped aqui, a referência seria dangling
```

Rust **recusa compilar**. A pergunta que o compilador faz é: "a referência retornada vive pelo menos tanto quanto o chamador espera?" A resposta é não — `buffer` morre ao sair da função. O sistema que verifica isso é o sistema de **lifetimes**.

Esse é o ponto central da aula:

- a referência parece sintaticamente correta;
- mas semanticamente ela apontaria para dados destruídos;
- então o compilador barra o programa antes de ele virar binário executável.

### 1.3 O que são lifetimes

> **Lifetime** é o intervalo durante o qual uma referência é válida.

Lifetimes **não mudam o comportamento do programa** — são **anotações para o compilador** verificar a segurança das referências em tempo de compilação.

Pense em lifetimes como uma **relação de tempo** entre referências: "esta referência vive pelo menos tanto quanto aquela". O compilador verifica se essas relações são respeitadas.

- **Válida** significa: a referência ainda aponta para dados que continuam existindo e podem ser acessados com segurança.
- **Garantia estática** significa: a prova é feita em compilação, não através de checagens constantes em runtime.

**Analogia:** Se o borrow checker é um guardião que garante que referências são válidas, lifetimes são o **sistema de identificação** que ele usa para rastrear quem vive até quando.

## 2. A Anatomia de um Lifetime

### 2.1 Lifetime explícito

```rust
fn mais_longo<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

Linha por linha:

- `<'a>` — declara um parâmetro de lifetime genérico chamado `'a`. Assim como `<T>` é um tipo genérico, `<'a>` é um lifetime genérico.
- `x: &'a str` — `x` é uma referência para `str` que vive pelo menos pelo lifetime `'a`.
- `y: &'a str` — `y` é uma referência para `str` que vive pelo menos pelo lifetime `'a`.
- `-> &'a str` — o retorno é uma referência para `str` que vive pelo menos pelo lifetime `'a`.

**O que isso significa:** O retorno vive pelo menor dos lifetimes de `x` e `y`. Isso garante que o retorno nunca sobrevive aos dados emprestados.

Aqui aparece um detalhe muito importante:

- `<'a>` funciona de forma parecida com `<T>`, mas para validade temporal de referências;
- `'a` não é "o nome de uma variável";
- `'a` é um parâmetro lógico que permite ao compilador conectar entrada e saída.

### 2.2 Uso prático

```rust
fn mais_longo<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

fn main() {
    let s1 = String::from("rust");           // lives from here...
    let resultado;
    {
        let s2 = String::from("go");          // lives from here...
        resultado = mais_longo(&s1, &s2);
        println!("Mais longo: {}", resultado); // OK — s1 e s2 ambos vivos
    }                                          // s2 morre aqui

    // println!("{}", resultado);             // ERRO: `s2` does not live long enough
    // resultado pode apontar para s2, que já morreu!
    // O compilador recusa porque resultado tem lifetime de s2
}
```

Se `resultado` apontasse para `s1` (que ainda vive), o código seria seguro em runtime. Mas o compilador não sabe qual ramo do `if` será tomado — ele assume o pior caso: o retorno pode ser `x` OU `y`, então o lifetime do retorno é a interseção dos dois.

- **Interseção**, neste contexto, significa o intervalo de tempo em que ambos continuam válidos.
- Rust prefere assumir o caso mais restritivo quando não consegue provar algo mais forte.

### 2.3 Quando os dois vivem o suficiente

```rust
fn main() {
    let s1 = String::from("linguagem rust");   // vive muito
    let s2 = String::from("go");                // vive muito
    let resultado = mais_longo(&s1, &s2);       // OK — ambos vivos
    println!("Mais longo: {}", resultado);       // OK — s1 e s2 ainda vivos
}
```

## 3. Elisão de Lifetimes — Quando Não Precisa Escrever

### 3.1 O compilador infere automaticamente

Em muitos casos, o compilador pode deduzir os lifetimes sem anotação explícita:

- **Elisão** significa omissão autorizada pela linguagem.
- Ou seja, você não escreveu os lifetimes, mas o compilador aplicou regras fixas para inferi-los.

```rust
// O QUE VOCÊ ESCREVE:
fn primeira_palavra(s: &str) -> &str {
    let bytes = s.as_bytes();
    for (i, &item) in bytes.iter().enumerate() {
        if item == b' ' {
            return &s[0..i];
        }
    }
    &s[..]
}

// O QUE O COMPILADOR ENTENDE:
fn primeira_palavra<'a>(s: &'a str) -> &'a str { ... }
```

O compilador infere: se há uma referência de entrada e uma de saída, a saída deve vir da entrada.

### 3.2 Regras de elisão (simplificadas)

O compilador aplica estas regras automaticamente:

**Regra 1:** Cada parâmetro de referência recebe seu próprio lifetime.

```rust
fn foo(x: &str, y: &str)
// vira:
fn foo<'a, 'b>(x: &'a str, y: &'b str)
```

**Regra 2:** Se há exatamente um parâmetro de lifetime, ele é atribuído a todas as referências de retorno.

```rust
fn foo(x: &str) -> &str
// vira:
fn foo<'a>(x: &'a str) -> &'a str
```

**Regra 3 (apenas em métodos):** Se há `&self` ou `&mut self`, o lifetime de `self` é atribuído ao retorno.

```rust
impl Struct {
    fn metodo(&self, x: &str) -> &str
    // vira:
    fn metodo<'a, 'b>(&'a self, x: &'b str) -> &'a str
    // retorna algo de self, não de x
}
```

**Quando essas regras falham**, você precisa escrever lifetimes explicitamente.

Essa é uma boa regra prática:

- se há uma única entrada por referência, a inferência costuma funcionar;
- se há várias entradas e uma saída por referência, normalmente você precisa explicar a relação manualmente.

### 3.3 Quando você DEVE escrever lifetimes

```rust
// DOIS parâmetros de referência + UM retorno
// Qual parâmetro o retorno vem? O compilador não sabe.
fn mais_longo(x: &str, y: &str) -> &str { ... }
// ERRO: missing lifetime specifier

// SOLUÇÃO:
fn mais_longo<'a>(x: &'a str, y: &'a str) -> &'a str { ... }
```

## 4. Lifetimes em Structs

### 4.1 Struct que guarda referências

```rust
struct Excerto<'a> {
    conteudo: &'a str,
}

fn main() {
    let texto = String::from("Rust é incrível. Go também é legal.");

    let primeira = &texto[0..16];    // "Rust é incrível"
    let excerto = Excerto { conteudo: primeira };

    println!("{}", excerto.conteudo);  // "Rust é incrível"
}
```

O `<'a>` em `Excerto<'a>` significa: **esta struct não pode viver mais que a referência que ela contém**.

Isso é importante porque uma struct com referência não é dona dos dados. Ela apenas carrega um ponteiro emprestado com uma restrição explícita de validade.

```rust
struct Excerto<'a> {
    conteudo: &'a str,
}

fn main() {
    let excerto;
    {
        let texto = String::from("temporário");
        excerto = Excerto { conteudo: &texto };
        // ERRO: `texto` does not live long enough
    }   // texto morre aqui, excerto seria dangling

    println!("{}", excerto.conteudo);
}
```

### 4.2 Métodos em structs com lifetimes

```rust
struct Excerto<'a> {
    conteudo: &'a str,
}

impl<'a> Excerto<'a> {
    fn novo(conteudo: &'a str) -> Excerto<'a> {
        Excerto { conteudo }
    }

    fn conteudo(&self) -> &'a str {
        self.conteudo
    }

    fn eh_vazio(&self) -> bool {
        self.conteudo.is_empty()
    }

    // Método que pode retornar parte do conteúdo
    fn prefixo(&self, n: usize) -> &'a str {
        if n <= self.conteudo.len() {
            &self.conteudo[..n]
        } else {
            self.conteudo
        }
    }
}

fn main() {
    let texto = String::from("Rust é incrível");
    let excerto = Excerto::novo(&texto);

    println!("Conteúdo: {}", excerto.conteudo());
    println!("É vazio: {}", excerto.eh_vazio());
    println!("Prefixo(4): {}", excerto.prefixo(4));  // "Rust"
}
```

### 4.3 Múltiplos lifetimes em structs

```rust
struct Trecho<'a, 'b> {
    inicio: &'a str,
    fim: &'b str,
}

fn main() {
    let texto1 = String::from("ABC");
    let trecho;

    {
        let texto2 = String::from("XYZ");
        trecho = Trecho { inicio: &texto1, fim: &texto2 };
        println!("{} {}", trecho.inicio, trecho.fim);  // OK — ambos vivos
    }
    // texto2 morreu

    println!("{}", trecho.inicio);   // OK — inicio vem de texto1, que ainda vive
    // println!("{}", trecho.fim);   // ERRO: texto2 morreu
}
```

Dois lifetimes diferentes permitem que cada referência tenha duração independente.

### 4.4 Struct com lifetime e generic

Aqui vemos lifetimes convivendo com generics:

- **generic** responde "qual é o tipo do valor?";
- **lifetime** responde "por quanto tempo a referência armazenada continua válida?".

```rust
struct Armazenamento<'a, T> {
    chave: &'a str,
    valor: T,
}

fn main() {
    let nome = "temperatura";
    let dado = Armazenamento { chave: nome, valor: 36.5f64 };
    println!("{}: {}", dado.chave, dado.valor);

    let tag = "ativo";
    let flag = Armazenamento { chave: tag, valor: true };
    println!("{}: {}", flag.chave, flag.valor);
}
```

## 5. Lifetimes em Enums

Enums também podem carregar referências, então as mesmas regras de validade continuam valendo. O enum em si não "resolve" o problema; ele apenas encapsula o formato do valor.

```rust
enum TalvezReferencia<'a> {
    Tem(&'a str),
    NaoTem,
}

fn encontrar_inicio<'a>(texto: &'a str, padrao: &str) -> TalvezReferencia<'a> {
    match texto.find(padrao) {
        Some(indice) => TalvezReferencia::Tem(&texto[..indice]),
        None => TalvezReferencia::NaoTem,
    }
}

fn main() {
    let texto = "olá mundo rust";
    let resultado = encontrar_inicio(texto, "mundo");

    match resultado {
        TalvezReferencia::Trecho(s) => println!("Antes: '{}'", s),
        TalvezReferencia::NaoTem => println!("Padrão não encontrado"),
    }
}
```

Isso é essencialmente o que `Option<&T>` faz — o `Option` padrão já tem lifetimes implícitos via elisão.

## 6. Lifetimes em Funções — Padrões Avançados

### 6.1 Retorno de dados alocados — sem lifetime

Quando você retorna dados **owned** (não referência), lifetimes não são necessários:

Essa é uma distinção arquitetural muito útil:

- se retornar referência estiver difícil, muitas vezes a solução correta é retornar um valor **owned**;
- isso simplifica bastante a relação de lifetimes porque o chamador recebe a posse do dado.

```rust
fn criar_string() -> String {    // String é owned — sem lifetime
    String::from("nova string")   // move para o chamador
}
```

### 6.2 Retorno de referência que NÃO vem dos parâmetros

```rust
// IMPOSSÍVEL — sem lifetime estático
fn gerar_string() -> &str {
    // &String::from("olá")  // ERRO: retorna referência para dado temporário
    // A String seria dropada imediatamente
}

// SOLUÇÃO 1: retornar owned
fn gerar_string() -> String {
    String::from("olá")
}

// SOLUÇÃO 2: lifetime estático (string literal)
fn gerar_literal() -> &'static str {
    "olá"   // string literal vive para sempre no binário
}
```

- **Owned**: valor possuído pelo chamador, responsável por sua destruição.
- **String literal** pode ser retornada como `&'static str` porque já vive embutida no binário.

### 6.3 `'_` — lifetime anônimo (elisão explícita)

Em contextos onde o compilador exige um lifetime mas você quer que ele infira:

- `'_` significa, na prática, "inferir o lifetime apropriado aqui".
- É útil quando você quer explicitar que existe um lifetime naquela posição, mas não quer nomeá-lo.

```rust
fn processar(s: &str) -> &str {   // elisão automática
    s
}

// Em type hints, você pode usar '_ para pedir inferência:
let mut v: Vec<&str> = Vec::new();
// Em posições onde lifetime é obrigatório mas óbvio:
// fn foo(x: &str) — equivalente a fn foo<'a>(x: &'a str)
```

### 6.4 Lifetimes diferentes para entradas e saídas

```rust
// O retorno pode vir de 'a OU de 'b
fn escolher<'a, 'b>(condicao: bool, a: &'a str, b: &'b str) -> &'a str {
    if condicao { a } else { a }   // sempre retorna de 'a
}

// Se quiser que possa retornar de qualquer um:
fn escolher<'a>(condicao: bool, a: &'a str, b: &'a str) -> &'a str {
    if condicao { a } else { b }   // pode ser 'a ou 'b, unificados em 'a
}

// Se os lifetimes são realmente independentes e o retorno é novo:
fn combinar<'a, 'b>(a: &'a str, b: &'b str) -> String {
    format!("{}{}", a, b)   // String owned — sem lifetime!
}
```

## 7. `'static` — Lifetime Eterno

### 7.1 O que é

`'static` significa que a referência vive por **todo o programa**. Strings literais são `'static`:

`'static` é especial porque representa a duração máxima possível de validade dentro do programa.

Mas atenção: isso não quer dizer "qualquer referência pode virar `'static`". Só referências para dados realmente duradouros podem ter esse tipo.

```rust
let s: &'static str = "olá";   // "olá" está no binário — nunca é desalocado
```

### 7.2 Quando usar

```rust
// Constantes globais
const NOME: &str = "Rust";            // &'static str implícito
static VERSAO: &str = "1.85.0";      // &'static str implícito

// Erros estáticos em mensagens
fn erro() -> &'static str {
    "algo deu errado"
}

// Threads requerem 'static (veremos na aula 13)
use std::thread;
fn main() {
    let msg = "olá da thread";       // &'static str
    thread::spawn(move || {
        println!("{}", msg);
    });
}
```

### 7.3 Cuidado com `'static`

**Não** use `'static` como "escape hatch" para problemas de lifetimes:

```rust
// ANTI-PATTERN — não faça isso:
fn pegar_referencia() -> &'static str {
    // Box::leak() vaza memória propositalmente para criar &'static
    Box::leak(String::from("vazou").into_boxed_str())
}
// Isso VAZA memória — use apenas se realmente precisa
```

- **Escape hatch**: gambiarra conceitual usada para fugir das restrições normais.
- Aqui isso é perigoso porque resolver lifetime à força com vazamento de memória normalmente piora o design em vez de corrigi-lo.

## 8. Lifetime Bounds em Generics

### 8.1 `T: 'a` — o tipo pode ser seguramente referenciado por `'a`

- **Lifetime bound**: restrição que relaciona o tempo de validade de um tipo ou referência com um lifetime específico.
- `T: 'a` lê-se aproximadamente como "T é válido pelo menos durante `'a`".

```rust
// A struct pode conter referências em T, e elas devem viver pelo menos 'a
struct Caixa<'a, T: 'a> {
    conteudo: &'a T,
}

fn main() {
    let x = 42;
    let caixa = Caixa { conteudo: &x };
    println!("{}", caixa.conteudo);  // 42
}
```

### 8.2 `T: 'static` — o tipo não contém referências não-static

```rust
fn foo<T: 'static>(valor: T) {
    // T pode ser: i32, String, Vec<u8>, etc.
    // T NÃO pode ser: &str apontando para uma String local
}
```

Isso aparece frequentemente com threads — tipos enviados para threads devem ser `'static`.

Essa restrição existe porque a thread pode continuar rodando depois que o escopo atual terminou. Então nada que ela use pode depender de referências temporárias já destruídas.

### 8.3 Lifetime bounds em traits

```rust
trait Parser<'a> {
    type Output;
    fn parse(&self, input: &'a str) -> Self::Output;
}

struct IntParser;

impl<'a> Parser<'a> for IntParser {
    type Output = i32;
    fn parse(&self, input: &'a str) -> i32 {
        input.trim().parse().unwrap()
    }
}

struct PalavraParser;

impl<'a> Parser<'a> for PalavraParser {
    type Output = &'a str;
    fn parse(&self, input: &'a str) -> &'a str {
        input.split_whitespace().next().unwrap_or("")
    }
}

fn main() {
    let texto = "42";
    let p1 = IntParser;
    println!("{}", p1.parse(texto));  // 42

    let texto2 = "olá mundo";
    let p2 = PalavraParser;
    println!("{}", p2.parse(texto2)); // "olá"
}
```

## 9. Covariância e Contravariância (Avançado)

Lifetimes em Rust são **covariantes** — você pode encurtar um lifetime:

Esse é um tópico mais avançado de teoria de tipos.

- **Covariância**, aqui, significa que uma referência com lifetime mais longo pode ser usada onde uma referência de lifetime mais curto é suficiente.

Você não precisa decorar toda a teoria formal agora; o importante é entender a intuição de substituição segura.

```rust
fn main() {
    fn primeiro<'a>(x: &'a str, _y: &str) -> &'a str { x }

    let s1 = String::from("longa vida");   // lifetime longo
    let resultado;
    {
        let s2 = String::from("curta");     // lifetime curto
        resultado = primeiro(&s1, &s2);     // empresta s1 e s2
        println!("{}", resultado);           // OK — resultado vem de s1
    }                                        // s2 morre, não importa

    println!("{}", resultado);               // OK — resultado aponta para s1
}
```

O lifetime de `resultado` é `'a`, que é o lifetime de `s1`. O `_y` tem lifetime diferente e não afeta o retorno.

**Regra simplificada:** Rust permite usar uma referência com lifetime mais longo onde se espera uma mais curta. Isso é covariância — o mesmo princípio de subtipagem em linguagens com herança (String <: Object → pode usar String onde espera Object).

## 10. Modelo Mental — Lifetimes em Ação

```rust
fn mais_longo<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

fn main() {
    //    's1 começa                     's1 termina
    //    ↓                                    ↓
    let s1 = String::from("linguagem rust");
    //              's2 começa 's2 termina
    //              ↓           ↓
    {   let s2 = String::from("go");
        let r = mais_longo(&s1, &s2);
        //      'r = min('s1, 's2) = 's2
        //      r só pode ser usado enquanto s2 vive
        println!("{}", r);       // OK — 's2 ainda ativo
    }   // s2 e 's2 terminam

    // println!("{}", r);  // ERRO — 'r = 's2 já terminou
}
```

```
Tempo ──────────────────────────────────────────────────→

s1:  |=========================...====================|
     's1

s2:           |==========|
              's2

r:            |==========|    ← r = min('s1, 's2) = 's2
              'r (= 's2)

main: |================================================|
      'main

Relação: 'r ⊆ 's2 ⊆ 's1 ⊆ 'main
```

## 11. Exemplo Completo — Parser com Lifetimes

```rust
// aula10_lifetimes.rs
// Compilar: rustc aula10_lifetimes.rs
// Executar: ./aula10_lifetimes

use std::fmt;

// === Struct com lifetime ===

#[derive(Debug)]
struct Trecho<'a> {
    inicio: usize,
    fim: usize,
    conteudo: &'a str,
}

impl<'a> Trecho<'a> {
    fn novo(conteudo: &'a str, inicio: usize, fim: usize) -> Self {
        Trecho { inicio, fim, conteudo }
    }

    fn comprimento(&self) -> usize {
        self.fim - self.inicio
    }
}

impl<'a> fmt::Display for Trecho<'a> {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "[{}..{}] '{}'", self.inicio, self.fim, self.conteudo)
    }
}

// === Parser que retorna referências ao texto original ===

struct TextoParser<'a> {
    texto: &'a str,
    posicao: usize,
}

impl<'a> TextoParser<'a> {
    fn novo(texto: &'a str) -> Self {
        TextoParser { texto, posicao: 0 }
    }

    // Retorna Trecho com referência ao texto original — precisa de lifetime
    fn proxima_palavra(&mut self) -> Option<Trecho<'a>> {
        let slice = &self.texto[self.posicao..];

        match slice.find(|c: char| !c.is_whitespace()) {
            Some(ini) => {
                let restante = &slice[ini..];
                let fim = restante.find(|c: char| c.is_whitespace())
                    .unwrap_or(restante.len());

                let inicio_absoluto = self.posicao + ini;
                let fim_absoluto = inicio_absoluto + fim;

                self.posicao = fim_absoluto;

                Some(Trecho::novo(
                    &self.texto[inicio_absoluto..fim_absoluto],
                    inicio_absoluto,
                    fim_absoluto,
                ))
            }
            None => None,
        }
    }

    fn resetar(&mut self) {
        self.posicao = 0;
    }
}

// === Funções com diferentes padrões de lifetime ===

// Dois parâmetros, retorno pode vir de qualquer um
fn mais_longo<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() >= y.len() { x } else { y }
}

// Dois lifetimes independentes — retorno é String (owned)
fn juntar<'a, 'b>(a: &'a str, b: &'b str) -> String {
    format!("{} + {}", a, b)
}

// Lifetime estático — string literal
fn separador() -> &'static str {
    "═══════════════════════════════════════"
}

// Retorno vem do primeiro parâmetro (elisão funciona)
fn primeira_linha(texto: &str) -> &str {
    match texto.find('\n') {
        Some(i) => &texto[..i],
        None => texto,
    }
}

fn main() {
    println!("{}", separador());
    println!("  Lifetimes em Ação");
    println!("{}", separador());

    // === Parser ===
    println!("\n=== Parser com Lifetimes ===\n");

    let texto = "Rust é uma linguagem de sistemas moderna e segura";
    let mut parser = TextoParser::novo(texto);

    println!("Texto: \"{}\"", texto);
    println!("Palavras:");

    while let Some(trecho) = parser.proxima_palavra() {
        println!("  {}", trecho);
    }

    parser.resetar();
    if let Some(trecho) = parser.proxima_palavra() {
        println!("  Apos resetar: {}", trecho);
    }

    // === mais_longo ===
    println!("\n=== Função mais_longo ===\n");

    let a = "linguagem Rust";
    let b = "Go";

    let resultado = mais_longo(a, b);
    println!("mais_longo(\"{}\", \"{}\") = \"{}\"", a, b, resultado);

    // Demonstrando que o lifetime é limitado pelo menor
    let s1 = String::from("string comprida aqui");
    let resultado;
    {
        let s2 = String::from("curta");
        resultado = mais_longo(&s1, &s2);
        println!("Dentro do escopo: {}", resultado);  // OK
    }
    // resultado pode apontar para s2 (já morto), MAS na verdade aponta para s1
    // O compilador não sabe — ele assume o pior caso
    // println!("{}", resultado);  // ERRO: s2 não vive o suficiente

    // === juntar com lifetimes independentes ===
    println!("\n=== Lifetimes Independentes ===\n");

    let parte1 = String::from("prefixo");
    {
        let parte2 = String::from("sufixo");
        let combinado = juntar(&parte1, &parte2);
        println!("Juntado: {}", combinado);  // OK — String owned
    }
    // combinado ainda existe? Depende — é String (owned), não referência

    // === primeira_linha (elisão) ===
    println!("\n=== Elisão de Lifetimes ===\n");

    let multi = "primeira linha\nsegunda linha\nterceira";
    println!("Texto: {:?}", multi);
    println!("Primeira linha: {:?}", primeira_linha(multi));

    let sem_newline = "sem newline";
    println!("Sem newline: {:?}", primeira_linha(sem_newline));

    // === Struct com lifetime em coleção ===
    println!("\n=== Coleção de Trechos ===\n");

    let frase = "O gato pulou o muro e o cachorro latiu";
    let mut parser2 = TextoParser::novo(frase);
    let mut trechos: Vec<Trecho> = Vec::new();

    while let Some(trecho) = parser2.proxima_palavra() {
        if trecho.comprimento() > 2 {
            trechos.push(trecho);
        }
    }

    println!("Palavras com mais de 2 caracteres:");
    for trecho in &trechos {
        println!("  {} ({} chars)", trecho.conteudo, trecho.comprimento());
    }

    // === 'static ===
    println!("\n=== Lifetime 'static ===\n");

    let estatico: &'static str = "Esta string vive para sempre";
    println!("Estático: {}", estatico);
    println!("Separador: {}", separador());

    // Constante com 'static implícito
    const PI_STR: &str = "3.14159";
    println!("Pi: {}", PI_STR);
}
```

## 12. Erros Comuns

### Erro 1: Missing lifetime specifier

```rust
fn primeira(s: &str, t: &str) -> &str { ... }
// erroE0106: missing lifetime specifier
```

**Solução:** Adicione lifetimes explícitos:
```rust
fn primeira<'a>(s: &'a str, t: &'a str) -> &'a str { ... }
```

### Erro 2: Lifetime does not live long enough

```rust
fn main() {
    let r;
    {
        let x = String::from("olá");
        r = &x;
    } // x morre
    println!("{}", r); // ERRO: `x` does not live long enough
}
```

**Solução:** Não empreste de variáveis que vão morrer. Copie em vez de referenciar.

### Erro 3: Tentar armazenar referência curta em struct longa

```rust
struct Cache<'a> { dado: &'a str }

fn main() {
    let cache;
    {
        let temp = String::from("temporário");
        cache = Cache { dado: &temp };
        // ERRO: `temp` does not live long enough
    }
}
```

**Solução:** Use `String` (owned) em vez de `&str` (referência) quando o struct precisa viver mais que os dados.

### Erro 4: Confundir lifetime com escopo

Lifetimes **não são escopos** — são **relações entre referências**. Duas referências com o mesmo lifetime `'a` não precisam ter o mesmo escopo real — apenas precisam ambas ser válidas no ponto onde são usadas.

### Erro 5: Adicionar lifetimes onde não precisa

```rust
// DESNECESSÁRIO — String é owned, não referência
fn criar<'a>() -> String {
    String::from("olá")
}

// CORRETO — sem lifetime
fn criar() -> String {
    String::from("olá")
}
```

Lifetimes só são necessários para **referências**. Tipos owned (`String`, `Vec<T>`, etc.) não precisam.

## 13. Comparação — C/C++ vs Rust (Lifetimes)

| Conceito | C/C++ | Rust |
|----------|-------|------|
| Referência inválida | Dangling pointer (UB em runtime) | Erro de compilação |
| Tempo de vida de dados | Responsabilidade do programador | Compilador verifica (lifetimes) |
| Anotação manual | Não existe | `<'a>` quando necessário |
| Inferência | Não aplicável | Elisão automática na maioria dos casos |
| 'static | Variáveis globais | `&'static str` (literais), `static`, `const` |
| Custo em runtime | Zero | Zero — tudo é verificado em compilação |

## 14. Resumo Prático — Checklist de Lifetimes

| Situação | Precisa de lifetime? | Exemplo |
|----------|---------------------|---------|
| Função com 1 referência de entrada e saída | Não (elisão) | `fn foo(s: &str) -> &str` |
| Função com 2+ referências e retorno referência | **Sim** | `fn foo<'a>(x: &'a str, y: &'a str) -> &'a str` |
| Função que retorna owned | Não | `fn foo() -> String` |
| Struct com referência | **Sim** | `struct S<'a> { dado: &'a str }` |
| Struct sem referência | Não | `struct S { dado: String }` |
| Enum com referência | **Sim** | `enum E<'a> { Var(&'a str) }` |
| Método que retorna &self | Não (elisão) | `fn get(&self) -> &str` |
| String literal | `'static` implícito | `let s: &str = "olá"` |

**Regra de ouro:** Se seu struct/função só usa tipos owned, você **não precisa** de lifetimes. Lifetimes são necessários apenas quando você **guarda referências** ou **retorna referências** de múltiplas entradas.

## 15. Exercícios Obrigatórios

### Exercício 1 — Função com dois lifetimes

Escreva `fn primeiro<'a, 'b>(x: &'a str, _y: &'b str) -> &'a str` que sempre retorna `x`. No main, demonstre que o resultado vive pelo lifetime de `x`, independente de `y`.

### Exercício 2 — Struct com referência

Crie `struct Palavra<'a> { texto: &'a str, inicio: usize }`. Implemente:
- `fn nova(texto: &str) -> Palavra` (com lifetime apropriado)
- `fn comprimento(&self) -> usize`
- `fn eh_maiuscula(&self) -> bool`

Demonstre que a struct não pode viver mais que o texto original.

### Exercício 3 — Parser com estado

Crie `struct Tokenizer<'a> { input: &'a str, pos: usize }` com métodos:
- `fn novo(input: &str) -> Tokenizer`
- `fn proximo(&mut self) -> Option<&'a str>` (retorna o próximo token delimitado por espaços)

Tokenize `"a b c d"` e colete todos os tokens em um `Vec<&str>`.

### Exercício 4 — Evitando lifetimes com owned

Reescreva a struct `Palavra<'a>` do exercício 2 como `Palavra` (sem lifetime), usando `String` em vez de `&str`. Compare: quando é melhor usar referências? Quando é melhor usar owned?

### Exercício 5 — Maior prefixo comum

Escreva `fn prefixo_comum<'a>(a: &'a str, b: &'a str) -> &'a str` que retorne o maior prefixo comum entre duas strings. Teste com ("abacate", "aba") → "aba".

### Exercício 6 — Cache com lifetime

Crie `struct Cache<'a, T> { valor: Option<&'a T> }` com métodos:
- `fn definir(&mut self, val: &'a T)`
- `fn obter(&self) -> Option<&'a T>`
- `fn invalidar(&mut self)`

Demonstre que o cache não pode reter referências após os valores originais saírem de escopo.

### Exercício 7 — Explain the error

Para cada trecho, explique por que não compila e corrija:

# Aula 18 — Boas Práticas para Sistemas de Alto Desempenho e Código de Produção

## Objetivo da Aula
Nesta aula, vamos consolidar tudo o que aprendemos até aqui para escrever código Rust de classe mundial. O objetivo é focar em como desenhar sistemas de alto desempenho, escaláveis e prontos para produção. Discutiremos o design de APIs performáticas (minimizando alocações), a escolha correta de ponteiros inteligentes (`Box`, `Rc`, `Arc`), como lidar com erros sem penalizar a performance, seleção criteriosa de dependências (crates), testes avançados de concorrência e estratégias de monitoramento (observabilidade).

Esta aula fecha a trilha fundamental e conecta linguagem, arquitetura e operação em produção. O foco aqui já não é aprender um recurso isolado do Rust, mas aprender a tomar decisões de engenharia.

Mapa mental:

- APIs performáticas evitam trabalho invisível;
- escolha de tipo influencia custo real de memória, cache e sincronização;
- produção exige medição, observabilidade, linter, auditoria e disciplina de build.

Ao final, você deverá: aplicar o checklist de código de produção (sem `warnings`, `clippy` limpo, erros tipados, sem `unwrap` em caminho quente, logs e limites), distinguir código que compila de código operável, e revisar um módulo apontando violações.
Mediremos com níveis de proficiência:
- **Nível 1 — Recordar:** `definir cada item do checklist de produção e por que ele existe`;
- **Nível 2 — Aplicar:** `auditar um módulo e corrigir violações priorizando as de maior risco`;
- **Nível 3 — Projetar:** `elevar um protótipo a padrão de produção justificando cada mudança pelo risco que elimina`.

## 1. Design de APIs Performáticas e Zero-Cost Abstractions

O coração do alto desempenho em Rust (assim como em C++) é a premissa do *zero-cost abstraction*: o que você não usa, não paga; o que você usa, não poderia ser implementado de forma mais eficiente à mão.

- **Zero-cost abstraction**: abstração de alto nível cujo custo final em código gerado é equivalente ao de uma implementação manual bem escrita.
- Isso existe para permitir ergonomia sem sacrificar performance.

Para desenhar APIs rápidas, a regra número 1 é **evitar alocações desnecessárias no heap** e **evitar cópias ocultas**.

- **Alocação no heap**: reserva dinâmica de memória, geralmente muito mais cara do que operar só com dados já existentes na stack ou em buffers reaproveitados.
- **Cópia oculta**: custo que o chamador não percebe pela assinatura, mas que acontece internamente, como materializar uma `String` nova sem necessidade.

### C/C++ vs Rust
Em C++, passamos parâmetros frequentemente como `const std::string&` ou `std::string_view` para evitar cópias de strings literais. Em Rust, fazemos o mesmo utilizando *slices* e referências dinâmicas.

- **Slice**: visão emprestada de uma sequência contígua de dados, sem ownership.
- A ideia é a mesma dos tipos "view" em C++ moderno: observar sem copiar.

### Exemplo de API Ineficiente vs Eficiente

```rust
// ❌ INEFICIENTE: Força o chamador a alocar uma String no heap, 
// mesmo que ele já tenha um &str na stack ou no segmento de dados (.rodata).
fn processa_texto_ruim(texto: String) {
    println!("Processando: {}", texto);
}

// ✅ EFICIENTE: Usa uma string slice (&str). O chamador pode passar um &str
// diretamente ou uma referência para uma String (via Deref coercion),
// sem alocações extras no heap.
fn processa_texto_bom(texto: &str) {
    println!("Processando: {}", texto);
}

// ✅ AINDA MAIS GENÉRICO (Zero-Cost): Aceita qualquer coisa que possa ser
// vista como uma string (String, &str, Cow, PathBuf, etc.).
fn processa_qualquer_texto<T: AsRef<str>>(texto: T) {
    println!("Processando: {}", texto.as_ref());
}

fn main() {
    let estatico = "Texto no segmento de dados";
    let dinamico = String::from("Texto no heap");

    // processa_texto_ruim(estatico); // Erro de compilação! Precisa de .to_string() (Alocação!)
    
    processa_texto_bom(estatico); // Zero custo
    processa_texto_bom(&dinamico); // Zero custo (Deref coercion de &String para &str)
    
    processa_qualquer_texto(estatico);
    processa_qualquer_texto(dinamico); // O ownership é transferido, mas não há nova alocação.
}
```

- **`AsRef<str>`**: trait usada para dizer "esse tipo pode ser visto como `&str` sem forçar a API a aceitar apenas um tipo concreto".
- Isso ajuda a criar APIs mais flexíveis sem necessariamente induzir novas alocações.

## 2. Escolha de Tipos: `Box` vs `Rc` vs `Arc`

Em sistemas de baixo nível, você precisa ter controle absoluto de onde seus dados vivem e como o tempo de vida (*lifetime*) deles é gerenciado.

Aqui a pergunta correta não é "qual compila?", mas sim:

- quantos donos existem?;
- há compartilhamento entre threads?;
- o custo de contagem de referências vale a pena?;
- esse dado realmente precisa ir para o heap?

*   `Box<T>`: O equivalente exato do `std::unique_ptr<T>` em C++. É um ponteiro inteligente que aloca `T` no heap. Possui *ownership exclusivo*. Quando o `Box` sai de escopo, a memória é liberada (Drop). Custo: 1 alocação de heap, sem overhead de contagem de referências.
*   `Rc<T>`: *Reference Counted*. Equivalente ao `std::shared_ptr<T>` de C++, mas **apenas para uso em uma única thread**. Mantém um contador de referências. Quando o contador chega a zero, a memória é liberada. Custo: 1 alocação de heap, leve overhead para incrementar/decrementar o contador (operações não atômicas).
*   `Arc<T>`: *Atomic Reference Counted*. Equivalente ao `std::shared_ptr<T>` em cenários multi-thread. O contador usa operações atômicas da CPU (como instruções `LOCK XADD` no x86). Custo: Overhead atômico em cada `clone()`.

### Regra de Ouro da Concorrência
**Não use `Arc<Mutex<T>>` para tudo.** Clonar um `Arc` tem um pequeno custo atômico, mas travar um `Mutex` pode causar contenção severa (*lock contention*), enfileirando threads no SO e matando o paralelismo.

- **Lock contention**: competição entre múltiplas threads pelo mesmo lock.
- Esse fenômeno transforma paralelismo em fila, e fila significa tempo parado.

```rust
use std::sync::{Arc, Mutex};
use std::thread;

// Exemplo de compartilhamento seguro entre threads.
fn main() {
    // Aloca um contador no heap, protegido por um Mutex, e o envolve em um Arc
    // para que múltiplas threads possam possuir o ponteiro.
    let contador = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..10 {
        // Incrementa o contador atômico do Arc (Rápido)
        let contador_clone = Arc::clone(&contador);
        
        let handle = thread::spawn(move || {
            // Trava o Mutex. Se outra thread estiver com o lock, esta thread dorme (Lento/Contenção)
            let mut num = contador_clone.lock().unwrap();
            *num += 1;
        });
        handles.push(handle);
    }

    for handle in handles {
        handle.join().unwrap();
    }

    println!("Total: {}", *contador.lock().unwrap());
}
```

*Dica de Performance:* Se você só precisa incrementar números concorrentemente, use `std::sync::atomic::AtomicUsize` em vez de `Mutex<usize>`. O overhead é ordens de grandeza menor!

## 3. Padrões de Erro sem Overhead

Sistemas em produção não devem falhar silenciosamente (panic!). Rust usa `Result<T, E>` para tratamento de erros explícito. Porém, alocar strings de erro dinamicamente (ex: `Result<T, String>`) causa degradação de performance no *happy path* (caminho sem erros) devido ao tamanho da enum.

- **Happy path**: caminho principal de execução, em que a operação funciona como esperado.
- Mesmo quando o erro não acontece, o formato do tipo de erro ainda influencia layout e custo do `Result`.

*   **Tamanho do Result**: O compilador precisa alocar espaço na stack igual ao tamanho da maior variante do Enum. Se seu tipo de Erro é muito grande (ex: uma struct gigante), todo `Result` será gigante, prejudicando o cache da CPU.
*   **A Abordagem Correta**: Use enums simples que implementam a trait `std::error::Error`, ou oculte o erro grande no heap usando `Box<dyn std::error::Error>`.

Esse ponto é importante porque design de erro também é design de memória.

Para aplicações de produção, o ecossistema adotou duas crates padrões:
1.  **`thiserror`** (Para Bibliotecas/APIs): Permite derivar a trait `Error` em enums customizadas sem overhead.
2.  **`anyhow`** (Para Aplicações/Binários): Fornece um tipo `anyhow::Result<T>` que usa ponteiros sob o capô (box) para armazenar qualquer tipo de erro com stack trace, focado em facilidade de uso em aplicações finais.

## 4. Crate Selection (O Ecossistema)

Em C++, você confia na STL ou no Boost. Em Rust, o ecossistema é modularizado através do `cargo`. Para alto desempenho, você deve escolher as ferramentas certas:

- **Crate**: unidade de compilação e distribuição do ecossistema Rust.
- **Selecionar crates** corretamente é uma decisão de arquitetura, não apenas de conveniência.

### Concorrência vs Paralelismo (I/O Bound vs CPU Bound)
*   **Tokio (`tokio`)**: O runtime assíncrono padrão da indústria. Use para **I/O Bound** (Servidores Web, Banco de Dados, Redes). Ele usa uma thread pool baseada em *epoll/kqueue* e *work-stealing*.
*   **Rayon (`rayon`)**: O framework padrão para paralelismo de dados. Use para **CPU Bound** (Processamento de Imagens, Machine Learning, Cálculos Matemáticos). Ele converte iteradores padrão em iteradores paralelos magicamente (`iter()` -> `par_iter()`).
*   **Crossbeam (`crossbeam`)**: Primitivas de concorrência avançadas. Oferece canais (channels) mais rápidos que a biblioteca padrão, filas *lock-free* e `scope` threads.
    Esse `scope` permite que threads tomem referências emprestadas da stack, algo que `std::thread::spawn` não permite facilmente devido ao `'static` bound.

- **I/O Bound**: carga dominada por espera de disco, rede, banco ou socket.
- **CPU Bound**: carga dominada por cálculo puro.
- **Lock-free**: estrutura/protocolo que evita o uso de locks tradicionais no caminho crítico, embora isso não signifique ausência total de sincronização.

## 5. Estratégias de Teste para Código Concorrente

Testar código multi-thread com testes de unidade normais é pedir por problemas intermitentes (*flaky tests*), pois o escalonador do SO determina a ordem de execução.

- **Flaky test**: teste que às vezes passa, às vezes falha, sem mudança real no código.
- Em concorrência, isso acontece porque a ordem de interleaving entre threads pode variar a cada execução.

**A solução definitiva em Rust é o `Loom`**.
`Loom` é uma ferramenta para testar código concorrente em geral, incluindo cenarios com atomicos, locks e protocolos sem travas.

Ele executa seu teste múltiplas vezes, permutando exaustivamente todas as possíveis ordens de intercalação de threads e operações de memória, ajudando a revelar *data races* lógicas, violações de ordem e *deadlocks* que um teste comum pode não expor.

- **Interleaving**: diferentes formas de entrelaçar as operações de múltiplas threads.
- `Loom` existe porque concorrência correta não depende só de um agendamento casual "que funcionou na minha máquina".

## 6. Monitoramento em Produção (Observabilidade)

`println!` é para scripts. Para produção, precisamos de observabilidade estruturada.
A arquitetura de telemetria padrão em Rust baseia-se na crate **`tracing`**.

- **Observabilidade**: capacidade de entender o comportamento interno do sistema a partir de sinais externos, como logs, métricas e traces.
- **Telemetria**: coleta estruturada desses sinais para análise local ou remota.

`tracing` não gera apenas logs de texto, mas *spans* (rastreamentos com tempo de início e fim) que são cientes de concorrência e programação assíncrona (onde uma tarefa pode pular de thread em thread).

- **Span**: intervalo temporal com começo, fim e contexto associado.
- Isso é muito mais poderoso do que um log solto, porque permite acompanhar causalidade e duração.

```rust
// Exemplo conceitual de Tracing
use tracing::{info, instrument};

// A macro instrument cria automaticamente um Span com os argumentos da função.
#[instrument]
fn processa_pagamento(usuario_id: u32, valor: f64) {
    info!("Iniciando processamento de pagamento"); // Log dentro do Span
    // ... logica ...
    info!("Pagamento concluído");
}
```

Para monitorar CPU e Memória:
*   Use ferramentas como `perf` (Linux) ou `Instruments` (macOS) integradas com *flamegraphs* (`cargo flamegraph`).
*   Substitua o alocador padrão se necessário.
    O alocador do sistema operacional às vezes sofre de fragmentação. Muitos sistemas Rust de alta performance usam `jemalloc` ou `mimalloc` (basta adicionar a crate e registrar como `#[global_allocator]`).

## 7. Checklist Final para Sistemas Rust de Produção

Antes de fazer o deploy de um binário Rust crítico:

1.  [ ] **Profile Release**: Compile com `cargo build --release`. O código de debug em Rust é *extremamente* lento porque não aplica otimizações do LLVM.
2.  [ ] **LTO (Link-Time Optimization)**: No seu `Cargo.toml`, ative LTO para permitir que o compilador otimize através do limite das crates:
    ```toml
    [profile.release]
    lto = true
    codegen-units = 1 # Mais lento para compilar, binário final mais rápido
    panic = "abort"   # Opcional: Desliga stack unwinding em panics, binário menor
    ```
3.  [ ] **Clippy**: Rode `cargo clippy --all-targets --all-features -- -D warnings`. Não ignore os avisos do linter oficial.
4.  [ ] **Audit**: Rode `cargo audit` para verificar se há vulnerabilidades conhecidas em suas dependências.
5.  [ ] **Alocador Customizado**: Avalie o uso de `jemalloc` se sua aplicação sofre com alta taxa de alocação/desalocação de memória ou fragmentação severa.
6.  [ ] **Evite `.clone()` às cegas**: Cada `clone()` em uma `String` ou `Vec` é um `malloc` disfarçado. Entenda quem é o dono dos dados.

- **LTO**: otimização na etapa de linkedição que permite ao compilador enxergar melhor o programa como um todo.
- **Fragmentação**: situação em que a memória livre existe, mas fica espalhada de forma pouco eficiente para novas alocações.

## Erros Comuns e Anti-Padrões

1.  **"Driven by compiler errors" (Guiado pelos erros do compilador):** Inserir `.clone()` em todo lugar só para calar o Borrow Checker. Isso destrói a performance. O Borrow Checker está te avisando que seu design arquitetural ou fluxo de dados está confuso.
2.  **Abuso de `Arc<Mutex<T>>`:** Achando que é o "garbage collector" de Rust para concorrência. Desenhe seus sistemas usando passagem de mensagens (channels) ao invés de estado mutável compartilhado, sempre que possível.
3.  **Não usar `--release`:** Avaliar a performance de Rust usando `cargo run` (debug build) e achar que a linguagem é lenta. O LLVM em modo release faz mágica (inlining, vectorization, dead code elimination).

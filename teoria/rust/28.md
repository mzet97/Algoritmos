# Aula 28 — Interagindo com o Kernel: Syscalls Diretas e `mmap`

Syscall direta e `mmap` são Rust conversando com o kernel sem intermediários. Interagir com o sistema operacional pelo nome das chamadas é entender o que a biblioteca padrão faz por você.

## Nesta aula
Nesta aula, continuaremos no Módulo 3, mas agora com um Sistema Operacional (SO) por perto. Em vez de usar as bibliotecas de alto nível (`std::fs`), vamos aprender a ignorá-las e conversar diretamente com o Kernel do Linux (ou macOS) de duas formas:
1. Fazendo **Syscalls (Chamadas de Sistema)** diretamente através de código Assembly embutido (`asm!`).
2. Usando o poderoso comando `mmap` para mapear um arquivo inteiro do disco diretamente para a memória RAM, fazendo um *bypass* nos buffers de leitura tradicionais do SO para obter velocidade extrema.

O ponto desta aula nao e "parar de usar std para sempre", e sim entender o que realmente existe abaixo dela. Quando voce domina syscall e mapeamento de memoria, deixa de tratar sistema operacional como caixa-preta e passa a enxergar o custo real de I/O, copia de bytes e transicao entre user space e kernel space.

Você vai aprender a invocar syscalls diretas com `asm!`, mapear arquivos com `mmap`, explicar a transição user/kernel e o custo de cópias e buffers, e distinguir observação via biblioteca padrão do que ela não observa.

---

## 1. O Modelo Mental: O que é uma Syscall?

O Sistema Operacional divide a memória em duas partes estritas:
*   **User Space (Espaço do Usuário):** Onde seu programa Rust roda. Você não tem permissão para acessar o disco, a rede ou o teclado diretamente.
*   **Kernel Space (Espaço do Kernel):** Onde os drivers rodam. Ele tem acesso a tudo.

Quando você chama `println!("Olá")` ou `File::open("dados.txt")`, seu programa não toca no hardware. Ele prepara alguns registradores na CPU e executa uma instrução especial (no x86_64, a instrução `syscall`). Isso pausa seu programa, transfere o controle para o Kernel (Ring 0), o Kernel executa a ação, e devolve o controle para o seu programa. **Ring 0** e o nivel de privilegio maximo da CPU; ele existe para impedir que qualquer processo em user space danifique o sistema inteiro.

A biblioteca padrão (`std`) ou a `libc` em C (glibc/musl) são apenas "envelopes" (*wrappers*) amigáveis para essas Syscalls. Um **wrapper** existe para esconder detalhes de arquitetura, numero da syscall, tipos de retorno e tratamento de erro, de modo que voce programe contra uma interface estavel em vez de contra a ABI crua do kernel.

## 2. Fazendo Syscalls Diretas (Sem a `std`)

Apenas por motivos educacionais e de entendimento de sistemas, vamos escrever a palavra "Hello" na tela **sem usar** `println!` e sem usar a biblioteca C (`libc`). Vamos falar diretamente com o Kernel do Linux (arquitetura x86_64).

*Nota: Este código só rodará nativamente em um Linux x86_64. No Windows ou macOS, os números das syscalls e as convenções de chamada são diferentes.*

```rust
// Requer o uso da macro asm!
// `asm!` permite embutir instrucoes Assembly diretamente no Rust.
// Ela existe para casos em que precisamos controlar registradores,
// instrucoes especiais da CPU ou chamar interfaces binarias de baixo nivel.
use core::arch::asm;

// O número da syscall `write` no Linux x86_64 é 1.
// Ela espera:
// rdi = file descriptor (1 para stdout / tela)
// rsi = ponteiro para a string
// rdx = tamanho da string
fn syscall_write(mensagem: &str) {
    let msg_ptr = mensagem.as_ptr();
    let msg_len = mensagem.len();

    unsafe {
        asm!(
            "syscall",                  // A instrução mágica que acorda o Kernel
            in("rax") 1,                // 1 = sys_write
            in("rdi") 1,                // 1 = File Descriptor do Stdout
            in("rsi") msg_ptr,          // Onde a string começa
            in("rdx") msg_len,          // Quantos bytes imprimir
            out("rcx") _,               // O kernel sobrescreve rcx, avisamos o compilador
            out("r11") _,               // O kernel sobrescreve r11, avisamos o compilador
        );
    }
}

fn main() {
    syscall_write("Olá direto do Kernel!\n");
}
```

**Por que não fazemos isso o tempo todo?**
Porque os números das syscalls mudam de SO para SO. A `std` faz esse trabalho sujo de cross-compilação para você. Mas em sistemas de altíssimo desempenho (como bancos de dados), às vezes os engenheiros fazem *bypass* da `libc` para usar Syscalls recém-criadas pelo Linux que a biblioteca padrão ainda não suporta (como o `io_uring`). **File descriptor** e o inteiro pequeno que o kernel usa para representar recursos abertos, como arquivos, sockets e pipes. Em Unix, stdout e o descritor `1`.

## 3. O Poder Absoluto do `mmap` (Memory-Mapped Files)

A forma tradicional de ler um arquivo de 1 Gigabyte em C/C++ ou Rust (`File::read`) envolve:
1. Alocar um buffer de 1GB na RAM do User Space.
2. Fazer uma Syscall `read`.
3. O Kernel lê o disco, coloca em um buffer do Kernel Space (Page Cache).
4. O Kernel **copia** do Kernel Space para o seu buffer no User Space.
*Custo:* Dobro de memória (1GB no Kernel + 1GB no seu app) e tempo perdido copiando bytes da RAM para a RAM.

O **Page Cache** e o cache de paginas de arquivo mantido pelo kernel na RAM. Ele existe para evitar acessar o disco fisico toda vez que o mesmo trecho for lido de novo, ja que disco e ordens de magnitude mais lento que memoria.

### A Solução: `mmap`
A syscall `mmap` diz ao Kernel: *"Pegue esse arquivo no disco e engane a minha CPU. Faça parecer que esse arquivo já está carregado na minha memória RAM no endereço X."* `mmap` significa **memory map**, ou mapeamento de memoria. Ele existe para transformar um recurso externo, como arquivo ou regiao anonima, em um intervalo de enderecos que o processo acessa como se fosse RAM comum.
*   Não há alocação de buffer duplo.
*   Não há cópia do Kernel para o User Space.
*   Se você modificar um byte no endereço de memória, o Kernel atualiza o disco automaticamente em background!

### O Código Prático (Mapeando um arquivo enorme)

Para não escrevermos Syscalls em Assembly manualmente para o `mmap`, usaremos a crate `memmap2` (que encapsula a chamada segura da syscall para Windows/Linux/Mac).

```bash
cargo new mmap_rust
cd mmap_rust
cargo add memmap2
```

```rust
use memmap2::MmapOptions;
use std::fs::OpenOptions;
use std::io::Write;

fn main() -> Result<(), std::io::Error> {
    let file_path = "banco_de_dados_falso.bin";

    // 1. Cria um arquivo falso de 100 Megabytes
    {
        let mut file = std::fs::File::create(file_path)?;
        // Define o tamanho do arquivo rapidamente sem escrever dados úteis
        file.set_len(100 * 1024 * 1024)?; 
    }

    // 2. Abre o arquivo com permissão de Leitura e Escrita
    let file = OpenOptions::new()
        .read(true)
        .write(true)
        .open(file_path)?;

    // 3. Faz a mágica do MMAP
    // A partir de agora, `mmap` é um slice (um array `&mut [u8]`) gigantesco.
    // Slice e uma visao contigua sobre bytes em memoria, sem ser dono deles.
    let mut mmap = unsafe { 
        MmapOptions::new().map_mut(&file)? 
    };

    println!("Arquivo mapeado na memória! Tamanho: {} bytes", mmap.len());

    // 4. Modificando o arquivo (Zero Syscalls de `write`)
    // Ao invés de chamar file.write(), nós apenas alteramos variáveis na RAM!
    mmap[0] = b'R';
    mmap[1] = b'U';
    mmap[2] = b'S';
    mmap[3] = b'T';

    // 5. Força o SO a descarregar as alterações da RAM para o disco imediatamente
    mmap.flush()?;

    println!("Primeiros bytes: {:?}", &mmap[0..4]);

    // Quando `mmap` sai de escopo (Drop), o Kernel desfaz o mapeamento automaticamente.
    Ok(())
}
```

**Por que o `mmap` precisa do bloco `unsafe`?**
Porque o arquivo está mapeado diretamente na memória. Se outro programa no computador abrir o mesmo arquivo e deletá-lo enquanto o seu programa está rodando, a próxima vez que você tentar ler `mmap[0]`, a sua CPU vai disparar uma falha de segmentação (Segmentation Fault / SIGBUS) que o compilador Rust não tem como prever em tempo de compilação. Em outras palavras: a memoria parece normal, mas depende de um estado externo controlado pelo kernel e por outros processos.

## Erros Comuns e Anti-Padrões

1.  **Achar que `mmap` carrega tudo na RAM de uma vez:** Não! O Kernel é preguiçoso (*Lazy Loading*). Ele só carrega para a RAM os pedaços (páginas de 4KB) que você efetivamente acessar. Se você fizer `mmap` de um arquivo de 50GB em um PC com 8GB de RAM, o comando funciona! O SO vai jogando partes antigas fora e carregando partes novas conforme você acessa os índices do array (isso se chama *Page Fault*). Um **page fault** e o evento em que a CPU acessa uma pagina virtual ainda nao materializada na RAM e o kernel precisa trazê-la ou mapear seu conteudo antes da execucao continuar.
2.  **Usar `mmap` para leitura sequencial:** Se você vai ler um arquivo do começo ao fim apenas uma vez, o `File::read` sequencial com buffer pode ser mais rápido que o `mmap`, porque o SO otimiza a leitura antecipada (*read-ahead*). O `mmap` é o rei absoluto para **leituras aleatórias** (como buscar um registro no meio de um arquivo de banco de dados).

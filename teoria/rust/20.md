# Aula 20 — Servidores HTTP de Alta Performance: Anatomia do `hyper` e `axum`

## Objetivo da Aula
Nesta aula, iniciaremos o Módulo 1 (Backend de Alta Performance) construindo um servidor HTTP capaz de suportar centenas de milhares de conexões simultâneas com uso mínimo de memória e CPU. Vamos entender a arquitetura em camadas (`tokio` → `hyper` → `axum`), como o roteamento é feito de forma *zero-copy* e, crucialmente, como compartilhar estado global entre as *worker threads* sem causar contenção (*lock contention*) que paralise o *Event Loop*.

Esta aula marca a entrada prática no backend assíncrono moderno em Rust. Aqui, o objetivo não é apenas "fazer um servidor responder", mas entender como um servidor de alta performance consegue continuar útil sob carga pesada.

Mapa mental:

- um servidor rápido não é só código "bonito", mas arquitetura correta de I/O;
- a escolha entre bloqueante e assíncrono muda completamente o uso de threads;
- compartilhar estado errado pode destruir toda a vantagem do runtime.

Ao final, você deverá: explicar a arquitetura em camadas (`tokio` → `hyper` → `axum`), implementar roteamento com extração zero-copy, compartilhar estado entre workers sem contenção, e prever o efeito de estado compartilhado errado no event loop.
Mediremos com níveis de proficiência:
- **Nível 1 — Recordar:** `definir runtime, event loop, roteador, extrator e contenção de locks`;
- **Nível 2 — Aplicar:** `diagnosticar contenção sob carga e corrigir compartilhamento de estado ineficiente`;
- **Nível 3 — Projetar:** `projetar um serviço HTTP pequeno justificando camadas, estado e pontos de `.await``.

## 1. O Modelo Mental: Como Funciona um Servidor em Rust vs C++

Em C/C++, se você quiser construir um servidor web de alta performance (como o Nginx ou o framework Drogon), você precisará escrever um *Event Loop* baseado em `epoll` (Linux) ou `kqueue` (macOS/BSD). O fluxo típico é:
1. O socket do servidor recebe um evento de I/O.
2. O `epoll_wait` acorda uma thread.
3. A thread lê os bytes, faz o parsing manual do protocolo HTTP (geralmente usando uma máquina de estados finitos muito otimizada em C, como o `llhttp`).
4. A thread processa a rota e envia a resposta de volta.

Se você bloquear essa thread (por exemplo, fazendo uma query síncrona no banco ou usando um `std::mutex` demorado), o `epoll` para de processar novas conexões. Isso é o temido **"travar o Event Loop"**.

Termos fundamentais:

- **Event Loop**: laço principal que espera eventos de I/O e despacha trabalho quando rede ou socket ficam prontos.
- **`epoll` / `kqueue`**: APIs do sistema operacional para monitorar muitos descritores de arquivo sem bloquear uma thread por conexão.
- **Descritor de arquivo / file descriptor**: identificador numérico que representa recursos como sockets, arquivos e pipes.
- **I/O**: entrada e saída de dados, especialmente rede e disco.

### A Arquitetura em Rust
Rust abstrai esse processo de forma segura usando três camadas fundamentais:

1.  **`tokio` (O Motor):** É o runtime assíncrono. Ele implementa o `epoll`/`kqueue` sob o capô e possui uma *thread pool* inteligente que usa *work-stealing* (se uma thread fica sem tarefas, ela rouba tarefas de outra thread).
2.  **`hyper` (O Parser HTTP):** Uma biblioteca de baixo nível, extremamente rápida, escrita em Rust, focada apenas em falar o protocolo HTTP/1.1 e HTTP/2 corretamente e sem alocações desnecessárias.
3.  **`axum` (O Framework):** Construído sobre o `hyper`, é mantido pela mesma equipe do `tokio`. Ele adiciona roteamento (ex: `/api/users/:id`), extração de dados (JSON, Path) e middlewares, tudo isso sendo compilado para um serviço puro do `hyper` com overhead virtualmente zero.

Essas três camadas existem para separar responsabilidades:

- `tokio` cuida do runtime e do agendamento das tarefas;
- `hyper` fala HTTP com eficiência;
- `axum` organiza a API da aplicação de forma ergonômica.

## 2. O Roteamento *Zero-Cost* e Extractors no Axum

Diferente de frameworks em linguagens interpretadas (como Express.js no Node) que alocam objetos iterando sobre o path da URL em tempo de execução, o `axum` usa o sistema de tipos avançado do Rust (Traits e Generics) para resolver as rotas em tempo de compilação o máximo possível.

Ele utiliza o padrão de **Extractors**. Um *extractor* é qualquer tipo que implemente a trait `FromRequest`. Se a sua função (handler) pede um parâmetro que o Axum sabe extrair da requisição, ele o injeta automaticamente.

- **Roteamento**: processo de decidir qual função da aplicação deve tratar uma determinada URL/método HTTP.
- **Handler**: função que efetivamente processa a requisição.
- **Extractor**: mecanismo tipado que transforma partes da requisição em parâmetros já prontos para o handler.

Por que isso é importante?

- porque desloca parsing repetitivo para uma camada reutilizável;
- porque torna a assinatura da função mais expressiva;
- porque reduz código manual de baixo nível sem pagar o preço típico de frameworks lentos.

## 3. Estado Global e o Perigo do *Lock Contention*

Em um servidor web, frequentemente precisamos compartilhar um estado global (como um cache em memória, um pool de conexões do banco de dados, ou contadores de métricas) entre todas as requisições.

Como o `tokio` espalha as requisições em várias threads, esse estado precisa ser *Thread-Safe* (implementar as traits `Send` e `Sync`). O instinto natural de quem vem do C++ é colocar tudo num `std::mutex` e usar um `std::shared_ptr` (`Arc<Mutex<T>>` em Rust).

- **Estado global**: dados compartilhados por múltiplas requisições, conexões ou handlers.
- **Thread-safe**: seguro para uso em ambiente com múltiplas threads.
- **Lock contention**: competição entre várias execuções pelo mesmo lock, formando fila e aumentando latência.

**O problema:** Se você usar um Mutex padrão da biblioteca `std` (bloqueante do SO) e mantiver o lock enquanto faz uma operação assíncrona (como esperar o banco de dados), você vai **adormecer a worker thread do Tokio**. O SO tira a thread do processador, e o Tokio perde um de seus poucos *workers* de I/O.

Esse é um dos erros arquiteturais mais importantes da aula:

- não basta "usar mutex";
- é preciso entender se ele bloqueia thread do SO ou apenas suspende task;
- em runtime async, bloquear thread errada reduz o paralelismo efetivo do servidor inteiro.

### Soluções de Alta Performance
1.  **Tipos Atômicos (`AtomicUsize`):** Se for apenas um contador, use operações atômicas da CPU. (Zero lock no SO).
2.  **`tokio::sync::Mutex`:** Um Mutex assíncrono. Se o lock estiver ocupado, ele devolve a execução para o Tokio (faz um *yield*), permitindo que a thread processe outras requisições em vez de dormir no SO.
3.  **`std::sync::RwLock`:** (Read-Write Lock). Permite múltiplas leituras simultâneas, mas apenas uma escrita. Excelente para caches em memória que são lidos frequentemente e escritos raramente, desde que você **não o segure durante um `.await`**.

- **Atômico**: operação indivisível suportada pelo hardware para certos tipos de atualização concorrente.
- **`RwLock`**: lock com dois modos, leitura compartilhada e escrita exclusiva.
- **Yield**, nesse contexto, significa devolver a execução ao runtime para que outra task possa avançar.

## 4. Código Prático: Um Servidor Axum Completo

Primeiro, crie o projeto e adicione as dependências:
```bash
cargo new servidor_axum
cd servidor_axum
cargo add axum tokio --features tokio/full
cargo add serde --features serde/derive
cargo add serde_json
```

Agora, vamos ao código (`src/main.rs`). Explicado linha por linha:

```rust
use axum::{
    extract::{Path, State},
    routing::{get, post},
    Json, Router,
};
use serde::{Deserialize, Serialize};
use std::sync::{atomic::{AtomicUsize, Ordering}, Arc};
use tokio::net::TcpListener;

// 1. O Estado Global da Aplicação.
// Deve ser barato para clonar. O Arc (Atomic Reference Counted) resolve isso.
// Cada nova requisição receberá um clone deste Arc (custo atômico de incremento, quase zero).
#[derive(Clone)]
struct AppState {
    nome_servidor: String, // Dados imutáveis, seguros para leitura concorrente.
    // Usamos AtomicUsize em vez de Mutex<usize> para performance máxima.
    contador_requisicoes: Arc<AtomicUsize>, 
}

// 2. Structs para Parsing de JSON (Zero-cost deserialization na medida do possível)
#[derive(Deserialize)]
struct CriarUsuarioReq {
    nome: String,
    idade: u8,
}

#[derive(Serialize)]
struct RespostaPadrao {
    mensagem: String,
    requisicao_numero: usize,
}

// 3. Função Principal (O Ponto de Entrada do Tokio)
#[tokio::main] // Essa macro inicializa a thread pool do epoll/kqueue
async fn main() {
    // Inicializa o estado
    let state = AppState {
        nome_servidor: String::from("Servidor-Rust-Axum/1.0"),
        contador_requisicoes: Arc::new(AtomicUsize::new(0)),
    };

    // Constroi o roteador da aplicação
    let app = Router::new()
        .route("/", get(handler_raiz))
        .route("/usuarios/:id", get(handler_buscar_usuario))
        .route("/usuarios", post(handler_criar_usuario))
        // Injeta o estado em todas as rotas (usa o pattern "Extractor")
        .with_state(state);

    // Faz o bind na porta (usamos o TcpListener assíncrono do Tokio)
    let addr = "0.0.0.0:3000";
    let listener = TcpListener::bind(addr).await.unwrap();
    
    println!("🚀 Servidor rodando em http://{}", addr);

    // Inicia o hyper server passando o listener e a aplicação axum
    axum::serve(listener, app).await.unwrap();
}

// --- HANDLERS ---

// Extractor `State`: Puxa o AppState injetado no Router.
async fn handler_raiz(State(estado): State<AppState>) -> String {
    // Incrementa o contador atomicamente (Relaxed é a ordem de memória mais rápida,
    // equivalente a uma instrução de assembly simples sem barreiras complexas).
    let atual = estado.contador_requisicoes.fetch_add(1, Ordering::Relaxed);
    
    format!(
        "Bem-vindo ao {}! Você é o visitante número {}.",
        estado.nome_servidor, atual + 1
    )
}

// Extractor `Path`: Extrai variáveis da URL.
async fn handler_buscar_usuario(Path(id): Path<u32>) -> String {
    format!("Buscando usuário com ID: {}", id)
}

// Extractors Múltiplos: State e Json.
// O Axum lê o Body do TCP, desserializa via Serde, e passa para a função.
async fn handler_criar_usuario(
    State(estado): State<AppState>,
    Json(payload): Json<CriarUsuarioReq>, // O Body é consumido e mapeado para a Struct
) -> Json<RespostaPadrao> {
    
    let atual = estado.contador_requisicoes.fetch_add(1, Ordering::Relaxed);
    
    // Processamento simulado (ex: salvar no banco de dados)
    let msg = format!("Usuário {} de {} anos criado com sucesso!", payload.nome, payload.idade);

    // Retorna um JSON serializado automaticamente
    Json(RespostaPadrao {
        mensagem: msg,
        requisicao_numero: atual + 1,
    })
}
```

- **Desserialização**: transformar bytes recebidos da rede em estruturas de dados da aplicação.
- **Serialização**: o processo inverso, transformar estruturas em bytes para enviar ao cliente.

## 5. Erros Comuns e Anti-Padrões em Servidores Async

### ❌ Erro Crítico: Manter um `std::sync::Mutex` guardado através de um `.await`

```rust
use std::sync::Mutex;
use std::time::Duration;

// Isso compila, mas é um desastre de performance (e pode causar deadlocks no Tokio)
async fn handler_ruim(estado: State<Arc<Mutex<String>>>) {
    let mut lock = estado.lock().unwrap();
    *lock = String::from("Processando...");
    
    // ERRO! A thread do Tokio vai estacionar. O Mutex do SO continuará travado!
    // Outras requisições que tentarem pegar esse Mutex vão travar outras threads.
    tokio::time::sleep(Duration::from_secs(2)).await; 
    
    *lock = String::from("Pronto!");
}
```

**Solução:** 
Se o trecho assíncrono for muito longo, use `tokio::sync::Mutex`. Mas se for apenas para alterar um dado rápido em memória (sem I/O), use o Mutex do `std`, faça a alteração, e **solte o lock** (feche o escopo) antes do `.await`.

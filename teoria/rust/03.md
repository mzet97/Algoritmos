# Aula 3 — Ownership, Borrowing e References

---

## Nesta aula

Entender o sistema de **ownership** — o conceito mais importante de Rust. É o que torna Rust memory-safe sem garbage collector. Vamos dominar: as 3 regras de ownership, o que é **move** vs **copy**, como funcionam **referências** (`&` e `&mut`), as regras do **borrow checker**, e o modelo mental completo do que acontece na stack e no heap. Você vai aprender a enunciar as três regras de ownership, prever quando ocorre move vs. cópia (`Copy`), emprestar com `&` e `&mut` respeitando as regras do borrow checker, e diagnosticar erros de uso após move e de empréstimo duplo mutável.
---

## 1. O Problema que Ownership Resolve

Antes de entender ownership, vamos entender o problema.

### 1.1 Os bugs de memória em C/C++

Em C/C++, os seguintes bugs são **comuns** e **difíceis de detectar**:

```c
// 1. Use-after-free
int* p = malloc(sizeof(int));
*p = 42;
free(p);
printf("%d\n", *p);   // UB — acessando memória liberada

// 2. Double free
int* p = malloc(sizeof(int));
free(p);
free(p);              // UB — double free

// 3. Dangling pointer
int* criar() {
    int x = 42;
    return &x;        // UB — retornando ponteiro para stack local
}

// 4. Memory leak
void f() {
    int* p = malloc(1000 * sizeof(int));
    // esqueceu o free — vazou memória
}

// 5. Data race (em concorrência)
// thread 1: *p = 42;
// thread 2: *p = 99;   // data race — UB
```

Esses bugs causam: crashes, corrupção de memória, vulnerabilidades de segurança (CVEs), comportamento indeterminado.

### 1.3 O que significam os termos desta seção?

Como esta é a primeira vez que vários termos aparecem, vamos defini-los com precisão:

- **Memory-safe**: significa "seguro em relação ao uso de memória". Um programa memory-safe não acessa memória já liberada, não lê fora de limites válidos, e não trata um endereço inválido como se fosse dado legítimo.
- **Garbage Collector (GC)**: é um sistema automático que detecta quais objetos não estão mais sendo usados e libera a memória deles em runtime. Ele reduz bugs, mas introduz custo extra de CPU, uso de memória e, em muitos runtimes, pausas imprevisíveis.
- **Use-after-free**: bug em que o programa continua usando uma região de memória depois que ela já foi liberada.
- **Double free**: bug em que a mesma região é liberada duas vezes.
- **Dangling pointer**: ponteiro que ainda existe, mas aponta para uma região que já saiu de validade.
- **Memory leak**: vazamento de memória. A memória continua alocada, mas o programa perde a forma correta de liberá-la.
- **Data race**: duas execuções concorrentes acessam a mesma memória ao mesmo tempo, sendo que pelo menos uma escreve, sem sincronização correta.
- **UB (Undefined Behavior)**: comportamento indefinido. Significa que, a partir dali, a linguagem não promete mais nada. O programa pode parecer funcionar, falhar depois, ou abrir uma vulnerabilidade.

Por que isso importa? Porque ownership existe exatamente para impedir, em código safe, que esse tipo de bug chegue ao binário final.

### 1.2 Como outras linguagens resolvem

| Linguagem | Solução | Custo |
|-----------|---------|-------|
| C/C++ | Responsabilidade do programador | Bugs, UB, CVEs |
| Java/Python/Go | Garbage Collector | Latência, pausas, overhead de memória |
| C++ (smart pointers) | RAII + reference counting | Overhead, ciclos de referência |
| **Rust** | **Ownership + Borrow Checker** | **Custo zero em runtime** |

Rust resolve esses problemas **em tempo de compilação**, sem custo em runtime. O borrow checker é essencialmente um analisador de aliasing e lifetime que roda durante a compilação.

Vamos explicar esta frase com calma:

- **Tempo de compilação**: é a fase em que o compilador está analisando e transformando seu código-fonte em binário. Se o erro for pego aqui, o programa nem chega a rodar.
- **Tempo de execução (runtime)**: é quando o programa já está executando de verdade na máquina do usuário.
- **Aliasing**: acontece quando dois nomes, duas referências ou dois ponteiros conseguem acessar o mesmo dado.
- **Lifetime**: é o intervalo de tempo em que um valor ou uma referência continua válido.

Então, quando dizemos que o borrow checker analisa aliasing e lifetime, estamos dizendo que o compilador tenta provar duas coisas:

1. se existe mais de um caminho para acessar o mesmo dado;
2. se esses caminhos continuam válidos durante o tempo em que são usados.

Se essa prova falhar, o Rust recusa o código.

## 2. As Três Regras de Ownership

Ownership é um conjunto de 3 regras simples:

> **Regra 1:** Cada valor em Rust tem exatamente **um dono** (owner).
>
> **Regra 2:** Apenas **um** dono por vez. Quando o dono sai de escopo, o valor é **dropped** (liberado).
>
> **Regra 3:** Quando o dono é **movido** para outra variável, o original **não pode mais ser usado**.

Vamos entender cada uma com exemplos.

### 2.1 O que é ownership, afinal?

**Ownership** significa "propriedade" ou "posse". Em Rust, todo valor precisa ter um responsável principal pela sua existência. Esse responsável é o **owner**.

Por que isso existe?

- Porque alguém precisa ser responsável por liberar a memória no momento correto.
- Porque, sem um dono claramente definido, o programa cai nos problemas clássicos do C/C++: ninguém libera, duas partes tentam liberar, ou alguém acessa depois da liberação.

Para que isso serve na prática?

- Determinar com exatidão quem pode destruir o valor.
- Eliminar double free e use-after-free sem GC.
- Tornar o gerenciamento de memória previsível e barato.

### 2.2 O que é `drop`?

O termo **drop** aparece o tempo todo em Rust. `Drop` é o processo de limpeza de um valor quando seu dono sai de escopo.

Em linguagem direta:

- se o valor possui apenas dados simples na stack, o fim do escopo basta;
- se o valor controla recursos externos ou memória no heap, seu destrutor lógico é executado.

Em C você faria isso manualmente com `free`, `close`, `fclose`, `delete` e similares.
Em Rust, o modelo de ownership garante que isso aconteça automaticamente e apenas uma vez.

## 3. Regra 1 e 2 — Dono Único e Drop Automático

```rust
fn main() {
    {
        let s = String::from("olá");  // s é dona da String
        println!("{}", s);
    }   // s sai de escopo → String é dropped → memória liberada automaticamente
        // Equivalente a free() em C, mas automático e garantido
}
```

**O que acontece em memória:**

`String::from("olá")` cria uma string no **heap**. A variável `s` na stack contém 3 campos:

```
Stack (variável s):          Heap:
┌──────────────────┐        ┌─────────────────────────┐
│ ptr: ────────────────────→ │ 'o' 'l' 'á'             │
│ len: 3            │        └─────────────────────────┘
│ capacity: 3       │
└──────────────────┘
```

- `ptr` — ponteiro para os bytes no heap
- `len` — comprimento atual
- `capacity` — capacidade alocada

Aqui aparecem dois conceitos fundamentais:

- **Stack (pilha)**: região de memória rápida, organizada e de tamanho previsível, usada para dados cujo tamanho o compilador conhece em tempo de compilação.
- **Heap (monte)**: região de memória usada para dados cujo tamanho pode variar em runtime, como `String`, `Vec<T>` e buffers dinâmicos.

`String` usa os dois ao mesmo tempo:

- o objeto de controle (`ptr`, `len`, `capacity`) fica na stack;
- os bytes reais do texto ficam no heap.

Isso é importante porque ownership quase sempre envolve esse padrão: a variável dona vive na stack, mas controla algo alocado no heap.

**Quando `s` sai do escopo**, Rust chama automaticamente o método `drop` de `String`, que libera a memória no heap. Isso é **determinístico** — você sabe exatamente quando a memória é liberada, ao contrário de um GC.

**Comparação com C++:**
```cpp
{
    std::string s = "olá";
    std::cout << s << std::endl;
}   // destrutor de s chamado automaticamente (RAII)
```

O princípio é o mesmo (RAII), mas Rust vai além: o borrow checker **garante** que ninguém segura uma referência para essa memória após o drop.

**Comparação com C:**
```c
{
    char* s = strdup("olá");   // malloc
    printf("%s\n", s);
    free(s);                    // MANUAL — se esquecer, vaza
}
```

## 4. Regra 3 — Move Semântica (o conceito mais diferente de C/C++)

### 4.1 O problema em C/C++

Em C/C++, atribuir um ponteiro/struct cria uma **cópia** do ponteiro — dois ponteiros apontam para o mesmo dado:

```c
#include <stdio.h>
#include <string.h>
#include <stdlib.h>

int main(void) {
    char* s1 = strdup("olá");
    char* s2 = s1;            // COPIA o ponteiro — s1 e s2 apontam para o MESMO dado

    free(s1);
    // free(s2);              // double free! s2 aponta para memória já liberada
    printf("%s\n", s2);       // use-after-free!

    return 0;
}
```

O C permite isso. É responsabilidade do programador gerenciar quem é dono. Erros causam UB.

### 4.2 Como Rust resolve: Move

Em Rust, atribuir um valor que está no heap **move** a ownership — o original deixa de ser válido:

```rust
fn main() {
    let s1 = String::from("olá");
    let s2 = s1;              // s1 é MOVIDO para s2 — s1 não pode mais ser usado

    // println!("{}", s1);    // ERRO: value borrowed here after move
    println!("{}", s2);       // OK — s2 é a nova dona
}
```

**O que acontece em memória:**

```
Antes do move:
Stack:                     Heap:
┌────────────┐            ┌─────────┐
│ s1:        │            │ "olá"   │
│  ptr ─────────────────→ │         │
│  len: 3    │            └─────────┘
│  cap: 3    │
└────────────┘

Depois do move (let s2 = s1):
Stack:                     Heap:
┌────────────┐            ┌─────────┐
│ s1:        │            │ "olá"   │  (a MESMA memória — não foi copiada)
│  INVALIDADO│            │         │
│            │            └─────────┘
├────────────┤                 ↑
│ s2:        │                 │
│  ptr ───────────────────────┘
│  len: 3    │
│  cap: 3    │
└────────────┘
```

**Importante:** Não há cópia dos dados no heap! Apenas os 3 campos na stack (ptr, len, capacity) são copiados para `s2`. E `s1` é marcado como inválido. Isso é essencialmente uma **cópia superficial** (shallow copy) seguida de invalidação.

Vamos destrinchar os termos da primeira vez que aparecem:

- **Move**: transferência de ownership. O dado continua existindo, mas o dono oficial muda.
- **Copy**: duplicação barata de um valor simples, normalmente inteiro, float, bool, char ou composição desses tipos.
- **Shallow copy**: cópia apenas da camada superficial do objeto, por exemplo copiar ponteiros e metadados, sem duplicar o conteúdo do heap.
- **Deep copy**: cópia completa, incluindo nova alocação e duplicação dos dados reais.

Por que o Rust escolheu move como padrão para tipos como `String`?

- Porque se ele copiasse implicitamente apenas o ponteiro, haveria risco de dois donos para a mesma memória.
- Porque se ele fizesse deep copy automática, haveria custo oculto de performance.

Então o Rust escolhe o meio-termo mais honesto:

- para tipos simples: `Copy`;
- para tipos com recursos reais: `Move`;
- para cópia profunda: `.clone()` explícito.

**Por que isso funciona:**
- Apenas um dono (`s2`) → apenas um `drop` → sem double free.
- `s1` é invalidado → não pode acessar memória liberada → sem use-after-free.
- Tudo verificado em **tempo de compilação**.

### 4.3 Move em funções

Passar um valor para uma função também move a ownership:

```rust
fn processar(s: String) {
    println!("Processando: {}", s);
}   // s é dropped aqui — memória liberada

fn main() {
    let s1 = String::from("olá");
    processar(s1);            // s1 é MOVIDO para o parâmetro s

    // println!("{}", s1);    // ERRO: value borrowed here after move
}
```

**Modelo mental:**

```
main() chama processar(s1):

Stack:
┌──────────────────────┐
│ main() frame         │
│   s1: INVALIDADO     │  ← move aconteceu, s1 não é mais válido
├──────────────────────┤
│ processar() frame    │
│   s: String ("olá")  │  ← novo dono
│     ptr → heap       │
└──────────────────────┘

Quando processar() retorna:
- s é dropped → heap liberado
- s1 já estava invalidado → sem problema
```

### 4.4 Retornando ownership

Uma função pode retornar ownership:

```rust
fn criar_string() -> String {
    let s = String::from("olá");
    s                         // move de s para o chamador
}

fn main() {
    let s1 = criar_string();  // ownership move de criar_string para s1
    println!("{}", s1);        // OK — s1 é a dona
}
```

### 4.5 Transferindo e retornando

```rust
fn calcular_tamanho(s: String) -> (String, usize) {
    let comprimento = s.len();  // len() não consome a String
    (s, comprimento)            // retorna a String de volta + o tamanho
}

fn main() {
    let s1 = String::from("olá");
    let (s2, tamanho) = calcular_tamanho(s1);  // s1 movido para a função, devolvido como s2

    println!("'{}' tem {} bytes", s2, tamanho);  // s2 é a nova dona
}
```

Isso funciona, mas é **verboso** — entrar e sair de funções movendo ownership para todo lado seria cansativo. É aqui que entram as **referências** (borrowing).

## 5. Tipos Copy — Quando não há Move

Tipos que vivem inteiramente na stack são **copiados** por padrão (não movidos):

```rust
fn main() {
    let x: i32 = 42;
    let y = x;              // x é COPIADO (não movido)

    println!("x = {}, y = {}", x, y);  // AMBOS são válidos!
}
```

**Por que?** Porque copiar tipos simples (inteiros, floats, bool, char) é barato — são poucos bytes na stack. Não há ponteiro para heap, não há risco de double free.

O nome técnico por trás disso é o trait `Copy`.

- **Trait** em Rust é um conjunto de capacidades que um tipo pode implementar.
- Quando um tipo implementa `Copy`, o compilador sabe que duplicá-lo byte a byte é sempre seguro.
- Quando um tipo não implementa `Copy`, a atribuição transfere ownership por move.

Você pode pensar em `Copy` como o equivalente conceitual de "este tipo pode ser duplicado sem cerimônia, sem custo relevante e sem risco de quebrar o gerenciamento de recursos".

### Tipos que implementam Copy:

| Tipo | Copy? | Motivo |
|------|-------|--------|
| `i32`, `u8`, `f64`, etc. | **Sim** | Valores simples na stack |
| `bool` | **Sim** | 1 byte na stack |
| `char` | **Sim** | 4 bytes na stack |
| `(i32, f64)` | **Sim** | Tupla de tipos Copy |
| `&T` (referência imutável) | **Sim** | Apenas um ponteiro |
| `String` | **Não** | Tem ptr para heap — mover |
| `Vec<T>` | **Não** | Tem ptr para heap — mover |
| `&mut T` | **Não** | Regras de borrowing (único mutável) |

### Regra geral:

> Se um tipo implementa o trait `Copy`, a atribuição **copia**.
> Se não implementa `Copy`, a atribuição **move**.

**Como saber?** Se o tipo contém algo que precisa ser liberado (heap, arquivo, lock), ele **não** é `Copy`. Tipos "simples" são `Copy`.

## 6. Clone — Cópia Explícita

Quando você **realmente** quer copiar um tipo que não é `Copy`, use `.clone()`:

```rust
fn main() {
    let s1 = String::from("olá");
    let s2 = s1.clone();    // CÓPIA PROFUNDA — aloca novo espaço no heap

    println!("s1 = {}, s2 = {}", s1, s2);  // AMBOS são válidos
}
```

**O que acontece em memória:**

```
Stack:                       Heap:
┌────────────┐              ┌─────────┐
│ s1:        │              │ "olá"   │  ← original
│  ptr ──────────────────→  └─────────┘
│  len: 3    │
│  cap: 3    │              ┌─────────┐
├────────────┤              │ "olá"   │  ← clone (nova alocação!)
│ s2:        │              └─────────┘
│  ptr ──────────────────→
│  len: 3    │
│  cap: 3    │
└────────────┘
```

`.clone()` é sempre **explícito** — nunca implícito. Isso faz você pensar: "eu realmente preciso dessa cópia?". Em C/C++, cópias profundas podem acontecer implicitamente e causar problemas de performance silenciosos.

Esse é um ponto importante de engenharia:

- **o que é**: `clone()` é uma operação que cria uma cópia lógica independente do valor;
- **por que existe**: porque às vezes você realmente precisa que dois valores distintos sobrevivam ao mesmo tempo;
- **para que serve**: para preservar o original e criar outro valor com o mesmo conteúdo, aceitando o custo extra de memória e CPU.

**Comparação com C++:**
```cpp
std::string s1 = "olá";
std::string s2 = s1;  // C++ copia implicitamente — pode ser caro!
```

Em Rust:
```rust
let s1 = String::from("olá");
let s2 = s1;        // MOVE — zero custo
let s3 = s1.clone(); // CLONE — custo explícito
// println!("{}", s1); // ERRO — s1 foi movido
```

## 7. Borrowing — Empréstimo com Referências

Borrowing é o mecanismo que permite **usar** um valor sem tomar ownership. É o equivalente a ponteiros em C, mas com garantias de segurança.

Vamos separar com muita clareza:

- **Ownership** responde: quem é o dono?
- **Borrowing** responde: quem pode usar temporariamente sem virar dono?
- **Reference** responde: por qual objeto esse empréstimo é representado no código?

Ou seja, borrowing existe para evitar aquele padrão verboso de "mover para a função e devolver depois". Em vez de transferir a posse, você só empresta acesso temporário.

### 7.1 Referência imutável `&T`

```rust
fn calcular_tamanho(s: &String) -> usize {  // s é uma referência para String
    s.len()   // podemos ler, mas não modificar
}   // s sai de escopo, mas como é apenas uma REFERÊNCIA, nada é dropped

fn main() {
    let s1 = String::from("olá mundo");
    let tamanho = calcular_tamanho(&s1);  // emprestamos s1 (não movemos)

    println!("'{}' tem {} bytes", s1, tamanho);  // s1 ainda é válido!
}
```

**O que acontece:**

```
main() chama calcular_tamanho(&s1):

Stack:                          Heap:
┌──────────────────┐           ┌───────────────┐
│ main() frame     │           │               │
│   s1: String     │           │  "olá mundo"  │
│     ptr ──────────────────→  │               │
│     len: 9       │           └───────────────┘
│     cap: 9       │                ↑
├──────────────────┤                │
│ calcular_tamanho │                │
│   s: &String     │                │
│     ptr ─────────────────────────┘
│     (referência, |   (não é dono — não dropa)
│      não dona)   │
└──────────────────┘
```

- `s1` permanece a **dona** da `String`.
- `s` na função é uma **referência** — aponta para o mesmo dado, mas não é dona.
- Quando `calcular_tamanho` retorna, `s` desaparece, mas **nada é dropped** porque `s` não é dona.

O `&` é o operador de referência:

- `&T` significa "referência imutável para um valor do tipo `T`";
- "imutável" significa que por esse caminho você só pode ler, não modificar.

Para que isso serve?

- passar dados grandes para funções sem copiar;
- permitir leitura compartilhada;
- deixar claro, já na assinatura da função, que ela não vai tomar ownership.

**Comparação com C:**
```c
size_t calcular_tamanho(const char* s) {  // ponteiro const — podemos ler
    return strlen(s);
}

int main(void) {
    char* s1 = strdup("olá mundo");
    size_t tamanho = calcular_tamanho(s1);  // passamos o ponteiro
    printf("'%s' tem %zu bytes\n", s1, tamanho);
    free(s1);
}
```

Semelhante, mas em C:
- `const` é uma convenção — pode ser castado.
- Nada impede que outro thread modifique `s1` enquanto você lê.
- Nada impede que `s1` seja liberado enquanto `s` ainda é usado.

Rust garante tudo isso em tempo de compilação.

### 7.2 Referência mutável `&mut T`

```rust
fn adicionar_mundo(s: &mut String) {
    s.push_str(", mundo!");  // podemos modificar via referência mutável
}

fn main() {
    let mut s1 = String::from("olá");  // s1 deve ser mut para emprestar &mut
    adicionar_mundo(&mut s1);

    println!("{}", s1);  // "olá, mundo!"
}
```

Saída:
```
olá, mundo!
```

`&mut T` significa "referência mutável para um valor do tipo `T`".

O que isso quer dizer na prática?

- a função não vira dona do valor;
- mas, durante o empréstimo, ela ganha permissão exclusiva para modificar esse valor.

Por que o Rust exige exclusividade?

- porque escrever em memória enquanto outra parte do programa também lê ou escreve é exatamente a raiz de data races e inconsistências lógicas;
- então o compilador exige um contrato mais forte para escrita do que para leitura.

### 7.3 As Duas Regras do Borrow Checker

O borrow checker enforce duas regras fundamentais:

> **Regra 1:** A qualquer momento, você pode ter **UMA** referência mutável `&mut T` **OU** qualquer número de referências imutáveis `&T`, mas **nunca ambas ao mesmo tempo**.
>
> **Regra 2:** Referências devem **sempre** ser válidas (não podem sobreviver ao dono).

**Visualização da Regra 1:**

```
VÁLIDO:
  &T   &T   &T   &T          (várias imutáveis — leitura compartilhada OK)

VÁLIDO:
  &mut T                       (uma mutável — escrita exclusiva)

INVÁLIDO:
  &T   &T   &mut T             (não pode ter mutável e imutáveis ao mesmo tempo)

INVÁLIDO:
  &mut T   &mut T              (não pode ter duas mutáveis ao mesmo tempo)
```

**Por que?**

Esta regra preserva exclusividade de escrita. Ela também ajuda a impedir data races quando os acessos ocorrem em threads diferentes:

- Múltiplas `&T` (leitura): seguro — ninguém está escrevendo.
- Uma `&mut T` (escrita): seguro — ninguém mais está lendo ou escrevendo.
- `&T` + `&mut T` ativos sobre o mesmo valor: conflito de empréstimos, mesmo em uma única thread.
- Duas `&mut T` ativas sobre o mesmo valor: conflito de empréstimos, mesmo sem concorrência.

Quando esses acessos conflitantes acontecem sem sincronização em threads diferentes, há uma **data race**. Em C/C++, isso é comportamento indefinido; o compilador e as regras de `Send`/`Sync` impedem sua construção em Rust seguro. Código `unsafe` incorreto ainda pode introduzi-la.

### 7.4 Exemplos das regras

**Válido — múltiplas referências imutáveis:**
```rust
fn main() {
    let s = String::from("olá");

    let r1 = &s;    // &T
    let r2 = &s;    // &T
    let r3 = &s;    // &T

    println!("{} {} {}", r1, r2, r3);  // OK — todos são &T
}
```

**Inválido — referência mutável + imutável:**
```rust
fn main() {
    let mut s = String::from("olá");

    let r1 = &s;           // &T
    let r2 = &mut s;       // &mut T — ERRO: cannot borrow `s` as mutable because it is also borrowed as immutable

    println!("{} {}", r1, r2);
}
```

**Inválido — duas referências mutáveis:**
```rust
fn main() {
    let mut s = String::from("olá");

    let r1 = &mut s;       // &mut T
    let r2 = &mut s;       // ERRO: cannot borrow `s` as mutable more than once at a time

    println!("{} {}", r1, r2);
}
```

### 7.5 O escopo das referências importa

Uma referência não precisa existir por todo o escopo — só precisa não se sobrepor a outra referência incompatível:

```rust
fn main() {
    let mut s = String::from("olá");

    let r1 = &s;
    println!("{}", r1);     // r1 é usado aqui e depois não é mais necessário

    // r1 não é mais usado após este ponto (NLL — Non-Lexical Lifetimes)
    let r2 = &mut s;        // OK! r1 já não está mais em uso
    println!("{}", r2);
}
```

Rust usa **Non-Lexical Lifetimes (NLL)** — o compilador percebe que `r1` não é mais usado antes de `r2` ser criado, então permite. O borrow checker olha para quando as referências são **realmente usadas pela última vez**, não apenas quando o escopo lexical termina.

Esse termo assusta à primeira vista, então vamos traduzir:

- **Lexical** significa "baseado no texto do código, no bloco entre chaves".
- **Non-Lexical Lifetime** significa que o compilador não olha apenas para onde o bloco termina, mas para o último uso real da referência.

Para que isso serve?

- reduzir rejeições desnecessárias do compilador;
- permitir código natural sem relaxar a segurança.

## 8. Referências e Slices de String (preview)

Referências para strings são tão comuns que Rust tem um tipo especial:

```rust
fn primeira_palavra(s: &str) -> &str {
    let bytes = s.as_bytes();

    for (i, &item) in bytes.iter().enumerate() {
        if item == b' ' {
            return &s[0..i];   // slice da string
        }
    }

    &s[..]
}

fn main() {
    let s = String::from("olá mundo");
    let palavra = primeira_palavra(&s);  // &String vira &str automaticamente (deref coercion)
    println!("Primeira palavra: {}", palavra);  // "olá"
}
```

Veremos slices em detalhes na Aula 4. O importante agora: `&str` é uma **referência para uma fatia de string** — empresta os dados sem tomar ownership.

## 9. O que o Borrow Checker NÃO Permite — e Por Que

### 9.1 Dangling pointer — impossível

```rust
fn gerar_dangling() -> &String {   // ERRO: missing lifetime specifier
    let s = String::from("olá");
    &s    // retornaria referência para variável local!
}   // s é dropped aqui — a referência apontaria para memória liberada
```

O compilador recusa. Em C:
```c
char* gerar_dangling(void) {
    char s[] = "olá";
    return s;   // COMPILA em C! Retorna endereço de stack local — UB
}
```

Rust **garante** que isso nunca compila. O sistema de lifetimes (que veremos na Aula 10) formaliza isso.

### 9.2 Aliasing com mutabilidade — impossível

```rust
fn main() {
    let mut dados = vec![1, 2, 3];  // Vec na heap

    let primeira = &dados[0];       // referência imutável para dados[0]
    dados.push(4);                  // ERRO: cannot borrow `dados` as mutable
                                    // (push precisa de &mut self)
    println!("{}", primeira);       // primeira poderia apontar para memória realocada!
}
```

**Por que é um erro:** `push(4)` pode realocar o array no heap (se capacity < 4). Se isso acontecesse, `primeira` apontaria para a memória antiga (já liberada). Em C/C++, isso seria um bug silencioso. Rust impede em compilação.

### 9.3 Iteração com modificação — o clássico

```rust
fn main() {
    let mut v = vec![1, 2, 3];

    // for val in &v {              // empresta v imutavelmente
    //     v.push(4);              // ERRO: tenta emprestar mutavelmente
    // }

    // A forma correta depende do que você quer fazer.
    // Coletar o que precisa e depois modificar:
    let copia: Vec<i32> = v.iter().copied().collect();
    for _ in &copia {
        v.push(4);
    }
    println!("{:?}", v);  // [1, 2, 3, 4, 4, 4]
}
```

Em C++, o equivalente com `std::vector` causaria UB (ponteiro/iterador invalidado após realocação). Rust impede em compilação.

## 11. Tabela Comparativa — C/C++ vs Rust (Gerenciamento de Memória)

| Situação | C/C++ | Rust |
|----------|-------|------|
| Criar string | `char* s = strdup("olá")` | `let s = String::from("olá")` |
| Atribuir | `s2 = s1` → dois ponteiros, mesmo dado | `let s2 = s1` → **move**, s1 inválido |
| Liberar | `free(s)` manual | Automático ao sair do escopo |
| Esquecer free | Vazamento de memória | `Drop` libera valores que saem do escopo; ciclos de `Rc` e `mem::forget` ainda podem vazar memória |
| Usar após free | UB | Impedido em Rust seguro; `unsafe`/FFI exigem contrato correto |
| Double free | UB | Impedido em Rust seguro; `unsafe`/FFI exigem contrato correto |
| Passar para função | Copia ponteiro → quem é dono? | Move ou borrow — sempre claro |
| Ler sem modificar | `const char*` (convenção) | `&T` (garantia do compilador) |
| Modificar | `char*` (qualquer um pode) | `&mut T` (exclusivo, compilador enforce) |
| Data race | UB em runtime | Impedida em Rust seguro pelo sistema de tipos e sincronização |

Vazamentos por ciclos de `Rc` são demonstrados no [livro oficial do Rust](https://doc.rust-lang.org/book/ch15-06-reference-cycles.html).

## 12. Exemplo Completo

```rust
// aula3_ownership.rs
// Compilar: rustc aula3_ownership.rs
// Executar: ./aula3_ownership


// 1. Borrowing imutável — função que apenas lê
fn descrever(s: &String) -> String {
    format!("String '{}' com {} bytes, capacidade {}", s, s.len(), s.capacity())
}

// 2. Borrowing mutável — função que modifica
fn gritar(s: &mut String) {
    s.push_str("!!!");
    s.make_ascii_uppercase();
}

// 3. Ownership transferida — função que consome
fn consumir(s: String) {
    println!("Consumiu: '{}'", s);
}   // s é dropped aqui

// 4. Retornando ownership
fn criar_mensagem(nome: &str) -> String {
    let mut msg = String::from("Olá, ");
    msg.push_str(nome);
    msg.push_str("! Bem-vindo ao Rust.");
    msg   // retorna ownership
}

// 5. Múltiplos parâmetros com diferentes modos
fn analise(origem: &String, destino: &mut String) -> usize {
    destino.push_str(origem);
    destino.len()
}

fn main() {
    println!("=== Ownership ===\n");

    // --- Move ---
    println!("--- Move ---");
    let s1 = String::from("rust");
    let s2 = s1;                    // move
    // println!("{}", s1);          // ERRO: s1 movido
    println!("s2 (depois do move): {}", s2);

    // --- Clone ---
    println!("\n--- Clone ---");
    let s3 = String::from("rust");
    let s4 = s3.clone();           // cópia profunda
    println!("s3 = {}, s4 = {} (ambos válidos)", s3, s4);

    // --- Copy ---
    println!("\n--- Copy ---");
    let x: i32 = 42;
    let y = x;                     // copy (i32 é Copy)
    println!("x = {}, y = {} (ambos válidos)", x, y);

    // --- Borrowing imutável ---
    println!("\n--- Borrowing Imutável ---");
    let s5 = String::from("Olá mundo");
    let desc = descrever(&s5);      // emprestamos s5 (não movemos)
    println!("{}", desc);
    println!("s5 ainda é válido: {}", s5);   // s5 ainda aqui!

    let r1 = &s5;
    let r2 = &s5;
    let r3 = &s5;                   // múltiplas &T — OK
    println!("r1={}, r2={}, r3={}", r1, r2, r3);

    // --- Borrowing mutável ---
    println!("\n--- Borrowing Mutável ---");
    let mut s6 = String::from("socorro");
    gritar(&mut s6);
    println!("Depois de gritar: {}", s6);

    // --- Transferência de ownership ---
    println!("\n--- Transferência de Ownership ---");
    let s7 = String::from("adeus");
    consumir(s7);                    // s7 é movido para consumir()
    // println!("{}", s7);          // ERRO: s7 movido

    // --- Retorno de ownership ---
    println!("\n--- Retorno de Ownership ---");
    let s8 = criar_mensagem("Doutor");
    println!("Mensagem criada: {}", s8);

    // --- Múltiplos borrows não-sobrepostos (NLL) ---
    println!("\n--- NLL (Non-Lexical Lifetimes) ---");
    let mut s9 = String::from("hello");
    let r4 = &s9;
    println!("r4 = {}", r4);        // r4 usado pela última vez aqui

    let r5 = &mut s9;               // OK! r4 não é mais usado (NLL)
    r5.push_str(" world");
    println!("r5 = {}", r5);

    // --- Análise com ambos os tipos ---
    println!("\n--- Análise ---");
    let mut buffer = String::new();
    let dados = String::from("dados importantes");
    let tamanho = analise(&dados, &mut buffer);
    println!("Buffer: '{}' ({} bytes)", buffer, tamanho);
    println!("Dados originais intactos: '{}'", dados);
}
```


## 13. Erros Comuns

### Erro 1: Usar variável após move

```rust
let s1 = String::from("olá");
let s2 = s1;
println!("{}", s1);  // erroE0382: borrow of moved value: `s1`
```

**Solução:** Use `&s1` antes do move, use `.clone()`, ou restruture o código.

### Erro 2: Múltiplas referências mutáveis

```rust
let mut s = String::from("olá");
let r1 = &mut s;
let r2 = &mut s;  // erroE0499: cannot borrow `s` as mutable more than once at a time
```

**Solução:** Use escopos separados:
```rust
let mut s = String::from("olá");
{
    let r1 = &mut s;
    r1.push_str("!");
}
let r2 = &mut s;  // OK — r1 já saiu de escopo
r2.push_str("?");
```

### Erro 3: Misturar &T e &mut T

```rust
let mut s = String::from("olá");
let r1 = &s;
let r2 = &mut s;   // erroE0502: cannot borrow `s` as mutable because it is also borrowed as immutable
println!("{} {}", r1, r2);
```

**Solução:** Garanta que `r1` não é mais usado antes de criar `r2` (NLL), ou use escopos.

### Erro 4: Esquecer `mut` na variável para &mut

```rust
let s = String::from("olá");     // sem mut
let r = &mut s;  // erroE0596: cannot borrow `s` as mutable, as it is not declared as mutable
```

**Solução:** `let mut s = ...`

### Erro 5: Retornar referência para local

```rust
fn pior_funcao() -> &String {
    let s = String::from("olá");
    &s    // erroE0515: cannot return reference to local variable `s`
}
```

**Solução:** Retorne a String (transfira ownership), não uma referência:
```rust
fn boa_funcao() -> String {
    String::from("olá")
}
```

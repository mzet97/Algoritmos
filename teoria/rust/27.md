# Aula 27 — Bare Metal: Rust `#![no_std]` e Sistemas Embarcados

Sem sistema operacional, sem alocador, sem desculpas: `#![no_std]` em bare metal é Rust provando que ownership funciona onde só há registradores e datasheets. A base dos embarcados deste livro.

## Nesta aula
Bem-vindo ao **Módulo 3: Programação de Sistemas e Baixo Nível (Bare Metal)**.
Nesta aula, daremos um passo atrás na complexidade das aplicações e um passo profundo em direção ao hardware. Vamos aprender a usar Rust **sem Sistema Operacional**. Veremos o que a macro `#![no_std]` realmente faz, como escrever código que roda diretamente em microcontroladores (como o Raspberry Pi Pico ou STM32) ou no bootloader de um PC, e como gerenciar pânicos quando não há um console para imprimir mensagens. Bare metal significa exatamente isso: código executando sobre o hardware quase cru, sem a camada de serviços de um sistema operacional para fornecer arquivos, processos, heap ou drivers genéricos.

Você vai aprender a configurar um alvo `#![no_std]`, distinguir `core` de `std`, implementar o ponto de entrada e o pânico em bare metal, e explicar o que o programa perde sem sistema operacional (alocador, threads, I/O).

---

## 1. O Modelo Mental: `std` vs `core`

Quando você escreve um programa normal em Rust (ou C/C++), você tem o luxo de um Sistema Operacional (SO) rodando por baixo.
Se você quer alocar memória (`String`, `Vec`, `Box`), o SO tem um alocador de *heap* gerenciando páginas de memória RAM. Heap e a regiao de memoria usada para alocacoes dinamicas, quando o tamanho ou tempo de vida dos dados nao cabe bem apenas na stack. Se você usa `println!()` ou `std::fs::File`, o programa faz uma *Syscall* (chamada de sistema) pedindo para o kernel do Linux ou Windows imprimir os bytes na tela ou ler o disco. Syscall existe porque programas em modo usuario nao podem tocar diretamente no hardware ou em recursos privilegiados; eles precisam pedir servico ao kernel.

### A Biblioteca Padrão (`std`)
A `std` é a biblioteca padrão do Rust que **depende** de um SO. Ela contém threads, I/O de rede, arquivos, e variáveis de ambiente. Em termos de modelo mental, `std` e a camada confortavel que pressupoe que alguem ja inicializou memoria, processo, console, relogio e servicos basicos.

### A Biblioteca Central (`core`)
Se você está escrevendo o *próprio* Sistema Operacional, ou o firmware de uma geladeira, não existe SO para fazer *syscalls*. Você está sozinho com a CPU e os registradores.
Para esses casos, usamos `#![no_std]`. O Rust desliga a `std` e nos deixa apenas com a **`core`**.
A `core` é puramente matemática e lógica. Ela não sabe o que é um arquivo, não sabe o que é a tela, e **não sabe o que é o heap** (sem `String` ou `Vec`). Ela só contém primitivas, traits, slices (`&[u8]`), Option, Result e iteradores. Na pratica, `core` existe para que a linguagem Rust continue utilizavel mesmo quando nao ha sistema operacional, exatamente o tipo de cenario em que C historicamente dominou.

## 2. Escrevendo um Binário Bare Metal (O Básico)

Se você simplesmente colocar `#![no_std]` no topo do seu `main.rs` e tentar compilar com `cargo build`, o compilador vai gritar com você. Por quê?

1.  Ele precisa de uma função para lidar com o *Panic* (quando o programa quebra, o que ele faz se não tem SO para abortar?).
2.  A função `main` normal do Rust é chamada por um ambiente de inicialização em C (o *crt0*), que prepara a pilha (stack) antes de chamar a sua `main`. A **stack** e a regiao de memoria onde ficam variaveis locais e dados de chamadas de funcao. Em bare metal, você precisa definir o ponto de entrada real.

### Setup do Projeto

```bash
cargo new bare_metal
cd bare_metal
```

### O Código (`src/main.rs`)

```rust
// 1. Remove a biblioteca padrão. Não há SO aqui.
#![no_std]
// 2. Remove o ponto de entrada padrão do Rust (a função main normal).
#![no_main]

use core::panic::PanicInfo;

// 3. O Ponto de Entrada Real (Entry Point)
// "Entry point" e o primeiro simbolo que o hardware, bootloader ou linker
// conhece como inicio formal da execucao do programa.
// O atributo `#[unsafe(no_mangle)]` diz ao compilador para não renomear a função
// para nomes bizarros (como _ZN10bare_metal5_start17...).
// Precisamos manter o nome `_start` exato, pois é aqui que o Bootloader ou o
// hardware vai procurar a primeira instrução para executar após ligar a energia.
#[unsafe(no_mangle)]
pub extern "C" fn _start() -> ! {
    // `extern "C"` usa a convenção de chamada da linguagem C (C ABI).
    // ABI significa Application Binary Interface: o contrato binario de como
    // funcoes recebem argumentos, retornam valores e organizam registradores.
    // O retorno `!` (Never type) significa que esta função nunca pode retornar.
    // Se o firmware de um microcontrolador retornar, para onde ele vai? Para o nada.

    // Como não temos println!, e não sabemos qual hardware estamos rodando,
    // não podemos imprimir "Hello World" facilmente sem drivers específicos.
    
    // Simulação de lógica Bare Metal:
    let mut contador = 0;
    
    // Loop infinito (Firmware sempre roda para sempre)
    loop {
        contador += 1;
        
        // Em um hardware real (ex: GBA, Arduino), você escreveria em 
        // endereços de memória físicos fixos (Memory Mapped I/O - MMIO)
        // para acender um LED.
        
        // let led_porta = 0x4000_0000 as *mut u32;
        // unsafe {
        //     core::ptr::write_volatile(led_porta, 1);
        // }
    }
}

// 4. O Panic Handler Obrigatório
// Se ocorrer um `panic!("erro")` ou um index out of bounds, o compilador pula para cá.
#[panic_handler]
fn panic(_info: &PanicInfo) -> ! {
    // Sem SO, não podemos imprimir a stack trace na tela.
    // A reação padrão de um hardware simples é travar em um loop infinito,
    // ou talvez enviar um sinal elétrico para reiniciar a placa (Watchdog Timer).
    loop {}
}
```

## 3. Alocação de Memória Dinâmica (O `alloc`)

Você pode pensar: *"Se não tenho `std`, eu nunca poderei usar um `Vec` ou `String` no meu Kernel?"*

Não exatamente. O Rust possui uma crate intermediária chamada **`alloc`**. Ela contém `Vec`, `String`, `Box` e `Rc`.
Para usá-la em um ambiente `#![no_std]`, você precisa fornecer um **Global Allocator** (Alocador Global). Um alocador global e o componente responsavel por entregar e liberar blocos do heap para toda a aplicacao. Ou seja, você precisa escrever (ou importar) a lógica de como pedir blocos de memória e como liberá-los.

```rust
// Habilita o uso da crate alloc (requer nightly ou features específicas)
extern crate alloc;

use alloc::vec::Vec;
use core::alloc::{GlobalAlloc, Layout};

// Um alocador "dummy" (falso) apenas para o exemplo compilar.
// Na vida real, você implementaria um algoritmo de "Buddy Allocator" ou "Slab Allocator".
struct MeuAlocadorBurro;

unsafe impl GlobalAlloc for MeuAlocadorBurro {
    unsafe fn alloc(&self, _layout: Layout) -> *mut u8 {
        core::ptr::null_mut() // Retorna nulo (falha sempre, mas compila)
    }
    unsafe fn dealloc(&self, _ptr: *mut u8, _layout: Layout) {}
}

// Registra nossa struct como o alocador oficial do sistema
#[global_allocator]
static ALOCADOR: MeuAlocadorBurro = MeuAlocadorBurro;

// Agora o compilador permite usar Vec!
// let meu_vetor = Vec::new();
```

## 4. MMIO (Memory Mapped I/O) e Hardware Real

Em bare metal, você não usa portas USB chamando APIs. O hardware mapeia pinos elétricos, sensores e LEDs diretamente para **endereços de memória RAM falsos**. Essa tecnica se chama **MMIO** (Memory Mapped I/O), isto e, entrada e saida mapeadas em memoria. Ela existe porque a CPU ja sabe ler e escrever enderecos; entao o hardware expoe registradores como se fossem memoria comum. Se você escrever o número `1` no endereço de memória `0x2000_0000`, a voltagem de um pino de cobre na placa sobe para 3.3V (acendendo um LED).

Em C, fazemos isso usando macros `#define` e cast de ponteiros.
Em Rust, fazemos o mesmo de forma segura:

```rust
// Endereço fictício de um periférico no manual do processador
const ENDERECO_LED: *mut u32 = 0x4002_0C14 as *mut u32;

pub fn ligar_led() {
    // Qualquer escrita direta em memória exige um bloco `unsafe`.
    unsafe {
        // Usamos write_volatile para garantir que o compilador LLVM não remova
        // esta escrita. Se usássemos `=` normal, o LLVM pensaria:
        // "Ninguém nunca lê dessa variável, vou apagá-la para otimizar!".
        // Volatile diz: "O hardware se importa com essa escrita, faça-a!".
        core::ptr::write_volatile(ENDERECO_LED, 1);
    }
}
```

Felizmente, no ecossistema Rust Embarcado (Embedded Rust), você não precisa decorar endereços hexadecimais. A comunidade fornece **PACs** (Peripheral Access Crates) geradas automaticamente a partir dos manuais em PDF das fabricantes de chips (SVD files). Uma PAC existe para expor registradores e perifericos reais do chip como tipos Rust, reduzindo erro humano ao lidar com enderecos crus. Isso fornece uma API 100% segura para ligar o LED sem nenhum `unsafe` no seu código final!

## Erros Comuns e Anti-Padrões

1.  **Esquecer o `write_volatile` / `read_volatile`:** Em C/C++ você usa a palavra-chave `volatile int *`. Em Rust, você usa as funções do módulo `core::ptr`. Se você usar ponteiros crus normais para interagir com o hardware, o LLVM otimizará seu código em Release e seu firmware vai parar de funcionar silenciosamente.
2.  **Usar floats sem FPU:** Muitos microcontroladores baratos (como o Cortex-M0) não possuem unidade de ponto flutuante no hardware. Se você usar `f32` no seu código `no_std`, o compilador terá que injetar milhares de linhas de código em software para simular a matemática, estourando a memória minúscula (Flash) da placa.
3.  **Recursão Infinita:** Sem SO, a sua Pilha (Stack) é minúscula (às vezes 2KB ou 4KB). Se você usar recursão, dará Stack Overflow muito rápido, corrompendo outras áreas vitais da memória e travando o chip.

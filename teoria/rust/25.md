# Aula 25 — Introdução a GPGPU: wgpu e Compute Shaders

## Objetivo da Aula
Nesta aula, daremos um salto colossal no paralelismo. Se na Aula 24 aprendemos a usar SIMD para processar 8 ou 16 elementos simultaneamente na CPU, agora vamos enviar dados para a memória da **Placa de Vídeo (VRAM)** e utilizar milhares de núcleos simultaneamente usando a tecnologia **GPGPU** (General-Purpose computing on Graphics Processing Units). GPGPU significa usar a GPU para computação geral, e não apenas para desenhar triângulos na tela. Ela existe porque certas cargas numéricas massivas, como álgebra linear, simulações físicas e inferência de redes neurais, escalam muito melhor em milhares de núcleos simples do que em poucos núcleos complexos da CPU. Faremos isso usando a crate `wgpu` e a linguagem de shaders **WGSL** (WebGPU Shading Language), uma abordagem moderna, agnóstica e mais portável que CUDA.

---

## 1. O Modelo Mental: CPU vs GPU

### A CPU (O Carro Esportivo)
A CPU tem poucos núcleos (4 a 32), mas eles são extremamente rápidos e complexos. Eles possuem caches gigantes (L1, L2, L3), predição de desvio (*branch prediction*) e são otimizados para executar tarefas seriais complexas (como um carro esportivo transportando poucas pessoas muito rápido).

### A GPU (O Ônibus Biarticulado)
A GPU possui **milhares** de núcleos (ex: uma RTX 3080 tem ~8700 núcleos CUDA). Esses núcleos são lentos, simples e não têm caches grandes nem predição de desvio complexa. Porém, se você precisa aplicar a mesma fórmula matemática a 10 milhões de elementos, a GPU faz tudo ao mesmo tempo (como um ônibus lento que transporta milhares de pessoas de uma vez).

**O Gargalo do Barramento (PCI-Express):**
A memória da CPU (RAM) e a memória da GPU (VRAM) são separadas. VRAM (Video RAM) existe porque a GPU precisa de uma memória própria, com largura de banda enorme, para alimentar milhares de núcleos em paralelo. O maior desafio em GPGPU é o tempo que leva para copiar dados da RAM para a VRAM pelo barramento PCI-Express. Se o cálculo for muito simples, o tempo de cópia será maior que o tempo de cálculo, e a CPU vencerá. Em outras palavras: GPU acelera computação, mas a movimentação de dados entre CPU e GPU pode destruir o ganho se o problema não for grande o bastante.

## 2. Abstrações: CUDA vs Vulkan vs wgpu

Em C++, o padrão para cálculos em placa de vídeo é o **CUDA** (da NVIDIA). CUDA é o ecossistema proprietário da NVIDIA para programar a GPU com extensões de C/C++ e bibliotecas de alto desempenho. O problema é que o código CUDA só roda em placas NVIDIA.
Se você quiser rodar na AMD ou Apple Silicon, precisa usar OpenCL, Vulkan ou Metal. Vulkan e Metal são APIs de baixo nível para conversar diretamente com o driver gráfico e a GPU; elas existem para dar controle fino sobre memória, sincronização e execução, mas cobram esse poder com enorme verbosidade. A dor de cabeça de configurar C++ para essas APIs é lendária (centenas de linhas de código apenas para inicializar a API).

**A Solução em Rust: `wgpu`**
A crate `wgpu` é uma implementação da API WebGPU (o novo padrão da web, sucessor do WebGL). WebGPU existe para oferecer um modelo moderno e relativamente uniforme de acesso a GPU em navegadores e também fora deles. O `wgpu` funciona como uma camada de abstração "segura" sobre Vulkan, Metal e DirectX. Você escreve o código do host (CPU) em Rust, o código do dispositivo (GPU) em **WGSL**, e o `wgpu` traduz isso para o backend correto do seu hardware. Na prática, ele resolve um problema clássico de C/C++: reduzir drasticamente a quantidade de código de inicialização específico por plataforma.

## 3. O Fluxo de Trabalho de um Compute Shader

Para rodar código na GPU, o fluxo sempre segue estes 5 passos:
1. **Host:** Inicializa a GPU (Device) e a Fila de Comandos (Queue).
2. **Host:** Aloca buffers na VRAM (Buffers de GPU).
3. **Host:** Copia os dados da RAM para os buffers da VRAM.
4. **Host:** Envia o *Compute Shader* (o código WGSL) e despacha o comando de execução.
5. **Host:** Espera a GPU terminar, copia o resultado de volta para a RAM.

Aqui, **Host** significa o lado CPU do programa, que organiza a execução. Já o **Device** representa a GPU lógica escolhida pelo driver, e a **Queue** é a fila onde você enfileira comandos para a GPU executar em ordem. O **Compute Shader** é um pequeno programa que roda na GPU focado em cálculo, não em renderização. Ele existe para aplicar a mesma rotina em milhares ou milhões de elementos sem o overhead de criar threads manuais na CPU.

## 4. O Código Prático: Multiplicação Paralela Extrema

Crie um novo projeto:
```bash
cargo new gpu_rust
cd gpu_rust
cargo add wgpu tokio bytemuck futures-intrusive
# bytemuck é usado para converter Vec<f32> em fatias de bytes puros &[u8] com segurança
# futures-intrusive fornece o canal one-shot usado para esperar o mapeamento assíncrono do buffer
```

### O Compute Shader (`src/shader.wgsl`)
Crie este arquivo. Um **shader** é um programa pequeno executado dentro da GPU. Historicamente, shaders nasceram para gráficos, mas hoje também executam cálculo geral. A linguagem **WGSL** existe para descrever esses programas de forma portável dentro do ecossistema WebGPU.

```wgsl
// O buffer que contém nossos dados de entrada.
// "storage" indica memória global da GPU, "read_write" permite leitura e escrita.
// Pense nele como um grande array residente na VRAM.
@group(0) @binding(0)
var<storage, read_write> dados: array<f32>;

// O Ponto de Entrada (Main)
// @workgroup_size(64) diz que a GPU agrupará 64 threads de execução juntas.
// Um workgroup e um bloco cooperativo de threads despachado como unidade.
@compute @workgroup_size(64)
fn main(@builtin(global_invocation_id) global_id: vec3<u32>) {
    // global_id.x é o "índice" único desta thread específica (de 0 até N)
    let index = global_id.x;

    // Se o índice for válido, multiplicamos o valor por 10
    if (index < arrayLength(&dados)) {
        dados[index] = dados[index] * 10.0;
    }
}
```

### O Código Rust (`src/main.rs`)

*Aviso: Código wgpu é verboso, mas em C++ seria 5x maior.*

```rust
use wgpu::util::DeviceExt;
use std::time::Instant;

// wgpu é assíncrono por natureza, então usamos tokio.
// "Assíncrono" aqui significa que várias operações dependem do driver e do hardware,
// então o programa não bloqueia a thread principal o tempo todo esperando a GPU.
#[tokio::main]
async fn main() {
    // Nossos dados de entrada: Array de 1 até 1 milhão
    let input_data: Vec<f32> = (0..1_000_000).map(|i| i as f32).collect();

    // 1. Inicialização da GPU
    let instance = wgpu::Instance::default();
    let adapter = instance
        .request_adapter(&wgpu::RequestAdapterOptions::default())
        .await
        .unwrap();
    let (device, queue) = adapter
        .request_device(&wgpu::DeviceDescriptor::default(), None)
        .await
        .unwrap();

    // 2. Compilar o Shader (WGSL)
    let shader = device.create_shader_module(wgpu::ShaderModuleDescriptor {
        label: Some("Meu Compute Shader"),
        source: wgpu::ShaderSource::Wgsl(include_str!("shader.wgsl").into()),
    });

    // 3. Criar os Buffers na GPU
    // Buffer A: Memória Global da GPU (VRAM rápida), onde o shader vai ler/escrever.
    // Buffer e a abstração básica de bloco linear de memória na GPU.
    let gpu_buffer = device.create_buffer_init(&wgpu::util::BufferInitDescriptor {
        label: Some("Buffer de Computação"),
        contents: bytemuck::cast_slice(&input_data),
        usage: wgpu::BufferUsages::STORAGE
            | wgpu::BufferUsages::COPY_DST  // CPU pode copiar PARA cá
            | wgpu::BufferUsages::COPY_SRC, // CPU pode copiar DAQUI
    });

    // Buffer B: Buffer de Leitura (Staging).
    // "Staging buffer" e um buffer intermediário usado para transferir dados
    // entre mundos com regras diferentes: a VRAM da GPU e a RAM acessível pela CPU.
    // Necessário porque a CPU não pode ler a VRAM diretamente de forma rápida.
    let staging_buffer = device.create_buffer(&wgpu::BufferDescriptor {
        label: Some("Buffer de Leitura"),
        size: gpu_buffer.size(),
        usage: wgpu::BufferUsages::MAP_READ | wgpu::BufferUsages::COPY_DST,
        mapped_at_creation: false,
    });

    // 4. Configurar o Pipeline e Bind Group (Como o shader acessa o buffer)
    // Pipeline descreve qual shader sera executado.
    // Bind Group descreve quais recursos de memoria esse shader enxergara.
    let compute_pipeline = device.create_compute_pipeline(&wgpu::ComputePipelineDescriptor {
        label: None,
        layout: None,
        module: &shader,
        entry_point: "main",
    });

    let bind_group_layout = compute_pipeline.get_bind_group_layout(0);
    let bind_group = device.create_bind_group(&wgpu::BindGroupDescriptor {
        label: None,
        layout: &bind_group_layout,
        entries: &[wgpu::BindGroupEntry {
            binding: 0,
            resource: gpu_buffer.as_entire_binding(),
        }],
    });

    // 5. Despachar os comandos para a GPU
    let mut encoder = device.create_command_encoder(&wgpu::CommandEncoderDescriptor { label: None });
    {
        let mut cpass = encoder.begin_compute_pass(&wgpu::ComputePassDescriptor { label: None, timestamp_writes: None });
        cpass.set_pipeline(&compute_pipeline);
        cpass.set_bind_group(0, &bind_group, &[]);
        // Despacha as threads. Se temos 1 milhão de elementos e blocos de 64,
        // precisamos de (1M / 64) blocos de trabalho (Workgroups).
        let workgroup_count = (input_data.len() as f32 / 64.0).ceil() as u32;
        cpass.dispatch_workgroups(workgroup_count, 1, 1);
    }

    // Copia o resultado do GPU_Buffer para o Staging_Buffer
    encoder.copy_buffer_to_buffer(&gpu_buffer, 0, &staging_buffer, 0, gpu_buffer.size());
    
    // Submete a fila para execução na Placa de Vídeo
    let start_time = Instant::now();
    queue.submit(Some(encoder.finish()));

    // 6. Ler o resultado de volta para a RAM (CPU)
    let buffer_slice = staging_buffer.slice(..);
    let (sender, receiver) = futures_intrusive::channel::shared::oneshot_channel();
    buffer_slice.map_async(wgpu::MapMode::Read, move |v| sender.send(v).unwrap());

    // Faz a GPU trabalhar e sincroniza
    device.poll(wgpu::Maintain::Wait);
    receiver.receive().await.unwrap().unwrap();

    let data = buffer_slice.get_mapped_range();
    let result: &[f32] = bytemuck::cast_slice(&data);

    println!("Tempo na GPU: {:?}", start_time.elapsed());
    println!("Exemplo de resultado (índice 500): original = {}, gpu = {}", input_data[500], result[500]);
}
```

## Erros Comuns

1.  **Achar que a GPU sempre será mais rápida:** Se o array for pequeno (ex: 10.000 floats) e a operação for simples (ex: `+ 1`), a CPU vencerá, pois o custo de fazer as cópias de memória via PCI-Express será maior que o tempo de cálculo. GPGPU brilha em matrizes gigantescas e cálculos densos (Machine Learning, Criptografia, Raytracing).
2.  **Aliasing e Sincronização:** GPUs executam threads em ordem arbitrária. Se duas threads tentarem escrever no mesmo índice do array ao mesmo tempo, você terá *Data Races* silenciosos (GPU não tem panic!, apenas gera "lixo" numérico).
3.  **Tamanhos de Workgroup Incompatíveis:** Sempre alinhe seus arrays ou passe variáveis uniformes para evitar que uma thread tente ler fora dos limites da memória alocada (por isso o `if (index < arrayLength(&dados))` no WGSL é fundamental).

## Exercícios Obrigatórios

1.  **Soma de Dois Vetores:** Modifique o código e o shader para aceitar **três** arrays: `buffer_a`, `buffer_b` e `buffer_c` (o resultado). O shader WGSL deverá fazer `buffer_c[i] = buffer_a[i] + buffer_b[i]`. Você precisará alterar as anotações `@binding(0)`, `@binding(1)` e `@binding(2)`.
2.  **Profile Real:** Aumente o tamanho do array para 100 milhões de elementos (`100_000_000`). Crie uma função em Rust que faça a mesma multiplicação (`* 10.0)`) em CPU e meça o tempo de ambas usando `Instant::now()`. Veja quem ganha (Lembre-se de usar `cargo run --release`).

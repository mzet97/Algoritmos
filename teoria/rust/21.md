# Aula 21 — WebSockets e Arquitetura Orientada a Eventos

## Objetivo da Aula
Nesta aula, evoluiremos nosso backend de alta performance para suportar conexões bidirecionais de longa duração (WebSockets). O desafio aqui não é apenas responder requisições rapidamente, mas sim **manter dezenas de milhares de conexões TCP ativas simultaneamente**, roteando mensagens entre elas em tempo real (Publish/Subscribe), com uso mínimo de RAM e sem causar travamentos (*deadlocks* ou *lock contention*).

Esta aula amplia a arquitetura da aula anterior. Agora, em vez de conexões curtas do tipo "pede e responde", vamos trabalhar com conexões persistentes, em que o servidor precisa continuar acompanhando cada cliente ao longo do tempo.

Mapa mental:

- HTTP tradicional é curto e pontual;
- WebSocket é duradouro e bidirecional;
- a arquitetura correta deixa de ser "responder rápido" e passa a ser "gerenciar milhares de conexões vivas sem desperdiçar memória".

---

## 1. O Modelo Mental: Conexões Persistentes em C++ vs Rust

Em um servidor HTTP tradicional (REST), a vida de uma conexão é curta:
`Aceitar Socket -> Ler Request -> Processar -> Escrever Response -> Fechar Socket`.

Com WebSockets, o fluxo muda drasticamente:
1. O cliente faz uma requisição HTTP pedindo um *Upgrade* para WebSocket.
2. O servidor aceita. A partir de agora, o socket TCP fica aberto indefinidamente.
3. Ambos podem enviar "Frames" (mensagens) a qualquer momento.

Termos fundamentais:

- **Conexão persistente**: conexão que permanece aberta por muito tempo.
- **Bidirecional**: ambos os lados podem enviar dados, não apenas cliente→servidor e depois resposta.
- **Frame**: unidade de mensagem no protocolo WebSocket.
- **Upgrade HTTP**: etapa inicial em que a conexão deixa de ser tratada como HTTP normal e passa a seguir o protocolo WebSocket.

**O Problema Clássico em C/C++ (Thread-per-Connection):**
Se você alocar uma thread real do SO (POSIX Thread) para cada cliente conectado esperando uma mensagem, com 10.000 usuários conectados, você terá 10.000 threads. O *Context Switch* (troca de contexto) do SO vai derreter a sua CPU, e o consumo de memória (cada thread tem sua própria stack de ~2MB a 8MB) vai estourar a RAM do servidor (8MB * 10.000 = 80GB apenas de overhead de stack).

- **Thread-per-connection**: modelo em que cada conexão ganha sua própria thread dedicada.
- **Context switch**: custo de pausar uma thread e retomar outra, trocando registradores, pilha e estado de execução.
- **Overhead**: custo extra de infraestrutura que não é o trabalho útil principal.

**A Solução do Rust (Tokio Tasks):**
No Tokio, cada conexão WebSocket rodará em uma **Task** (uma *green thread* leve). Uma Task do Tokio consome apenas algumas centenas de **bytes** e não requer uma thread do SO exclusiva. O Tokio consegue colocar 10.000 conexões WebSocket dormentes dentro de um punhado de threads reais do SO usando a API `epoll` do Linux. Quando um pacote chega na placa de rede, o SO avisa o `epoll`, o Tokio acorda a Task exata que estava esperando, ela processa a mensagem, e volta a dormir.

Esse modelo existe porque a maior parte do tempo dessas conexões é espera de I/O, não cálculo puro.

## 2. Comunicação entre Tasks (Canais / Channels)

Se temos 10.000 clientes conectados (10.000 Tasks independentes), como um cliente envia uma mensagem para todos os outros (como em um Chat)?

Nós **não** usamos um vetor global `Vec<Socket>` protegido por um `Mutex`. Iterar sobre 10.000 sockets segurando um lock vai destruir a concorrência.

Em vez disso, usamos a filosofia de Go e Rust: *"Não comunique compartilhando memória; compartilhe memória comunicando"*.

Essa frase resume um princípio de arquitetura:

- em vez de todo mundo disputar a mesma estrutura mutável;
- fazemos as tasks trocarem mensagens explicitamente;
- isso reduz lock contention e simplifica o raciocínio de concorrência.

Usamos os **Canais Assíncronos do Tokio (`tokio::sync`)**:
*   `mpsc` (Multi-Producer, Single-Consumer): Várias tasks enviam dados, uma única task recebe.
*   **`broadcast` (Multi-Producer, Multi-Consumer):** O canal perfeito para WebSockets! Várias tasks podem publicar uma mensagem, e *todas* as tasks inscritas no canal recebem uma cópia.

- **Canal assíncrono**: estrutura de passagem de mensagens cuja espera por envio/recebimento coopera com o runtime async.
- **Publish/Subscribe**: padrão em que emissores publicam mensagens e assinantes interessados recebem essas mensagens.

## 3. Código Prático: Um Servidor de Chat Real-Time com Axum

Primeiro, atualize as dependências do projeto da aula anterior (ou crie um novo):
```bash
cargo add axum --features ws
cargo add tokio --features full
cargo add futures
```
*Nota: Adicionamos a feature `ws` no axum e o pacote `futures` (usado para lidar com streams assíncronos).*

- **Feature**, aqui, é uma opção de compilação que habilita subconjuntos da crate.
- **Stream assíncrono** é uma sequência de itens que chega ao longo do tempo, semelhante a um iterator, mas com espera assíncrona entre elementos.

### `src/main.rs`

```rust
use axum::{
    extract::{
        ws::{Message, WebSocket, WebSocketUpgrade},
        State,
    },
    response::IntoResponse,
    routing::get,
    Router,
};
use futures::{sink::SinkExt, stream::StreamExt};
use std::sync::Arc;
use tokio::sync::broadcast;
use tokio::net::TcpListener;

// 1. Nosso Estado Global da Aplicação
// Diferente da aula anterior, agora armazenamos um Canal de Broadcast.
// O "tx" (Transmitter) é usado para ENVIAR mensagens.
// Quando precisarmos RECEBER, clonaremos o "tx" para gerar um novo "rx" (Receiver).
#[derive(Clone)]
struct AppState {
    tx: broadcast::Sender<String>,
}

#[tokio::main]
async fn main() {
    // Cria um canal broadcast que suporta até 100 mensagens na fila.
    // Se a fila encher porque os consumidores (clientes) estão lentos,
    // os consumidores mais atrasados tomarão erro de "Lagged" e serão desconectados,
    // protegendo a RAM do servidor de OOM (Out Of Memory).

- **Fila**, aqui, é o buffer interno temporário do canal.
- **OOM (Out Of Memory)**: condição em que o processo ou o sistema fica sem memória disponível.
- Limitar a fila é uma decisão de proteção: é melhor desconectar consumidores muito lentos do que deixar a RAM crescer sem limite.
    let (tx, _rx) = broadcast::channel(100);

    let state = AppState { tx };

    let app = Router::new()
        .route("/ws", get(handler_websocket))
        .with_state(state);

    let addr = "0.0.0.0:3000";
    let listener = TcpListener::bind(addr).await.unwrap();
    println!("🚀 Servidor WebSocket rodando em ws://{}", addr);

    axum::serve(listener, app).await.unwrap();
}

// 2. O Handler da Rota HTTP
// Recebe a requisição inicial HTTP e faz o "Upgrade" para o protocolo WebSocket.
async fn handler_websocket(
    ws: WebSocketUpgrade,
    State(state): State<AppState>,
) -> impl IntoResponse {
    // O Axum toma conta do handshake HTTP 101 Switching Protocols.
    // Quando a conexão for estabelecida, ele chamará a função `gerenciar_conexao_ws`.
    ws.on_upgrade(move |socket| gerenciar_conexao_ws(socket, state))
}

// 3. O Loop Principal de cada Cliente (Rodando em uma Task concorrente)
async fn gerenciar_conexao_ws(stream: WebSocket, state: AppState) {
    // Um WebSocket é um stream bidirecional (Lê e Escreve ao mesmo tempo).
    // Usamos o método .split() da trait StreamExt para dividir o socket em dois:
    // `sender` (para enviar dados para O ESTE cliente)
    // `receiver` (para ler dados DESTE cliente)
    let (mut sender, mut receiver) = stream.split();

    // Nós nos inscrevemos no canal global para receber as mensagens do servidor.
    let mut rx_global = state.tx.subscribe();

    // Precisamos rodar duas coisas simultaneamente DESTE cliente:
    // A) Escutar mensagens que chegam da rede (do cliente) e publicar no canal global.
    // B) Escutar o canal global e enviar as mensagens para a rede (para o cliente).
    // Para isso, usamos a macro `tokio::spawn` para criar uma nova Task para o recebimento.

    // TASK A: Lendo do Canal Global e enviando para o WebSocket
    // Fazemos o `spawn` (thread leve separada) pois essa task precisa ficar
    // bloqueada esperando mensagens chegarem no `rx_global` indefinidamente.
    let mut send_task = tokio::spawn(async move {
        // Loop infinito esperando mensagens do sistema
        while let Ok(msg) = rx_global.recv().await {
            // Se enviar falhar (ex: cliente fechou a aba do navegador abruptamente),
            // quebramos o loop para encerrar a task.
            if sender.send(Message::Text(msg)).await.is_err() {
                break;
            }
        }
    });

    // TASK B: Lendo do WebSocket e enviando para o Canal Global
    // Fica na Task atual.
    let tx_clone = state.tx.clone();
    let mut recv_task = tokio::spawn(async move {
        // receiver.next().await fica "dormindo" no epoll do Linux sem gastar CPU
        // até que o cliente envie uma nova mensagem TCP.
        while let Some(Ok(Message::Text(texto))) = receiver.next().await {
            // Cliente enviou texto. Fazemos o broadcast para todos!
            // Ignoramos erro de "não há ninguém ouvindo" usando `let _ =`
            let _ = tx_clone.send(format!("Cliente diz: {}", texto));
        }
    });

    // A mágica da concorrência: `tokio::select!`
    // Espera até que QUALQUER UMA das duas tasks (send ou recv) termine.
    // Se o cliente desconectar, o `recv_task` termina. O `select!` acorda e encerra
    // a função, o que cancela (drop) automaticamente a `send_task` que estava sobrando.
    tokio::select! {
        _ = (&mut send_task) => println!("Send task finalizada"),
        _ = (&mut recv_task) => println!("Recv task finalizada"),
    };

    println!("Cliente desconectado. Limpando recursos (Zero vazamento de memória).");
}
```

- **`tokio::select!`**: macro que espera múltiplas operações assíncronas ao mesmo tempo e segue a primeira que terminar.
- **Cancelamento**, aqui, significa descartar futures/tasks que perderam a corrida, permitindo liberar recursos cedo.

- **Transmitter (`tx`)**: ponta do canal usada para publicar mensagens.
- **Receiver (`rx`)**: ponta usada para receber mensagens.

- **Handshake**: negociação inicial entre cliente e servidor para estabelecer o protocolo e o estado da conexão.

- **`split()`** existe para separar logicamente a metade de leitura e a metade de escrita do socket.
- Isso é importante porque ler e escrever ao mesmo tempo é exatamente o comportamento normal de um WebSocket real.

## 4. Análise de Memória e Ownership

O que acontece com a memória quando o cliente conecta e desconecta?

1.  **Ownership do Socket:** Quando chamamos `stream.split()`, o socket TCP interno é consumido e dividido logicamente. O compilador garante que você não pode ler do `sender` nem escrever no `receiver`.
2.  **O Canal de Broadcast:** O `tx` principal mora no `AppState`. Cada nova conexão WebSocket clona o `tx` e chama `.subscribe()`.
3.  **Cancelamento Seguro (Drop):** Em C++, gerenciar o tempo de vida de duas threads lidando com o mesmo socket geralmente requer *weak_ptrs* ou flags atômicas complexas de desligamento. No código acima, o `tokio::select!` cancela a Task perdedora instantaneamente. Quando a task é cancelada, todas as variáveis dentro dela (`rx_global`, `sender`, etc.) saem de escopo e têm seu destrutor (`Drop`) chamado. O TCP é fechado limpo e a inscrição no canal é removida da memória automaticamente.

Esse é um dos grandes benefícios do modelo Rust + Tokio: cancelamento conversa naturalmente com escopo, ownership e `Drop`.

## Erros Comuns

1.  **Usar std::sync::mpsc ao invés de tokio::sync::mpsc:** Os canais da biblioteca padrão do Rust são **bloqueantes** para a thread do SO. Nunca os use dentro de um contexto async do Tokio, ou você causará *lock contention*.
2.  **Não lidar com mensagens do tipo Ping/Pong:** No mundo real (atrás de Nginx/AWS/Cloudflare), conexões inativas são derrubadas após ~60 segundos. Se o cliente não envia mensagens frequentemente, seu servidor precisa enviar `Message::Ping` periodicamente e esperar um `Message::Pong` do cliente para manter o roteador da nuvem acordado.
3.  **Vazamento de Tasks:** Fazer um `tokio::spawn` em um loop infinito que nunca termina, mesmo após o socket ser fechado (evitamos isso com o `tokio::select!`).

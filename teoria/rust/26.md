# Aula 26 — Ecossistema CUDA e Compilando Rust para a GPU (`rust-gpu`)

## Objetivo da Aula
Nesta aula, encerraremos o Módulo 2 (HPC e GPU) explorando o estado da arte e a fronteira experimental da linguagem. Na aula anterior, escrevemos shaders em WGSL, o que significa que tínhamos duas linguagens diferentes (Rust na CPU, WGSL na GPU). Agora, vamos entender como usar o ecossistema **`rust-gpu`** para compilar **Rust puro** diretamente para instruções de Placa de Vídeo (SPIR-V), permitindo o compartilhamento das mesmas *structs* e lógicas entre CPU e GPU sem duplicação de código. O objetivo aqui não é apenas aprender uma ferramenta exótica, mas entender um problema de engenharia real: manter CPU e GPU coerentes sem duplicar tipos, regras de alinhamento e lógica matemática.

---

## 1. O Modelo Mental: O Problema das Duas Linguagens

Em projetos sérios de C++ com CUDA, o programador escreve código em um dialeto misto (`.cu`). O compilador da NVIDIA (`nvcc`) separa o que é código de CPU (Host) do que é código de GPU (Device), permitindo usar as mesmas `structs` C++ em ambos os lados.

Quando usamos `wgpu` com WGSL (ou Vulkan com GLSL/HLSL), sofremos do **Problema das Duas Linguagens**:
1. Você define uma `struct Player { x: f32, y: f32 }` em Rust.
2. Você tem que reescrever `struct Player { x: f32, y: f32 }` em WGSL.
3. Se você mudar a struct no Rust e esquecer de mudar no WGSL, os bytes ficam desalinhados, e a GPU lê lixo da memória (o famoso erro de *padding/alignment*).

### A Solução: `rust-gpu`
O projeto `rust-gpu` (patrocinado pela Embark Studios) modifica o compilador do Rust (`rustc`) adicionando um novo backend. Em vez de o LLVM gerar assembly x86 ou ARM, o compilador gera **SPIR-V** (Standard Portable Intermediate Representation). SPIR-V e uma representação intermediaria padronizada para programas de GPU. Ela existe para servir como "linguagem de montagem portavel" entre compiladores de alto nivel e drivers graficos.

SPIR-V é o "assembly" padrão da indústria gráfica, consumido por Vulkan, OpenGL e WebGPU. Isso significa que **você escreve uma função em Rust, e ela roda nos núcleos CUDA da NVIDIA ou RDNA da AMD**. Na pratica, ele resolve parte do problema classico de C/C++ com shaders: tipos duplicados, layout de memoria mantido manualmente e muito risco de divergencia silenciosa entre host e device.

## 2. A Arquitetura de um Workspace `rust-gpu`

Diferente de um projeto Rust normal, um projeto `rust-gpu` exige a configuração de um *Workspace* do Cargo com três crates distintas. Um **workspace** do Cargo e um agrupamento de multiplos pacotes Rust sob o mesmo projeto, compartilhando dependencia, build e organizacao. Ele existe para separar responsabilidades sem perder coesao arquitetural.

1.  **`shared` (A Ponte):** Uma biblioteca comum que contém as `structs` e lógicas matemáticas que serão usadas por ambos os lados. Compilada para `no_std` (já que a GPU não tem Sistema Operacional nem alocador de heap).
2.  **`shader` (A GPU):** O código que rodará na placa de vídeo. É escrito em Rust, mas com atributos especiais (`#[spirv(compute)]`).
3.  **`runner` (A CPU):** O código normal (usando `wgpu` ou Vulkan) que lê o arquivo SPIR-V gerado pelo `shader`, copia os dados e comanda a placa de vídeo.

Essa divisao existe porque CPU e GPU vivem em ambientes radicalmente diferentes. A CPU pode ter `std`, sistema de arquivos e heap geral; a GPU nao. Separar em crates impede que dependencias invalidas "vazem" para o lado do shader.

## 3. O Código Prático: Rust Puro na GPU

*Nota: O `rust-gpu` é um projeto altamente experimental que roda estritamente na versão Nightly e muda constantemente. Este código serve para ilustrar o modelo mental da fronteira do HPC.*

### A) O Crate `shared` (`shared/src/lib.rs`)
Este código será compilado duas vezes: uma para a CPU (x86/ARM) e outra para a GPU (SPIR-V).

```rust
// A GPU não tem heap (malloc) nem SO, então não podemos usar a stdlib.
#![no_std]

// Uma biblioteca de matemática gráfica compatível com no_std
use glam::Vec3;

// Esta struct é garantidamente idêntica na CPU e na GPU!
// #[repr(C)] pede layout compativel com C.
// Isso existe para impedir que o compilador reorganize campos livremente,
// algo perigoso quando os bytes serao interpretados por outro processador.
#[repr(C)]
#[derive(Copy, Clone)]
pub struct Particula {
    pub posicao: Vec3,
    pub velocidade: Vec3,
    pub massa: f32,
    pub _padding: f32, // GPU exige alinhamento de 16 bytes para Vec3
}

impl Particula {
    // Uma lógica de negócios escrita uma única vez
    pub fn aplicar_gravidade(&mut self, gravidade: f32, delta_time: f32) {
        self.velocidade.y -= gravidade * delta_time;
        self.posicao += self.velocidade * delta_time;
    }
}
```

### B) O Crate `shader` (`shader/src/lib.rs`)
Este é o código que o compilador transformará em SPIR-V.

```rust
#![no_std]
// Atributos especiais do rust-gpu
use spirv_std::spirv;
use shared::Particula;

// O atributo define que este é um Compute Shader e rodará em blocos de 64 threads.
// Atributos em Rust sao metadados que alteram geracao de codigo ou comportamento do compilador.
#[spirv(compute(threads(64)))]
pub fn main_compute(
    // Global Invocation ID (qual thread sou eu?)
    // Cada execucao da GPU recebe um identificador unico para saber
    // qual elemento do vetor ela deve processar.
    #[spirv(global_invocation_id)] id: glam::UVec3,
    // Nosso buffer de partículas mapeado na VRAM
    #[spirv(storage_buffer, descriptor_set = 0, binding = 0)] particulas: &mut [Particula],
) {
    let index = id.x as usize;
    
    // Proteção contra leitura fora dos limites
    if index < particulas.len() {
        // Chamamos o método Rust definido no crate `shared`!
        // Sem reescrever a lógica em WGSL/GLSL.
        particulas[index].aplicar_gravidade(9.8, 0.016);
    }
}
```

Um **binario SPIR-V** nada mais e do que a forma compilada do shader, pronta para o driver entender sem precisar recompilar uma linguagem textual em tempo de execucao.

## 4. Limitações Atuais do `rust-gpu` (A Fronteira Sangrenta)

Como Engenheiro de Sistemas, você precisa saber quando adotar uma tecnologia. O `rust-gpu` é o futuro, mas o presente tem ressalvas:

1. **Ausência de Heap:** Você não pode usar `String`, `Vec`, `Box` ou qualquer coisa que aloque dinamicamente dentro do `shader`. Tudo precisa ter tamanho fixo conhecido em tempo de compilação.
2. **Sem Recursão e Ponteiros Complexos:** GPUs não lidam bem com pilhas de chamadas (*call stacks*) profundas. Uma *call stack* e a estrutura de memoria que guarda retornos de funcao e variaveis locais durante chamadas encadeadas. Recursão geralmente é proibida pelo compilador SPIR-V.
3. **Erros Crípticos:** Quando o compilador LLVM tenta gerar assembly de GPU para um código Rust que usa recursos não suportados (ex: *trait objects* dinâmicos via `dyn`), o erro gerado é extremamente difícil de decifrar.

---

## Erros Comuns e Anti-Padrões em Memória de GPU

1.  **Ignorar o Alinhamento (Padding):** Em C++ e Rust, structs são empacotadas para economizar memória. Na GPU (std140 / std430 layout), as regras são estritas: um `Vec3` (12 bytes) exige alinhamento de 16 bytes. **Padding** sao bytes extras inseridos para respeitar o alinhamento exigido pela arquitetura. Se você não adicionar um campo `_padding: f32` (ou usar uma crate como `crevice`), a CPU enviará os dados desalinhados e a GPU calculará posições incorretas.
2.  **Usar `f64` na GPU sem necessidade:** Embora GPUs modernas suportem *Double Precision* (f64), a performance cai drasticamente (em placas de consumo, a taxa de FP64 chega a ser 1/32 da taxa de FP32). Sempre prefira `f32` em *Compute Shaders* a menos que precisão científica estrita seja exigida.

# Aula 22 - Banco de Dados, Pools e Transacoes

---

## Objetivo da Aula

Entender como backend em Go conversa com banco de dados usando `database/sql`, como `*sql.DB` funciona como pool de conexoes, por que `context` importa em queries, quando usar transacoes e quais erros de desenho degradam latencia, throughput e previsibilidade operacional. Ao final, voce deve conseguir ler e estruturar acesso a banco de forma idiomatica, sem tratar banco como caixa-preta lenta e misteriosa.

## 1. Ponte com as aulas anteriores

Na aula 20, estruturamos um servidor HTTP de producao.

Na aula 21, passamos a pensar em muitas conexoes concorrentes, filas, custo por cliente e backpressure.

Agora chegamos a uma das dependencias mais comuns e mais perigosas de um backend real:

Em backend, latencia quase sempre passa por algum lugar como:

- consulta SQL;
- pool de conexoes;
- lock interno do banco;
- transacao longa;

## 2. O que e `database/sql`?

`database/sql` e o package da biblioteca padrao que fornece a camada generica de acesso a bancos relacionais em Go.

Importante:

> `database/sql` nao fala sozinho com um banco especifico. Ele define a API comum; o driver concreto faz a ponte real.

Exemplo de driver muito usado:

```go
github.com/lib/pq
```

ou, em outros cenarios:

```go
github.com/go-sql-driver/mysql
```

### 2.1 O que isso resolve?

Permite:

- API uniforme;
- troca de driver com menos impacto estrutural;
- uso da biblioteca padrao como base;
- instrumentacao e padroes operacionais mais consistentes.

---

## 3. O que e `*sql.DB` de verdade?

Esse e um dos pontos mais importantes da aula.

Muita gente olha para:

```go
db, err := sql.Open("postgres", dsn)
```

e pensa:

> "isso abriu uma conexao com o banco".

Mentalmente, isso esta incompleto.

Na pratica, `*sql.DB` representa principalmente:

- uma handle compartilhada de acesso ao banco;
- um pool de conexoes gerenciado internamente;
- configuracao de abertura, reuso e limite de conexoes.

### 3.1 Regra pratica crucial

`*sql.DB` normalmente deve ser:

- criada uma vez no bootstrap da aplicacao;
- compartilhada como dependencia;
- fechada no shutdown.

Nao crie `sql.Open(...)` por requisicao HTTP.

Isso seria desastroso do ponto de vista operacional.

---

## 4. `sql.Open` nao valida tudo imediatamente

Exemplo:

```go
db, err := sql.Open("postgres", dsn)
if err != nil {
    return err
}
```

Mesmo apos isso, ainda e comum validar conectividade com:

```go
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()

if err := db.PingContext(ctx); err != nil {
    return err
}
```

### 4.1 Por que `PingContext` importa?

Porque voce quer descobrir cedo:

- DSN invalido;
- credencial errada;
- banco indisponivel;
- rede quebrada;
- timeout de bootstrap.

Falhar cedo no startup costuma ser muito melhor do que aceitar trafego e descobrir depois.

---

## 5. Pool de conexoes

Como `*sql.DB` e um pool, ele precisa de limites sensatos.

Principais configuracoes:

```go
db.SetMaxOpenConns(25)
db.SetMaxIdleConns(25)
db.SetConnMaxLifetime(30 * time.Minute)
db.SetConnMaxIdleTime(5 * time.Minute)
```

### 5.1 O que cada uma faz?

- `SetMaxOpenConns`: limite maximo de conexoes abertas simultaneamente.
- `SetMaxIdleConns`: quantas conexoes podem ficar paradas, prontas para reuso.
- `SetConnMaxLifetime`: tempo maximo de vida de uma conexao antes de ser reciclada.
- `SetConnMaxIdleTime`: tempo maximo de ociosidade antes de reciclar.

### 5.2 Por que isso importa?

Porque conexao demais nao significa throughput infinito.

Conexao demais pode significar:

- banco saturado;
- mais contencao;
- mais memoria do lado do banco;
- mais tempo preso aguardando recurso;
- comportamento erratico em pico.

Backend serio precisa respeitar o banco como recurso finito.

## 6. `context` em query e comando

Na pratica, use:

```go
db.QueryContext(ctx, query, args...)
db.ExecContext(ctx, query, args...)
db.QueryRowContext(ctx, query, args...)
```

Em vez das variantes sem contexto.

### 6.1 Por que isso e obrigatorio em backend serio?

Porque o contexto carrega:

- timeout;
- deadline;
- cancelamento por requisicao;
- desligamento do servidor;
- controle de trabalho inutil.

Sem `context`, uma query pode continuar consumindo recurso mesmo quando:

- cliente ja desistiu;
- request expirou;
- handler ja deveria ter terminado.

Isso se conecta diretamente com as aulas 15 e 20.

---

## 7. `QueryRow`, `Query` e `Exec`

Essas tres familias resolvem problemas diferentes.

### 7.1 `QueryRowContext`

Use quando espera uma unica linha:

```go
row := db.QueryRowContext(ctx, "SELECT id, nome FROM usuarios WHERE id = $1", id)
```

Depois:

```go
var u Usuario
err := row.Scan(&u.ID, &u.Nome)
```

### 7.2 `QueryContext`

Use quando espera varias linhas:

```go
rows, err := db.QueryContext(ctx, "SELECT id, nome FROM usuarios")
```

Lembre de:

```go
defer rows.Close()
```

### 7.3 `ExecContext`

Use quando quer executar comando sem ler linhas de resultado:

```go
_, err := db.ExecContext(ctx, "DELETE FROM sessoes WHERE expirado = true")
```

---

## 8. `Scan` e mapeamento de dados

O banco devolve colunas; seu codigo precisa mapear isso para variaveis Go.

Exemplo:

```go
type Usuario struct {
    ID   int
    Nome string
}
```

Leitura:

```go
var u Usuario
err := row.Scan(&u.ID, &u.Nome)
```

### 8.1 Cuidado importante

A ordem do `Scan` precisa casar com a ordem das colunas retornadas.

Nao trate isso como detalhe cosmetico.

Se a query mudar e o `Scan` nao acompanhar, o comportamento quebra.

---

## 9. `sql.ErrNoRows`

Quando uma busca por linha unica nao encontra resultado, um caso classico e:

```go
if errors.Is(err, sql.ErrNoRows) {
    // nao encontrado
}
```

### 9.1 Por que isso importa?

Porque "nao achei nada" nao e o mesmo tipo de erro que:

- conexao caiu;
- banco indisponivel;
- SQL invalido;
- timeout.

Backend bom diferencia:

- ausencia de dado;
- falha operacional.

Isso afeta:

- status HTTP;
- log;
- retry;
- telemetria.

---

## 10. Loop de linhas e `rows.Err()`

Quando usar `QueryContext`, faca o fluxo completo:

```go
rows, err := db.QueryContext(ctx, query)
if err != nil {
    return err
}
defer rows.Close()

for rows.Next() {
    // scan
}

if err := rows.Err(); err != nil {
    return err
}
```

### 10.1 Por que `rows.Err()` existe?

Porque erro de leitura pode aparecer durante a iteracao, nao apenas na abertura do cursor.

Ignorar isso e perder falha real no meio do caminho.

## 11. Transacoes

Transacao existe para agrupar operacoes que precisam de consistencia conjunta.

Exemplo conceitual:

- debitar conta A;
- creditar conta B;
- registrar historico.

Ou tudo acontece com consistencia, ou nada deve ficar aplicado parcialmente.

### 11.1 Comecando transacao

```go
tx, err := db.BeginTx(ctx, nil)
if err != nil {
    return err
}
```

### 11.2 Fluxo tipico

```go
defer tx.Rollback()

_, err = tx.ExecContext(ctx, "UPDATE contas SET saldo = saldo - $1 WHERE id = $2", valor, origem)
if err != nil {
    return err
}

_, err = tx.ExecContext(ctx, "UPDATE contas SET saldo = saldo + $1 WHERE id = $2", valor, destino)
if err != nil {
    return err
}

if err := tx.Commit(); err != nil {
    return err
}
```

### 11.3 Por que `defer tx.Rollback()` e tao comum?

Porque simplifica o caminho de erro.

Se tudo der certo:

- `Commit()` fecha a transacao com sucesso;
- `Rollback()` depois nao tera efeito util relevante.

Se algo falhar antes:

- o rollback ja fica garantido.

---

## 12. Transacao longa e latencia ruim

Um erro grave e segurar transacao enquanto faz:

- chamada HTTP externa;
- processamento pesado;
- espera humana;
- logica lenta demais;
- loops grandes sem necessidade.

Transacao longa pode causar:

- lock prolongado;
- maior contencao;
- throughput pior;
- filas no banco;
- latencia mais alta em outras operacoes.

Regra pratica:

> entre na transacao tarde e saia cedo.

---

## 13. N+1 queries

Esse e um problema classico de backend.

Exemplo ruim:

1. consulta lista de 100 usuarios;
2. para cada usuario, faz outra query para buscar perfil;
3. termina com 101 queries no total.

Isso amplifica:

- latencia;
- overhead de round-trip;
- carga no banco;
- uso do pool.

Esse problema aparece em qualquer linguagem. Em Go, ele continua sendo um problema de arquitetura, nao de sintaxe.

---

## 14. Banco como recurso concorrente finito

Pense no banco como voce pensou no hub da aula anterior:

- ha produtores de demanda;
- ha consumidores reais do lado do banco;
- existe limite de capacidade;
- fila e espera podem aparecer.

Se cada request faz query sem disciplina, o banco vira gargalo natural.

Por isso, backend bom observa:

- quantidade de conexoes abertas;
- tempo medio de query;
- taxa de erro;
- saturacao do pool;
- tamanho das transacoes;
- quantidade de round-trips.

---

## 15. Repositorio e separacao de camadas

Uma forma comum e organizar acesso a banco em uma camada dedicada.

Exemplo mental:

- handler HTTP traduz request;
- servico aplica regra;
- repositorio fala com banco.

Isso nao e dogma absoluto, mas ajuda a:

- isolar SQL;
- testar melhor;
- trocar implementacao com menos impacto;
- manter handler mais limpo.

## 17. Exemplo completo da aula

```go
package main

import (
    "context"
    "database/sql"
    "errors"
    "fmt"
    "log"
    "time"

    _ "github.com/lib/pq"
)

type Usuario struct {
    ID   int
    Nome string
}

type Repo struct {
    db *sql.DB
}

func newRepo(db *sql.DB) *Repo {
    return &Repo{db: db}
}

func (r *Repo) BuscarUsuarioPorID(ctx context.Context, id int) (Usuario, error) {
    row := r.db.QueryRowContext(ctx, "SELECT id, nome FROM usuarios WHERE id = $1", id)

    var u Usuario
    if err := row.Scan(&u.ID, &u.Nome); err != nil {
        if errors.Is(err, sql.ErrNoRows) {
            return Usuario{}, fmt.Errorf("usuario %d nao encontrado: %w", id, err)
        }
        return Usuario{}, fmt.Errorf("falha ao buscar usuario %d: %w", id, err)
    }

    return u, nil
}

func transferir(ctx context.Context, db *sql.DB, origem, destino, valor int) error {
    tx, err := db.BeginTx(ctx, nil)
    if err != nil {
        return fmt.Errorf("falha ao iniciar transacao: %w", err)
    }
    defer tx.Rollback()

    if _, err := tx.ExecContext(ctx, "UPDATE contas SET saldo = saldo - $1 WHERE id = $2", valor, origem); err != nil {
        return fmt.Errorf("falha ao debitar origem: %w", err)
    }

    if _, err := tx.ExecContext(ctx, "UPDATE contas SET saldo = saldo + $1 WHERE id = $2", valor, destino); err != nil {
        return fmt.Errorf("falha ao creditar destino: %w", err)
    }

    if err := tx.Commit(); err != nil {
        return fmt.Errorf("falha ao confirmar transacao: %w", err)
    }

    return nil
}

func main() {
    dsn := "postgres://usuario:senha@localhost:5432/app?sslmode=disable"

    db, err := sql.Open("postgres", dsn)
    if err != nil {
        log.Fatal(err)
    }
    defer db.Close()

    db.SetMaxOpenConns(25)
    db.SetMaxIdleConns(25)
    db.SetConnMaxLifetime(30 * time.Minute)
    db.SetConnMaxIdleTime(5 * time.Minute)

    ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
    defer cancel()

    if err := db.PingContext(ctx); err != nil {
        log.Fatal(err)
    }

    repo := newRepo(db)

    usuario, err := repo.BuscarUsuarioPorID(ctx, 1)
    if err != nil {
        log.Println("erro:", err)
    } else {
        log.Printf("usuario: %+v", usuario)
    }

    if err := transferir(ctx, db, 1, 2, 100); err != nil {
        log.Println("erro na transferencia:", err)
    }
}
```

## 18. Explicacao linha por linha

- `_ "github.com/lib/pq"`: importa o driver por efeito colateral de registro no `database/sql`.
- `type Repo struct { db *sql.DB }`: injeta a handle compartilhada do pool na camada de acesso.
- `QueryRowContext(...)`: busca linha unica com contexto.
- `row.Scan(...)`: converte colunas em campos Go.
- `errors.Is(err, sql.ErrNoRows)`: diferencia ausencia de dado de falha operacional.
- `db.BeginTx(ctx, nil)`: inicia transacao ligada ao contexto atual.
- `defer tx.Rollback()`: garante caminho de erro limpo.
- `tx.ExecContext(...)`: executa comandos dentro da mesma transacao.
- `tx.Commit()`: confirma aplicacao atomica do conjunto.
- `db.SetMaxOpenConns(...)` e similares: ajustam politica do pool.
- `db.PingContext(ctx)`: valida conectividade com timeout no bootstrap.

## 19. Comparacao com C, C++ e Rust

- Em C, voce costuma lidar mais diretamente com bibliotecas de cliente, buffers, codigos de erro e detalhes operacionais com bem menos padronizacao.
- Em C++, ORMs e wrappers podem abstrair bastante, mas com frequencia adicionam complexidade estrutural e variacao grande de estilo entre projetos.
- Em Rust, o acesso a banco tende a enfatizar mais tipo e seguranca em compile time, mas muitas vezes com superficie de tipos maior e custo conceitual superior para iniciantes.
- Em Go, `database/sql` entrega uma base simples, previsivel e muito apropriada para servicos de producao, desde que voce entenda corretamente pool, contexto e transacao.

O ponto central e:

- Go simplifica a API;
- mas nao elimina os custos reais do banco.

Latencia, lock, round-trip e saturacao continuam existindo.

## 20. Erros Comuns e Anti-Padroes

1. **Criar `sql.Open` por requisicao**: isso destroi eficiencia e previsibilidade.
2. **Achar que `*sql.DB` e uma conexao unica**: ele e uma handle de pool.
3. **Nao usar `Context` nas queries**: cancelamento e timeout deixam de funcionar.
4. **Ignorar `rows.Close()` e `rows.Err()`**: isso causa vazamento logico e perda de erro.
5. **Segurar transacao por tempo demais**: throughput e latencia pioram.
6. **Confundir `sql.ErrNoRows` com falha operacional geral**: semantica de erro fica errada.
7. **Produzir N+1 queries sem perceber**: round-trip e carga no banco explodem.
8. **Achar que aumentar conexoes indefinidamente resolve lentidao**: muitas vezes so desloca o gargalo.

# Aula 18 - Integracao com C/C++ via `cgo`, syscalls e proximidade com o sistema

---

## Objetivo da Aula

Entender como Go pode se aproximar do sistema e interoperar com codigo nativo usando `cgo`, quando isso faz sentido, quais custos essa integracao introduz e onde entram syscalls e fronteiras com o sistema operacional. Ao final, você deverá: chamar C via `cgo`, explicar custo de transição e regras de ponteiros, usar syscalls diretas quando adequado, e prever o que quebra na fronteira.
Mediremos com níveis de proficiência:
- **Nível 1 — Recordar:** `definir `cgo`, custo de chamada e regras de compartilhamento de ponteiros`;
- **Nível 2 — Aplicar:** `diagnosticar falha de `cgo` (ponteiro, link) e corrigir`;
- **Nível 3 — Projetar:** `projetar uma fronteira mínima justificando `cgo` vs. reimplementação`.
---

## 1. Por que integrar com C/C++?

Mesmo com biblioteca padrao forte, ha cenarios em que um projeto Go precisa:

- reutilizar biblioteca nativa existente;
- acessar API legada em C;
- chamar recurso do sistema ainda nao exposto na forma desejada;
- aproveitar codigo especializado de alto desempenho ja pronto;
- interagir com drivers, bindings ou SDKs nativos.

Nesses casos, a fronteira com C/C++ aparece naturalmente.

---

## 2. O que e `cgo`?

`cgo` e o mecanismo que permite integrar Go com codigo C.

Exemplo conceitual minimo:

```go
package main

/*
#include <stdio.h>
*/
import "C"

func main() {
    C.puts(C.CString("ola do C"))
}
```

### 2.1 O que isso faz?

- o comentario especial antes de `import "C"` contem declaracoes C;
- `import "C"` ativa o mecanismo de ponte;
- simbolos C ficam acessiveis pelo prefixo `C.`.

---

## 3. Custos de `cgo`

`cgo` nao e gratuito.

Custos comuns:

- build mais complexo;
- dependencia de toolchain C no ambiente;
- overhead de fronteira entre runtimes;
- deploy menos simples que binario puro em alguns casos;
- cuidado adicional com memoria e ownership.

Logo, a pergunta correta nao e "posso usar cgo?", mas sim:

> o beneficio real justifica o custo operacional e tecnico?

---

## 4. Memoria e ownership na fronteira

Quando Go e C trocam dados, ownership importa muito.

- **Ownership**: quem e responsavel pelo ciclo de vida de um recurso ou bloco de memoria.

Exemplo conceitual:

```go
cs := C.CString("texto")
defer C.free(unsafe.Pointer(cs))
```

Aqui a string foi alocada para o lado C e precisa ser liberada adequadamente.

Esse tipo de detalhe lembra por que a fronteira com codigo nativo e mais perigosa que Go puro.

---

## 5. Go pointer rules

Go tem regras importantes para ponteiros ao cruzar a fronteira com C.

A razao principal e proteger:

- integridade do garbage collector;
- mobilidade e rastreamento de memoria;
- seguranca do runtime.

Nao vamos entrar em todas as regras formais agora, mas o principio e:

- nao trate ponteiros Go e ponteiros C como se fossem livres e intercambiaveis sem restricao.

Esse e um ponto onde o modelo mental de C puro pode induzir erro grave.

---

## 6. `unsafe`

Existe tambem o package `unsafe`.

Ele permite operacoes fora das garantias normais do sistema de tipos.

Isso pode ser util para:

- interoperabilidade especial;
- estruturas muito sensiveis a layout;
- otimizacoes ou bindings especificos.

Mas tambem abre porta para:

- bugs sutis;
- dependencia de layout interno;
- fragilidade entre versoes e plataformas.

Regra pratica: `unsafe` so deve entrar com justificativa tecnica forte.

---

## 7. Syscalls

Syscall e a chamada que cruza da aplicacao para o kernel solicitando um servico do sistema operacional.

Exemplos conceituais:

- abrir arquivo;
- criar socket;
- ler do disco;
- mapear memoria;
- manipular processo.

Em alto nivel, muita coisa que voce faz em Go ja termina em syscalls por baixo.

A diferenca e que, em geral, a biblioteca padrao abstrai isso com seguranca melhor.

---

## 8. Quando usar syscall direto?

Raramente no comeco.

Faz mais sentido quando voce precisa:

- controle muito especifico do SO;
- funcionalidade ainda nao encapsulada do jeito desejado;
- proximidade com mecanismo de kernel ou processo;
- integracao de infraestrutura muito particular.

Na maioria dos casos, comece por `os`, `net`, `syscall` moderno encapsulado por packages mais seguros e outras APIs da biblioteca padrao.

---

## 9. Portabilidade e custo de plataforma

Quanto mais perto do sistema, menor a portabilidade automatica.

Perguntas importantes:

- isso precisa rodar em Windows e Linux?
- existe dependencia de ABI nativa?
- o ambiente de build tem compilador C?
- a equipe consegue manter essa fronteira?

- **ABI**: application binary interface, isto e, contrato binario de chamada, layout e ligacao entre componentes compilados.

Esse tipo de analise e tao importante quanto a sintaxe da chamada.

## 11. Exemplo completo da aula

```go
package main

import "fmt"

func abrirRecurso(nome string) error {
    if nome == "" {
        return fmt.Errorf("nome invalido")
    }

    fmt.Println("em um caso real, aqui poderiamos chamar biblioteca nativa ou API de sistema")
    return nil
}

func main() {
    if err := abrirRecurso("driver-x"); err != nil {
        fmt.Println("erro:", err)
        return
    }

    fmt.Println("integracao conceitual concluida")
}
```

### Explicacao linha por linha

- `abrirRecurso(...)`: representa fronteira conceitual com sistema ou biblioteca nativa.
- validacao inicial: reduz erro antes de cruzar fronteira sensivel.
- `fmt.Errorf(...)`: adiciona contexto a falha.
- `fmt.Println(...)`: destaca que o foco da aula e o modelo tecnico, nao um binding especifico de plataforma.

## 12. Erros Comuns e Anti-Padroes

1. **Usar `cgo` cedo demais sem necessidade real**: isso complica build e operacao.
2. **Ignorar ownership de memoria**: vazamentos e uso invalido podem surgir.
3. **Assumir que ponteiros Go e C se comportam igual**: o runtime de Go impone regras importantes.
4. **Abusar de `unsafe`**: isso reduz garantias da linguagem.
5. **Esquecer impacto de portabilidade**: o codigo pode ficar preso a plataforma.
6. **Cruzar fronteira nativa sem medir beneficio**: custo tecnico pode superar o ganho.

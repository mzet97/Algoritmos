# Aula 11 - Sincronizacao com `WaitGroup`, `Mutex`, atomics e race detector

---

## Objetivo da Aula

Entender como coordenar goroutines com seguranca em Go usando `sync.WaitGroup`, `sync.Mutex`, operacoes atomicas e o race detector. Ao final, voce deve conseguir distinguir comunicacao por channels de sincronizacao por primitivas de memoria compartilhada, escolhendo a ferramenta certa para cada situacao.

## 1. Concorrencia cria coordenacao, e coordenacao custa

Na aula anterior, vimos goroutines, channels e `select`.

Agora entramos em outro lado da concorrencia:

- esperar varias tarefas terminarem;
- proteger estado compartilhado;
- evitar condicoes de corrida;

Nem todo problema concorrente e melhor resolvido com channels.

As vezes o problema nao e "trocar mensagem", mas sim:

- contar tarefas concluidas;
- proteger um mapa compartilhado;

## 2. O que e `WaitGroup`?

`WaitGroup` e uma estrutura da biblioteca `sync` usada para esperar um conjunto de goroutines terminar.

Modelo mental:

- voce incrementa um contador de trabalho pendente;
- cada goroutine concluida decrementa esse contador;
- a goroutine principal espera o contador chegar a zero.

Exemplo:

```go
package main

import (
    "fmt"
    "sync"
)

func tarefa(id int, wg *sync.WaitGroup) {
    defer wg.Done()
    fmt.Println("tarefa", id, "concluida")
}

func main() {
    var wg sync.WaitGroup

    for i := 1; i <= 3; i++ {
        wg.Add(1)
        go tarefa(i, &wg)
    }

    wg.Wait()
    fmt.Println("todas as tarefas terminaram")
}
```

### 2.1 O que cada parte faz?

- `wg.Add(1)`: registra uma unidade de trabalho pendente.
- `defer wg.Done()`: garante decremento ao fim da goroutine.
- `wg.Wait()`: bloqueia ate todas terminarem.

Sem isso, `main` pode acabar cedo demais.

---

## 3. O que e uma race condition?

Condicao de corrida acontece quando duas ou mais execucoes concorrentes acessam o mesmo dado e pelo menos uma delas escreve, sem sincronizacao correta.

Exemplo conceitual perigoso:

```go
contador++
```

Esse trecho parece pequeno, mas nao e uma operacao indivisivel obrigatoriamente.

Ele envolve, conceitualmente:

- ler o valor atual;
- somar `1`;
- gravar o novo valor.

Se duas goroutines fizerem isso ao mesmo tempo sem protecao, o resultado final pode ficar incorreto.

---

## 4. O que e `Mutex`?

`Mutex` vem de mutual exclusion.

- **Mutual exclusion**: garantia de que apenas uma execucao por vez entra em uma secao critica.
- **Secao critica**: trecho que acessa estado compartilhado e precisa de exclusao mutua.

Exemplo:

```go
package main

import (
    "fmt"
    "sync"
)

func main() {
    var wg sync.WaitGroup
    var mu sync.Mutex
    contador := 0

    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            mu.Lock()
            contador++
            mu.Unlock()
        }()
    }

    wg.Wait()
    fmt.Println("contador:", contador)
}
```

### 4.1 O que o `Lock` protege?

Ele protege a regiao em que `contador` e lido e modificado.

Sem `Lock` e `Unlock`, o contador poderia terminar com valor menor que `1000`.

---

## 5. Cuidado com `defer` em `Mutex`

Em muitos casos, o padrao mais seguro e:

```go
mu.Lock()
defer mu.Unlock()
```

Isso reduz risco de esquecer o desbloqueio em caminhos de retorno diferentes.

Mas tambem e importante entender o custo mental e estrutural:

- segure o lock pelo menor tempo necessario;
- nao coloque trabalho pesado dentro da secao critica;
- nao faca I/O lento segurando mutex sem necessidade.

---

## 6. Atomics

Operacoes atomicas permitem atualizar certos valores compartilhados sem usar um `Mutex` explicito para casos simples.

Hoje, em Go moderno, elas vivem em `sync/atomic`.

Exemplo conceitual:

```go
package main

import (
    "fmt"
    "sync"
    "sync/atomic"
)

func main() {
    var wg sync.WaitGroup
    var contador atomic.Int64

    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            contador.Add(1)
        }()
    }

    wg.Wait()
    fmt.Println(contador.Load())
}
```

### 6.1 Quando atomics fazem sentido?

Quando voce precisa de operacoes muito simples e frequentes, como:

- contador;
- flag de estado;
- acumulador simples;
- leitura e escrita coordenada de um valor pequeno.

### 6.2 Quando `Mutex` ainda e melhor?

Quando voce precisa proteger invariantes mais complexas, por exemplo:

- atualizar varios campos juntos;
- manter consistencia entre mapa e contador;
- proteger estrutura inteira com varias operacoes relacionadas.

Atomics sao poderosas, mas nao substituem modelagem correta de invariantes.

## 7. `RWMutex`

Existe tambem `sync.RWMutex`.

- leitores podem entrar em paralelo;
- escritor exige exclusividade total.

Isso pode ajudar em cargas com muitas leituras e poucas escritas.

Mas so vale a pena quando o padrao real de acesso justifica. Nao use por impulso so porque parece "mais avancado".

---

## 8. Race detector

O race detector e uma das ferramentas mais importantes do ecossistema Go para codigo concorrente.

Comando:

```bash
go test -race ./...
```

Tambem pode ser usado em execucao:

```bash
go run -race 11_exemplo.go
```

Ele instrumenta o programa para detectar acessos concorrentes inseguros a memoria.

### 8.1 Por que isso e valioso?

Porque bugs de corrida costumam ser:

- intermitentes;
- dificeis de reproduzir;
- dependentes de timing;
- perigosos em producao.

O race detector nao substitui raciocinio tecnico, mas aumenta muito a chance de encontrar problemas cedo.

---

## 9. Channels vs mutex

Regra mental util:

Use channels quando o problema principal for:

- comunicar eventos;
- passar trabalho entre goroutines;
- coordenar pipelines;
- estruturar fluxo concorrente.

Use mutex quando o problema principal for:

- proteger estado compartilhado;
- manter integridade de dados mutaveis;
- serializar acesso a uma estrutura.

As duas abordagens coexistem em Go. O codigo idiomatico nao e fanatico por uma unica ferramenta.

## 11. Exemplo completo da aula

```go
package main

import (
    "fmt"
    "sync"
    "sync/atomic"
)

func main() {
    var wg sync.WaitGroup
    var mu sync.Mutex
    contadorSeguro := 0
    var contadorAtomico atomic.Int64

    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()

            mu.Lock()
            contadorSeguro++
            mu.Unlock()

            contadorAtomico.Add(1)
        }()
    }

    wg.Wait()
    fmt.Println("com mutex:", contadorSeguro)
    fmt.Println("com atomic:", contadorAtomico.Load())
}
```

### Explicacao linha por linha

- `var wg sync.WaitGroup`: controla termino das goroutines.
- `var mu sync.Mutex`: protege secao critica.
- `contadorSeguro++`: executa sob exclusao mutua.
- `var contadorAtomico atomic.Int64`: contador com operacoes atomicas.
- `contadorAtomico.Add(1)`: incremento seguro sem mutex explicito.
- `wg.Wait()`: espera todo o trabalho terminar.

## 12. Erros Comuns e Anti-Padroes

1. **Esquecer `wg.Done()`**: `Wait()` pode bloquear para sempre.
2. **Chamar `Add` no momento errado**: o contador do `WaitGroup` precisa refletir corretamente o trabalho criado.
3. **Acessar estado compartilhado sem protecao**: isso gera corrida de dados.
4. **Usar atomic para invariantes complexas**: muitas vezes `Mutex` e a ferramenta certa.
5. **Segurar lock por tempo demais**: isso reduz paralelismo e aumenta contencao.
6. **Ignorar `-race`**: voce perde uma das melhores defesas do ecossistema Go.

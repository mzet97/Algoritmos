# Aula 19 - Boas praticas para servicos, CLIs, automacao e sistemas de producao

---

## Objetivo da Aula

Consolidar a trilha de Go com criterios de engenharia para software real, cobrindo organizacao de servicos, CLIs, automacao, observabilidade, configuracao, shutdown, erros, deploy e manutencao. Ao final, voce deve conseguir distinguir codigo que apenas funciona localmente de codigo preparado para operar de forma previsivel em producao.

---

## 1. Fechando a trilha: do exemplo ao sistema

Ao longo das aulas, vimos linguagem, memoria, concorrencia, I/O, HTTP, testes, performance e fronteiras com o sistema.

Agora a pergunta muda de foco:

> como transformar esses blocos em software de verdade que possa ser executado, observado, mantido e evoluido?

Essa e a diferenca entre demonstracao tecnica e engenharia de producao.

---

## 2. Responsabilidades claras

Projetos saudaveis tendem a separar responsabilidades como:

- entrada do programa;
- configuracao;
- log e observabilidade;
- regras de negocio;
- integracoes externas;
- shutdown e limpeza;
- testes e validacao.

Se tudo fica em `main`, o sistema cresce mal.

`main` deve coordenar bootstrap, nao concentrar todo o dominio.

---

## 3. Configuracao

Configuracao de producao precisa ser explicita e previsivel.

Fontes comuns:

- argumentos de linha de comando;
- variaveis de ambiente;
- arquivos de configuracao;
- segredos fornecidos por ambiente controlado.

Boas praticas:

- validar configuracao logo no startup;
- falhar cedo em configuracao invalida;
- registrar valores relevantes sem vazar segredo;
- evitar valores magicos espalhados no codigo.

---

## 4. Logs e observabilidade

Sem observabilidade, diagnostico em producao vira adivinhacao.

No minimo, pense em:

- logs estruturados ou pelo menos consistentes;
- mensagens com contexto util;
- correlacao por request ou operacao;
- metricas;
- health checks;
- profiling e tracing quando fizer sentido.

Log bom ajuda a responder:

- o que aconteceu?
- quando aconteceu?
- em qual parte do sistema?
- com qual impacto?

---

## 5. Shutdown gracioso

Servicos de producao nao devem simplesmente "sumir" no meio do trabalho.

Shutdown gracioso significa:

- parar de aceitar novas requisicoes;
- sinalizar cancelamento do trabalho em andamento;
- esperar o que faz sentido esperar;
- liberar recursos;
- encerrar de modo previsivel.

Aqui voltam `context`, goroutines e coordenacao correta.

---

## 6. Tratamento de erro em sistema real

Erro em producao nao e so mensagem no terminal.

Boas praticas:

- adicionar contexto a falhas;
- distinguir erro esperado de falha fatal;
- evitar `panic` como controle normal;
- registrar falha no lugar certo;
- devolver status coerente em APIs e CLIs.

Em CLI, erro precisa resultar em:

- mensagem util;
- codigo de saida adequado;
- comportamento previsivel para automacao.

---

## 7. CLIs e automacao

Go e excelente para ferramentas internas e automacao porque entrega:

- binario simples;
- inicializacao rapida;
- boa portabilidade;
- acesso razoavel a rede e sistema de arquivos;
- concorrencia quando necessario.

Boas praticas para CLI:

- interface clara;
- ajuda e uso previsiveis;
- codigos de saida consistentes;
- logs ou saida adequados para humano e script;
- validacao robusta de entrada.

---

## 8. Servicos HTTP em producao

Para backend, alguns pontos viram obrigatorios rapidamente:

- timeout de entrada e saida;
- limites de recursos;
- contexto propagado;
- logs por requisicao;
- metricas;
- readiness e liveness quando aplicavel;
- testes automatizados e `-race` onde fizer sentido.

A biblioteca padrao resolve boa parte da base, mas a disciplina de operacao continua sendo responsabilidade da equipe.

---

## 9. Dependencias e simplicidade

Cada dependencia nova traz:

- superficie de API;
- risco de manutencao;
- custo de atualizacao;
- impacto de seguranca;
- acoplamento arquitetural.

Regra pratica forte em Go:

- prefira biblioteca padrao quando ela resolve bem o problema;
- adicione dependencia quando o ganho real compensar.

Isso combina com a filosofia geral da linguagem: simplicidade pragmatica.

---

## 10. Fluxo de qualidade minimo

Antes de entregar software, um fluxo razoavel costuma incluir:

```bash
go fmt ./...
go vet ./...
go test ./...
go test -race ./...
```

Se houver benchmark importante:

```bash
go test -bench=. -benchmem ./...
```

Esse conjunto nao garante perfeicao, mas evita uma enorme classe de regressoes e descuidos.

---

## 11. Organizacao de projeto e manutencao

Sinais de projeto saudavel:

- nomes claros;
- packages com responsabilidade coerente;
- fronteiras bem definidas;
- baixo acoplamento acidental;
- testes proximos do comportamento importante;
- bootstrap separado da regra principal.

Sinais ruins:

- `main` enorme;
- utilitarios globais sem criterio;
- contextos e erros ignorados;
- concorrencia criada sem estrategia de encerramento;
- configuracao espalhada.

---

## 12. Comandos exatos para executar

Formatacao global:

```bash
go fmt ./...
```

Analise estatica:

```bash
go vet ./...
```

Testes:

```bash
go test ./...
```

Race detector:

```bash
go test -race ./...
```

Benchmarks quando aplicavel:

```bash
go test -bench=. -benchmem ./...
```

## 13. Exemplo completo da aula

```go
package main

import (
    "context"
    "fmt"
    "time"
)

type Config struct {
    NomeServico string
    Timeout     time.Duration
}

func executar(ctx context.Context, cfg Config) error {
    select {
    case <-time.After(100 * time.Millisecond):
        fmt.Println("servico", cfg.NomeServico, "executou com timeout configurado de", cfg.Timeout)
        return nil
    case <-ctx.Done():
        return ctx.Err()
    }
}

func main() {
    cfg := Config{
        NomeServico: "processador",
        Timeout:     2 * time.Second,
    }

    ctx, cancel := context.WithTimeout(context.Background(), cfg.Timeout)
    defer cancel()

    if err := executar(ctx, cfg); err != nil {
        fmt.Println("erro:", err)
        return
    }

    fmt.Println("encerramento limpo")
}
```

### Explicacao linha por linha

- `Config`: centraliza configuracao relevante do processo.
- `executar(...)`: representa unidade principal de trabalho com contexto.
- `select { ... }`: permite reagir a termino normal ou cancelamento.
- `context.WithTimeout(...)`: limita tempo de execucao.
- `defer cancel()`: libera recursos associados ao contexto.
- `fmt.Println(...)`: neste exemplo didatico, representa ponto de observabilidade basico.

## 14. Erros Comuns e Anti-Padroes

1. **Colocar toda a aplicacao em `main`**: isso destroi modularidade e teste.
2. **Ignorar configuracao e timeout**: o sistema vira imprevisivel em producao.
3. **Nao pensar em shutdown**: goroutines e recursos podem ficar abandonados.
4. **Adicionar dependencia por impulso**: cada pacote extra aumenta custo de manutencao.
5. **Nao ter fluxo minimo com `fmt`, `vet`, `test` e `-race`**: a qualidade degrada cedo.
6. **Confundir software que roda localmente com software pronto para operar**: producao exige criterios adicionais.

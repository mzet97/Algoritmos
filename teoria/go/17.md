# Aula 17 - Performance tuning, `pprof`, alocacoes e uso eficiente de memoria

---

## Nesta aula

Entender como medir desempenho em Go antes de otimizar, como usar `pprof` para localizar hotspots, como alocacoes afetam garbage collector e latencia, e quais padroes ajudam a usar memoria de forma eficiente sem sacrificar clareza. Você vai aprender a perfilar alocações com `pprof`, reduzir escapes e cópias no caminho quente, e distinguir otimização medida de micro-otimização prematura.
---

## 1. A primeira regra: nao otimize no escuro

Performance tuning serio comeca com medicao.

Sem medir, e facil cair em varios erros:

- otimizar trecho irrelevante;
- piorar legibilidade sem ganho real;
- reduzir throughput em nome de micro-ajuste local;
- atacar sintoma em vez de causa.

Fluxo saudavel:

1. medir;
2. localizar hotspot;
3. entender causa;
4. aplicar mudanca;
5. medir de novo.

---

## 2. O que e hotspot?

Hotspot e uma regiao do programa onde custo relevante se concentra.

Esse custo pode ser:

- CPU;
- alocacao de memoria;
- contencao de lock;
- espera em I/O;
- bloqueio concorrente.

A ferramenta so e util quando o modelo mental acompanha a leitura.

---

## 3. `pprof`

`pprof` e o conjunto de ferramentas de profiling mais associado ao ecossistema Go.

Ele permite inspecionar, entre outras coisas:

- uso de CPU;
- heap;
- goroutines;
- blocos e contencao;
- alocacoes.

### 3.1 Por que isso importa?

Porque olhar apenas para "esta lento" nao basta.

Voce precisa descobrir se o problema e:

- algoritmo ruim;
- alocacao excessiva;
- serializacao demais;
- lock demais;
- espera externa;
- trabalho desnecessario repetido.

---

## 4. Benchmarks antes de tuning

Como vimos na aula anterior, benchmarks sao parte do fluxo.

```bash
go test -bench=. ./...
```

Para alocacoes:

```bash
go test -bench=. -benchmem ./...
```

`-benchmem` mostra informacoes como:

- bytes por operacao;
- alocacoes por operacao.

Isso conecta diretamente a questao de heap e GC.

---

## 5. Alocacoes importam

Em Go, alocar nao e "proibido", mas alocar demais custa.

Custos comuns:

- mais trabalho para o garbage collector;
- maior pressao em heap;
- possivel aumento de latencia;
- perda de cache locality em alguns cenarios.

- **Cache locality**: proximidade de dados acessados com frequencia, o que favorece hierarquia de cache do processador.

### 5.1 Fontes comuns de alocacao desnecessaria

- criar slices e maps repetidamente sem necessidade;
- concatenar strings em loop de forma ineficiente;
- converter entre `string` e `[]byte` sem pensar;
- devolver ponteiros quando valores simples bastariam;
- escapar valores para heap sem necessidade estrutural.

---

## 6. `strings.Builder` e buffers

Exemplo comum:

```go
var b strings.Builder
b.WriteString("ola")
b.WriteString(" ")
b.WriteString("Go")
resultado := b.String()
```

Isso costuma ser melhor do que concatenar muitas strings pequenas em loop.

Para bytes, `bytes.Buffer` tambem aparece bastante.

---

## 7. Reuso de memoria

Em caminhos criticos, reuso pode ajudar.

Exemplos:

- reaproveitar slices com cuidado;
- prealocar capacidade conhecida;
- usar pools em cenarios justificados.

Prealocacao:

```go
valores := make([]int, 0, 1000)
```

Isso reduz realocacoes se voce ja souber ordem de grandeza da carga.

### 7.1 `sync.Pool`

`sync.Pool` pode ajudar em objetos temporarios frequentemente reciclados, mas so quando ha beneficio real.

Nao transforme tudo em pool por impulso. Isso pode complicar o design e ate piorar a situacao.

---

## 8. Escape analysis e performance

Voltando a uma aula anterior:

```bash
go build -gcflags="-m" .
```

Esse comando ajuda a observar indicios de escape para heap.

Ponto importante:

- nem todo escape e ruim;
- mas escape frequente em caminho quente pode importar.

Performance tuning em Go exige combinar:

- benchmark;
- profile;
- modelo de heap e stack;
- leitura do codigo real.

---

## 9. `pprof` em servidor HTTP

Um padrao comum e expor endpoint de profiling em ambiente controlado.

Exemplo conceitual:

```go
import _ "net/http/pprof"
```

Depois, um servidor pode expor rotas de profile.

Importante:

- isso exige cuidado operacional;
- nao exponha profiling abertamente sem controle adequado em producao.

---

## 10. Nem toda lentidao e CPU

Muita gente confunde performance com uso de CPU apenas.

Mas gargalo pode estar em:

- lock contendido;
- rede lenta;
- disco;
- serializacao excessiva;
- alocacao e GC;
- coordenacao concorrente ruim.

Logo, profiling precisa ser interpretado dentro do sistema inteiro.

Benchmarks:

## 12. Exemplo completo da aula

```go
package main

import (
    "fmt"
    "strings"
)

func montarMensagem(partes []string) string {
    var b strings.Builder
    for i, parte := range partes {
        if i > 0 {
            b.WriteString(" ")
        }
        b.WriteString(parte)
    }
    return b.String()
}

func main() {
    partes := []string{"Go", "mede", "antes", "de", "otimizar"}
    fmt.Println(montarMensagem(partes))
}
```

### Explicacao linha por linha

- `strings.Builder`: ajuda a montar strings com menos sobrecarga que concatenacao repetitiva em varios casos.
- `for i, parte := range partes`: percorre elementos do slice.
- `if i > 0`: adiciona separador entre partes.
- `b.WriteString(...)`: acumula conteudo no builder.
- `b.String()`: materializa resultado final.

---

## 13. Erros Comuns e Anti-Padroes

1. **Otimizar antes de medir**: esse e o erro mais comum.
2. **Achar que toda alocacao e bug**: a questao e custo real, nao dogma.
3. **Trocar clareza por micro-otimizacao sem benchmark**: manutencao piora sem prova de ganho.
4. **Ignorar `-benchmem`**: memoria tambem e parte do desempenho.
5. **Usar pool sem justificativa**: reuso mal aplicado complica o codigo.
6. **Interpretar profile sem entender a carga real**: resultado pode enganar fora do contexto.

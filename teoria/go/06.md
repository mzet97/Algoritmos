# Aula 6 - Metodos, interfaces, composicao e embedding

---

## Objetivo da Aula

Entender como Go adiciona comportamento a tipos com metodos, como interfaces representam contratos, por que a linguagem favorece composicao em vez de heranca classica e como embedding ajuda a reutilizar estrutura e comportamento de forma simples. Ao final, voce deve conseguir modelar tipos com responsabilidade clara e conectar comportamento a dados de forma idiomatica.

---

## 1. Go nao usa classes como eixo central

Apos aprender `struct`, a pergunta natural e: onde entram classes, heranca e hierarquias?

A resposta curta e importante:

> Go nao organiza seu modelo principal em torno de classes e heranca como C++ ou Java.

Em vez disso, Go combina:

- `struct` para dados;
- metodos para comportamento;
- interfaces para contratos;
- composicao para reutilizacao estrutural.

Essa escolha reduz hierarquias profundas e favorece codigo mais direto.

---

## 2. O que e um metodo?

Metodo e uma funcao associada a um tipo.

Exemplo:

```go
package main

import "fmt"

type Retangulo struct {
    Largura float64
    Altura  float64
}

func (r Retangulo) Area() float64 {
    return r.Largura * r.Altura
}

func main() {
    r := Retangulo{Largura: 10, Altura: 5}
    fmt.Println(r.Area())
}
```

- `func (r Retangulo) Area() float64` define um metodo.
- `r` e o **receiver** do metodo.
- `Retangulo` e o tipo ao qual o metodo pertence.

### 2.1 Receiver nao e parametro comum

O receiver aparece antes do nome do metodo porque ele define a ligacao entre comportamento e tipo.

Mentalmente, pense assim:

- funcao: `Area(r)`;
- metodo: `r.Area()`.

A segunda forma organiza melhor o comportamento por tipo.

## 3. Receiver por valor e receiver por ponteiro

Esse e um ponto central em Go.

### 3.1 Receiver por valor

```go
func (r Retangulo) DobrarAltura() {
    r.Altura = r.Altura * 2
}
```

Aqui `r` e uma copia do valor original. A alteracao nao afeta o objeto fora do metodo.

### 3.2 Receiver por ponteiro

```go
func (r *Retangulo) DobrarAltura() {
    r.Altura = r.Altura * 2
}
```

Agora o metodo opera sobre o valor original por meio de um ponteiro.

- **Ponteiro**: valor que carrega o endereco de outro valor em memoria.

### 3.3 Quando usar cada um?

Use receiver por valor quando:

- o tipo e pequeno;
- o metodo nao precisa modificar estado;
- a copia e barata e semantica clara.

Use receiver por ponteiro quando:

- o metodo precisa modificar o estado;
- o tipo e grande e copiar seria custoso;
- voce quer consistencia entre varios metodos do mesmo tipo.

## 4. Interfaces

Interface em Go define um conjunto de metodos exigidos.

```go
type Desenhavel interface {
    Area() float64
}
```

Qualquer tipo que implemente `Area() float64` satisfaz essa interface.

Ponto crucial:

> Em Go, a implementacao de interface e implicita.

Voce nao escreve algo como `implements Desenhavel`.

### 4.1 Por que isso existe?

Para reduzir acoplamento entre tipos concretos e contratos.

O tipo apenas oferece os metodos. Se a assinatura bate, ele satisfaz a interface.

## 5. Exemplo de interface em acao

```go
package main

import "fmt"

type Forma interface {
    Area() float64
}

type Retangulo struct {
    Largura float64
    Altura  float64
}

func (r Retangulo) Area() float64 {
    return r.Largura * r.Altura
}

type Circulo struct {
    Raio float64
}

func (c Circulo) Area() float64 {
    return 3.14159 * c.Raio * c.Raio
}

func imprimirArea(f Forma) {
    fmt.Println(f.Area())
}

func main() {
    imprimirArea(Retangulo{Largura: 10, Altura: 5})
    imprimirArea(Circulo{Raio: 3})
}
```

Temos aqui polimorfismo por interface, sem heranca classica.

- **Polimorfismo**: capacidade de tratar valores diferentes por meio de um mesmo contrato comportamental.

## 6. Interfaces pequenas sao melhores

Go tende a preferir interfaces pequenas e focadas.

Bom exemplo:

```go
type Leitor interface {
    Read(p []byte) (n int, err error)
}
```

Ruim como impulso inicial:

```go
type MegaInterface interface {
    Ler()
    Escrever()
    Fechar()
    Sincronizar()
    Validar()
    Exportar()
}
```

Interfaces grandes geram acoplamento e dificultam reutilizacao.

Regra pratica:

- defina interfaces pequenas;
- perto do ponto de consumo;
- baseadas no comportamento necessario, nao em tudo que um tipo poderia fazer.

## 7. Composicao em vez de heranca

Go nao tem heranca de classes do tipo "classe filha herda tudo da classe pai".

O caminho idiomatico e composicao.

```go
type Motor struct {
    Potencia int
}

type Carro struct {
    Marca string
    Motor Motor
}
```

Aqui `Carro` contem um `Motor`. Em vez de dizer "Carro e um Motor", dizemos "Carro tem um Motor".

Isso costuma produzir modelos mais honestos e menos artificiais.

---

## 8. Embedding

Embedding e uma forma especial de composicao em Go.

```go
type Motor struct {
    Potencia int
}

func (m Motor) Info() string {
    return "motor pronto"
}

type Carro struct {
    Marca string
    Motor
}
```

Agora `Carro` contem um `Motor` embutido.

Voce pode acessar:

```go
c := Carro{Marca: "GoCar", Motor: Motor{Potencia: 150}}
fmt.Println(c.Potencia)
fmt.Println(c.Info())
```

`c.Potencia` e `c.Info()` sao promovidos a partir do campo embutido.

### 8.1 O que embedding nao e

Embedding nao deve ser confundido com heranca classica completa.

Ele promove campos e metodos, mas o modelo continua sendo de composicao, nao de arvore de classes com substituicao estrutural total.

## 9. Method set e consistencia

Quando voce mistura receivers por valor e por ponteiro, entra o conceito de **method set**.

Versao pratica e suficiente por enquanto:

- um valor `T` acessa metodos definidos com receiver `T`;
- um ponteiro `*T` acessa metodos definidos com receiver `T` e `*T`.

Isso afeta se um tipo satisfaz ou nao uma interface, especialmente quando a interface exige um metodo implementado so em `*T`.

Voltaremos a esse detalhe mais tarde, mas ja e importante saber que a escolha do receiver muda a semantica do tipo.

## 11. Exemplo completo da aula

```go
package main

import "fmt"

type Forma interface {
    Area() float64
}

type Retangulo struct {
    Largura float64
    Altura  float64
}

func (r Retangulo) Area() float64 {
    return r.Largura * r.Altura
}

func (r *Retangulo) DobrarAltura() {
    r.Altura = r.Altura * 2
}

type Motor struct {
    Potencia int
}

func (m Motor) Info() string {
    return "motor configurado"
}

type Carro struct {
    Marca string
    Motor
}

func imprimirArea(f Forma) {
    fmt.Println("area:", f.Area())
}

func main() {
    r := Retangulo{Largura: 10, Altura: 5}
    imprimirArea(r)

    r.DobrarAltura()
    imprimirArea(r)

    c := Carro{Marca: "GoCar", Motor: Motor{Potencia: 150}}
    fmt.Println(c.Marca)
    fmt.Println(c.Potencia)
    fmt.Println(c.Info())
}
```

### Explicacao linha por linha

- `type Forma interface { ... }`: define um contrato por metodo.
- `func (r Retangulo) Area() float64`: associa comportamento ao tipo `Retangulo`.
- `func (r *Retangulo) DobrarAltura()`: usa receiver por ponteiro para modificar estado.
- `type Motor struct { ... }`: define um tipo reutilizavel.
- `type Carro struct { Marca string; Motor }`: embute `Motor` em `Carro`.
- `imprimirArea(f Forma)`: recebe qualquer valor que satisfaz a interface `Forma`.
- `c.Potencia` e `c.Info()`: acessam membros promovidos por embedding.

## 12. Erros Comuns e Anti-Padroes

1. **Tentar reproduzir heranca classica em Go**: a linguagem favorece composicao.
2. **Usar receiver por valor quando precisa modificar estado**: a alteracao some porque voce editou uma copia.
3. **Criar interfaces grandes cedo demais**: isso piora acoplamento.
4. **Definir interface do lado do produtor sem necessidade**: muitas vezes a interface deve nascer no consumidor.
5. **Confundir embedding com heranca total**: ha promocao de membros, nao uma hierarquia OO tradicional.
6. **Misturar receivers sem criterio**: isso pode gerar confusao de method set e satisfacao de interface.

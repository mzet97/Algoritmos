# Aula 20 - Servidores HTTP de Producao

Servidor HTTP de produção aguenta timeout, cliente lento, shutdown gracioso e carga sem cair de pé. A diferença entre o exemplo da documentação e o serviço real é exatamente esta aula.

---

## Nesta aula

Sair do servidor HTTP minimo da aula 16 e entrar no modelo de servidor HTTP de producao em Go, entendendo como usar `http.Server`, `ServeMux`, middlewares, timeouts, limites de entrada, contextos e shutdown gracioso. Você vai aprender a construir servidor HTTP de produção (roteamento, middlewares, timeouts, shutdown gracioso), expor health checks, e medir o comportamento sob carga.

## 2. Servidor minimo vs servidor de producao

Servidor minimo:

```go
http.HandleFunc("/", handler)
http.ListenAndServe(":8080", nil)
```

Isso e bom para aprender e para demos pequenas.

Mas, em producao, geralmente voce precisa controlar explicitamente:

- timeouts;
- roteamento isolado;
- limites de corpo de requisicao;
- shutdown gracioso;
- logs;
- erros de inicializacao;
- separacao entre bootstrap e regra de negocio.

Por isso, o centro da aula passa a ser `http.Server`.

---

## 3. O que e `http.Server`?

`http.Server` e a estrutura que representa o servidor HTTP propriamente dito.

Exemplo:

```go
srv := &http.Server{
    Addr:              ":8080",
    Handler:           mux,
    ReadHeaderTimeout: 2 * time.Second,
    ReadTimeout:       5 * time.Second,
    WriteTimeout:      10 * time.Second,
    IdleTimeout:       30 * time.Second,
}
```

### 3.1 Por que isso existe?

Porque `ListenAndServe` simples esconde configuracoes importantes demais para software real.

Com `http.Server`, voce ganha controle de:

- endereco de escuta;
- handler raiz;
- timeouts de leitura e escrita;
- ciclo de vida do servidor;
- desligamento controlado.

---

## 4. Timeouts importam muito

Em servicos de rede, timeout nao e detalhe. E defesa.

Sem timeout adequado, voce pode sofrer com:

- clientes lentos segurando conexoes;
- recursos presos por tempo demais;
- backlog de goroutines;
- aumento de latencia e uso de memoria.

### 4.1 Principais timeouts

- `ReadHeaderTimeout`: limita tempo para receber headers da requisicao.
- `ReadTimeout`: limita leitura completa da requisicao.
- `WriteTimeout`: limita escrita da resposta.
- `IdleTimeout`: controla quanto tempo conexoes keep-alive podem ficar ociosas.

### 4.2 Por que `ReadHeaderTimeout` merece destaque?

Porque protege contra clientes lentos ou maliciosos que ficam enviando cabecalhos muito devagar.

Esse tipo de defesa lembra um ponto importante de engenharia:

- backend nao precisa apenas responder rapido;
- backend tambem precisa se proteger contra consumo ruim de recurso.

---

## 5. `ServeMux` e roteamento explicito

Em vez de registrar tudo no mux global do pacote, prefira um roteador explicito:

```go
mux := http.NewServeMux()
mux.HandleFunc("/healthz", healthHandler)
mux.HandleFunc("/users", usersHandler)
```

### 5.1 Por que isso e melhor?

Porque o mux global:

- aumenta acoplamento implicito;
- dificulta testes isolados;
- mistura registro global com bootstrap.

Com um `ServeMux` proprio, o fluxo fica mais claro:

- monta dependencias;
- monta handlers;
- monta mux;
- injeta no `http.Server`.

---

## 6. Handler de producao nao deve virar monolito

Um erro comum e concentrar tudo dentro do handler:

- parse de JSON;
- validacao;
- regra de negocio;
- acesso a banco;
- serializacao da resposta;
- log;
- metrica;
- tratamento de erro.

Em codigo serio, prefira dividir:

- camada HTTP: traduz requisicao e resposta;
- camada de servico: executa regra de negocio;
- camada de integracao: banco, cache, APIs externas.

### 6.1 Modelo mental

Handler bom e adaptador.

Ele deve:

- ler dados de entrada;
- chamar a camada certa;
- mapear erro para status HTTP coerente;
- escrever resposta.

Ele nao deve virar o sistema inteiro.

---

## 7. Middleware

Middleware e uma funcao que envolve um handler para adicionar comportamento transversal.

Exemplo mental:

- log;
- medicao de tempo;
- autenticacao;
- recuperacao de panic;
- injecao de contexto;
- controle de headers.

Forma comum:

```go
func loggingMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        inicio := time.Now()
        next.ServeHTTP(w, r)
        log.Println(r.Method, r.URL.Path, time.Since(inicio))
    })
}
```

### 7.1 Por que middleware existe?

Porque certas responsabilidades atravessam varias rotas.

Sem middleware, voce repetiria:

- log em toda rota;
- medicao em toda rota;
- validacao generica em toda rota.

Isso piora manutencao e consistencia.

---

## 8. Limites de entrada

Servidor de producao nao deve aceitar corpo arbitrariamente grande por padrao.

Exemplo:

```go
r.Body = http.MaxBytesReader(w, r.Body, 1<<20)
```

Aqui, o limite e de aproximadamente 1 MB.

### 8.1 Por que isso importa?

Porque entrada sem limite:

- facilita abuso de memoria;
- aumenta superficie de ataque;
- piora previsibilidade operacional.

Esse ponto se conecta diretamente ao foco de Go em simplicidade com controle explicito.

---

## 9. JSON, status code e erro coerente

Em backend real, resposta nao e apenas "deu certo".

Voce precisa:

- devolver status code correto;
- serializar JSON de forma consistente;
- escrever erro util sem vazar detalhe interno demais.

Exemplo:

```go
http.Error(w, "json invalido", http.StatusBadRequest)
```

Ou, quando quiser JSON consistente:

```go
w.Header().Set("Content-Type", "application/json")
w.WriteHeader(http.StatusOK)
json.NewEncoder(w).Encode(resposta)
```

---

## 10. `context` por requisicao

Cada requisicao HTTP carrega um contexto proprio:

```go
ctx := r.Context()
```

Esse contexto deve ser propagado para:

- banco de dados;
- chamadas HTTP de saida;
- filas;
- servicos internos;
- operacoes longas.

### 10.1 Por que isso e importante?

Porque, se o cliente desistir ou o servidor estiver desligando, o trabalho descendente tambem precisa parar.

Esse modelo evita:

- goroutines abandonadas;
- I/O desnecessario;
- custo inutil em dependencia externa.

---

## 11. Shutdown gracioso

Encerrar servidor corretamente e parte do design, nao detalhe final.

Fluxo tipico:

1. receber sinal de encerramento;
2. parar de aceitar novas conexoes;
3. dar um prazo para requisicoes em andamento terminarem;
4. cancelar o que exceder o limite;
5. liberar recursos.

Em Go, isso aparece com:

```go
srv.Shutdown(ctx)
```

### 11.1 Diferenca entre `Close` e `Shutdown`

- `Close`: encerra de forma mais abrupta.
- `Shutdown`: tenta encerramento gracioso.

Para servicos HTTP, `Shutdown` costuma ser o caminho certo.

---

## 12. Tratando `panic` no HTTP

Em producao, um `panic` nao deveria derrubar o processo inteiro por causa de uma unica requisicao.

Por isso, um middleware de recuperacao pode fazer sentido:

```go
func recoverMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if rec := recover(); rec != nil {
                log.Println("panic recuperado:", rec)
                http.Error(w, "erro interno", http.StatusInternalServerError)
            }
        }()

        next.ServeHTTP(w, r)
    })
}
```

### 12.1 Cuidado

Recuperar `panic` nao substitui corrigir bug.

O objetivo e:

- isolar dano;
- preservar processo;
- registrar falha;
- responder sem corromper protocolo.

## 13. Health check

Servico real quase sempre precisa de rota simples de saude.

Exemplo:

```go
func healthHandler(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(http.StatusOK)
    w.Write([]byte("ok"))
}
```

Isso ajuda em:

- probes de orquestrador;
- monitoramento;
- balanceadores;
- diagnostico rapido.

Mais tarde, voce pode separar:

- `liveness`;
- `readiness`.

---

## 14. Comparacao com C, C++ e Rust

Esse ponto merece ser explicitado.

- Em C, montar servidor HTTP robusto com esse nivel de seguranca e ergonomia costuma exigir bem mais infraestrutura manual.
- Em C++, frameworks podem ajudar, mas o custo de ecossistema e a variacao de estilo tendem a ser maiores.
- Em Rust, o nivel de seguranca de tipo e controle de ownership e maior, mas a superficie conceitual inicial para backend costuma ser mais pesada.
- Em Go, a biblioteca padrao entrega uma base muito forte com custo cognitivo relativamente baixo.

O trade-off central de Go aqui e claro:

- menos poder abstrato que alguns ecossistemas;
- mais simplicidade operacional e velocidade de entrega para servicos de rede.

## 16. Exemplo completo da aula

```go
package main

import (
    "context"
    "encoding/json"
    "errors"
    "log"
    "net/http"
    "os"
    "os/signal"
    "syscall"
    "time"
)

type App struct{}

type resposta struct {
    Mensagem string `json:"mensagem"`
}

func (a *App) healthHandler(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(http.StatusOK)
    w.Write([]byte("ok"))
}

func (a *App) helloHandler(w http.ResponseWriter, r *http.Request) {
    if r.Method != http.MethodGet {
        http.Error(w, "metodo nao permitido", http.StatusMethodNotAllowed)
        return
    }

    w.Header().Set("Content-Type", "application/json")
    if err := json.NewEncoder(w).Encode(resposta{Mensagem: "servidor pronto"}); err != nil {
        http.Error(w, "falha ao escrever resposta", http.StatusInternalServerError)
        return
    }
}

func loggingMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        inicio := time.Now()
        next.ServeHTTP(w, r)
        log.Printf("method=%s path=%s duracao=%s", r.Method, r.URL.Path, time.Since(inicio))
    })
}

func recoverMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if rec := recover(); rec != nil {
                log.Printf("panic=%v", rec)
                http.Error(w, "erro interno", http.StatusInternalServerError)
            }
        }()

        next.ServeHTTP(w, r)
    })
}

func main() {
    app := &App{}

    mux := http.NewServeMux()
    mux.HandleFunc("/healthz", app.healthHandler)
    mux.HandleFunc("/hello", app.helloHandler)

    handler := recoverMiddleware(loggingMiddleware(mux))

    srv := &http.Server{
        Addr:              ":8080",
        Handler:           handler,
        ReadHeaderTimeout: 2 * time.Second,
        ReadTimeout:       5 * time.Second,
        WriteTimeout:      10 * time.Second,
        IdleTimeout:       30 * time.Second,
    }

    go func() {
        log.Println("servidor em http://localhost:8080")
        if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
            log.Fatalf("erro no servidor: %v", err)
        }
    }()

    stop := make(chan os.Signal, 1)
    signal.Notify(stop, os.Interrupt, syscall.SIGTERM)
    <-stop

    log.Println("iniciando shutdown gracioso")

    ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel()

    if err := srv.Shutdown(ctx); err != nil {
        log.Printf("erro no shutdown: %v", err)
    }

    log.Println("servidor encerrado")
}
```

### Explicacao linha por linha

- `type App struct{}`: ponto simples para agrupar handlers e futuras dependencias.
- `http.NewServeMux()`: cria roteador explicito, evitando mux global.
- `loggingMiddleware(...)`: adiciona log transversal de requisicao.
- `recoverMiddleware(...)`: evita que um `panic` isolado derrube o servidor inteiro.
- `http.Server{...}`: explicita configuracao operacional do servidor.
- `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, `IdleTimeout`: limitam uso ruim ou indefinido de conexoes.
- `srv.ListenAndServe()`: inicia o servidor HTTP.
- `errors.Is(err, http.ErrServerClosed)`: evita tratar shutdown normal como erro fatal.
- `signal.Notify(...)`: escuta sinal do sistema operacional para encerramento.
- `srv.Shutdown(ctx)`: faz desligamento gracioso com prazo maximo.

## 17. Erros Comuns e Anti-Padroes

1. **Usar apenas `ListenAndServe` cru em servico real**: voce perde configuracao importante de timeout e ciclo de vida.
2. **Registrar tudo no mux global**: isso aumenta acoplamento e dificulta testes.
3. **Nao limitar leitura de entrada**: corpo grande demais pode desperdicar recurso.
4. **Misturar regra de negocio inteira dentro do handler**: manutencao e teste pioram.
5. **Ignorar `r.Context()`**: cancelamento e shutdown deixam de se propagar.
6. **Nao tratar shutdown gracioso**: o processo pode morrer no meio de requisicoes em andamento.
7. **Usar middleware de recover para esconder bugs**: ele serve para isolamento, nao para desculpar falha sistemica.

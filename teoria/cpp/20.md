# Aula 20 - Event loops, reactor, proactor e o lugar de C++ em I/O assincrono

---

## Objetivo da Aula

Entender o que e I/O assincrono em termos de arquitetura, qual o papel de event loops, qual a diferenca entre reactor e proactor, e como C++ se posiciona sobre mecanismos nativos de sistema operacional sem apagar o custo real do modelo. Ao final, voce deve conseguir olhar para um servidor ou runtime assincrono e enxergar fila de eventos, handlers, estado pendente, ownership e integracao com a API do SO como partes do mesmo sistema.

## 1. Ponte com a trilha principal

Na trilha principal de C++, vimos:

- RAII;

- concorrencia com `std::thread`;

- bibliotecas e organizacao de sistemas.

A primeira pergunta importante e:

- como lidar com muitas operacoes de I/O sem criar uma thread bloqueada para cada conexao ou tarefa?

Essa pergunta aparece em:

- servidores TCP;
- proxies;
- runtimes de rede;
- loops de GUI;
- motores de eventos;

## 2. O problema do modelo bloqueante ingenuo

Imagine um servidor que:

- aceita uma conexao;
- chama `recv`;
- fica esperando;
- responde;
- passa para a proxima conexao.

Isso e simples.

Mas escala mal quando:

- muitos clientes ficam ociosos;
- cada conexao faz pouco trabalho e muita espera;
- o custo de thread por conexao vira alto;
- pilhas, contexto e scheduling viram gargalo.

### 2.1 Thread por conexao resolve tudo?

Nao.

Pode funcionar por um tempo.

Mas costuma cobrar:

- memoria por stack;
- custo de troca de contexto;
- contencao;
- maior variabilidade de latencia;
- dificuldade de observar estado global.

---

## 3. O que e I/O assincrono, na pratica?

Em termos operacionais, I/O assincrono e uma forma de:

- iniciar ou acompanhar operacoes de I/O sem bloquear a linha principal de execucao daquele componente;
- reagir a eventos de readiness ou conclusao;
- continuar trabalho quando a operacao puder progredir.

### 3.1 O ponto central

I/O assincrono nao significa:

- "magicamente mais rapido"

Significa:

- melhor uso de uma thread ou de um pequeno conjunto de threads quando muito do custo e espera por I/O.

### 3.2 O custo trocado

Voce troca simplicidade linear por:

- maquinas de estado;
- callbacks;
- buffers pendentes;
- handlers;
- coordenacao de eventos;
- lifecycle mais delicado.

---

## 4. Event loop

- **Event loop**: laco central que espera eventos, acorda quando algo relevante acontece e despacha handlers ou continuacoes.

Modelo mental:

1. registrar interesse em eventos
2. dormir esperando atividade
3. acordar quando ha algo pronto
4. despachar trabalho associado
5. voltar ao loop

### 4.1 O que pode ser evento?

- socket legivel;
- socket pronto para escrita;
- timer expirado;
- sinal de shutdown;
- tarefa agendada internamente;
- completude de operacao assincrona.

### 4.2 Onde isso aparece?

- `select`
- `poll`
- `epoll`
- `kqueue`
- IOCP
- runtimes de GUI
- runtimes de rede de alto nivel

---

## 5. Reactor

- **Reactor**: modelo em que o sistema operacional informa que um recurso esta pronto para progredir, e o programa reage executando o trabalho correspondente.

Exemplo conceitual:

- socket ficou legivel
- event loop chama handler
- handler faz `recv`

### 5.1 O que o SO entrega?

No reactor, o SO normalmente entrega algo como:

- readiness

ou seja:

- "agora vale a pena tentar ler ou escrever"

### 5.2 Exemplos classicos

- `select`
- `poll`
- `epoll`
- `kqueue`

### 5.3 Consequencia pratica

Seu codigo ainda executa a operacao real de I/O quando recebe o evento.

---

## 6. Proactor

- **Proactor**: modelo em que a operacao e submetida antes, e o sistema ou runtime notifica quando ela conclui.

Exemplo conceitual:

1. submeter leitura
2. o sistema conduz a operacao
3. ao concluir, chega notificacao
4. handler processa o resultado

### 6.1 O que o SO entrega?

No proactor, a notificacao tende a ser:

- completion

ou seja:

- "a operacao terminou"

### 6.2 Exemplo famoso

- IO Completion Ports no Windows

### 6.3 Diferenca mental para reactor

- reactor: "o recurso esta pronto, faca"
- proactor: "a operacao terminou, lide com o resultado"

---

## 7. Nem toda biblioteca assincrona e puramente uma coisa

Na pratica, varias bibliotecas misturam:

- readiness;
- filas internas;
- thread pools;
- timers;
- completions sintetizadas;
- callbacks e continuacoes.

Ou seja:

- reactor e proactor sao modelos mentais muito uteis;
- implementacoes reais podem hibridizar os dois.

---

## 8. O lugar de C++ nisso tudo

C++ nao fornece um runtime assincrono universal que substitui o SO.

O papel da linguagem e da biblioteca costuma ser:

- modelar ownership de recursos;
- encapsular descritores, buffers e handlers;
- organizar estado pendente;
- ajudar a compor callbacks, futures ou coroutines;
- expor contratos mais claros sobre lifetime e erro.

### 8.1 O que continua vindo do sistema?

- readiness ou completions;
- file descriptors ou handles;
- APIs nativas de espera;
- custo real de syscalls;
- semantica de rede e arquivo.

### 8.2 O risco de abstracao ruim

Uma camada C++ mal desenhada pode:

- esconder custo demais;
- apagar erro demais;
- embaralhar ownership;
- dificultar debug;
- tornar o loop de eventos incompreensivel.

## 9. Exemplo conceitual de event loop pequeno

Este exemplo nao depende de `epoll` ou IOCP reais.

Ele modela a estrutura mental de um loop:

```cpp
#include <functional>
#include <iostream>
#include <queue>
#include <string>
#include <vector>

struct Event {
    int source_id;
    std::string kind;
};

class EventLoop {
public:
    using Handler = std::function<void(const Event&)>;

    void register_handler(Handler h) {
        handlers_.push_back(std::move(h));
    }

    void push_event(Event e) {
        queue_.push(std::move(e));
    }

    void run() {
        while (!queue_.empty()) {
            Event ev = std::move(queue_.front());
            queue_.pop();

            for (const auto& h : handlers_) {
                h(ev);
            }
        }
    }

private:
    std::queue<Event> queue_;
    std::vector<Handler> handlers_;
};

int main() {
    EventLoop loop;

    loop.register_handler([](const Event& ev) {
        std::cout << "handler A: source=" << ev.source_id
                  << " kind=" << ev.kind << "\n";
    });

    loop.register_handler([](const Event& ev) {
        if (ev.kind == "readable") {
            std::cout << "handler B: tentaria ler do recurso "
                      << ev.source_id << "\n";
        }
    });

    loop.push_event({10, "readable"});
    loop.push_event({11, "timer"});
    loop.push_event({10, "writable"});

    loop.run();
    return 0;
}
```

---

## 10. O que esse exemplo ensina?

### 10.1 Ha uma fila de eventos

Mesmo sem API nativa real, o exemplo mostra:

- eventos chegam;
- entram numa fila;
- o loop despacha.

### 10.2 Handlers sao comportamento associado

Cada handler representa:

- uma reacao;
- uma parte da logica;
- um consumidor do evento.

### 10.3 O loop nao faz o trabalho de negocio inteiro

Ele:

- observa;
- despacha;
- coordena.

Essa divisao de papeis e central em arquiteturas assincronas.

---

## 11. Exemplo mais proximo de reactor

Modelo mental:

```cpp
for (;;) {
    auto ready_list = wait_for_readiness();
    for (auto resource : ready_list) {
        dispatch_handler(resource);
    }
}
```

### 11.1 O que o handler faria?

Algo como:

- `recv`
- `send`
- ler arquivo
- aceitar conexao
- consumir timer

### 11.2 O que isso implica?

O handler precisa conhecer:

- estado do recurso;
- buffer parcial;
- politica de erro;
- o que fazer se nao der para concluir tudo numa vez.

---

## 12. Exemplo mais proximo de proactor

Modelo mental:

```cpp
submit_async_read(resource, buffer);

for (;;) {
    auto completions = wait_for_completions();
    for (auto done : completions) {
        handle_completion(done);
    }
}
```

### 12.1 O que muda?

Agora o codigo nao reage a readiness para fazer a leitura.

Ele reage a:

- operacao concluida

Isso muda bastante:

- forma do estado;
- fila de operacoes pendentes;
- como buffers e callbacks vivem;
- integracao com o runtime.

## 13. Ownership em arquiteturas assincronas

Este e um ponto onde C++ brilha e tambem cobra caro.

Perguntas obrigatorias:

- quem possui o socket?
- quem possui o buffer?
- o handler pode sobreviver ao objeto capturado?
- quem cancela a operacao pendente?
- o que acontece no shutdown do loop?

### 13.1 Exemplo de armadilha

Uma lambda captura referencia para objeto local:

```cpp
auto handler = [&obj](const Event&) {
    obj.process();
};
```

Se o loop chamar isso depois que `obj` morrer:

- bug grave de lifetime

### 13.2 Moral

Em async, lifetime e ownership viram parte do desenho arquitetural, nao so detalhe de implementacao.

---

## 14. Buffers, estado parcial e maquina de estados

Em I/O assincrono real, raramente uma operacao faz tudo de uma vez.

Pode haver:

- leitura parcial;
- escrita parcial;
- parse incompleto;
- operacao pendente;
- backpressure;
- timeout.

### 14.1 Consequencia

Cada conexao ou operacao costuma precisar de estado proprio:

- buffer de entrada;
- buffer de saida;
- estado do protocolo;
- flags de fechamento;
- operacao pendente.

### 14.2 O event loop coordena, mas nao elimina o estado

Pelo contrario:

- ele exige modelagem mais explicita desse estado.

---

## 15. Event loop nao e sinonimo de single-thread para sempre

Muita gente associa event loop a:

- uma thread unica para tudo

Mas sistemas reais podem combinar:

- event loop para I/O;
- thread pool para CPU-bound;
- fila de tarefas internas;
- timers;
- workers especializados.

### 15.1 Regra pratica

Nao misture:

- espera por I/O;
- processamento pesado;

na mesma thread do loop se isso destruir latencia.

---

## 16. Comparacao com C, Rust, Go e Python

- Em C, o modelo mecanico e o mesmo, mas ownership e organizacao ficam muito mais manuais.
- Em Rust, runtimes async ajudam bastante, e o sistema de tipos pressiona muito mais a corretude de lifetime.
- Em Go, goroutines e runtime escondem boa parte do desenho de loop de eventos do usuario comum.
- Em Python, `asyncio` expoe o modelo de event loop de forma mais direta, mas o custo e a proximidade com o SO sao diferentes.

C++ ocupa um espaco interessante:

- proximo do sistema;
- bom para wrappers e runtimes;
- forte em modelar estado e ownership;
- perigoso se abstracao esconder demais a mecanica real.

## 19. Erros comuns e anti-padroes

1. **Achar que async significa automaticamente mais rapido**.
2. **Confundir readiness com conclusao de operacao**.
3. **Esconder lifetime em lambdas e callbacks sem contrato claro**.
4. **Misturar processamento pesado dentro da thread principal do event loop**.
5. **Achar que event loop elimina a necessidade de buffers, parser e estado parcial**.
6. **Criar abstracao C++ que apaga tanto o mecanismo que debugging vira inferno**.

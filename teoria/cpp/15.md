# Aula 15 - Alocadores, layout, cache, profiling e otimizacao real

---

## Objetivo da Aula

Entender como alocacao, layout de dados, cache, profiling e escolhas de containers afetam desempenho real em C++, e por que otimizar na linguagem sem olhar para memoria e hardware costuma gerar intuicoes ruins. Ao final, voce devera: medir um hot path com baseline e dispersao; demonstrar um ganho vindo de layout (e um caso em que a "otimizacao" perde); e explicar por que medir precede otimizar.

### Como ler esta aula (tres niveis)

- **Fundamental:** medir antes, baseline, repetir.
- **Intermediario:** cache/localidade, containers e alocacao.
- **Aprofundamento (opcional):** profiler e vetorizacao (aulas 26–28 retomam).

- desempenho real.

Porque CPU e memoria importam profundamente.

---

## 2. Complexidade nao basta

Big-O ajuda a comparar crescimento.

Mas desempenho real tambem depende de:

- contiguidade;
- cache;
- indirecao;
- branch prediction;
- alocacoes;
- tamanho do objeto;
- copy/move;
- layout de dados.

### 2.1 Exemplo intuitivo

Somar um `std::vector<int>` contiguo normalmente e muito mais amigavel ao hardware do que percorrer uma estrutura espalhada por ponteiros.

---

## 3. Layout de dados

Layout de dados responde:

- como os campos e objetos estao dispostos em memoria?

Exemplo:

```cpp
struct Ponto {
    int x;
    int y;
};
```

e:

```cpp
struct Ruim {
    char a;
    int b;
    char c;
};
```

O segundo pode ter padding e pior aproveitamento de espaco por alinhamento.

### 3.1 Por que isso importa?

Porque:

- tamanho de objeto afeta cache;
- contiguidade afeta prefetch;
- padding afeta densidade;
- indirecao afeta misses.

---

## 4. `std::vector` e localidade

`std::vector` costuma ser excelente base inicial de desempenho porque:

- e contiguo;
- favorece localidade espacial;
- conversa bem com cache;
- reduz indirecao.

Isso nao significa:

- usar `vector` para tudo cegamente.

Mas significa:

- valorizar layout contiguo antes de inventar estrutura fragmentada.

---

## 5. Alocacao e custo

Alocacao dinamica tem custo:

- tempo de alocar;
- tempo de liberar;
- fragmentacao;
- ruido em profiling;
- indirecao no acesso posterior.

### 5.1 Regra pratica

Se um hot path faz alocacoes demais, suspeite disso cedo.

### 5.2 Ferramentas idiomaticas

Em C++ moderno, vale observar:

- `reserve()` em `std::vector`
- mover em vez de copiar
- evitar `shared_ptr` desnecessario
- evitar `std::function` no hot path quando template resolveria melhor

---

## 6. Alocadores

Alocador e o mecanismo usado por certos containers para obter memoria.

Exemplo conceitual:

- `std::vector<T, Allocator>`

### 6.1 O que isso significa?

Containers podem ser parametrizados por estrategia de alocacao.

No uso inicial, voce quase sempre fica com o default.

### 6.2 Entao por que estudar isso?

Porque em software de alta performance:

- politicas de alocacao importam;
- pools e arenas podem reduzir custo;
- o desenho da memoria vira parte da engenharia.

---

## 7. Profiling

Nao otimize no escuro.

Profile primeiro.

Ferramentas uteis:

- `perf`
- `callgrind`
- profiler do sistema
- relatorios do compilador

### 7.1 O que queremos descobrir?

- qual funcao esta quente?;
- ha alocacao demais?;
- o custo esta em copia?;
- ha misses e indirecao demais?;
- branch ruim esta doendo?;

## 8. Exemplo completo da aula

```cpp
#include <chrono>
#include <iostream>
#include <list>
#include <numeric>
#include <vector>

template <typename F>
long long medir_ms(F f) {
    auto inicio = std::chrono::steady_clock::now();
    f();
    auto fim = std::chrono::steady_clock::now();
    return std::chrono::duration_cast<std::chrono::milliseconds>(fim - inicio).count();
}

int main() {
    constexpr int n = 2'000'000;

    std::vector<int> v;
    v.reserve(n);
    for (int i = 0; i < n; i++) {
        v.push_back(i);
    }

    std::list<int> lst;
    for (int i = 0; i < n; i++) {
        lst.push_back(i);
    }

    long long soma_v = 0;
    auto tempo_v = medir_ms([&] {
        for (int x : v) {
            soma_v += x;
        }
    });

    long long soma_l = 0;
    auto tempo_l = medir_ms([&] {
        for (int x : lst) {
            soma_l += x;
        }
    });

    std::cout << "soma vector = " << soma_v << "\n";
    std::cout << "tempo vector (ms) = " << tempo_v << "\n";
    std::cout << "soma list = " << soma_l << "\n";
    std::cout << "tempo list (ms) = " << tempo_l << "\n";

    return 0;
}
```

---

## 9. O que esse exemplo mostra?

### 9.1 Mesmo trabalho logico

Nos dois casos, estamos:

- armazenando inteiros;
- percorrendo tudo;
- somando tudo.

### 9.2 Mas o custo fisico muda

`std::vector` tende a ganhar porque:

- memoria contigua;
- menos indirecao;
- melhor prefetch;
- cache mais feliz.

`std::list` tende a perder porque:

- cada no geralmente fica espalhado;
- ha ponteiros extras;
- localidade piora;
- prefetch sofre.

### 9.3 Licao principal

Estrutura de dados e custo de hardware estao profundamente conectados.

## 10. `reserve`, realocacao e copy/move

Quando um `std::vector` cresce sem capacidade suficiente, pode haver realocacao.

Isso pode implicar:

- nova alocacao;
- mover ou copiar elementos;
- invalidacao de ponteiros, referencias e iteradores em certos casos.

### 10.1 Por que `reserve(n)` ajuda?

Porque evita varias realocacoes se voce ja conhece a escala aproximada.

### 10.2 Ligacao com aulas anteriores

Aqui entram:

- move semantics;
- copy semantics;
- ownership;
- containers.

---

## 11. Small wins saudaveis

Antes de pensar em micro-otimizacao exotica, verifique:

- estrutura de dados certa;
- evitar alocacao repetida;
- evitar copia desnecessaria;
- passar por referencia quando apropriado;
- usar `emplace_back` ou `push_back` corretamente;
- medir antes e depois.

---

## 12. O que acontece em memoria?

### 12.1 `std::vector`

Tipicamente:

- bloco contiguo no heap;
- crescimento por capacidade;
- acesso linear previsivel.

### 12.2 `std::list`

Tipicamente:

- varios nos alocados separadamente;
- cada no com payload e ponteiros;
- pior localidade espacial.

### 12.3 Ponto essencial

Hardware gosta de:

- sequencia;
- previsibilidade;
- poucos saltos;
- poucos misses.

---

## 13. Comparacao com C, Rust, Go e Python

- Em C, as mesmas leis fisicas valem, mas voce implementa mais infraestrutura manualmente.
- Em Rust, `Vec<T>` tambem se beneficia fortemente de localidade e ownership bem definido.
- Em Go, slices e alocacao do runtime mudam parte da historia, mas cache e layout continuam reais.
- Em Python, boa parte fica escondida pelo runtime, mas extensoes nativas e estruturas internas continuam obedecendo ao mesmo hardware.

C++ deixa essas decisoes muito expostas e muito influentes.

## 15. Erros comuns e anti-padroes

1. **Otimizar sem medir**.
2. **Escolher estrutura por gosto em vez de acesso real**.
3. **Usar `std::list` cedo demais sem necessidade concreta**.
4. **Ignorar custo de alocacao e realocacao**.
5. **Confundir "mais abstrato" com "mais lento" sem medir**.
6. **Trocar codigo claro por micro-otimizacao sem ganho observado**.

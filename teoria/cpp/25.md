# Aula 25 - Type erasure, `std::function`, SBO e custo de abstracoes de chamada

---

## Objetivo da Aula

Entender o que e type erasure em C++, como `std::function` entrega flexibilidade para armazenar e passar callables heterogeneos, o que e SBO e quais custos de dispatch, indirecao e alocacao podem aparecer nesse modelo. Ao final, voce deve conseguir escolher com mais criterio entre template, ponteiro para funcao, functor, lambda e `std::function`, sem tratar abstracao de chamada como custo invisivel.

---

## 1. Ponte com a aula anterior

Na Aula 24, vimos:

- `std::pmr`;
- `memory_resource`;
- arenas;
- pools;
- custo de heap e lifetime.

Agora vamos olhar para outro tipo de custo importante em C++:

- custo de abstracoes de chamada

Essa discussao aparece em:

- callbacks;
- handlers;
- pipelines;
- APIs flexiveis;
- event loops;
- bibliotecas que aceitam comportamento do usuario.

Pergunta central:

- como armazenar "algo chamavel" sem fixar o tipo concreto, e quanto isso custa?

---

## 2. As formas mais comuns de representar comportamento

Em C++, comportamento pode aparecer como:

- funcao livre;
- ponteiro para funcao;
- lambda;
- functor;
- template parametrizado por callable;
- `std::function`.

### 2.1 Essas formas sao equivalentes?

Nao.

Elas podem parecer parecidas na superficie:

- "algo que posso chamar"

Mas mudam bastante em:

- custo;
- inlining;
- armazenamento;
- flexibilidade;
- ABI;
- debugabilidade.

---

## 3. Polimorfismo estatico vs type erasure

Quando voce usa template:

```cpp
template <typename F>
void run(F f) {
    f();
}
```

o tipo concreto do callable e conhecido na instanciacao.

Isso favorece:

- inlining;
- otimizacao;
- ausencia de indirecao de dispatch.

### 3.1 Ja no type erasure

Com `std::function<void()>`:

```cpp
void run(std::function<void()> f) {
    f();
}
```

o codigo opera sobre:

- interface apagada do callable

e nao sobre:

- tipo concreto conhecido estaticamente no ponto de chamada.

---

## 4. O que e type erasure?

- **Type erasure**: tecnica para esconder o tipo concreto atras de uma interface uniforme, preservando certas operacoes suportadas.

No caso de `std::function`, a ideia e:

- aceitar callables de tipos diferentes;
- guardar isso num objeto com API comum;
- permitir invocacao uniforme.

### 4.1 O que se perde?

Em geral, voce perde parte de:

- conhecimento estatico do tipo;
- oportunidades de inlining;
- previsibilidade total de layout;
- eventualmente performance.

### 4.2 O que se ganha?

- flexibilidade de API;
- armazenamento homogeneo;
- desacoplamento entre produtor e consumidor do callable.

---

## 5. `std::function`

`std::function<R(Args...)>` e um wrapper type-erased para callables compativeis com certa assinatura.

Exemplo:

```cpp
std::function<int(int, int)> op;
```

Isso pode guardar:

- ponteiro para funcao;
- lambda sem captura;
- lambda com captura;
- functor;
- binders e outros callables compativeis.

---

## 6. Por que `std::function` e tao usada?

Porque ela simplifica muita API.

Exemplo conceitual:

```cpp
class EventLoop {
public:
    void on_timer(std::function<void()> cb);
};
```

Para o usuario da API, isso e muito ergonomico:

- qualquer callable compativel entra.

### 6.1 O que a ergonomia esconde?

- type erasure;
- possivel alocacao;
- chamada indireta;
- impossibilidade de inlining pleno em varios casos.

---

## 7. Exemplo completo da aula

Este exemplo compara:

- ponteiro para funcao;
- functor;
- lambda com captura;
- `std::function`.

```cpp
#include <functional>
#include <iostream>
#include <vector>

int add_free(int a, int b) {
    return a + b;
}

struct Multiplier {
    int factor;

    int operator()(int x) const {
        return x * factor;
    }
};

template <typename F>
int apply_template(F f, int x) {
    return f(x);
}

int apply_function_ptr(int (*f)(int), int x) {
    return f(x);
}

int apply_std_function(const std::function<int(int)>& f, int x) {
    return f(x);
}

int increment(int x) {
    return x + 1;
}

int main() {
    Multiplier mult{3};
    auto lambda = [offset = 10](int x) {
        return x + offset;
    };

    std::cout << "template/functor = "
              << apply_template(mult, 5) << "\n";

    std::cout << "function ptr = "
              << apply_function_ptr(&increment, 5) << "\n";

    std::cout << "std::function/lambda = "
              << apply_std_function(lambda, 5) << "\n";

    std::vector<std::function<int(int)>> pipeline;
    pipeline.push_back(mult);
    pipeline.push_back(lambda);
    pipeline.push_back([](int x) {
        return x - 2;
    });

    int value = 4;
    for (const auto& step : pipeline) {
        value = step(value);
    }

    std::cout << "pipeline result = " << value << "\n";
    std::cout << "free add = " << add_free(2, 3) << "\n";
    return 0;
}
```

---

## 8. O que esse exemplo mostra?

### 8.1 `apply_template`

O tipo do callable chega conhecido no ponto de instanciacao.

Isso pode favorecer:

- inlining;
- propagacao de constantes;
- eliminacao de overhead desnecessario.

### 8.2 `apply_function_ptr`

Simples e direto.

Mas aceita apenas:

- ponteiro para funcao com assinatura exata.

Nao carrega estado proprio como lambda com captura ou functor com campo interno, a menos que voce crie contexto separado.

### 8.3 `apply_std_function`

Mais flexivel.

Mas entra o custo de:

- wrapper type-erased;
- possivel indirecao;
- possivel alocacao interna.

### 8.4 `pipeline`

Esse e um caso classico em que `std::function` brilha:

- varios callables diferentes;
- mesmo contrato de chamada;
- armazenamento em container homogeneo.

---

## 9. O que `std::function` costuma ter por baixo?

Sem depender de detalhes exatos de implementacao, a intuicao geral e:

- ponteiro ou mecanismo equivalente para invocacao;
- ponteiro ou estrutura para gerenciamento do objeto armazenado;
- armazenamento interno pequeno para certos casos;
- fallback para alocacao dinamica quando o objeto nao cabe no espaco interno.

---

## 10. SBO

- **SBO**: Small Buffer Optimization.

No contexto de wrappers como `std::function`, a ideia e:

- guardar callables pequenos dentro do proprio objeto;
- evitar heap quando o tamanho e alinhamento cabem nesse espaco interno.

### 10.1 Por que isso importa?

Porque sem SBO, mesmo um callable pequeno poderia exigir:

- alocacao dinamica;
- indirecao extra;
- custo adicional de lifetime.

### 10.2 O detalhe importante

O tamanho exato do buffer e detalhes precisos da implementacao:

- dependem da biblioteca padrao.

Entao a maneira correta de pensar e:

- alguns callables pequenos podem caber sem heap;
- callables maiores ou mais estranhos podem cair em alocacao.

---

## 11. Quando `std::function` aloca?

Nao ha regra simples e universal por padrao da linguagem.

Mas a chance cresce quando:

- a captura da lambda e grande;
- o callable tem estado grande;
- o alinhamento exigido nao cabe;
- a implementacao da biblioteca nao consegue usar storage interno naquele caso.

### 11.1 Consequencia pratica

Em hot path, isso pode significar:

- custo de construir wrapper;
- custo de copiar wrapper;
- custo de mover wrapper;
- possivel pressao extra no heap.

---

## 12. Custo de chamada

Quando o tipo concreto e conhecido estaticamente, o compilador pode otimizar muito melhor.

Com type erasure, a chamada geralmente envolve:

- nivel extra de indirecao;
- menos visibilidade para inlining;
- menos informacao para certas otimizacoes.

### 12.1 Isso significa que `std::function` e ruim?

Nao.

Significa apenas:

- tem custo;
- custo precisa ser contextualizado.

### 12.2 Em que casos esse custo e irrelevante?

- callback de GUI;
- cola entre componentes;
- operacoes raras;
- APIs onde ergonomia vale muito.

### 12.3 Em que casos pode importar muito?

- hot loop;
- processamento por elemento;
- pipeline de baixo nivel;
- path critico de servidor;
- callback chamado milhoes de vezes.

---

## 13. Custo de construcao e copia

Muita gente olha so para:

- custo de chamar

Mas tambem existe:

- custo de construir `std::function`;
- custo de mover;
- custo de copiar;
- custo de destruir.

### 13.1 Caso perigoso

Criar `std::function` repetidamente dentro de loop apertado quando o callable podia ser resolvido estaticamente.

---

## 14. `std::function` vs template

### 14.1 Template

Melhor quando:

- voce quer zero-cost mais proximo;
- o tipo pode ser conhecido pelo compilador;
- a API nao precisa armazenar callable heterogeneo num mesmo objeto;
- voce aceita instanciacao por tipo.

### 14.2 `std::function`

Melhor quando:

- precisa armazenar varios callables diferentes sob mesma assinatura;
- quer fronteira de API simples;
- quer desacoplamento de implementacao;
- aceita custo adicional em troca de flexibilidade.

### 14.3 Regra pratica

Se o callable:

- cruza fronteira de armazenamento heterogeneo

`std::function` faz mais sentido.

Se o callable:

- e apenas parametrizacao local de algoritmo

template costuma ser melhor.

---

## 15. `std::function` vs ponteiro para funcao

Ponteiro para funcao e mais simples quando:

- nao ha estado capturado;
- assinatura e fixa;
- voce quer custo mais previsivel;
- interoperabilidade com C importa.

`std::function` ganha quando:

- o comportamento precisa carregar estado;
- lambdas com captura e functors sao naturais;
- a API quer aceitar mais formas de callable.

---

## 16. Exemplo de type erasure conceitual manual

Para entender a ideia, pense em algo assim:

```cpp
struct CallableBox {
    void* object;
    int (*invoke)(void*, int);
};
```

Aqui:

- `object` aponta para algo concreto;
- `invoke` sabe como chamar esse algo.

Isso nao e uma implementacao completa nem segura para uso real.

Mas ajuda a enxergar o principio:

- esconder tipo concreto;
- manter operacao uniforme.

### 16.1 O que `std::function` faz alem disso?

- gerencia lifetime;
- suporta copia e move;
- lida com destruicao;
- abstrai detalhes;
- tenta otimizar pequenos objetos.

---

## 17. Relacao com a Aula 24

Agora a ligacao fica clara.

`std::function` pode cobrar:

- dispatch indireto;
- e em alguns casos, alocacao.

Ou seja:

- abstracao de chamada

e tambem:

- problema de memoria

Se o sistema cria muitos wrappers, ou cria/destroi callables frequentemente, vale olhar para:

- padrao de captura;
- tamanho do callable;
- lifetime;
- numero de criacoes;
- se a fronteira realmente precisa de type erasure.

---

## 18. Relacao com servidores e event loops

Em sistemas orientados a eventos, aparece a tentacao de usar:

- `std::function` para todo handler

Isso pode ser excelente para ergonomia.

Mas em servidor de alto throughput, perguntas importantes sao:

- handlers sao recriados o tempo todo?;
- cada conexao carrega varios wrappers?;
- ha alocacao demais?;
- o dispatch indireto esta no hot path?;

### 18.1 Conclusao pratica

Nao existe regra dogmatica.

Existe:

- medir;
- entender a arquitetura;
- usar a ferramenta certa no lugar certo.

---

## 19. Comparacao com C, Rust, Go e Python

- Em C, callbacks costumam ser ponteiro para funcao mais `void*` de contexto.
- Em Rust, closures, generics e trait objects ocupam espaco conceitual parecido, com separacao forte entre dispatch estatico e dinamico.
- Em Go, funcoes como valores sao muito naturais, mas com outro runtime e outro custo global.
- Em Python, tudo isso e muito mais dinamico por natureza, com custo e modelo de objetos completamente diferentes.

C++ obriga voce a escolher com mais granularidade:

- template;
- ponteiro para funcao;
- functor;
- lambda;
- `std::function`.

E essa escolha pode aparecer no perfil.

## 21. Erros comuns e anti-padroes

1. **Achar que todo callable deve virar `std::function` por padrao**.
2. **Ignorar custo de construcao e copia de wrappers**.
3. **Usar `std::function` em hot loop onde template resolveria melhor**.
4. **Assumir que lambda com captura nunca aloca ao entrar em `std::function`**.
5. **Escolher ponteiro para funcao quando o problema exigia estado capturado**.
6. **Discutir abstracao de chamada sem medir o contexto real**.

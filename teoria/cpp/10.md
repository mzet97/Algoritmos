# Aula 10 - Polimorfismo, heranca, `virtual`, interfaces e object model de C++

---

## Objetivo da Aula

Entender como heranca e polimorfismo funcionam em C++, quando `virtual` e necessario, como modelar interfaces com classes abstratas, e quais custos e limites existem no object model da linguagem. Ao final, voce deve conseguir distinguir polimorfismo estatico e dinamico e saber quando hierarquia de tipos ajuda ou atrapalha.

## 2. O que e heranca?

Heranca permite definir um tipo derivado a partir de um tipo base.

Exemplo:

```cpp
class Animal {
};

class Cachorro : public Animal {
};
```

### 2.1 O que isso significa?

Conceitualmente:

- `Cachorro` e um `Animal`
- `Cachorro` pode herdar interface e comportamento da base

### 2.2 Quando isso pode ser util?

Quando existe relacao semantica forte de:

- "e um"

e quando a hierarquia realmente modela dominio.

---

## 3. Polimorfismo dinamico

Polimorfismo dinamico permite chamar comportamento apropriado em runtime via referencia ou ponteiro para base.

Exemplo:

```cpp
class Animal {
public:
    virtual void falar() const {
        std::cout << "som generico\n";
    }
};
```

```cpp
class Cachorro : public Animal {
public:
    void falar() const override {
        std::cout << "au au\n";
    }
};
```

Uso:

```cpp
Animal* a = new Cachorro();
a->falar();
```

Se `falar` for `virtual`, a chamada correta em runtime acontece para `Cachorro`.

---

## 4. Sem `virtual`, o que acontece?

Se a funcao nao for `virtual`, a resolucao em geral depende do tipo estatico visivel no ponto da chamada.

Ou seja:

- a interface da base nao despacha dinamicamente

Esse e um erro classico de iniciante.

---

## 5. `override`

Sempre que reimplementar metodo virtual da base, prefira marcar com:

```cpp
override
```

Exemplo:

```cpp
void falar() const override;
```

### 5.1 Por que isso existe?

Porque protege contra erros como:

- assinatura ligeiramente diferente;
- falta de virtual real;
- override acidental quebrado.

---

## 6. Interface em C++

C++ nao tem palavra separada obrigatoria como `interface` de outras linguagens.

Uma interface costuma ser modelada com classe abstrata:

```cpp
class Forma {
public:
    virtual double area() const = 0;
    virtual ~Forma() = default;
};
```

### 6.1 O que `= 0` significa?

Significa funcao virtual pura.

Ou seja:

- a classe passa a ser abstrata;
- nao pode ser instanciada diretamente;
- tipos derivados devem fornecer implementacao concreta.

---

## 7. Destrutor virtual

Se uma classe base vai ser usada polimorficamente, normalmente o destrutor dela deve ser virtual.

Exemplo:

```cpp
virtual ~Forma() = default;
```

### 7.1 Por que isso importa?

Porque se voce destruir um objeto derivado por ponteiro para base sem destrutor virtual:

- o comportamento pode ficar incorreto;
- cleanup do derivado pode nao rodar como esperado;
- isso pode causar leak ou UB.

---

## 8. Exemplo completo da aula

```cpp
#include <iostream>
#include <memory>
#include <vector>

class Forma {
public:
    virtual double area() const = 0;
    virtual void desenhar() const = 0;
    virtual ~Forma() = default;
};

class Retangulo : public Forma {
public:
    Retangulo(double largura, double altura)
        : largura_(largura), altura_(altura) {}

    double area() const override {
        return largura_ * altura_;
    }

    void desenhar() const override {
        std::cout << "Retangulo(" << largura_ << ", " << altura_ << ")\n";
    }

private:
    double largura_;
    double altura_;
};

class Circulo : public Forma {
public:
    explicit Circulo(double raio) : raio_(raio) {}

    double area() const override {
        return 3.141592653589793 * raio_ * raio_;
    }

    void desenhar() const override {
        std::cout << "Circulo(" << raio_ << ")\n";
    }

private:
    double raio_;
};

void imprimir_relatorio(const Forma& forma) {
    forma.desenhar();
    std::cout << "area = " << forma.area() << "\n";
}

int main() {
    Retangulo r(4.0, 3.0);
    Circulo c(2.0);

    imprimir_relatorio(r);
    imprimir_relatorio(c);

    std::vector<std::unique_ptr<Forma>> formas;
    formas.push_back(std::make_unique<Retangulo>(10.0, 2.0));
    formas.push_back(std::make_unique<Circulo>(1.5));

    std::cout << "relatorio do vetor polimorfico:\n";
    for (const auto& f : formas) {
        f->desenhar();
        std::cout << "area = " << f->area() << "\n";
    }

    return 0;
}
```

---

## 9. O que esse exemplo mostra?

### 9.1 `Forma`

Classe abstrata:

- define contrato comum;
- nao define implementacao concreta total.

### 9.2 `Retangulo` e `Circulo`

Tipos derivados:

- implementam `area()`
- implementam `desenhar()`

### 9.3 `const Forma&`

Permite receber qualquer derivado sem copiar e com despacho virtual.

### 9.4 `std::vector<std::unique_ptr<Forma>>`

Mostra combinacao de:

- polimorfismo dinamico;
- ownership dinamico seguro;
- heterogeneidade sob interface comum.

---

## 10. O que `virtual` muda no object model?

Sem entrar ainda em detalhes de ABI especifica, o modelo mental util e:

- objeto polimorfico costuma carregar metadado para despacho virtual;
- a chamada virtual precisa descobrir qual implementacao concreta usar;
- isso tem custo de indirecao em runtime.

### 10.1 Isso e proibitivamente caro?

Quase nunca por si so.

Mas tambem nao e custo zero.

Em hot path muito sensivel, isso pode importar.

---

## 11. Heranca nao e o unico caminho

Em C++ moderno, antes de usar heranca, pergunte:

- preciso realmente de despacho dinamico?
- composicao resolveria melhor?
- template ou callback resolveria melhor?

### 11.1 Quando heranca ajuda

- contrato realmente comum entre tipos;
- uso polimorfico em runtime;
- necessidade de colecao heterogenea sob interface unica.

### 11.2 Quando atrapalha

- hierarquia artificial;
- reuso de implementacao forcado;
- muitos detalhes acoplados na base;
- custo conceitual maior do que o beneficio.

---

## 12. Polimorfismo estatico vs dinamico

### 12.1 Polimorfismo estatico

Exemplos:

- templates;
- sobrecarga;
- lambdas resolvidas em compilacao.

### 12.2 Polimorfismo dinamico

Exemplos:

- `virtual`
- classe abstrata
- despacho via ponteiro ou referencia para base

### 12.3 Regra pratica

Use polimorfismo dinamico quando a escolha real da implementacao precisa acontecer em runtime entre tipos da mesma familia.

---

## 13. O que acontece em memoria?

Cada objeto derivado contem:

- a parte correspondente a base;
- seus membros proprios;
- e, em tipos polimorficos, geralmente estrutura de apoio ao despacho virtual.

Quando voce acessa por `Forma&` ou `Forma*`:

- o tipo estatico conhecido e `Forma`
- o tipo dinamico real pode ser `Retangulo` ou `Circulo`

Esse desacoplamento e a alma do polimorfismo dinamico.

---

## 14. Comparacao com C, Rust, Go e Python

- Em C, algo parecido costuma ser montado manualmente com `struct` + tabela de funcoes.
- Em Rust, trait objects lembram parte dessa historia, com custos e regras proprios.
- Em Go, interfaces fazem papel semelhante no uso, embora o modelo interno e a ergonomia sejam diferentes.
- Em Python, tudo isso parece mais natural porque o runtime dinamico assume mais responsabilidade.

C++ te da:

- polimorfismo dinamico explicito;
- controle de layout maior;
- custo mais visivel;

mas exige:

- design cuidadoso;
- destrutor virtual quando necessario;
- clareza sobre ownership.

## 16. Erros comuns e anti-padroes

1. **Esquecer `virtual` e esperar despacho dinamico**.
2. **Nao usar `override` em metodos sobrescritos**.
3. **Esquecer destrutor virtual em base polimorfica**.
4. **Usar heranca quando composicao resolveria melhor**.
5. **Criar hierarquias profundas e artificiais cedo demais**.
6. **Confundir polimorfismo por template com polimorfismo por `virtual`**.

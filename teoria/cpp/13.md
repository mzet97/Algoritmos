# Aula 13 - Depuracao com `gdb`, sanitizers e `valgrind`

Depurar com `gdb`, sanitizers e valgrind é interrogar o programa com método, não com prints. Em C++, onde o erro pode estar no destrutor de um objeto temporário, método é a única coisa entre você e uma semana perdida.

---

## Nesta aula

Entender como investigar bugs em C++ com `gdb`, AddressSanitizer, UndefinedBehaviorSanitizer, ThreadSanitizer e `valgrind`, conectando sintomas observados a causas reais de memoria, lifetime e comportamento indefinido. Ao final, voce deve conseguir sair do modo "adivinhacao por print" e entrar num fluxo mais tecnico de diagnostico. Você vai aprender a reproduzir um crash e extrair a causa com `gdb` + sanitizer; classificar o relatorio (categoria, arquivo, linha); e montar o fluxo sintoma → hipotese → instrumento → confirmacao.

## 2. Tipos de problema que queremos investigar

Exemplos comuns:

- crash;
- segmentation fault;
- use-after-free;
- double delete;
- leitura fora de faixa;
- comportamento indefinido;
- data race;
- valor estranho em runtime;
- logica correta aparente com resultado incorreto.

Cada ferramenta ajuda mais em certos tipos de problema.

---

## 3. `gdb`

`gdb` e debugger interativo.

Ele ajuda a:

- parar o programa;
- inspecionar variaveis;
- caminhar linha por linha;
- ler stack trace;
- entender o estado no momento da falha.

### 3.1 Para usar bem

Compile com:

- `-g`
- normalmente `-O0` no inicio da investigacao

Exemplo:

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -O0 -g bug.cpp -o bug
```

---

## 4. Breakpoints e stack trace

Comandos iniciais uteis no `gdb`:

- `break main`
- `run`
- `next`
- `step`
- `print variavel`
- `backtrace`

### 4.1 `next` vs `step`

- `next`: executa a linha atual sem entrar em chamada
- `step`: entra na chamada

### 4.2 `backtrace`

Mostra a pilha de chamadas no ponto atual ou no ponto de falha.

Isso e crucial para:

- descobrir quem chamou quem;
- localizar o caminho ate o erro.

---

## 5. AddressSanitizer

AddressSanitizer, ou ASan, ajuda a detectar:

- use-after-free;
- buffer overflow;
- stack overflow de certos tipos;
- acesso invalido a memoria.

Compilacao tipica:

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -O0 -g -fsanitize=address bug.cpp -o bug
```

### 5.1 Por que ele e tao valioso?

Porque muitos bugs de memoria em C++:

- nao quebram imediatamente;
- quebram longe da causa;
- produzem sintoma enganoso.

ASan costuma apontar:

- o acesso invalido;
- a origem do bloco;
- onde o bloco foi liberado.

---

## 6. UndefinedBehaviorSanitizer

UBSan ajuda a detectar varias formas de comportamento indefinido, como:

- overflow assinado em certos contextos;
- cast invalido;
- alinhamento invalido;
- acesso a objeto errado em alguns casos.

Compilacao tipica:

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -O0 -g -fsanitize=undefined bug.cpp -o bug
```

### 6.1 Regra pratica

ASan e UBSan combinados frequentemente valem muito em debug:

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -O0 -g -fsanitize=address -fsanitize=undefined bug.cpp -o bug
```

---

## 7. ThreadSanitizer

TSan ajuda a detectar:

- data races;
- acessos concorrentes sem sincronizacao adequada.

Compilacao tipica:

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -O1 -g -fsanitize=thread bug.cpp -o bug
```

### 7.1 Quando ele importa?

Quando estamos lidando com:

- `std::thread`
- mutex
- atomics
- compartilhamento de estado

Vamos retomar isso na aula de concorrencia, mas ja vale fixar a ferramenta.

---

## 8. `valgrind`

`valgrind` e uma ferramenta poderosa para:

- leaks;
- acessos invalidos;
- observacao de memoria em runtime.

Uso tipico:

```bash
valgrind --leak-check=full ./bug
```

### 8.1 Limites

- bem mais lento;
- nem sempre combina com todos os sanitizers ao mesmo tempo;
- algumas plataformas ou setups modernos favorecem mais sanitizers do compilador.

Mesmo assim, continua sendo excelente ferramenta mental e pratica.

---

## 9. Exemplo completo da aula

```cpp
#include <iostream>

int main() {
    int* v = new int[3];
    for (int i = 0; i < 3; i++) {
        v[i] = i * 10;
    }

    delete[] v;

    std::cout << "acesso invalido: " << v[1] << "\n";

    return 0;
}
```

### 9.1 O que esse programa faz?

- aloca array
- preenche
- libera
- acessa depois da liberacao

Ou seja:

- use-after-free

---

## 10. Como investigar esse bug

### 10.1 Com `gdb`

Compilar:

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -O0 -g aula13.cpp -o aula13
```

Rodar:

```bash
gdb ./aula13
```

Dentro do `gdb`:

```text
run
backtrace
```

### 10.2 Com ASan

Compilar:

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -O0 -g -fsanitize=address aula13.cpp -o aula13
```

Rodar:

```bash
./aula13
```

ASan deve apontar o acesso apos liberacao.

### 10.3 Com `valgrind`

Compilar sem sanitizer:

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -O0 -g aula13.cpp -o aula13
```

Rodar:

```bash
valgrind --leak-check=full ./aula13
```

---

## 11. Fluxo de depuracao saudavel

1. reproduza o bug
2. reduza o caso quando possivel
3. compile com warnings fortes
4. rode com sanitizers
5. se preciso, use `gdb` para inspecionar estado
6. confirme a hipotese com nova execucao

### 11.1 O que evitar?

- editar aleatoriamente sem entender a causa;
- confiar so em `std::cout`;
- mudar varias coisas ao mesmo tempo;
- assumir que "sumiu o crash" significa "corrigi a causa".

---

## 12. O que acontece em memoria nesse bug?

No exemplo:

- `new[]` aloca bloco no heap
- `v` guarda o endereco
- `delete[] v` libera o bloco
- `v` continua com um endereco antigo, agora pendurado

Quando fazemos:

```cpp
v[1]
```

estamos lendo memoria que ja nao pertence legitimamente ao objeto.

Isso e o coracao do dangling pointer.

---

## 13. Comparacao com C, Rust, Go e Python

- Em C, o fluxo de depuracao com `gdb`, `valgrind` e sanitizers e muito parecido.
- Em Rust, muitas classes de erro de memoria nem chegam ao runtime por conta do borrow checker, mas debugging continua importante para logica e unsafe.
- Em Go, GC remove certas classes de bug, mas corrida, logica e ponteiros ainda podem exigir investigacao.
- Em Python, debugging de memoria manual e bem menos comum, mas bugs logicos e de integracao continuam existindo.

C++ fica num ponto em que:

- ferramentas de depuracao sao obrigatorias;
- ignorar sanitizers costuma custar caro.

## 15. Erros comuns e anti-padroes

1. **Depurar so com `std::cout` em bug de memoria serio**.
2. **Nao compilar com `-g` e depois reclamar que `gdb` nao ajuda**.
3. **Rolar `-O2` cedo demais durante investigacao inicial**.
4. **Ignorar warnings antes de abrir debugger**.
5. **Nao usar sanitizer em codigo C++ com alocacao e lifetime complicados**.
6. **Achar que `valgrind` e ASan fazem exatamente a mesma coisa**.

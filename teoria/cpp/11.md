# Aula 11 - Tratamento de erros com excecoes, `std::optional`, `std::variant` e `std::expected` quando fizer sentido

Exceção, `optional`, `variant`, `expected`: quatro gramáticas para dizer 'algo deu errado'. Escolher a errada espalha erro pelo sistema inteiro; escolher bem é design de API, não sintaxe.

---

## Nesta aula

Entender como C++ moderno modela falha e ausencia de valor com excecoes e tipos de retorno explicitos como `std::optional`, `std::variant` e `std::expected`, e como escolher entre esses mecanismos sem misturar fluxo nominal com erro operacional. Você vai aprender a escolher entre excecao, `optional`, `variant` e `expected` para tres falhas distintas, justificando cada uma; e explicar a garantia que cada escolha da ao chamador.


---

## 1. Ponte com a aula anterior

Na Aula 10, vimos:

- polimorfismo;
- interfaces;
- despacho dinamico;
- custo operacional de certas decisoes.

Agora precisamos enfrentar outra pergunta de engenharia:

- como representar falha?

Em C++ isso nao tem resposta unica.

Temos pelo menos quatro familias importantes:

- excecoes;
- retorno opcional;
- retorno discriminado por variante;
- retorno esperado com valor ou erro.

---

## 2. O problema do erro em C++

Qualquer operacao pode falhar por motivos como:

- arquivo inexistente;
- indice invalido;
- parse invalido;
- falta de memoria;
- precondicao quebrada;
- estado logico impossivel.

Se a API nao deixa isso claro, o usuario pode:

- ignorar erro;
- interpretar dado lixo;
- misturar "nao achei" com "falhou";
- quebrar invariantes.

---

## 3. Excecoes

Excecao e um mecanismo de propagacao de erro fora do fluxo normal por meio de `throw` e `catch`.

Exemplo:

```cpp
throw std::runtime_error("falha ao abrir arquivo");
```

Tratamento:

```cpp
try {
    // codigo
} catch (const std::exception& e) {
    std::cout << e.what() << "\n";
}
```

### 3.1 O que isso compra?

- separa caminho nominal de tratamento de falha;
- evita encadear erro manual em toda chamada;
- integra bem com RAII no unwind de stack.

### 3.2 O que isso cobra?

- custo mental maior;
- contratos menos visiveis no tipo;
- necessidade de disciplina sobre onde lancar e onde capturar;
- possivel politica de projeto contraria a excecoes.

---

## 4. RAII e excecoes

Esse ponto e crucial.

Se uma excecao atravessa escopos, destrutores de objetos automaticos ainda rodam.

Isso e um dos motivos de RAII ser tao central em C++.

Exemplo conceitual:

```cpp
void f() {
    std::string nome = "tmp";
    throw std::runtime_error("erro");
}
```

Mesmo com `throw`, `nome` e destruido no unwind.

### 4.1 Comparacao com C

Em C, isso normalmente exigiria:

- checagem manual;
- `goto cleanup`;
- disciplina repetitiva.

---

## 5. `std::optional`

`std::optional<T>` representa:

- ou ha um `T`;
- ou nao ha valor.

Exemplo:

```cpp
std::optional<int> procurar_id();
```

### 5.1 Quando ele e bom?

Quando a ausencia de valor:

- e esperada;
- nao e excepcional;
- nao precisa carregar diagnostico rico.

### 5.2 Exemplo classico

- busca que pode nao encontrar;
- parse simples que pode falhar sem contexto rico;
- cache que pode nao ter entrada.

---

## 6. `std::variant`

`std::variant<A, B, C>` representa um valor que pode estar em um entre varios tipos possiveis.

Exemplo:

```cpp
std::variant<int, std::string>
```

### 6.1 Quando isso e util?

Quando o resultado legitimo pode assumir formas diferentes.

Nao e necessariamente "tipo de erro".

Pode ser:

- token numerico ou textual;
- resposta de varios tipos;
- estado discriminado.

### 6.2 Cuidado

`variant` nao deve virar gaveta generica para evitar design.

---

## 7. `std::expected`

`std::expected` faz parte de **C++23**, não de C++20. Esta aula é uma exceção
à base C++20 do livro: confirme que o compilador e a biblioteca padrão
oferecem `<expected>` antes de executá-la. Se não oferecerem, estude os
conceitos e execute os trechos de `optional` e `variant` separadamente; não
substitua `std::expected` por uma biblioteca externa no percurso obrigatório.

`std::expected<T, E>` representa:

- ou ha um valor `T`;
- ou ha um erro `E`.

Esse modelo e extremamente interessante para APIs que querem:

- falha explicita no tipo;
- sem excecao;
- com diagnostico estruturado.

### 7.1 Intuicao

Melhor pensar como:

- "resultado esperado de sucesso ou erro"

### 7.2 Quando usar?

Quando falha e parte normal do contrato e voce quer que o chamador trate isso explicitamente.
O tipo documenta a possibilidade de erro, mas C++ nao obriga o chamador a
verificar um `expected` retornado. Construir `T` ou `E` tambem pode lancar
excecao; `expected` nao garante, por si so, uma API livre de excecoes.

---

## 8. Exemplo completo da aula

```cpp
#include <charconv>
#include <expected>
#include <iostream>
#include <limits>
#include <optional>
#include <stdexcept>
#include <string>
#include <variant>

int dividir_ou_lancar(int a, int b) {
    if (b == 0 || (a == std::numeric_limits<int>::min() && b == -1)) {
        throw std::runtime_error("divisao invalida");
    }
    return a / b;
}

std::optional<int> parse_int_optional(const std::string& s) {
    if (s.empty()) {
        return std::nullopt;
    }

    for (char c : s) {
        if (c < '0' || c > '9') {
            return std::nullopt;
        }
    }

    int valor = 0;
    auto [fim, erro] = std::from_chars(s.data(), s.data() + s.size(), valor);
    if (erro != std::errc{} || fim != s.data() + s.size()) {
        return std::nullopt;
    }
    return valor;
}

using Token = std::variant<int, std::string>;

Token parse_token(const std::string& s) {
    if (auto v = parse_int_optional(s)) {
        return *v;
    }
    return s;
}

std::expected<int, std::string> dividir_esperado(int a, int b) {
    if (b == 0 || (a == std::numeric_limits<int>::min() && b == -1)) {
        return std::unexpected("divisao invalida");
    }
    return a / b;
}

int main() {
    try {
        std::cout << "10 / 2 = " << dividir_ou_lancar(10, 2) << "\n";
        std::cout << "10 / 0 = " << dividir_ou_lancar(10, 0) << "\n";
    } catch (const std::exception& e) {
        std::cout << "excecao capturada: " << e.what() << "\n";
    }

    auto numero = parse_int_optional("123");
    auto falha = parse_int_optional("12x");

    if (numero) {
        std::cout << "numero parseado: " << *numero << "\n";
    }
    if (!falha) {
        std::cout << "falha de parse em optional\n";
    }

    Token t1 = parse_token("77");
    Token t2 = parse_token("abc");

    std::visit([](const auto& valor) {
        std::cout << "token 1: " << valor << "\n";
    }, t1);

    std::visit([](const auto& valor) {
        std::cout << "token 2: " << valor << "\n";
    }, t2);

    auto r1 = dividir_esperado(20, 5);
    auto r2 = dividir_esperado(20, 0);

    if (r1) {
        std::cout << "resultado expected ok: " << *r1 << "\n";
    }
    if (!r2) {
        std::cout << "erro expected: " << r2.error() << "\n";
    }

    return 0;
}
```

---

## 9. O que esse exemplo mostra?

### 9.1 `dividir_ou_lancar`

Usa excecao para erro excepcional.

### 9.2 `parse_int_optional`

Usa `optional` quando:

- pode haver valor;
- pode nao haver;
- sem diagnostico rico.

`std::from_chars` recusa inteiros maiores que `int` sem provocar overflow.
O exemplo aceita apenas digitos ASCII nao negativos; outros formatos exigem
uma politica de parse explicita. Divisao por zero e `INT_MIN / -1` tambem
sao recusadas antes da operacao, pois ambas invalidam o calculo em `int`.

### 9.3 `parse_token`

Usa `variant` quando o resultado legitimo pode ser:

- inteiro;
- string.

### 9.4 `dividir_esperado`

Usa `expected` quando:

- o erro faz parte do contrato;
- queremos deixar valor ou erro visiveis no tipo de retorno.

---

## 10. Quando escolher cada um?

### 10.1 Excecao

Use quando:

- falha e realmente excepcional;
- a camada do projeto aceita excecoes;
- quer separar caminho normal de erro;
- RAII ja cobre cleanup.

### 10.2 `optional`

Use quando:

- ausencia de valor e normal;
- nao precisa erro detalhado.

### 10.3 `variant`

Use quando:

- varios tipos de resultado sao legitimos;
- nao necessariamente estamos falando de falha.

### 10.4 `expected`

Use quando:

- quer valor ou erro explicito no tipo;
- sem excecao;
- com contrato visivel e estruturado.

---

## 11. O que acontece em memoria e no fluxo?

Excecoes podem causar unwind de stack.

Isso significa:

- a execucao salta para o handler apropriado;
- objetos automaticos no caminho sao destruidos.

`optional`, `variant` e `expected` normalmente carregam estado discriminado no proprio objeto de retorno.

Ou seja:

- o chamador recebe um valor normal de C++;
- precisa inspecionar explicitamente seu estado.

### 11.1 Ponto importante

Excecao muda fluxo de controle.

`optional`, `variant` e `expected` mantem fluxo explicito no retorno.

---

## 12. Comparacao com C, Rust, Go e Python

- Em C, erro costuma ser retorno manual, `errno` e convencoes locais.
- Em Rust, `Option<T>` e `Result<T, E>` lembram fortemente `optional` e `expected`.
- Em Go, o padrao classico e retorno de valor + `error`.
- Em Python, excecoes sao mecanismo dominante e onipresente.

C++ mistura varios estilos e por isso exige mais criterio arquitetural.

## 14. Erros comuns e anti-padroes

1. **Usar excecao para fluxo nominal comum**.
2. **Usar `optional` quando o erro precisava de contexto**.
3. **Usar `variant` como saco de tipos sem contrato claro**.
4. **Ignorar retorno de `expected` ou `optional`**.
5. **Misturar politicas de erro diferentes sem criterio entre modulos**.
6. **Achar que uma tecnica substitui todas as outras**.

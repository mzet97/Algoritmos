# Aula 19 - Boas praticas para bibliotecas, backend, ferramentas e sistemas de producao em C++

Escrever código que funciona é metade do trabalho; a outra metade é escrever código que outra pessoa consegue operar, depurar e confiar em produção. Boas práticas para bibliotecas, backend e ferramentas em C++ são, no fundo, respeito por quem vem depois — incluindo você daqui a seis meses.

---

## Nesta aula

Consolidar a trilha principal de C++ mostrando como transformar os conceitos estudados em praticas saudaveis para bibliotecas, backends, ferramentas internas e sistemas de producao. Ao final, voce deve conseguir avaliar uma base de codigo C++ com criterios de contrato, ownership, build, erro, observabilidade e desempenho, em vez de olhar apenas para "compila ou nao compila". Você vai aprender a auditar uma base real com o checklist de contrato/ownership/build/erro/observabilidade; apontar tres defeitos com severidade; e propor a correcao com o custo declarado.

## 2. Contrato antes de implementacao

Em producao, o primeiro passo nao deveria ser:

- "sair implementando"

mas:

- definir contrato.

### 2.1 O que entra no contrato?

- quem chama a API;
- o que ela promete;
- quem possui o que;
- como erros sao reportados;
- que invariantes precisam ser mantidas;
- se a API e thread-safe ou nao;
- quais custos importam.

### 2.2 Consequencia pratica

Muita arquitetura ruim em C++ nasce de ownership e erro mal definidos, nao de sintaxe ruim.

---

## 3. Ownership explicito sempre que possivel

Perguntas obrigatorias em qualquer modulo:

- quem e dono desse recurso?
- essa referencia observa ou possui?
- esse ponteiro pode ser nulo?
- pode haver compartilhamento?

### 3.1 Sinais saudaveis

- uso claro de valor, referencia e smart pointer;
- pouca ambiguidade;
- RAII em recursos reais;
- raridade de `new`/`delete` no codigo de aplicacao.

### 3.2 Sinais perigosos

- ponteiro cru sem contrato;
- ownership implicito;
- `shared_ptr` espalhado sem necessidade;
- ciclos de responsabilidade mal definidos.

---

## 4. API pequena e previsivel

Bibliotecas boas tendem a:

- expor superficie pequena;
- esconder detalhes internos;
- separar interface publica de implementacao;
- evitar leaking de tipo interno sem necessidade.

### 4.1 Regra pratica

Se a API publica esta crescendo sem disciplina, estabilize antes de adicionar mais features.

### 4.2 Ligacao com ABI

Quanto maior a superficie exposta:

- maior o acoplamento;
- maior o risco binario;
- maior a dificuldade de evolucao.

---

## 5. Build reproduzivel

Projeto serio precisa build previsivel.

Isso inclui:

- flags conhecidas;
- modo debug;
- modo release;
- warnings fortes;
- sanitizers no fluxo normal;
- organizacao clara de dependencias.

### 5.1 Minimo saudavel

- `-Wall`
- `-Wextra`
- `-Wpedantic`
- `-g`
- `-O0` em debug
- `-O2` ou `-O3` com criterio em release

### 5.2 Ferramentas

- `make`
- `cmake`
- testes automatizados
- CI

---

## 6. Politica de erro coerente

Escolha precisa ser consciente:

- excecao?
- `expected`?
- `optional`?
- codigo de erro?

### 6.1 O que evitar

Misturar tudo aleatoriamente.

### 6.2 Regra pratica

Defina por camada.

Exemplo:

- camada interna critica pode usar `expected`
- camada de alto nivel pode traduzir para excecao
- fronteira C-style pode converter tudo em codigo de erro

---

## 7. Observabilidade e debugging

Programa de producao precisa ser investigavel.

Isso significa:

- logs com contexto;
- mensagens de erro legiveis;
- asserts onde cabem;
- stack traces quando possivel;
- diagnostico reproduzivel;
- capacidade de rodar com sanitizers em ambiente de teste.

### 7.1 Anti-padrao classico

- falhar silenciosamente;
- ou imprimir erro generico sem contexto.

---

## 8. Performance como disciplina, nao supersticao

Codigo C++ de producao nao deve oscilar entre:

- zero preocupacao com desempenho;
- paranoia micro-otimizadora sem medicao.

### 8.1 Fluxo saudavel

1. escolha estrutura adequada
2. escreva codigo claro
3. meca
4. localize gargalo
5. otimize o hot path real
6. meca de novo

### 8.2 Perguntas boas

- ha alocacao demais?;
- ha copia demais?;
- o container faz sentido?;
- o layout ajuda cache?;
- existe contencao entre threads?;

---

## 9. Concorrencia: declare garantias

Nao basta ter `mutex`.

A base precisa dizer:

- este tipo e thread-safe?
- este objeto pode ser compartilhado?
- a sincronizacao e interna ou externa?

### 9.1 Regra pratica

Se a thread safety nao estiver clara, ela nao existe como contrato confiavel.

---

## 10. Exemplo conceitual de modulo mais saudavel

Imagine um pequeno modulo `TaskQueue`.

Boas decisoes:

- header pequeno;
- ownership interno escondido;
- API clara;
- erro documentado;
- thread safety declarada;
- testes para cenarios criticos;
- benchmark so para hot paths relevantes.

### 10.1 Exemplo de interface pequena

```cpp
class TaskQueue {
public:
    TaskQueue();
    ~TaskQueue();

    void push(Task task);
    std::optional<Task> try_pop();

private:
    struct Impl;
    std::unique_ptr<Impl> impl_;
};
```

### 10.2 O que isso sugere?

- PIMPL para reduzir acoplamento binario e esconder detalhes;
- `optional` para "talvez nao haja tarefa";
- ownership explicito via `unique_ptr`.

## 11. Ferramentas internas e CLIs

Para ferramentas internas, priorize:

- clareza operacional;
- contratos simples;
- exit codes previsiveis;
- logs uteis;
- erros compreensiveis;
- custo de manutencao baixo.

### 11.1 O que evitar

- excesso de framework para ferramenta pequena;
- dependencia inutil;
- API interna mal definida;
- parser improvisado sem validacao.

---

## 12. Backend e servicos

Em backend C++:

- latencia;
- throughput;
- memory footprint;
- observabilidade;
- comportamento sob carga;

tornam-se decisivos.

### 12.1 Isso muda o que?

- thread pools e fila de trabalho precisam contrato claro;
- buffers e parsing precisam ser medidos;
- alocacao e copia importam muito;
- shutdown e tratamento de erro precisam ser previsiveis.

---

## 13. Bibliotecas

Biblioteca boa costuma ter:

- API pequena;
- nomes claros;
- ownership claro;
- contrato de erro claro;
- build reproduzivel;
- documentacao objetiva;
- testes.

### 13.1 Se for biblioteca publica

Pense tambem em:

- estabilidade de ABI;
- compatibilidade de versao;
- politica de deprecacao;
- custo de mudar assinatura exposta.

---

## 14. PIMPL, headers estaveis e reducao de acoplamento

PIMPL e um padrao onde a classe publica guarda ponteiro para implementacao privada.

Isso ajuda a:

- reduzir dependencia em header;
- esconder detalhes;
- aliviar impacto de mudancas internas;
- melhorar estabilidade binaria em alguns cenarios.

### 14.1 Custo

- indirecao extra;
- mais complexidade;
- possivel alocacao adicional.

Entao use com criterio.

---

## 15. O que acontece em memoria, build e runtime?

Produzir software nativo serio em C++ significa pensar simultaneamente em:

- layout e lifetime;
- fronteira de modulo;
- flags de build;
- custo de abstracao;
- estrategia de erro;
- integracao com o sistema.

### 15.1 Ponto central da trilha

C++ e poderoso porque junta:

- controle fino;
- abstracoes fortes;
- performance;
- capacidade de modelar sistemas reais.

Mas isso cobra:

- disciplina;
- coerencia;
- criterio tecnico.

---

## 16. Comparacao com C, Rust, Go e Python

- Em C, muito do que discutimos existe, mas com menos apoio da linguagem para RAII, tipos ricos e abstracoes seguras.
- Em Rust, varias dessas boas praticas sao empurradas mais agressivamente pelo compilador e pelo modelo de ownership.
- Em Go, simplicidade de linguagem e runtime forte reduzem parte do custo arquitetural, mas tambem limitam certo controle fino.
- Em Python, produtividade inicial e excelente, mas custo, layout e fronteiras nativas seguem outra historia.

C++ exige mais maturidade, mas paga isso com flexibilidade enorme.

## 17. Comandos exatos e fluxo minimo saudavel

Build de debug:

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -O0 -g main.cpp -o app
```

Build com sanitizers:

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -O0 -g -fsanitize=address -fsanitize=undefined main.cpp -o app
```

Build de release baseline:

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -O2 main.cpp -o app
```

### 17.1 Fluxo de trabalho recomendado

1. warnings fortes sempre
2. debug build frequente
3. sanitizer no fluxo de teste
4. benchmark e profiling antes de otimizar
5. release build so depois de corretude e observabilidade

---

## 18. Erros comuns e anti-padroes

1. **Escrever API antes de pensar em ownership e erro**.
2. **Expor internals demais no header publico**.
3. **Tratar `shared_ptr` como solucao universal**.
4. **Nao definir politica de erro por modulo ou camada**.
5. **Ignorar sanitizers e observabilidade em nome de "performance"**.
6. **Otimizar sem profiling**.
7. **Achar que compilar sem warning ja significa codigo saudavel**.
8. **Misturar concerns demais no mesmo tipo ou modulo**.

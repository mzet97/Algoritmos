# Aula 6 - Ponteiros, referencias, `new`, `delete`, smart pointers e ownership

---

## Objetivo da Aula

Entender como ponteiros e referencias se relacionam em C++, por que `new` e `delete` existem, quais problemas ownership manual cria, e como smart pointers ajudam a acoplar lifetime de recurso a objetos mais seguros. Ao final, voce deve conseguir diferenciar observacao, posse e compartilhamento de recurso sem misturar alias, dono e responsabilidade de destruicao.

## 2. Ponteiro nao e referencia

Isso precisa ficar cristalino.

Referencia:

- e alias com sintaxe mais simples;
- normalmente deve sempre referenciar algo valido;
- nao e pensada como "talvez nula" no uso idiomatico;
- nao tem a mesma semantica de reseat de um ponteiro.

Ponteiro:

- guarda endereco;
- pode ser nulo;
- pode ser mudado para apontar para outro objeto;
- pode participar de ownership manual ou apenas observacao.

Exemplo:

```cpp
int x = 10;

int& ref = x;
int* ptr = &x;
```

### 2.1 Leitura mental

- `ref` e outro nome para `x`
- `ptr` guarda o endereco de `x`

---

## 3. Operadores `&` e `*`

Em contextos iniciais:

- `&x` significa "endereco de `x`"
- `*ptr` significa "objeto apontado por `ptr`"

Exemplo:

```cpp
int x = 42;
int* p = &x;

std::cout << *p << "\n";
```

### 3.1 Cuidado

`*` aparece em papeis diferentes:

- declaracao de ponteiro: `int* p`
- dereference: `*p`

O significado depende do contexto sintatico.

---

## 4. Exemplo simples com ponteiro cru

```cpp
#include <iostream>

int main() {
    int valor = 25;
    int* p = &valor;

    std::cout << "valor = " << valor << "\n";
    std::cout << "*p = " << *p << "\n";

    *p = 99;

    std::cout << "valor depois = " << valor << "\n";
    return 0;
}
```

### 4.1 O que isso mostra?

- `p` aponta para `valor`
- ler `*p` le `valor`
- escrever `*p` altera `valor`

---

## 5. `nullptr`

Em C++ moderno, ponteiro nulo deve ser expresso com:

```cpp
nullptr
```

e nao com:

```cpp
0
NULL
```

### 5.1 Por que `nullptr` existe?

Porque:

- e semanticamente claro;
- evita ambiguidade;
- se integra melhor ao sistema de tipos de C++.

Exemplo:

```cpp
int* p = nullptr;
```

---

## 6. O que e memoria dinamica?

Memoria dinamica e memoria cujo lifetime nao fica preso ao escopo automatico de uma funcao.

Em C++ classico, ela pode ser obtida com:

- `new`

e liberada com:

- `delete`

Exemplo:

```cpp
int* p = new int(42);
delete p;
```

### 6.1 Por que isso existe?

Porque nem todo objeto:

- tem tamanho conhecido cedo;
- pode viver so na stack;
- pode morrer automaticamente ao fim do escopo local.

### 6.2 Qual o problema?

Ownership manual e facil de errar:

- leak;
- double delete;
- dangling pointer;
- excecao no meio do caminho;
- multiplos retornos sem cleanup.

---

## 7. `new` e `delete` na pratica

Exemplo:

```cpp
int* p = new int(7);
std::cout << *p << "\n";
delete p;
p = nullptr;
```

### 7.1 O que acontece?

- `new int(7)` aloca memoria e constroi um `int`
- `p` recebe o endereco
- `delete p` destroi o objeto e libera a memoria

### 7.2 E arrays?

```cpp
int* v = new int[5];
delete[] v;
```

Aqui:

- `new[]` combina com `delete[]`

Misturar:

- `new[]` com `delete`
- `new` com `delete[]`

e erro serio.

---

## 8. Ponteiro observador vs ponteiro dono

Essa distincao e uma das mais importantes de engenharia em C++.

### 8.1 Ponteiro observador

Usado para:

- apontar;
- observar;
- acessar algo sem ser dono.

Exemplo:

```cpp
void imprimir(const int* p) {
    if (p != nullptr) {
        std::cout << *p << "\n";
    }
}
```

Aqui a funcao:

- nao aloca;
- nao libera;
- so observa.

### 8.2 Ponteiro dono

Quando um ponteiro cru e dono, ele se torna perigoso:

- alguem precisa lembrar de `delete`
- ownership precisa ser documentado manualmente

Em C++ moderno, queremos reduzir muito esse caso.

---

## 9. Smart pointers

Smart pointers sao classes que encapsulam ponteiros e ownership.

Os principais no ecossistema moderno:

- `std::unique_ptr`
- `std::shared_ptr`
- `std::weak_ptr`

### 9.1 Ideia central

Em vez de:

- ponteiro cru + disciplina manual

preferimos:

- objeto com RAII para o recurso dinamico

Ou seja:

- o smart pointer nasce;
- o recurso fica sob sua responsabilidade;
- o smart pointer morre;
- o recurso e liberado corretamente.

---

## 10. `std::unique_ptr`

`std::unique_ptr<T>` representa ownership exclusivo.

Exemplo:

```cpp
#include <memory>

std::unique_ptr<int> p = std::make_unique<int>(42);
```

### 10.1 O que isso significa?

- `p` e dono unico do `int`
- nao ha copia permitida
- pode haver movimento

### 10.2 Por que isso e tao bom?

Porque torna ownership explicito no tipo.

---

## 11. `std::shared_ptr`

`std::shared_ptr<T>` representa ownership compartilhado por contagem de referencias.

Exemplo:

```cpp
auto p = std::make_shared<int>(42);
auto q = p;
```

Agora:

- `p` e `q` compartilham a posse
- o recurso morre quando o ultimo dono morre

### 11.1 Cuidado

`shared_ptr` nao e "mais moderno" por padrao.

Ele e mais pesado e mais complexo.

Use quando ownership compartilhado for realmente necessario.

---

## 12. `std::weak_ptr`

Serve para observar um objeto gerenciado por `shared_ptr` sem participar da posse.

Ele existe para evitar certos ciclos de ownership.

Hoje basta guardar:

- `weak_ptr` observa
- `shared_ptr` possui

## 13. Exemplo completo da aula

```cpp
#include <iostream>
#include <memory>

class Recurso {
public:
    explicit Recurso(int id) : id_(id) {
        std::cout << "Recurso " << id_ << " criado\n";
    }

    ~Recurso() {
        std::cout << "Recurso " << id_ << " destruido\n";
    }

    void usar() const {
        std::cout << "Usando recurso " << id_ << "\n";
    }

private:
    int id_;
};

void observar(const Recurso* r) {
    if (r != nullptr) {
        r->usar();
    }
}

void usar_unique(std::unique_ptr<Recurso> r) {
    if (r) {
        r->usar();
    }
}

int main() {
    Recurso local(1);
    observar(&local);

    auto p = std::make_unique<Recurso>(2);
    p->usar();

    usar_unique(std::move(p));

    if (!p) {
        std::cout << "p ficou vazio apos movimento\n";
    }

    auto s1 = std::make_shared<Recurso>(3);
    auto s2 = s1;

    std::cout << "uso compartilhado ativo\n";
    s1->usar();
    s2->usar();

    return 0;
}
```

---

## 14. O que esse exemplo mostra?

### 14.1 `Recurso local(1);`

- objeto automatico
- lifetime preso ao escopo

### 14.2 `observar(&local);`

- ponteiro cru como observador
- sem ownership

### 14.3 `std::make_unique<Recurso>(2)`

- cria recurso dinamico sob ownership exclusivo
- evita `new` explicito no codigo de usuario

### 14.4 `usar_unique(std::move(p));`

- transfere ownership para a funcao
- `p` deixa de ser dono

### 14.5 `make_shared`

- cria objeto com ownership compartilhado

---

## 15. Por que `make_unique` e `make_shared`?

Em codigo moderno, prefira:

- `std::make_unique<T>(...)`
- `std::make_shared<T>(...)`

em vez de:

```cpp
std::unique_ptr<T>(new T(...))
```

ou:

```cpp
std::shared_ptr<T>(new T(...))
```

### 15.1 Motivos

- mais clareza;
- menos repeticao de tipo;
- menos oportunidade de erro;
- padrao idiomatico moderno.

---

## 16. O que acontece em memoria?

No exemplo:

- `local` vive na stack frame de `main`
- o recurso de `unique_ptr` vive no heap
- o proprio `unique_ptr` pode viver na stack
- `shared_ptr` geralmente envolve objeto no heap e estrutura de controle de contagem

### 16.1 O ponto essencial

Nao confunda:

- onde vive o objeto wrapper

com:

- onde vive o recurso que ele administra

`unique_ptr` muitas vezes vive na stack, mas gerencia algo no heap.

---

## 17. Comparacao com C, Rust, Go e Python

- Em C, tudo isso tende a ser ponteiro cru e disciplina manual de `malloc/free`.
- Em Rust, `Box`, `Rc`, `Arc` e referencias fazem papeis relacionados, com checks muito mais fortes de ownership.
- Em Go, ponteiros existem, mas o GC muda completamente a historia de destruicao.
- Em Python, nomes e objetos vivem em modelo gerenciado automaticamente, com custo e semantica diferentes.

Em C++ moderno, a regra saudavel e:

- ponteiro cru para observacao, quando necessario;
- smart pointer para ownership dinamico;
- objeto automatico por valor quando possivel.

## 19. Erros comuns e anti-padroes

1. **Usar ponteiro cru como dono sem contrato claro**.
2. **Esquecer `delete` ao usar `new`**.
3. **Dar `delete` duas vezes no mesmo ponteiro**.
4. **Usar `delete` em vez de `delete[]` para array**.
5. **Achar que `shared_ptr` e default melhor que `unique_ptr`**.
6. **Mover `unique_ptr` e continuar usando como se ainda fosse dono**.
7. **Misturar observacao e ownership sem deixar isso explicito no tipo**.

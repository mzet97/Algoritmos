# Aula 32 - Projeto pratico de biblioteca/CLI de infraestrutura em C++

---

## Objetivo da Aula

Construir o modelo mental de uma pequena biblioteca de infraestrutura em C++ consumida por uma CLI separada, integrando API publica pequena, implementacao escondida, ownership previsivel, politica de erro clara, build reproduzivel, observabilidade minima e contrato operacional. Ao final, voce deve conseguir enxergar como transformar logica utilitaria interna em um componente mais reutilizavel, previsivel e maduro.

## 2. O que vamos construir?

O projeto sera uma pequena biblioteca de configuracao chave/valor em memoria, com:

- API publica pequena;
- classe com `Impl` escondida;
- ownership interno de strings;
- politica de erro explicita;
- CLI separada;
- build com varios arquivos;
- observabilidade minima.

### 2.1 Por que esse exemplo e bom?

Porque ele obriga voce a pensar em:

- fronteira publica vs privada;
- quem possui os dados;
- erros de uso vs erro operacional;
- formato de retorno;
- build e composicao;
- reutilizacao por outros programas.

---

## 3. Forma do projeto

Organizacao conceitual:

```text
config_store.hpp   -> API publica
config_store.cpp   -> implementacao interna
main.cpp           -> CLI
Makefile           -> build reproduzivel
```

### 3.1 Papel de cada parte

- `config_store.hpp`: contrato publico
- `config_store.cpp`: detalhes internos e armazenamento
- `main.cpp`: orquestra argumentos, chama API e exibe saida
- `Makefile`: padroniza build e variantes

## 4. API publica pequena

Uma API pequena e boa quando deixa claro:

- como iniciar;
- como usar;
- como ler erro;
- como destruir;
- o que fica escondido.

### 4.1 Escolha didatica

Vamos usar:

- classe `ConfigStore`
- `Status` por `enum class`
- `std::string_view` para entrada
- `std::optional<std::string>` para consulta

---

## 5. Implementacao escondida

Da Aula 26, trazemos PIMPL.

Isso ajuda a:

- reduzir dependencia de header;
- esconder container interno;
- evitar vazamento de layout;
- tornar a API mais estavel para evolucao interna.

### 5.1 O ponto importante

Usuario da biblioteca precisa saber:

- o que a classe faz

Nao precisa saber:

- como a tabela interna e guardada.

---

## 6. Politica de erro

Nesta biblioteca, queremos distinguir:

- uso correto que retorna ausencia de valor;
- tentativa invalida de inserir chave vazia;
- falha operacional mais rara.

### 6.1 Escolha do exemplo

- `set()` retorna `Status`
- `get()` retorna `std::optional<std::string>`
- `status_to_string()` traduz codigo para texto

### 6.2 Por que isso e bom didaticamente?

Porque mostra que:

- nem tudo precisa ser excecao;
- nem toda falha precisa ficar escondida;
- contrato de API precisa deixar semantica clara.

---

## 7. Observabilidade minima

Mesmo biblioteca pequena pode se beneficiar de:

- callback opcional de log;
- mensagem de erro coerente na CLI;
- separacao entre `stdout` e `stderr`.

### 7.1 Regra importante

Biblioteca nao deve:

- despejar logs arbitrarios no console sem acordo com o usuario.

Biblioteca deve preferir:

- hooks;
- callbacks;
- politica configuravel.

## 8. Exemplo completo da aula

### 8.1 `config_store.hpp`

```cpp
#pragma once

#include <functional>
#include <memory>
#include <optional>
#include <string>
#include <string_view>

class ConfigStore {
public:
    enum class Status {
        Ok,
        EmptyKey,
        InvalidArgument
    };

    using LogFn = std::function<void(std::string_view)>;

    ConfigStore();
    ~ConfigStore();

    ConfigStore(ConfigStore&&) noexcept;
    ConfigStore& operator=(ConfigStore&&) noexcept;

    ConfigStore(const ConfigStore&) = delete;
    ConfigStore& operator=(const ConfigStore&) = delete;

    void set_logger(LogFn logger);
    Status set(std::string_view key, std::string_view value);
    std::optional<std::string> get(std::string_view key) const;
    std::size_t size() const;

    static std::string_view status_to_string(Status status);

private:
    struct Impl;
    std::unique_ptr<Impl> impl_;
};
```

### 8.2 `config_store.cpp`

```cpp
#include "config_store.hpp"

#include <unordered_map>
#include <utility>

struct ConfigStore::Impl {
    std::unordered_map<std::string, std::string> data;
    LogFn logger;
};

ConfigStore::ConfigStore() : impl_(std::make_unique<Impl>()) {}

ConfigStore::~ConfigStore() = default;

ConfigStore::ConfigStore(ConfigStore&&) noexcept = default;
ConfigStore& ConfigStore::operator=(ConfigStore&&) noexcept = default;

void ConfigStore::set_logger(LogFn logger) {
    impl_->logger = std::move(logger);
}

ConfigStore::Status ConfigStore::set(std::string_view key, std::string_view value) {
    if (key.empty()) {
        if (impl_->logger) {
            impl_->logger("set failed: empty key");
        }
        return Status::EmptyKey;
    }

    impl_->data[std::string(key)] = std::string(value);

    if (impl_->logger) {
        impl_->logger("set ok");
    }

    return Status::Ok;
}

std::optional<std::string> ConfigStore::get(std::string_view key) const {
    auto it = impl_->data.find(std::string(key));
    if (it == impl_->data.end()) {
        return std::nullopt;
    }

    return it->second;
}

std::size_t ConfigStore::size() const {
    return impl_->data.size();
}

std::string_view ConfigStore::status_to_string(Status status) {
    switch (status) {
    case Status::Ok:
        return "ok";
    case Status::EmptyKey:
        return "empty_key";
    case Status::InvalidArgument:
        return "invalid_argument";
    }

    return "unknown";
}
```

### 8.3 `main.cpp`

```cpp
#include "config_store.hpp"

#include <iostream>
#include <string_view>

int main(int argc, char** argv) {
    if (argc < 3) {
        std::cerr << "usage:\n";
        std::cerr << "  app set <key> <value>\n";
        std::cerr << "  app get <key>\n";
        return 1;
    }

    ConfigStore store;
    store.set_logger([](std::string_view msg) {
        std::cerr << "[lib] " << msg << "\n";
    });

    std::string_view cmd = argv[1];

    if (cmd == "set") {
        if (argc != 4) {
            std::cerr << "set requires key and value\n";
            return 1;
        }

        auto status = store.set(argv[2], argv[3]);
        if (status != ConfigStore::Status::Ok) {
            std::cerr << "error: " << ConfigStore::status_to_string(status) << "\n";
            return 2;
        }

        std::cout << "ok size=" << store.size() << "\n";
        return 0;
    }

    if (cmd == "get") {
        auto value = store.get(argv[2]);
        if (!value) {
            std::cerr << "not found\n";
            return 3;
        }

        std::cout << *value << "\n";
        return 0;
    }

    std::cerr << "unknown command\n";
    return 1;
}
```

### 8.4 `Makefile`

```make
CXX := g++
CXXFLAGS := -std=c++20 -Wall -Wextra -Wpedantic
DBGFLAGS := -O0 -g
RELFLAGS := -O2
SANFLAGS := -O1 -g -fsanitize=address,undefined

all: debug

debug:
	$(CXX) $(CXXFLAGS) $(DBGFLAGS) config_store.cpp main.cpp -o app

release:
	$(CXX) $(CXXFLAGS) $(RELFLAGS) config_store.cpp main.cpp -o app

sanitize:
	$(CXX) $(CXXFLAGS) $(SANFLAGS) config_store.cpp main.cpp -o app

clean:
	rm -f app
```

## 9. O que esse projeto ensina?

### 9.1 Header pequeno

Usuario enxerga:

- contrato;
- tipos publicos;
- semantica.

Nao enxerga:

- container interno;
- estrategia exata de armazenamento.

### 9.2 `Impl`

Esconde detalhes e deixa a classe mais facil de evoluir internamente.

### 9.3 `std::string_view`

Ajuda a receber entrada sem impor copia na interface.

### 9.4 Copia interna

Biblioteca copia para `std::string` e passa a possuir os dados.

Isso simplifica:

- ownership;
- lifetime;
- previsibilidade.

### 9.5 CLI separada

Mostra como uma biblioteca pode ser:

- consumida por um executavel;
- testada isoladamente;
- reutilizada em outro contexto.

---

## 10. Por que nao retornar referencia interna?

Porque isso complicaria:

- ownership;
- lifetime;
- estabilidade de contrato;
- invalidacao futura.

### 10.1 Escolha didatica

`std::optional<std::string>` e mais caro do que algumas alternativas.

Mas torna a semantica:

- clara;
- segura;
- simples de explicar.

Depois, em sistemas reais, voce pode refinar o contrato.

---

## 11. E excecoes?

Poderiamos usar excecoes.

Mas aqui a escolha de retorno explicito ajuda a mostrar:

- politica de erro como parte do design;
- previsibilidade de CLI;
- separacao entre erro de uso e fluxo nominal.

### 11.1 Licao

Nao existe uma unica politica universal.

O importante e:

- consistencia;
- clareza de contrato;
- ergonomia adequada ao contexto.

## 12. Como isso conversa com a Aula 26?

PIMPL entra aqui de forma concreta:

- `ConfigStore` exposta;
- `Impl` escondida;
- destrutor definido no `.cpp`;
- move habilitado;
- copia desabilitada por simplicidade do exemplo.

Isso ajuda a conectar teoria de ABI e header leve a um desenho real de componente.

## 13. Como isso conversa com a Aula 27?

A biblioteca oferece:

- `set_logger`

Assim, o usuario decide:

- se quer log;
- para onde vai o log;
- com qual politica.

Isso e muito melhor do que:

- biblioteca imprimindo sozinha em `stdout`.

## 17. Erros comuns e anti-padroes

1. **Expor detalhes internos no header sem necessidade**.
2. **Nao deixar claro quem possui os dados recebidos pela biblioteca**.
3. **Misturar politica de log da biblioteca com a do usuario sem contrato**.
4. **Usar CLI para acessar detalhes internos que deveriam ficar atras da API**.
5. **Misturar `stdout` e `stderr` sem criterio**.
6. **Ter apenas um modo de build e nunca testar com sanitizer**.
7. **Aumentar funcionalidade antes de estabilizar contrato e ownership**.

# Aula 22 - Coroutines em C++ com `co_await`, `co_return`, frame e custo real

---

## Objetivo da Aula

Entender o que coroutines em C++ realmente sao, como `co_await`, `co_return` e `co_yield` se relacionam com suspensao e retomada, o que e o coroutine frame, e por que a aparencia de codigo linear nao elimina custo, estado nem problemas de lifetime. Ao final, voce deve conseguir ler uma coroutine sem misticismo, enxergando state machine, ownership, continuacoes e contrato de execucao.

---

## 1. Ponte com a aula anterior

Na Aula 21, vimos:

- `std::future`;
- `std::promise`;
- `std::packaged_task`;
- thread pools;
- composicao de tarefas.

La apareceu um problema importante:

- sincronizar resultado futuro e util;
- mas callbacks, pools e futures podem ficar duros de compor e ler.

Coroutines entram exatamente nesse ponto.

Pergunta central:

- como escrever fluxo que parece linear, mas representa trabalho que pode suspender e retomar depois?

---

## 2. O que coroutine nao e

Antes de definir o que e, vale limpar erros comuns.

Coroutine nao e automaticamente:

- thread;
- parallelismo;
- I/O assincrono pronto;
- runtime completo;
- performance gratis;
- eliminacao de estado.

### 2.1 O que ela e, entao?

Coroutine e um mecanismo da linguagem para:

- suspender execucao;
- preservar estado;
- retomar depois;
- expressar continuacoes de forma mais linear.

---

## 3. Modelo mental inicial

Pense em uma funcao comum:

- entra;
- executa;
- retorna;
- acabou.

Pense agora numa coroutine:

- entra;
- executa ate certo ponto;
- pode suspender;
- preserva estado local;
- mais tarde retoma;
- pode suspender de novo;
- eventualmente conclui.

### 3.1 O ponto mais importante

Coroutine e melhor entendida como:

- state machine gerada pelo compilador

e nao como:

- "funcao especial que roda de forma magica"

---

## 4. Palavras-chave principais

As tres palavras-chave mais marcantes sao:

- `co_await`
- `co_return`
- `co_yield`

### 4.1 `co_await`

Usada para:

- aguardar algo awaitable;
- possivelmente suspender a coroutine;
- retomar quando fizer sentido.

### 4.2 `co_return`

Usada para:

- concluir a coroutine produzindo resultado final.

### 4.3 `co_yield`

Usada para:

- produzir valores intermediarios em certos tipos de coroutine, como geradores.

Nesta aula, o foco principal sera:

- `co_await`
- `co_return`

---

## 5. O que o compilador precisa gerar?

Quando voce escreve coroutine, o compilador precisa dar conta de:

- estado local que sobrevive a suspensoes;
- ponto atual de execucao;
- valor final ou intermediario;
- tratamento de excecao;
- logica de retomada;
- logica de destruicao.

Tudo isso costuma viver no:

- coroutine frame

---

## 6. Coroutine frame

- **Coroutine frame**: estrutura de estado associada a uma coroutine, contendo o que precisa sobreviver entre suspensoes e retomadas.

Tipicamente isso inclui:

- parametros;
- variaveis locais vivas atraves de `co_await`;
- ponteiro ou identificador do estado atual;
- promise object;
- metadados de excecao ou resultado.

### 6.1 Onde esse frame vive?

Muitas vezes no heap.

Mas nao sempre do mesmo jeito ou com o mesmo custo observavel em todo contexto.

### 6.2 Consequencia pratica

Coroutine nao e "sintaxe sem custo".

Ela pode implicar:

- alocacao;
- indirecao;
- estado mais complexo;
- lifetime mais sutil.

---

## 7. Promise type

Toda coroutine em C++ esta ligada a um:

- promise type

Esse tipo participa do protocolo que define:

- como a coroutine nasce;
- como ela suspende inicialmente;
- como retorna valor;
- como trata excecao;
- o que acontece no final.

### 7.1 Intuicao

Se `future/promise` na aula anterior separavam produtor e consumidor de resultado, aqui a promise type da coroutine e parte do mecanismo interno que organiza o contrato da coroutine.

---

## 8. `co_await` nao significa "esperar bloqueando"

Esse e um erro conceitual comum.

Quando voce escreve:

```cpp
co_await algo;
```

o objetivo nao e necessariamente:

- bloquear a thread ate o resultado chegar

O objetivo e:

- consultar o protocolo do awaitable;
- decidir se suspende ou nao;
- organizar retomada quando apropriado.

### 8.1 Por que isso importa?

Porque `co_await` e sobre:

- suspensao cooperativa e continuacao

nao sobre:

- `sleep` bloqueante disfarcado.

---

## 9. Awaitable e protocolo

Para algo ser awaitable, ele precisa se encaixar no protocolo esperado por `co_await`.

Em termos conceituais, entram operacoes como:

- verificar se esta pronto;
- decidir suspensao;
- retomar depois;
- produzir resultado.

### 9.1 O ponto importante

Coroutine por si so nao sabe esperar rede, disco ou timer.

Ela depende de:

- awaitables;
- runtime;
- scheduler;
- integracao com event loop ou mecanismo de execucao.

## 10. Exemplo completo da aula

Este exemplo e didatico e nao tenta construir um runtime real.

Ele serve para mostrar:

- coroutine;
- promise type;
- suspensao explicita;
- retomada manual.

```cpp
#include <coroutine>
#include <exception>
#include <iostream>

struct SimpleTask {
    struct promise_type {
        SimpleTask get_return_object() {
            return SimpleTask{
                std::coroutine_handle<promise_type>::from_promise(*this)
            };
        }

        std::suspend_always initial_suspend() noexcept {
            return {};
        }

        std::suspend_always final_suspend() noexcept {
            return {};
        }

        void return_void() noexcept {}

        void unhandled_exception() {
            std::terminate();
        }
    };

    explicit SimpleTask(std::coroutine_handle<promise_type> h) : handle(h) {}

    SimpleTask(const SimpleTask&) = delete;
    SimpleTask& operator=(const SimpleTask&) = delete;

    SimpleTask(SimpleTask&& other) noexcept : handle(other.handle) {
        other.handle = {};
    }

    SimpleTask& operator=(SimpleTask&& other) noexcept {
        if (this == &other) {
            return *this;
        }

        if (handle) {
            handle.destroy();
        }

        handle = other.handle;
        other.handle = {};
        return *this;
    }

    ~SimpleTask() {
        if (handle) {
            handle.destroy();
        }
    }

    bool resume() {
        if (!handle || handle.done()) {
            return false;
        }

        handle.resume();
        return !handle.done();
    }

    std::coroutine_handle<promise_type> handle;
};

SimpleTask demo_coroutine() {
    std::cout << "inicio da coroutine\n";
    co_await std::suspend_always{};
    std::cout << "retomada 1\n";
    co_await std::suspend_always{};
    std::cout << "retomada 2\n";
    co_return;
}

int main() {
    auto task = demo_coroutine();

    std::cout << "coroutine criada\n";
    task.resume();
    std::cout << "apos primeira retomada\n";
    task.resume();
    std::cout << "apos segunda retomada\n";
    task.resume();
    std::cout << "apos terceira retomada\n";

    return 0;
}
```

---

## 11. O que esse exemplo mostra?

### 11.1 `initial_suspend`

Aqui escolhemos:

- `std::suspend_always`

Isso faz a coroutine nascer suspensa.

Ou seja:

- chamar `demo_coroutine()` cria a coroutine;
- ela ainda nao executa o corpo ate o primeiro `resume()`.

### 11.2 `final_suspend`

Tambem usamos:

- `std::suspend_always`

Isso facilita observar o ciclo de vida e controlar destruicao pelo handle.

### 11.3 `co_await std::suspend_always{}`

Usamos um awaitable pronto da biblioteca para forcar suspensao.

### 11.4 `resume()`

Retoma a coroutine manualmente.

No mundo real, essa retomada normalmente seria coordenada por:

- scheduler;
- event loop;
- executor;
- runtime.

---

## 12. Linha por linha do ponto central

Trecho:

```cpp
SimpleTask demo_coroutine() {
    std::cout << "inicio da coroutine\n";
    co_await std::suspend_always{};
    std::cout << "retomada 1\n";
    co_await std::suspend_always{};
    std::cout << "retomada 2\n";
    co_return;
}
```

Leitura correta:

- a coroutine comeca;
- imprime;
- suspende no primeiro `co_await`;
- ao retomar, continua dali;
- imprime de novo;
- suspende no segundo `co_await`;
- ao retomar, continua dali;
- imprime;
- conclui com `co_return`.

### 12.1 Moral

O corpo parece linear, mas o fluxo real e:

- fragmentado em etapas.

---

## 13. O que aconteceu com as variaveis locais?

Se uma variavel local precisa sobreviver entre suspensoes, ela vai para o estado que o frame precisa preservar.

Exemplo conceitual:

```cpp
Task exemplo() {
    int x = 10;
    co_await algo;
    use(x);
}
```

`x` nao pode simplesmente viver como local efemero de funcao comum.

Ela precisa sobreviver ate a retomada.

### 13.1 Consequencia

Isso explica por que:

- coroutine tem frame;
- frame tem custo;
- lifetime precisa ser entendido com seriedade.

---

## 14. Coroutines e ownership

Perguntas obrigatorias:

- quem possui o handle da coroutine?
- quem destroi o frame?
- quem garante que capturas e referencias ainda estao validas quando houver retomada?
- quem decide cancelamento?

### 14.1 Armadilha classica

Capturar referencia para algo que morre antes da retomada:

```cpp
// exemplo conceitual perigoso
Task t = [&]() -> Task {
    co_await algo;
    usar(obj_local);
}();
```

Se `obj_local` nao existir mais quando a coroutine retomar:

- bug grave de lifetime

### 14.2 Ligacao com a Aula 20

O problema conceitual e o mesmo de callbacks:

- async desloca execucao no tempo;
- lifetime deixa de ser obvio;
- ownership vira parte da arquitetura.

---

## 15. Coroutines nao substituem runtime

Uma das maiores fontes de confusao e achar que coroutines:

- "fazem async sozinhas"

Nao fazem.

Elas oferecem:

- mecanismo de linguagem para suspensao e retomada;
- melhor forma de expressar continuacoes.

Mas continuam precisando de:

- scheduler;
- executor;
- event loop;
- awaitables concretos;
- integracao com I/O ou fila de tarefas.

### 15.1 Regra pratica

Coroutine melhora:

- ergonomia

Nao elimina:

- problema arquitetural subjacente.

---

## 16. Coroutines vs callbacks

### 16.1 Callback

Pode levar a:

- nesting;
- espalhamento de estado;
- fluxo menos linear;
- dificuldade de seguir continuidade.

### 16.2 Coroutine

Pode trazer:

- codigo mais linear;
- estado mais local ao corpo;
- expressao mais clara de suspensao e retomada.

### 16.3 Mas o custo some?

Nao.

Ele apenas muda de forma:

- frame;
- protocolo awaitable;
- alocacao potencial;
- runtime de retomada;
- debugging diferente.

---

## 17. Coroutines vs `future`

### 17.1 `future`

Bom para:

- um resultado eventual;
- bloqueio controlado ou espera explicita;
- sincronizacao simples de produtor e consumidor.

### 17.2 Coroutine

Boa para:

- expressar fluxo com varios pontos de suspensao;
- evitar encadear callbacks ou futuros manualmente;
- compor continuacoes com sintaxe mais linear.

### 17.3 Nao sao rivais puros

Em sistemas reais, coroutines podem inclusive:

- esperar awaitables construidos sobre futures;
- ou conviver com pool, timers, fila e event loop.

## 18. `co_yield` em uma intuicao rapida

Mesmo sem aprofundar geradores hoje, vale registrar:

- `co_yield` serve para produzir valores intermediarios e suspender, em vez de so concluir com valor final.

Isso ajuda a modelar:

- generators;
- streams de valores;
- iteracao preguicosa.

Mais tarde, se fizer sentido, isso pode virar aula propria ou extensao pratica.

## 19. O que acontece em memoria e execucao?

Quando a coroutine nasce, o compilador e o runtime precisam montar estado suficiente para:

- guardar locals vivos;
- saber onde retomar;
- saber como finalizar;
- saber como destruir.

Isso costuma se materializar como:

- coroutine frame;
- promise object;
- handle.

### 19.1 Ponto central

O fluxo parece:

- linear

Mas a execucao real e:

- fragmentada;
- reentravel em pontos especificos;
- governada por protocolo de suspensao.

---

## 20. Comparacao com C, Rust, Go e Python

- Em C, algo parecido exige state machine manual, callbacks e estruturas de estado escritas a mao.
- Em Rust, `async`/`await` tambem compila para state machines, mas com outro ecossistema, executors e regras de ownership.
- Em Go, goroutines parecem muito mais leves de usar no dia a dia, mas seguem outro modelo de runtime e scheduling.
- Em Python, `async`/`await` tambem expressa continuacoes de forma linear, normalmente apoiado em event loop de alto nivel.

C++ oferece grande poder, mas pede que voce entenda:

- o mecanismo;
- o frame;
- o runtime envolvido;
- o custo real.

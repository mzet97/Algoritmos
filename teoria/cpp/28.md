## 2. Cache line

- **Cache line**: unidade de transferencia de dados entre niveis de cache e memoria principal, tipicamente algumas dezenas de bytes, sendo 64 bytes um valor muito comum.

### 2.1 O que isso significa na pratica?

Quando a CPU precisa de um dado, ela normalmente nao busca:

- apenas aquele byte isolado

Ela tende a trazer:

- uma linha inteira.

### 2.2 Consequencia

Se dados relacionados estiverem proximos:

- uma unica linha pode alimentar varios acessos.

Se dados estiverem espalhados:

- a CPU precisa buscar mais linhas;
- a localidade piora;
- a latencia aparece.

---

## 3. Layout de dados

Layout de dados responde:

- como os bytes de uma estrutura realmente ficam organizados na memoria?

Em C++, isso depende de:

- ordem dos membros;
- alinhamento;
- padding;
- contiguidade do container;
- indirecao extra;
- alocacoes separadas.

### 3.1 Por que isso importa?

Porque duas estruturas "equivalentes" em nivel conceitual podem ter custos muito diferentes:

- uma amigavel a cache;
- outra hostil ao hardware.

---

## 4. Localidade espacial e temporal

### 4.1 Localidade espacial

Se voce acessa um elemento, e provavel que acesse logo depois elementos vizinhos.

Exemplo tipico:

```cpp
for (std::size_t i = 0; i < v.size(); i++) {
    sum += v[i];
}
```

### 4.2 Localidade temporal

Se voce acessou algo recentemente, talvez acesse de novo em breve.

### 4.3 Moral

O hardware gosta de:

- dados contiguos;
- padroes previsiveis;
- reuso razoavel;

e sofre com:

- saltos;
- ponteiros espalhados;
- acesso aleatorio;
- concorrencia mal alinhada.

---

## 5. `std::vector` vs estruturas espalhadas

`std::vector<T>` costuma ajudar muito quando:

- `T` e razoavelmente compacto;
- o acesso e sequencial;
- a iteracao percorre elementos contiguos.

Ja estruturas baseadas em:

- ponteiros dispersos;
- listas encadeadas;
- grafos de objetos pequenos e separados;

podem pagar mais caro em:

- cache miss;
- prefetch ruim;
- TLB pressure;
- latencia por indirecao.

### 5.1 Isso significa "sempre use vector"?

Nao.

Significa:

- saiba o que o layout compra ou cobra.

## 6. False sharing

- **False sharing**: situacao em que threads diferentes acessam dados logicos independentes, mas esses dados caem na mesma cache line, gerando trafego de coerencia desnecessario.

### 6.1 O ponto mais importante

Nao precisa haver race condition logica para haver false sharing.

Basta que:

- duas threads escrevam em campos diferentes;
- mas esses campos morem na mesma linha de cache.

### 6.2 Consequencia

Cada escrita invalida a linha na cache da outra CPU.

Resultado:

- trafego de coerencia;
- perda de throughput;
- piora de latencia;
- escalabilidade decepcionante.

---

## 7. Exemplo conceitual de false sharing

```cpp
struct Counters {
    std::atomic<long long> a{0};
    std::atomic<long long> b{0};
};
```

Se uma thread faz:

- `a.fetch_add(...)`

e outra faz:

- `b.fetch_add(...)`

os campos podem acabar muito proximos.

Se estiverem na mesma cache line:

- falso compartilhamento possivel.

---

## 8. Exemplo de mitigacao por alinhamento/padding

```cpp
struct alignas(64) PaddedCounter {
    std::atomic<long long> value{0};
};

struct Counters {
    PaddedCounter a;
    PaddedCounter b;
};
```

### 8.1 O que a ideia tenta fazer?

- separar campos quentes de escrita em linhas diferentes;
- reduzir interferencia de coerencia.

### 8.2 Aviso importante

Padding e alinhamento nao sao brinquedo.

Eles podem:

- aumentar memoria total;
- mudar layout;
- piorar localidade para outros acessos;
- ser desnecessarios se o gargalo real for outro.

## 9. Exemplo completo da aula

Este exemplo compara:

- vetor contiguo de `int`;
- estrutura inflada com padding;
- counters compartilhados proximos;
- counters separados por alinhamento.

```cpp
#include <atomic>
#include <chrono>
#include <cstddef>
#include <iostream>
#include <thread>
#include <vector>

struct WideInt {
    int value;
    char padding[60];
};

struct SharedCounters {
    std::atomic<long long> a{0};
    std::atomic<long long> b{0};
};

struct alignas(64) PaddedAtomic {
    std::atomic<long long> value{0};
};

struct SplitCounters {
    PaddedAtomic a;
    PaddedAtomic b;
};

template <typename F>
long long timed_run(F f) {
    auto start = std::chrono::steady_clock::now();
    f();
    auto end = std::chrono::steady_clock::now();
    return std::chrono::duration_cast<std::chrono::microseconds>(end - start).count();
}

int main() {
    constexpr std::size_t n = 1'000'000;
    std::vector<int> compact(n, 1);
    std::vector<WideInt> wide(n);

    for (auto& x : wide) {
        x.value = 1;
    }

    volatile long long sum1 = 0;
    volatile long long sum2 = 0;

    auto t_compact = timed_run([&] {
        for (std::size_t i = 0; i < compact.size(); i++) {
            sum1 += compact[i];
        }
    });

    auto t_wide = timed_run([&] {
        for (std::size_t i = 0; i < wide.size(); i++) {
            sum2 += wide[i].value;
        }
    });

    SharedCounters shared;
    SplitCounters split;
    constexpr long long iters = 2'000'000;

    auto t_shared = timed_run([&] {
        std::thread t1([&] {
            for (long long i = 0; i < iters; i++) {
                shared.a.fetch_add(1, std::memory_order_relaxed);
            }
        });
        std::thread t2([&] {
            for (long long i = 0; i < iters; i++) {
                shared.b.fetch_add(1, std::memory_order_relaxed);
            }
        });
        t1.join();
        t2.join();
    });

    auto t_split = timed_run([&] {
        std::thread t1([&] {
            for (long long i = 0; i < iters; i++) {
                split.a.value.fetch_add(1, std::memory_order_relaxed);
            }
        });
        std::thread t2([&] {
            for (long long i = 0; i < iters; i++) {
                split.b.value.fetch_add(1, std::memory_order_relaxed);
            }
        });
        t1.join();
        t2.join();
    });

    std::cout << "compact_us=" << t_compact << "\n";
    std::cout << "wide_us=" << t_wide << "\n";
    std::cout << "shared_false_sharing_us=" << t_shared << "\n";
    std::cout << "split_counters_us=" << t_split << "\n";
    std::cout << "sum1=" << sum1 << " sum2=" << sum2 << "\n";
    return 0;
}
```

---

## 10. O que esse exemplo mostra?

### 10.1 `compact` vs `wide`

Mesmo valor logico:

- ambos representam inteiros

Mas o custo fisico muda porque `wide` ocupa muito mais espaco por elemento.

### 10.2 `SharedCounters`

Pode sofrer com false sharing se `a` e `b` cairem na mesma linha.

### 10.3 `SplitCounters`

Tenta separar os contadores em linhas diferentes.

### 10.4 O que medir?

- tempo da iteracao compacta vs larga;
- tempo do contador compartilhado vs separado.

Nao espere sempre a mesma diferenca em toda maquina.

Mas espere aprender o modelo.

## 11. Padding, alinhamento e trade-offs

Padding nao e so "desperdicio".

As vezes ele:

- evita false sharing;
- melhora alinhamento de vetorizacao;
- ajuda hardware.

Mas tambem pode:

- inflar memoria;
- reduzir densidade de dados;
- piorar cache para leituras sequenciais.

### 11.1 Conclusao

Nao existe "mais padding = melhor".

Existe:

- medir;
- entender padrao de acesso;
- decidir conforme o gargalo.

## 12. AoS vs SoA

Dois arranjos classicos:

- **AoS**: Array of Structs
- **SoA**: Struct of Arrays

### 12.1 AoS

Exemplo:

```cpp
struct Particle {
    float x;
    float y;
    float z;
    float mass;
};

std::vector<Particle> particles;
```

### 12.2 SoA

Exemplo:

```cpp
struct ParticleData {
    std::vector<float> x;
    std::vector<float> y;
    std::vector<float> z;
    std::vector<float> mass;
};
```

### 12.3 Quando SoA pode ganhar?

Quando um loop usa:

- apenas alguns campos;
- muito processamento vetorial;
- acesso sequencial por atributo.

### 12.4 Quando AoS pode ser melhor?

Quando a unidade semantica e:

- o objeto inteiro

e o codigo consome varios campos juntos.

## 13. Multicore e escrita compartilhada

Em multicore, cada escrita em dado compartilhado pode acionar trabalho de coerencia.

Isso vale especialmente para:

- atomics muito disputados;
- contadores globais;
- filas compartilhadas;
- locks quentes.

### 13.1 Regra pratica

Se varias threads escrevem frequentemente em dados proximos:

- suspeite de contencao e false sharing.

### 13.2 Possiveis tecnicas

- counters por thread;
- reducao por lote;
- sharding;
- alinhamento/padding;
- reduzir escrita compartilhada.

## 15. Localidade e alocacao conversam entre si

Da Aula 24, voce aprendeu que alocacao importa.

Aqui, o ponto fica mais forte:

- nao importa so alocar;
- importa como os dados ficam depois de alocados.

Dois programas podem:

- alocar a mesma quantidade total;

mas ter desempenho muito diferente porque:

- um layout e denso e previsivel;
- outro espalha e intercala dados demais.

## 16. Comparacao com C, Rust, Go e Python

- Em C, as mesmas leis fisicas valem, mas o controle de layout costuma ficar ainda mais explicito.
- Em Rust, ownership ajuda a organizar dados com mais seguranca, mas cache line e false sharing continuam problemas fisicos identicos.
- Em Go, o runtime muda parte da ergonomia, mas contencao, localidade e coerencia de cache continuam existindo.
- Em Python, muito disso fica soterrado sob o runtime, mas extensoes nativas e hot paths em baixo nivel obedecem exatamente ao mesmo hardware.

C++ e um ponto muito bom para estudar isso porque:

- permite controle fino de layout;
- oferece containers e atomics expressivos;
- fica perto o bastante do hardware para o custo aparecer claramente.

## 18. Erros comuns e anti-padroes

1. **Achar que Big-O basta para explicar custo real**.
2. **Ignorar layout e padding em estruturas quentes**.
3. **Assumir que threads independentes logicamente nao interferem fisicamente**.
4. **Adicionar padding sem medir se false sharing era mesmo o problema**.
5. **Usar estrutura espalhada quando acesso contiguo resolveria melhor**.
6. **Otimizar multicore olhando so para locks e esquecendo coerencia de cache**.

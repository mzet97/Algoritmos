# Aula 27 - Instrumentation, observabilidade nativa, logs, tracing e metricas em C++

---

## Objetivo da Aula

Entender como instrumentar software nativo em C++ com logs, metricas e tracing, quais perguntas cada mecanismo responde melhor, e como desenhar observabilidade sem transformar diagnostico operacional em improviso ou overhead cego. Ao final, voce deve conseguir olhar para uma biblioteca, CLI ou servidor e decidir o que observar, em que granularidade, com qual custo e com qual contrato semantico.

## 2. Observabilidade nao e "jogar print"

Muita gente comeca assim:

- adiciona `std::cout`
- roda de novo
- tenta adivinhar

Isso pode ajudar em casos pequenos.

Mas em sistema real, precisamos responder perguntas como:

- quantas requisicoes por segundo estao entrando?;
- qual etapa esta lenta?;
- quantas conexoes estao abertas?;
- quantos erros por categoria ocorreram?;
- onde o tempo de uma operacao foi gasto?;
- qual cliente ou request ficou preso?;

### 2.1 Conclusao

Observabilidade boa exige:

- modelo;
- semantica;
- identificadores coerentes;
- custo controlado;
- instrumentacao deliberada.

## 3. Tres pilares uteis: logs, metricas e tracing

### 3.1 Logs

Respondem bem:

- o que aconteceu?;
- em que ordem?;
- com quais parametros?;
- com qual mensagem humana?

### 3.2 Metricas

Respondem bem:

- quanto?;
- com que frequencia?;
- qual taxa?;
- qual distribuicao agregada?

### 3.3 Tracing

Responde bem:

- como uma operacao percorreu o sistema?;
- quais spans compoem a requisicao?;
- onde a latencia apareceu?;
- que relacao causal existe entre etapas?

### 3.4 Erro comum

Tentar usar uma so ferramenta para tudo.

## 4. Logs

Log e evento textual ou estruturado emitido pelo software.

Exemplos:

- inicializacao do servidor;
- erro ao abrir arquivo;
- cliente desconectado;
- timeout de operacao;
- falha de parse.

### 4.1 O que um bom log costuma ter?

- nivel;
- timestamp;
- contexto;
- identificador relevante;
- mensagem clara;

### 4.2 Niveis comuns

- `DEBUG`
- `INFO`
- `WARN`
- `ERROR`

### 4.3 O que evitar?

- mensagem vaga;
- log sem contexto;
- spam em hot path;
- log que muda formato a toda hora;
- log que vaza dado sensivel.

---

## 5. Metricas

Metrica e medicao agregavel.

Exemplos:

- total de requests;
- latencia media;
- p95 de resposta;
- numero de conexoes abertas;
- bytes enviados;
- erros por categoria.

### 5.1 Tipos conceituais uteis

- contador;
- gauge;
- histograma.

### 5.2 Intuicao rapida

- **contador**: cresce com eventos, como total de requests.
- **gauge**: valor atual, como conexoes abertas agora.
- **histograma**: distribuicao de latencias ou tamanhos.

---

## 6. Tracing

Tracing tenta modelar o caminho de uma operacao ao longo do sistema.

Uma request pode ser quebrada em:

- aceitar conexao;
- ler dados;
- parsear;
- consultar cache;
- chamar backend;
- serializar resposta;
- enviar bytes.

Cada parte pode virar:

- span

### 6.1 O que tracing compra?

- causalidade;
- hierarquia temporal;
- visao de latencia ponta a ponta;
- correlacao entre componentes.

### 6.2 Onde ele cobra?

- overhead;
- volume de dados;
- complexidade de integracao;
- necessidade de IDs coerentes.

---

## 7. O que instrumentar primeiro?

Regra pratica:

1. eventos de ciclo de vida importantes
2. erros e falhas relevantes
3. contadores e gauges basicos
4. latencias de operacoes importantes
5. tracing de fluxos criticos

### 7.1 Exemplos para servidor

- servidor iniciou;
- conexao aceita;
- conexao fechada por erro;
- request parseada;
- timeout de backend;
- total de requests;
- conexoes ativas;
- histograma de latencia por endpoint.

## 8. Exemplo completo da aula

Este exemplo mostra uma base didatica com:

- logger simples;
- metricas simples;
- span RAII para medir duracao.

```cpp
#include <chrono>
#include <iostream>
#include <map>
#include <string>
#include <string_view>

enum class LogLevel {
    Debug,
    Info,
    Warn,
    Error
};

std::string_view level_name(LogLevel level) {
    switch (level) {
    case LogLevel::Debug:
        return "DEBUG";
    case LogLevel::Info:
        return "INFO";
    case LogLevel::Warn:
        return "WARN";
    case LogLevel::Error:
        return "ERROR";
    }

    return "UNKNOWN";
}

class Logger {
public:
    void log(LogLevel level, std::string_view message) const {
        std::cout << "[" << level_name(level) << "] " << message << "\n";
    }
};

class Metrics {
public:
    void inc(std::string name) {
        ++counters_[std::move(name)];
    }

    void set_gauge(std::string name, long long value) {
        gauges_[std::move(name)] = value;
    }

    void dump() const {
        std::cout << "--- counters ---\n";
        for (const auto& [k, v] : counters_) {
            std::cout << k << "=" << v << "\n";
        }

        std::cout << "--- gauges ---\n";
        for (const auto& [k, v] : gauges_) {
            std::cout << k << "=" << v << "\n";
        }
    }

private:
    std::map<std::string, long long> counters_;
    std::map<std::string, long long> gauges_;
};

class ScopedSpan {
public:
    ScopedSpan(const Logger& logger, std::string name)
        : logger_(logger),
          name_(std::move(name)),
          start_(std::chrono::steady_clock::now()) {
        logger_.log(LogLevel::Debug, "span begin: " + name_);
    }

    ~ScopedSpan() {
        auto end = std::chrono::steady_clock::now();
        auto us = std::chrono::duration_cast<std::chrono::microseconds>(end - start_).count();
        logger_.log(LogLevel::Debug,
                    "span end: " + name_ + " duration_us=" + std::to_string(us));
    }

private:
    const Logger& logger_;
    std::string name_;
    std::chrono::steady_clock::time_point start_;
};

void process_request(const Logger& logger, Metrics& metrics, std::string_view input) {
    ScopedSpan span(logger, "process_request");

    metrics.inc("requests_total");

    if (input.empty()) {
        metrics.inc("request_errors_total");
        logger.log(LogLevel::Warn, "empty request");
        return;
    }

    logger.log(LogLevel::Info, "processing request");
    metrics.set_gauge("connections_active", 12);
}

int main() {
    Logger logger;
    Metrics metrics;

    logger.log(LogLevel::Info, "server starting");

    process_request(logger, metrics, "PING");
    process_request(logger, metrics, "");

    metrics.dump();
    return 0;
}
```

## 9. O que esse exemplo mostra?

### 9.1 `Logger`

Abstracao minima para centralizar formato.

### 9.2 `Metrics`

Separa:

- contadores;
- gauges.

### 9.3 `ScopedSpan`

Usa RAII para:

- marcar inicio;
- medir duracao;
- emitir fechamento automatico.

Essa tecnica e muito natural em C++.

### 9.4 `process_request`

Mostra como:

- log;
- metrica;
- medicao de duracao;

podem coexistir dentro de um fluxo de request.

## 10. RAII combina muito bem com instrumentation

Esse ponto merece destaque.

C++ consegue usar RAII muito bem para:

- medir escopo;
- restaurar contexto;
- abrir e fechar spans;
- contar recursos ativos;
- garantir cleanup mesmo em return antecipado ou excecao.

### 10.1 Exemplo mental

```cpp
ScopedSpan span(tracer, "db_query");
```

Ao sair do escopo:

- span fecha;
- duracao e registrada;
- caminho de erro nao esquece cleanup.

## 11. Logs estruturados vs logs livres

### 11.1 Log livre

Exemplo:

```text
cliente falhou
```

Ruim porque falta contexto.

### 11.2 Log melhor

Exemplo:

```text
level=ERROR event=client_read_failed conn_id=42 errno=104
```

Melhor porque facilita:

- grep;
- parse automatizado;
- agregacao;
- correlacao com outras fontes.

### 11.3 Regra pratica

Mesmo sem framework sofisticado, pense em:

- chaves estaveis;
- nomes consistentes;
- IDs reutilizaveis.

---

## 12. Cardinalidade de metricas

Esse e um erro classico de observabilidade.

Metrica com labels demais ou com valores muito variaveis pode explodir.

Exemplo ruim:

- `request_latency{user_id="1234567"}`

### 12.1 Por que e ruim?

Porque cria quantidade enorme de series.

### 12.2 Melhor

- endpoint;
- status;
- categoria de erro;

em vez de:

- IDs unicos por usuario ou request em metricas agregadas.

IDs unicos combinam mais com:

- tracing;
- logs.

---

## 13. Sampling e custo

Observabilidade tambem custa.

Pode custar:

- CPU;
- heap;
- I/O;
- lock;
- volume de dados;
- contencao.

### 13.1 Sampling

Uma estrategia comum e:

- registrar tudo que e critico;
- amostrar o que e volumoso.

Exemplos:

- erros: registrar todos
- traces completos: amostrar parte
- logs debug de hot path: amostrar ou desabilitar por padrao

## 14. O que logar e o que medir em servidor C++?

Perguntas boas:

- quantas conexoes ativas existem?;
- quantas requests por segundo?;
- quanto tempo o parse leva?;
- qual etapa do pipeline e gargalo?;
- quantos timeouts ocorreram?;
- quantos bytes estao em buffers de saida?;

### 14.1 Possivel mapeamento

- logs: erro de parse, falha de socket, shutdown, configuracao carregada
- metricas: requests_total, errors_total, connections_active, latency histogram
- tracing: request_span, backend_call_span, serialize_span, flush_span

## 15. Biblioteca tambem precisa de observabilidade?

Sim, mas com mais cuidado.

Biblioteca nao deve:

- despejar log arbitrario sem controle;
- impor backend gigantesco ao usuario;
- vazar detalhes demais;
- quebrar performance sem permitir configuracao.

### 15.1 Estrategias saudaveis

- hooks de logger;
- callbacks configuraveis;
- niveis de log;
- metricas opcionais;
- tracing integravel por API.

### 15.2 Ligacao com PIMPL e ABI

A forma de expor observabilidade tambem e parte do contrato publico.

## 16. Correlacao e IDs

Sem correlacao, diagnostico distribui dor em vez de informacao.

Boas perguntas:

- qual request gerou este erro?;
- qual conexao gerou este timeout?;
- qual span corresponde a este log?;

### 16.1 Elementos uteis

- `request_id`
- `connection_id`
- `trace_id`
- `span_id`

### 16.2 Regra pratica

Escolha alguns IDs centrais e propague-os de forma consistente.

## 17. Observabilidade e performance

Instrumentar sem pensar pode piorar exatamente o sistema que voce quer entender.

Perigos comuns:

- log com formatacao cara em hot path;
- lock global para toda emissao;
- alocacao excessiva por evento;
- flush sincrono demais;
- tags demais em metricas;
- tracing completo sem sampling.

### 17.1 Conclusao

Observabilidade boa precisa ser:

- util;
- controlavel;
- relativamente barata;
- semanticamente consistente.

## 18. Comparacao com C, Rust, Go e Python

- Em C, boa parte disso costuma ser mais manual, com macros, callbacks e bibliotecas menores ou caseiras.
- Em Rust, o ecossistema costuma integrar muito bem logging e tracing com tipos e macros dedicadas.
- Em Go, observabilidade tende a ser muito presente em servidores e ferramentas, com estilo mais padronizado em muitos projetos.
- Em Python, a ergonomia para instrumentar pode ser alta, mas o custo e o modelo operacional sao diferentes.

C++ tem uma vantagem interessante:

- RAII;
- controle fino;
- possibilidade de instrumentacao muito proxima do hot path;

e um risco correspondente:

- ficar caro ou incoerente se o desenho for improvisado.

## 20. Erros comuns e anti-padroes

1. **Confundir observabilidade com `printf` espalhado**.
2. **Logar demais no hot path sem controle de custo**.
3. **Criar metricas com cardinalidade explosiva**.
4. **Nao propagar IDs de correlacao**.
5. **Achar que tracing substitui metricas ou logs**.
6. **Instrumentar sem definir antes quais perguntas operacionais precisam ser respondidas**.

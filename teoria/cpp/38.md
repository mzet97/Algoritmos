# Aula 38 — E/S e sistema de arquivos mínimo: a ROM didática

Você vai ao terminar, você deverá executar `teoria/cpp/kernel38/`, ler os dois arquivos pela syscall `a7 == 3` a partir de modo-S e explicar por que o `id == 99` retorna `-1` em vez de desligar — e por que essa é a decisão de segurança da aula.

sistema de arquivos completo tem disco, bloco, diretório, escrita e permissão — nenhum deles cabe com honestidade num estágio. O que cabe é o contrato de leitura: nome (aqui, id) → (base, tamanho), cópia para o buffer do chamador, tamanho devolvido, id inválido negado. Esta aula entrega exatamente esse contrato sobre bytes estáticos do kernel: ROM didática, não FS real, e dizê-lo é parte do contrato.

## 1. Contrato antes do código

- `make -C teoria/cpp/kernel38 && python3 teoria/cpp/kernel38/test_kernel.py teoria/cpp/kernel38/kernel.elf` imprime `KERNEL38_OK`.
- Syscall `a7 == 3`: `a0` id, `a1` destino em S, `a2` máximo; devolve o tamanho em `a0`, ou `-1` se o id não existe. O tamanho copia o menor entre arquivo e buffer — truncar com tamanho avisado é contrato; estourar o buffer seria bug.
- Fora do contrato: escrita, persistência, diretórios, nomes por string (ids numéricos nesta etapa), permissão por usuário. A UART continua sendo a única "saída" observável.

## 2. Por que negar em vez de desligar

Nas aulas 34–37, causa desconhecida desliga com `0x3333`: trap inesperada é defeito do experimento. Aqui o `id == 99` não é defeito — é entrada hostil (ou bug do chamador), e entrada se nega, não se pune com desligamento. Essa é a primeira decisão de segurança do kernel: distinguir falha interna (desliga e diagnostica) de pedido inválido (nega com código e segue). O teste executa os três casos — arquivo 0, arquivo 1, id inválido — e só aceita `FS_OK` se os tamanhos baterem e a negação vier.

A cópia `dst[i] = dados[i]` em modo-M para buffer de S merece atenção explícita: nesta etapa não há validação do ponteiro (`a1` pode apontar para qualquer lugar, inclusive para cima do kernel). A aula declara a lacuna em vez de escondê-la: validação de ponteiro de usuário — checar faixa antes de copiar — é trabalho futuro, listado no checklist, e o kernel da 33 não a tem tampouco.

### Truncar com tamanho avisado é contrato; o resto é bug

A fórmula `n = min(tamanho, max)` carrega três decisões que o POSIX levou décadas para estabilizar: (a) nunca escrever além do `max` do chamador — o buffer é dele, e estourá-lo seria o kernel corrompendo quem pediu ajuda; (b) devolver o `n` realmente copiado, para o chamador detectar o truncamento e pedir o resto (leitura em loop: `while ((n = ler(...)) > 0)`) — sem o `n` honesto, o chamador não distingue "arquivo menor" de "cortei seu dado"; (c) devolver `-1` só para pedido inválido, nunca para arquivo vazio ou curto — EOF parcial é dado, não falha, a mesma distinção que a 32d de C cobra com o arquivo vazio. O teste dos três casos (arquivo 0, arquivo 1, id 99) cobre exatamente as três decisões: conteúdo certo, conteúdo certo de outro tamanho, negação. E a guarda vem antes do índice (`id` conferido antes de tocar `arquivos[id]`), nunca depois: tabela indexada por entrada externa sem guarda prévia é leitura fora dos limites com sintaxe de syscall.

## 3. Exemplo completo e executável

O [núcleo deste estágio](kernel38/kernel.cpp) (`boot.S`, `trap.S`, `link.ld`, `Makefile` e `test_kernel.py` no mesmo diretório):

```bash
make -C teoria/cpp/kernel38 kernel.elf
python3 teoria/cpp/kernel38/test_kernel.py teoria/cpp/kernel38/kernel.elf
# KERNEL38_OK marcadores=BOOT_OK,FS_OK,DONE
```

Transcrição serial esperada (determinística: o conteúdo dos arquivos é ecoado, saída 0):

```text
BOOT_OK
kernel38 v1
PI=314159
FS_OK
DONE
```

### Leitura guiada: o eco é o teste

Repare que a serial contém os próprios bytes dos arquivos (`kernel38 v1`, `PI=314159`) — não porque o kernel "imprime arquivos", mas porque a tarefa lê pela syscall e ecoa pela UART, e o teste só aceita `FS_OK` se os tamanhos baterem. O eco é conferência de ponta a ponta: byte que saiu da ROM, atravessou a cópia `dst[i] = dados[i]`, voltou no `a0` como tamanho e reapareceu na serial. Se a cópia truncasse errado, o eco divergiria; se o `n` mentisse, o eco cortaria. E o `id == 99` não deixa rastro na serial além da ausência de lixo — a negação certa é silenciosa (`-1` no registrador), enquanto a negação errada (ler fora da tabela) deixaria bytes aleatórios ou falta inesperada. Aqui, ausência de evidência (nada impresso pelo caso 99) É a evidência, porque o teste confere o `-1` no registrador antes de anunciar.

## 4. Erros comuns e implicações defensivas

1. **Confiar no `a1` sem checar:** o kernel copia para onde o chamador mandar. Nesta etapa a tarefa é benigna; num chamador hostil, isso é escrita arbitrária. A correção (validar faixa) está nomeada, não implementada — e a diferença entre as duas coisas é o tema da aula.
2. **Copiar `max` em vez de `min(tamanho, max)`:** estoura o buffer do chamador quando o arquivo é maior. O `n` devolvido precisa ser o que foi copiado, para o chamador detectar o truncamento.
3. **Esquecer o `-1` de id inválido:** sem o ramo de negação, `arquivos[99]` lê fora da tabela — no melhor caso lixo, no pior falta que o tratador não espera. Tabela indexada por entrada externa exige guarda antes do índice, sempre.
4. **Chamar de "sistema de arquivos":** sem escrita, sem nomes e sem persistência, é ROM com índice. O nome certo evita que o checklist da 40 cobre o que nunca foi prometido.
5. **Devolver o tamanho do arquivo em vez do copiado:** quando `max < tamanho`, anunciar o tamanho total mente sobre o que está no buffer — o chamador confia e lê lixo além do copiado. O `n` devolvido descreve o buffer, não o arquivo; o tamanho do arquivo se descobre pedindo de novo.
6. **Negar com desligamento:** tratar `id` inválido como defeito interno (`0x3333`) transforma bug do chamador em queda do kernel — negação de serviço por design. Entrada externa se nega com código; só falha interna desliga. A distinção é a aula inteira em uma frase.

## 5. Ponte com as demais trilhas

A 32a de C declara o FS além da UART como trabalho futuro — esta aula é a primeira parcela desse futuro, em C++. O par "syscall copia, tamanho devolve, inválido nega" é o mesmo protocolo que a 23f usa em espaço de usuário (erro memorizado, repetição servida): a diferença é que lá quem nega é o servidor, aqui é o kernel. Em Python/Go, o análogo honesto é `open()` sobre arquivo real — com a diferença de que lá o SO valida tudo por você, e aqui a aula mostra o que "validar tudo" significa.



**Referencias primarias:** contrato read(2) do POSIX (EOF parcial, EBADF).

## 7. Exercícios obrigatórios

Trabalhe numa cópia de `teoria/cpp/kernel38/` — o estágio do repositório não muda. Recompile com `make` e rode no QEMU (`qemu-system-riscv64 -machine virt -cpu rv64 -smp 1 -bios none -kernel kernel.elf -nographic`).

1. (Previsão) Leia o arquivo 0 com `max = 4`: preveja o retorno. Rode e explique por que leitura parcial é dado (`n = min(tamanho, max)`), não erro — e quem decide o resto (o chamador, com a próxima leitura... que aqui recomeça do zero).
2. (Diagnóstico) Leia o `id = 2` (com 2 arquivos, ids 0–1): preveja — aceito ou negado? Rode e explique o par que prende o off-by-one (1 passa, 2 nega): `id >= N_ARQUIVOS` nega o limite, e o teste do par prova os dois lados.
3. (Projeto) Adicione o 3º arquivo (`novo.txt`) à tabela e estenda a tarefa (ler, conferir tamanho, ecoar). Rode e explique o que não mudou: nem o handler, nem a syscall, nem o `N_ARQUIVOS` escrito à mão (`sizeof` conta sozinho).
4. (Previsão) Leia o arquivo 0 duas vezes seguidas: a 2ª devolve o mesmo conteúdo? Rode e explique — sem descritor não há posição: toda leitura recomeça do zero. Compare com o VFS da 32d em C, onde a posição mora no fd e a segunda leitura continua de onde parou.

# Aula 14 - Concorrencia com `std::thread`, mutexes, condvars, atomics e memory model

---

## Objetivo da Aula

Entender como C++ moderno modela concorrencia com `std::thread`, mutexes, condition variables, atomics e memory model, e por que compartilhar estado entre threads sem disciplina leva a data races e comportamento indefinido. Ao final, voce deve conseguir reconhecer quando sincronizar, quando evitar compartilhamento e por que concorrencia e muito mais do que "rodar duas coisas ao mesmo tempo".

## 2. `std::thread`

`std::thread` representa uma thread de execucao.

Exemplo:

```cpp
#include <thread>

void trabalho() {
}

int main() {
    std::thread t(trabalho);
    t.join();
}
```

### 2.1 O que `join()` faz?

- espera a thread terminar

### 2.2 Por que isso importa?

Porque o objeto `std::thread` precisa ser encerrado corretamente.

Se uma thread joinable morre sem `join()` ou `detach()` apropriado:

- o programa pode chamar `std::terminate()`.

---

## 3. Compartilhar estado e o problema real

Criar thread e facil.

Dificil e:

- compartilhar dados corretamente.

Exemplo perigoso:

```cpp
int contador = 0;
```

Se duas threads fazem:

```cpp
contador++;
```

sem sincronizacao, isso pode gerar data race.

### 3.1 Data race

Data race e acesso concorrente ao mesmo dado, com pelo menos uma escrita, sem sincronizacao adequada.

Em C++, data race implica:

- comportamento indefinido.

---

## 4. Mutex

Mutex e mecanismo de exclusao mutua.

Exemplo:

```cpp
#include <mutex>

std::mutex m;
```

Uso idiomatico:

```cpp
std::lock_guard<std::mutex> lock(m);
```

### 4.1 Por que `lock_guard`?

Porque usa RAII:

- trava no construtor;
- destrava no destrutor.

Isso evita esquecer `unlock()` em caminhos de erro.

---

## 5. Condition variable

Condition variable coordena espera por condicao entre threads.

Ela e muito usada quando:

- uma thread produz;
- outra consome;
- e precisamos dormir ate algo ficar pronto.

Mecanismo basico:

- `std::condition_variable`
- `wait`
- `notify_one`
- `notify_all`

---

## 6. Atomics

`std::atomic<T>` permite certas operacoes concorrentes sem data race no objeto atomico.

Exemplo:

```cpp
std::atomic<int> contador{0};
contador.fetch_add(1);
```

### 6.1 O que isso resolve?

- evita data race naquele dado atomico

### 6.2 O que isso nao resolve automaticamente?

- invariantes multi-campo;
- protocolos complexos;
- ordem de varias estruturas sem pensar no memory model.

---

## 7. Memory model

O memory model define regras de visibilidade e ordenacao entre operacoes concorrentes.

No comeco, o mais importante e guardar:

- sem sincronizacao, o compilador e a CPU podem reorganizar e observar estados inesperados;
- mutex e certos usos de atomics estabelecem relacoes seguras;
- concorrencia exige mais que intuicao sequencial.

---

## 8. Exemplo completo da aula

```cpp
#include <atomic>
#include <condition_variable>
#include <iostream>
#include <mutex>
#include <queue>
#include <thread>

std::mutex g_mutex;
std::condition_variable g_cv;
std::queue<int> g_fila;
bool g_done = false;
std::atomic<int> g_processados{0};

void produtor() {
    for (int i = 1; i <= 5; i++) {
        {
            std::lock_guard<std::mutex> lock(g_mutex);
            g_fila.push(i);
            std::cout << "produziu " << i << "\n";
        }
        g_cv.notify_one();
    }

    {
        std::lock_guard<std::mutex> lock(g_mutex);
        g_done = true;
    }
    g_cv.notify_one();
}

void consumidor() {
    for (;;) {
        int valor = 0;

        {
            std::unique_lock<std::mutex> lock(g_mutex);
            g_cv.wait(lock, [] {
                return !g_fila.empty() || g_done;
            });

            if (g_fila.empty() && g_done) {
                break;
            }

            valor = g_fila.front();
            g_fila.pop();
        }

        std::cout << "consumiu " << valor << "\n";
        g_processados.fetch_add(1);
    }
}

int main() {
    std::thread t1(produtor);
    std::thread t2(consumidor);

    t1.join();
    t2.join();

    std::cout << "total processado = "
              << g_processados.load() << "\n";

    return 0;
}
```

---

## 9. O que esse exemplo mostra?

### 9.1 Fila compartilhada

`g_fila` e estado compartilhado.

Por isso, acesso fica protegido por mutex.

### 9.2 `lock_guard`

Usado no produtor para secoes pequenas e simples.

### 9.3 `unique_lock`

Usado com `condition_variable`, porque a API de espera precisa dessa flexibilidade.

### 9.4 `wait(lock, predicado)`

Forma correta e idiomatica:

- espera dormindo;
- reacorda;
- revalida a condicao.

### 9.5 `std::atomic<int>`

Usado para contador simples de itens processados.

## 10. O que acontece em memoria e execucao?

Cada thread tem:

- sua propria stack;
- seu proprio fluxo de execucao.

Mas objetos globais e heap podem ser compartilhados.

Sem sincronizacao:

- leituras e escritas podem intercalar de forma perigosa;
- o compilador e a CPU nao sao obrigados a se comportar como seu modelo mental sequencial ingenuo.

### 10.1 Ponto central

Concorrencia correta exige:

- ownership;
- sincronizacao;
- modelo mental de visibilidade;
- disciplina de acesso.

---

## 11. `join`, `detach` e lifetime

### 11.1 `join`

Bom quando:

- voce quer esperar a thread terminar;
- o lifetime e claro;
- a thread faz parte do fluxo controlado.

### 11.2 `detach`

Mais perigoso.

Depois de `detach`, a thread segue independente.

Isso complica:

- lifetime de dados capturados;
- shutdown;
- observabilidade;
- cleanup.

### 11.3 Regra pratica

Prefira `join` ate ter motivo muito forte e desenho claro para `detach`.

---

## 12. Comparacao com C, Rust, Go e Python

- Em C, bibliotecas como pthreads cumprem papel semelhante, mas com API menos integrada ao object model de C++.
- Em Rust, concorrencia tambem e poderosa, com checks mais fortes de ownership e `Send`/`Sync`.
- Em Go, goroutines e channels mudam bastante a ergonomia, escondendo parte da mecanica bruta de threads.
- Em Python, threads convivem com outras limitacoes e o custo mental e diferente, especialmente por detalhes do runtime.

C++ te da poder alto e custo mental igualmente alto nesse tema.

## 14. Erros comuns e anti-padroes

1. **Compartilhar variavel mutavel entre threads sem sincronizacao**.
2. **Achar que `int++` e automaticamente seguro em concorrencia**.
3. **Usar atomics para protocolo complexo sem entender memory model**.
4. **Esquecer `join()` em thread ainda joinable**.
5. **Usar `detach()` para "resolver" problema de lifecycle**.
6. **Esperar em condition variable sem predicado correto**.

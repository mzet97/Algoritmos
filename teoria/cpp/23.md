# Aula 23 - Servidores modernos em C++ com buffers, protocolo, backpressure e arquitetura orientada a eventos

---

## Objetivo da Aula

Entender como desenhar um servidor moderno em C++ orientado a eventos, combinando event loop, buffers por conexao, protocolo com framing, controle de escrita e backpressure, sem esconder ownership, estado parcial e limites operacionais. Ao final, voce deve conseguir olhar para um servidor de rede e enxergar claramente a relacao entre API nativa, wrapper C++, parser incremental, fila de saida e politica de carga.

## 2. O que um servidor real precisa fazer alem de "ler e responder"

Servidor serio nao faz apenas:

- `recv`
- processar
- `send`

Ele precisa lidar com:

- conexoes lentas;
- leituras parciais;
- escritas parciais;
- mensagens incompletas;
- clientes malformados;
- limites de memoria;
- shutdown;
- fairness;
- observabilidade.

### 2.1 Consequencia

Isso obriga a pensar em:

- estado por conexao;
- buffer de entrada;
- buffer de saida;
- parser;
- fila de escrita;
- regras de fechamento.

## 3. Arquitetura orientada a eventos

No modelo orientado a eventos, o servidor tipicamente:

1. observa readiness do socket de escuta e dos sockets de clientes
2. aceita conexoes quando necessario
3. le o que estiver disponivel
4. alimenta parser incremental
5. enfileira respostas
6. tenta escrever quando houver oportunidade
7. fecha conexoes problematicas ou encerradas

### 3.1 O event loop coordena, nao "resolve tudo"

Ele organiza o ciclo.

Mas a corretude depende de:

- buffers corretos;
- parser correto;
- ownership correto;
- limites corretos.

---

## 4. Framing: a base do protocolo

Framing responde:

- como separar uma mensagem da outra?

Exemplos de framing:

- por delimitador, como `\n`
- por tamanho prefixado
- por formato fixo
- por cabecalho mais corpo

### 4.1 Erro classico

Assumir:

- um `recv` == uma mensagem completa

Isso e falso.

Rede entrega:

- fluxo de bytes;

nao:

- fronteira logica de mensagem.

---

## 5. Buffer de entrada por conexao

Cada conexao normalmente precisa de um buffer de entrada proprio.

Por que?

Porque a leitura pode trazer:

- meia mensagem;
- uma mensagem e meia;
- varias mensagens;
- dados ainda nao parseaveis por completo.

### 5.1 O que o buffer faz?

- acumula bytes recebidos;
- permite parser incremental;
- preserva resto nao consumido.

### 5.2 Consequencia arquitetural

Conexao nao e so um socket.

Conexao e:

- socket;
- buffer de entrada;
- buffer de saida;
- estado do protocolo;
- flags operacionais.

---

## 6. Buffer de saida por conexao

Muita gente esquece isso no primeiro desenho.

Mas escrita em rede tambem pode ser parcial.

### 6.1 Exemplo

Voce quer enviar 1 KB.

`send()` pode escrever:

- 200 bytes

e parar.

### 6.2 Consequencia

Voce precisa:

- guardar o resto;
- tentar de novo quando o socket estiver pronto para escrita;
- nao perder o offset do que ja foi enviado.

### 6.3 Moral

Servidor event-driven serio costuma ter:

- fila de saida por conexao

ou ao menos:

- buffer com cursor de envio pendente.

## 7. Backpressure

- **Backpressure**: mecanismos e politicas para impedir que produtores ou clientes lentos forcem crescimento descontrolado de buffers e trabalho pendente.

### 7.1 Quando ele aparece?

- cliente envia mais rapido do que voce processa;
- servidor produz resposta mais rapido do que cliente consome;
- fila de saida cresce;
- memoria por conexao explode;
- latencia do sistema piora.

### 7.2 Opcoes comuns

- impor limite por conexao;
- fechar conexao que excede limite;
- parar de ler temporariamente;
- degradar qualidade de servico;
- aplicar politicas de shedding.

## 8. Estado minimo de uma conexao

Modelo mental razoavel:

```cpp
struct Connection {
    SocketFd fd;
    std::string input_buffer;
    std::string output_buffer;
    std::size_t write_offset = 0;
    bool closing = false;
};
```

### 8.1 O que isso expressa?

- ownership do recurso;
- bytes recebidos e ainda nao consumidos;
- bytes a enviar;
- progresso de envio;
- decisao de fechamento.

## 9. Exemplo completo da aula

Este exemplo e didatico.

Ele nao implementa um servidor real completo.

Ele modela:

- conexao com buffers;
- parser por linha;
- fila de resposta;
- tentativa de flush parcial.

```cpp
#include <algorithm>
#include <cstddef>
#include <iostream>
#include <string>
#include <string_view>

struct Connection {
    int id;
    std::string input_buffer;
    std::string output_buffer;
    std::size_t write_offset = 0;
    bool closing = false;
};

void process_complete_line(Connection& conn, std::string_view line) {
    if (line == "PING") {
        conn.output_buffer += "PONG\n";
        return;
    }

    if (line == "QUIT") {
        conn.output_buffer += "BYE\n";
        conn.closing = true;
        return;
    }

    conn.output_buffer += "ERR unknown command\n";
}

void consume_input(Connection& conn) {
    for (;;) {
        std::size_t pos = conn.input_buffer.find('\n');
        if (pos == std::string::npos) {
            break;
        }

        std::string line = conn.input_buffer.substr(0, pos);
        conn.input_buffer.erase(0, pos + 1);
        process_complete_line(conn, line);
    }
}

void fake_recv(Connection& conn, std::string_view chunk) {
    conn.input_buffer.append(chunk.data(), chunk.size());
    consume_input(conn);
}

void fake_send_some(Connection& conn, std::size_t max_bytes) {
    if (conn.write_offset >= conn.output_buffer.size()) {
        return;
    }

    std::size_t remaining = conn.output_buffer.size() - conn.write_offset;
    std::size_t n = std::min(max_bytes, remaining);

    std::string_view sent_chunk(conn.output_buffer.data() + conn.write_offset, n);
    std::cout << "conn " << conn.id << " enviando: " << sent_chunk;

    conn.write_offset += n;

    if (conn.write_offset == conn.output_buffer.size()) {
        conn.output_buffer.clear();
        conn.write_offset = 0;
    }
}

int main() {
    Connection conn{1, {}, {}, 0, false};

    fake_recv(conn, "PIN");
    fake_recv(conn, "G\nQUIT");
    fake_recv(conn, "\n");

    fake_send_some(conn, 3);
    fake_send_some(conn, 1024);

    std::cout << "closing=" << conn.closing << "\n";
    return 0;
}
```

## 10. O que esse exemplo mostra?

### 10.1 `fake_recv`

Simula chegada parcial de bytes.

### 10.2 `consume_input`

Parser incremental:

- procura delimitador;
- consome linhas completas;
- preserva resto incompleto.

### 10.3 `process_complete_line`

Transforma mensagem de protocolo em resposta.

### 10.4 `fake_send_some`

Simula escrita parcial:

- envia so parte;
- avanca offset;
- limpa buffer quando tudo terminou.

### 10.5 `closing`

Decisao de encerramento tambem faz parte do estado da conexao.

## 11. O que esse exemplo ainda nao mostra?

Um servidor real precisaria ainda de:

- socket de escuta;
- event loop com API nativa;
- tabela de conexoes;
- tratamento de EOF e erro de socket;
- timeout;
- limites de buffer;
- logs;
- politica de backpressure;
- shutdown coordenado.

### 11.1 Mas o ganho do exemplo?

Ele mostra o mais importante:

- como o estado por conexao realmente se organiza.

## 12. Parser incremental e separacao de responsabilidades

Boa divisao:

- camada de I/O: le e escreve bytes
- camada de buffer: acumula e drena
- camada de framing: descobre mensagens completas
- camada de protocolo: interpreta comando
- camada de aplicacao: decide regra de negocio

### 12.1 Por que isso importa?

Porque misturar tudo no mesmo handler leva a:

- codigo fragil;
- bugs de reentrada;
- dificuldade de teste;
- evolucao cara.

## 13. Backpressure em termos concretos

Imagine que um cliente:

- manda milhares de comandos;
- ou nao consome respostas;
- ou responde muito devagar.

Se o servidor simplesmente continuar acumulando:

- `input_buffer`
- `output_buffer`

sem limite, uma conexao pode virar dreno de memoria.

### 13.1 Politicas possiveis

- limite maximo de `input_buffer`
- limite maximo de `output_buffer`
- fechar conexao se exceder
- deixar de registrar interesse em leitura por um tempo
- priorizar flush antes de aceitar mais carga

### 13.2 Isso e detalhe?

Nao.

Isso e parte da corretude operacional.

## 14. Onde entram thread pool e coroutines?

### 14.1 Thread pool

Pode ajudar quando:

- ha parte CPU-bound;
- parse ou transformacao fica pesada;
- voce nao quer bloquear a thread do loop.

Mas precisa de cuidado para:

- nao copiar buffers sem criterio;
- nao quebrar ordering;
- nao explodir contencao.

### 14.2 Coroutines

Podem ajudar a expressar:

- fluxo por conexao;
- espera por eventos;
- encadeamento de operacoes;

com sintaxe mais linear.

Mas continuam precisando:

- event loop;
- scheduler;
- ownership claro;
- cuidado com frame e lifetime.

### 14.3 Moral

Thread pool e coroutine nao substituem a arquitetura.

Eles a servem.

## 15. O que acontece em memoria?

Para cada conexao, o processo pode manter:

- objeto de estado;
- strings ou buffers dinamicos;
- fila de saida;
- parser parcial.

Se houver milhares de conexoes, pequenas decisoes importam muito:

- tamanho inicial de buffer;
- crescimento;
- copia;
- realocacao;
- contiguidade;
- lifetime de handlers e tarefas.

### 15.1 Ligacao com performance

Servidor moderno e tambem problema de:

- cache;
- alocacao;
- latencia;
- fairness;
- footprint de memoria.

---

## 16. O que acontece em fluxo de execucao?

No modelo event-driven:

- o loop acorda;
- identifica sockets prontos;
- chama manipuladores pequenos;
- cada manipulador avanca um pouco do estado;
- se ainda faltar trabalho, o estado fica pendente para a proxima rodada.

### 16.1 Ponto central

Voce raramente "termina tudo" em uma so chamada.

O desenho correto aceita:

- progresso parcial

como parte normal da vida do servidor.

---

## 17. Comparacao com C, Rust, Go e Python

- Em C, o modelo mecanico do servidor e o mesmo, mas buffers, ownership e parsing costumam ficar bem mais manuais.
- Em Rust, tipos ajudam bastante a modelar estado e ownership por conexao, e ecossistema async e forte.
- Em Go, goroutines e netpoll interno escondem boa parte da mecanica do event loop.
- Em Python, `asyncio` e frameworks simplificam muito a expressao, mas o custo e o controle fino seguem outra historia.

C++ oferece um meio-termo poderoso:

- bem proximo do sistema;
- bom para modelar buffers e wrappers RAII;
- capaz de integrar callback, pool e coroutine;
- perigoso se a arquitetura esconder demais custo e lifetime.

## 19. Erros comuns e anti-padroes

1. **Assumir que um `recv` entrega exatamente uma mensagem**.
2. **Nao manter buffer de saida e esquecer escrita parcial**.
3. **Misturar parser, protocolo, I/O e regra de negocio no mesmo bloco**.
4. **Nao impor limite de memoria por conexao**.
5. **Desenhar servidor sem politica de backpressure**.
6. **Jogar trabalho pesado na thread do event loop sem criterio**.
7. **Achar que coroutine ou pool eliminam necessidade de arquitetura clara**.

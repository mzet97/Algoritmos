# Aula 21 - `std::future`, `std::promise`, thread pools e composicao de tarefas

---

## Objetivo da Aula

Entender como `std::future`, `std::promise`, `std::packaged_task` e thread pools ajudam a modelar tarefas concorrentes e sincronizacao de resultado em C++, e quais sao os limites dessas ferramentas quando comparadas a event loops e I/O assincrono de verdade. Ao final, voce devera: compor tarefas com future/promise e pool sem vazar excecao; medir o teto de um pool fixo; e justificar quando pool basta e quando so event loop resolve.

### Como ler esta aula (tres niveis)

- **Fundamental:** future/promise, pool, esperar resultado.
- **Intermediario:** teto do pool, excecao que atravessa.
- **Aprofundamento (opcional):** pool vs event loop medidos (aula 23 decide).

Pergunta central:

- como representar trabalho que sera concluido depois e cujo resultado alguem quer observar ou aguardar?

## 2. Tarefa nao e a mesma coisa que I/O assincrono

Esse ponto precisa ficar muito claro.

Uma tarefa concorrente pode ser:

- computacao em outra thread;
- parse pesado;
- compressao;
- transformacao de dados;
- trabalho que termina e produz resultado.

I/O assincrono, por outro lado, lida com:

- espera por rede;
- espera por disco;
- espera por readiness ou completion;
- integracao com o sistema operacional.

### 2.1 Conclusao importante

`std::future` e `std::promise` ajudam muito a modelar:

- resultado futuro;
- sincronizacao;
- passagem de valor ou erro.

Mas nao equivalem, sozinhos, a:

- event loop;
- reactor;
- proactor;
- runtime async completo.

---

## 3. `std::future`

`std::future<T>` representa um resultado que ficara disponivel mais tarde.

Exemplo mental:

- alguem produz `T`
- alguem espera ou consulta esse `T`

### 3.1 Operacoes importantes

- `get()`
- `wait()`
- `wait_for()`
- `wait_until()`

### 3.2 O que `get()` faz?

- espera, se ainda nao estiver pronto;
- devolve o resultado;
- consome o valor do future.

Depois de `get()`, em geral aquele `future` nao pode ser usado para obter o mesmo valor de novo.

---

## 4. `std::promise`

`std::promise<T>` representa o lado produtor de um resultado.

Com ele, um componente pode:

- produzir valor depois;
- ou sinalizar erro via excecao armazenada.

Exemplo conceitual:

```cpp
std::promise<int> p;
std::future<int> f = p.get_future();
```

Agora:

- `p` produz
- `f` consome

### 4.1 O que isso compra?

Separacao explicita entre:

- quem calcula;
- quem espera;
- quem recebe o resultado.

---

## 5. Exemplo minimo com `promise` e `future`

```cpp
#include <future>
#include <iostream>
#include <thread>

int main() {
    std::promise<int> p;
    std::future<int> f = p.get_future();

    std::thread worker([p = std::move(p)]() mutable {
        p.set_value(42);
    });

    std::cout << "resultado = " << f.get() << "\n";

    worker.join();
    return 0;
}
```

### 5.1 O que acontece aqui?

- o `future` fica com o consumidor;
- a `promise` vai para a thread worker;
- a worker produz `42`;
- `f.get()` espera e recebe o valor.

---

## 6. Excecao em `future`

`promise` pode transportar falha tambem.

Exemplo conceitual:

```cpp
p.set_exception(std::make_exception_ptr(std::runtime_error("falha")));
```

Quando o consumidor fizer:

```cpp
f.get();
```

a excecao sera relancada no lado consumidor.

### 6.1 Por que isso e importante?

Porque `future` nao transporta apenas sucesso.

Ele pode transportar:

- valor;
- falha.

---

## 7. `std::async`

`std::async` fornece forma simples de obter `future` a partir de uma tarefa.

Exemplo:

```cpp
auto f = std::async(std::launch::async, [] {
    return 123;
});
```

### 7.1 Por que ele parece conveniente?

Porque junta:

- disparo de trabalho;
- entrega de future;
- gerenciamento inicial simplificado.

### 7.2 Qual o cuidado?

A politica de execucao pode variar.

Por isso, se quiser semantica mais explicita, prefira pensar bem em:

- `std::launch::async`
- ou desenho proprio com thread pool

---

## 8. `std::packaged_task`

`std::packaged_task` empacota uma chamada executavel que produz `future`.

Exemplo mental:

- funcao ou callable
- embrulhado em objeto
- executado depois
- future ligado ao resultado

Isso e muito util para:

- fila de tarefas;
- thread pools;
- agendamento explicito.

---

## 9. Thread pool

Thread pool e um conjunto fixo ou controlado de workers que consomem tarefas de uma fila comum.

### 9.1 Por que ele existe?

Porque criar thread para toda tarefa pode cobrar:

- overhead de criacao;
- overhead de destruicao;
- explosao de concorrencia;
- piora de latencia;
- pressao sobre scheduler.

### 9.2 O que o pool tenta fazer?

- reaproveitar workers;
- limitar paralelismo;
- centralizar fila;
- desacoplar submissao de execucao.

---

## 10. Exemplo completo da aula

Este exemplo mostra:

- fila de tarefas;
- workers;
- `packaged_task`;
- `future`.

```cpp
#include <condition_variable>
#include <cstddef>
#include <functional>
#include <future>
#include <iostream>
#include <mutex>
#include <queue>
#include <thread>
#include <utility>
#include <vector>

class ThreadPool {
public:
    explicit ThreadPool(std::size_t n) : stop_(false) {
        for (std::size_t i = 0; i < n; i++) {
            workers_.emplace_back([this] {
                for (;;) {
                    std::function<void()> job;

                    {
                        std::unique_lock<std::mutex> lock(mutex_);
                        cv_.wait(lock, [this] {
                            return stop_ || !jobs_.empty();
                        });

                        if (stop_ && jobs_.empty()) {
                            return;
                        }

                        job = std::move(jobs_.front());
                        jobs_.pop();
                    }

                    job();
                }
            });
        }
    }

    ~ThreadPool() {
        {
            std::lock_guard<std::mutex> lock(mutex_);
            stop_ = true;
        }
        cv_.notify_all();

        for (auto& t : workers_) {
            t.join();
        }
    }

    template <typename F>
    auto submit(F f) -> std::future<decltype(f())> {
        using Result = decltype(f());

        // packaged_task e move-only e std::function exige alvo copiavel:
        // quem atravessa a fila e um shared_ptr para a task, nao a task.
        auto task = std::make_shared<std::packaged_task<Result()>>(std::move(f));
        std::future<Result> future = task->get_future();

        {
            std::lock_guard<std::mutex> lock(mutex_);
            jobs_.push([task]() mutable {
                (*task)();
            });
        }

        cv_.notify_one();
        return future;
    }

private:
    std::vector<std::thread> workers_;
    std::queue<std::function<void()>> jobs_;
    std::mutex mutex_;
    std::condition_variable cv_;
    bool stop_;
};

int main() {
    ThreadPool pool(2);

    auto f1 = pool.submit([] {
        return 10 + 20;
    });

    auto f2 = pool.submit([] {
        int total = 0;
        for (int i = 1; i <= 5; i++) {
            total += i;
        }
        return total;
    });

    std::cout << "f1 = " << f1.get() << "\n";
    std::cout << "f2 = " << f2.get() << "\n";

    return 0;
}
```

---

## 11. O que esse exemplo mostra?

### 11.1 `ThreadPool`

O pool:

- possui workers;
- possui fila de jobs;
- sincroniza fila com mutex e condition variable.

### 11.2 `submit`

Recebe um callable, monta `packaged_task`, captura o `future` e agenda execucao.

### 11.3 `future`

O chamador continua com um handle para:

- aguardar;
- ou obter o resultado depois.

### 11.4 RAII no pool

O destrutor:

- sinaliza parada;
- acorda workers;
- faz `join`.

Ou seja:

- o lifetime do pool controla o lifetime dos workers.

---

## 12. O que esse exemplo nao resolve?

Muito importante:

- nao e event loop;
- nao e reactor;
- nao e runtime de rede;
- nao e scheduler universal;
- nao trata cancelamento sofisticado;
- nao trata prioridade;
- nao trata dependencias entre tarefas de forma rica.

### 12.1 O que ele resolve bem?

- fila simples de trabalho;
- reaproveitamento de threads;
- entrega de resultado futuro;
- composicao basica de tarefas.

---

## 13. `future` bloqueia, e isso importa

Quando voce faz:

```cpp
f.get();
```

ou:

```cpp
f.wait();
```

voce esta aguardando.

Se isso ocorrer no lugar errado, por exemplo:

- dentro da thread principal de um event loop

voce pode destruir:

- latencia;
- responsividade;
- throughput.

### 13.1 Moral

`future` e abstracao de sincronizacao de resultado.

Ele nao elimina o problema arquitetural de:

- onde posso bloquear?;
- onde nao posso bloquear?;

---

## 14. Thread pool nao e bala de prata

Pool ajuda quando:

- ha muitas tarefas pequenas ou medias;
- criar thread por tarefa seria caro;
- voce quer limitar paralelismo.

Mas pode piorar quando:

- tarefas bloqueiam demais;
- ha trabalho muito heterogeneo;
- fila unica vira gargalo;
- contencao em mutex cresce;
- o problema real era I/O e nao CPU.

### 14.1 Erro classico

Tentar resolver grande volume de conexoes de rede apenas com pool de threads e `future`, sem pensar no modelo de I/O subjacente.

---

## 15. `future` vs callback vs event loop

### 15.1 `future`

Bom para:

- um resultado eventual;
- sincronizacao de produtor e consumidor;
- trabalho executado em background;
- API de tarefa relativamente simples.

### 15.2 Callback

Bom para:

- reagir a evento;
- integrar com runtime ou loop externo;
- fluxo dirigido por evento.

### 15.3 Event loop

Bom para:

- muitas fontes de I/O;
- multiplexacao;
- alto numero de operacoes pendentes;
- integracao com timers e eventos do sistema.

### 15.4 Conclusao

Essas coisas podem coexistir.

Um sistema real pode ter:

- event loop para I/O;
- thread pool para CPU-bound;
- futures para resultados internos;
- callbacks ou coroutines na fronteira de composicao.

---

## 16. O que acontece em memoria e lifetime?

No exemplo:

- o pool possui vetor de threads;
- a fila possui jobs pendentes;
- `packaged_task` encapsula callable e estado do resultado;
- `future` observa o estado compartilhado do resultado.

### 16.1 Ponto importante

`future` e `promise` implicam estado compartilhado interno.

Esse estado precisa viver o bastante para:

- producao do valor;
- consumo do valor;
- propagacao de excecao se houver.

### 16.2 Ligacao com a Aula 20

Assim como em async de I/O, aqui tambem:

- lifetime e ownership nao desaparecem;
- eles apenas ficam encapsulados em outras estruturas.

## 17. Comparacao com C, Rust, Go e Python

- Em C, tudo isso costuma ser muito mais manual: fila, locks, estado de resultado e sinalizacao.
- Em Rust, `Future`, executors e tipos de sincronizacao seguem filosofia mais profunda de async e ownership.
- Em Go, goroutines e channels simplificam bastante a ergonomia para certos casos.
- Em Python, `concurrent.futures` e `asyncio` separam modelos parecidos em ergonomia de alto nivel.

C++ oferece boas pecas, mas nao um modelo unico e universalmente integrado para tudo.

## 20. Erros comuns e anti-padroes

1. **Achar que `future` sozinho equivale a runtime async completo**.
2. **Bloquear com `get()` no lugar errado e travar o fluxo inteiro**.
3. **Criar thread por tarefa quando um pool seria suficiente**.
4. **Usar pool para problema que era majoritariamente I/O-bound sem pensar no event loop**.
5. **Esquecer que fila unica e mutex podem virar gargalo**.
6. **Achar que thread pool resolve automaticamente cancelamento, prioridade e dependencia complexa**.

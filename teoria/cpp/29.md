# Aula 29 - Profiling de CPU e memoria com `perf`, `callgrind` e counters em C++

---

## Objetivo da Aula

Entender como sair de intuicao e entrar em diagnostico objetivo de desempenho em C++, usando `perf`, `callgrind` e counters para localizar hot paths, suspeitar de gargalos de CPU, branch ou memoria, e validar se hipoteses sobre layout, multicore e alocacao realmente aparecem nas medicoes. Ao final, voce deve conseguir investigar um programa C++ com mais metodo, distinguindo palpite de evidencia.

## 2. Benchmark simples nao basta

Medir tempo total e util.

Mas responde pouco.

Se um programa ficou mais lento, ainda faltam perguntas como:

- qual funcao esta quente?;
- o custo esta em CPU ou memoria?;
- existe branch miss relevante?;
- cache e layout parecem suspeitos?;
- a mudanca piorou contencao?;

### 2.1 Conclusao

Tempo total e:

- sintoma agregado

Profiling e counters ajudam a enxergar:

- distribuicao interna do custo.

---

## 3. O que queremos descobrir de verdade?

Quando voce perfila um programa C++, perguntas fortes sao:

- onde esta o hot path?;
- a CPU esta gastando ciclos em qual trecho?;
- ha indicio de branch imprevisivel?;
- ha suspeita de cache miss alto?;
- o custo esta em alocacao, chamada indireta, parsing ou sincronizacao?;
- throughput piorou por efeito fisico ou por logica de alto nivel?;

---

## 4. `perf`

`perf` e um conjunto de ferramentas Linux para:

- amostragem;
- call stacks;
- contadores de hardware;
- visao do sistema real.

### 4.1 O que ele entrega bem?

- quais funcoes aparecem mais em amostras;
- contagem de ciclos e instrucoes;
- branch misses;
- cache misses em varias configuracoes;
- call graph;
- anotacao de assembly.

### 4.2 O que ele nao e?

- nao e simulador perfeito;
- nao substitui leitura de codigo;
- nao explica sem contexto arquitetural.

---

## 5. `callgrind`

`callgrind` e uma ferramenta do ecossistema Valgrind focada em:

- custo por funcao;
- relacao entre chamadas;
- estrutura de call graph;
- simulacao detalhada.

### 5.1 Em que ele ajuda muito?

- entender distribuicao estrutural do custo;
- comparar funcoes e chamadores;
- explorar call graph com mais calma;
- raciocinar sobre custo relativo.

### 5.2 Em que ele cobra?

- execucao bem mais lenta;
- ambiente instrumentado, nao o sistema real puro.

---

## 6. Counters

Counters de hardware ajudam a observar eventos como:

- `cycles`
- `instructions`
- `branches`
- `branch-misses`
- `cache-references`
- `cache-misses`

### 6.1 O que eles dizem?

Nao dizem "a resposta final".

Eles dao pistas.

Exemplo:

- `branch-misses` alto pode sugerir padrao de controle ruim ou dados imprevisiveis;
- `cache-misses` alto pode sugerir localidade ruim ou working set grande;
- poucas instrucoes com muitos ciclos pode sugerir espera por memoria ou contencao.

---

## 7. Exemplo completo da aula

Este exemplo junta tres tipos de comportamento:

- acesso contiguo;
- acesso com stride grande;
- branch pouco previsivel.

```cpp
#include <chrono>
#include <cstddef>
#include <iostream>
#include <vector>

long long sum_linear(const std::vector<int>& v) {
    long long sum = 0;
    for (std::size_t i = 0; i < v.size(); i++) {
        sum += v[i];
    }
    return sum;
}

long long sum_stride(const std::vector<int>& v, std::size_t stride) {
    long long sum = 0;
    for (std::size_t i = 0; i < v.size(); i += stride) {
        sum += v[i];
    }
    return sum;
}

long long count_branchy(const std::vector<int>& v) {
    long long total = 0;
    for (int x : v) {
        if ((x % 7) < 3) {
            total += x;
        } else {
            total -= x;
        }
    }
    return total;
}

template <typename F>
long long timed_us(F f) {
    auto start = std::chrono::steady_clock::now();
    volatile long long result = f();
    auto end = std::chrono::steady_clock::now();
    (void)result;
    return std::chrono::duration_cast<std::chrono::microseconds>(end - start).count();
}

int main() {
    constexpr std::size_t n = 4'000'000;
    std::vector<int> data(n);

    for (std::size_t i = 0; i < data.size(); i++) {
        data[i] = static_cast<int>((i * 17) % 1024);
    }

    auto t1 = timed_us([&] { return sum_linear(data); });
    auto t2 = timed_us([&] { return sum_stride(data, 16); });
    auto t3 = timed_us([&] { return count_branchy(data); });

    std::cout << "sum_linear_us=" << t1 << "\n";
    std::cout << "sum_stride_us=" << t2 << "\n";
    std::cout << "count_branchy_us=" << t3 << "\n";
    return 0;
}
```

---

## 8. O que esse exemplo foi desenhado para mostrar?

### 8.1 `sum_linear`

Caso mais amigavel a:

- contiguidade;
- prefetch;
- cache.

### 8.2 `sum_stride`

Pode ter menos iteracoes, mas pior localidade.

Isso e importante porque:

- menos trabalho logico

nao significa automaticamente:

- menor custo fisico

### 8.3 `count_branchy`

Ajuda a suspeitar de:

- branch prediction;
- mistura entre controle e dados.

## 9. Como compilar para profiling?

Para um baseline razoavel:

- use simbolos de debug;
- evite otimizacao totalmente desligada se quiser algo mais proximo da realidade;
- compare tambem com niveis diferentes quando fizer sentido.

### 9.1 Baseline comum

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -O2 -g aula29.cpp -o aula29
```

ou:

```bash
clang++ -std=c++20 -Wall -Wextra -Wpedantic -O2 -g aula29.cpp -o aula29
```

## 10. `perf stat`

Primeiro passo muito util:

```bash
perf stat ./aula29
```

Ou escolhendo eventos:

```bash
perf stat -e cycles,instructions,branches,branch-misses,cache-references,cache-misses ./aula29
```

### 10.1 O que olhar?

- `cycles`
- `instructions`
- razao entre ambos
- `branch-misses`
- `cache-misses`

### 10.2 Perguntas uteis

- `sum_stride` gasta mais ciclos mesmo com menos iteracoes?;
- `count_branchy` parece pior em branch misses?;
- a intuicao da Aula 28 aparece nos counters?

---

## 11. `perf record` e `perf report`

Depois de olhar counters agregados, avance para hotspots:

```bash
perf record ./aula29
perf report
```

### 11.1 O que isso ajuda a ver?

- quais funcoes aparecem mais no perfil;
- como o custo se distribui;
- se o hot path esta onde voce esperava.

### 11.2 Licao importante

As vezes o gargalo nao esta onde a intuicao inicial apontava.

---

## 12. `perf annotate`

Quando quiser descer mais:

```bash
perf annotate
```

Isso ajuda a ligar:

- funcao quente;
- assembly relevante;
- pontos de carga, branch ou chamada.

### 12.1 Quando isso vale a pena?

- hot path realmente importante;
- diferenca pequena mas persistente;
- suspeita de branch, chamada indireta ou layout.

---

## 13. `callgrind`

Para ver a estrutura do custo:

```bash
valgrind --tool=callgrind ./aula29
callgrind_annotate callgrind.out.*
```

### 13.1 O que observar?

- custo por funcao;
- cadeia de chamadas;
- peso relativo entre partes;
- custo que sobe por wrapper ou indirecao.

### 13.2 Quando ele brilha?

- bibliotecas com muitas camadas;
- pipelines;
- exploracao mais calma da hierarquia de chamadas.

---

## 14. `callgrind` com simulacao adicional

Em alguns casos:

```bash
valgrind --tool=callgrind --cache-sim=yes --branch-sim=yes ./aula29
callgrind_annotate --auto=yes callgrind.out.*
```

### 14.1 Cuidado

Isso e mais pesado e mais artificial.

Use como apoio para raciocinio estrutural, nao como verdade absoluta do mundo real.

---

## 15. O que counters podem sugerir, sem exagero?

### 15.1 `branch-misses` alto

Pode sugerir:

- padrao de branch ruim;
- dados imprevisiveis;
- controle pouco amigavel.

### 15.2 `cache-misses` alto

Pode sugerir:

- localidade ruim;
- stride hostil;
- working set maior que o confortavel;
- indirecao excessiva.

### 15.3 `instructions` alto

Pode sugerir:

- trabalho demais;
- abstracao que expandiu muito;
- codigo menos otimizado.

### 15.4 `cycles` muito alto sem salto proporcional de instrucoes

Pode sugerir:

- memoria;
- espera;
- contencao;
- efeitos fisicos mais caros que "quantidade de codigo".

## 16. O que esta aula ensina alem da ferramenta?

Ferramenta sem modelo mental vira ruido.

Voce precisa conectar:

- sintomas observados;
- estrutura do codigo;
- layout dos dados;
- padrao de acesso;
- counters;
- hot paths.

### 16.1 Exemplo de raciocinio bom

1. suspeitei de localidade ruim
2. comparei `sum_linear` e `sum_stride`
3. vi counters e hotspots
4. confirmei que o problema fazia sentido fisico
5. so depois pensei em mudar layout ou loop

## 18. Comparacao com C, Rust, Go e Python

- Em C, as ferramentas e o hardware contam historia parecida, mas a infraestrutura costuma ser ainda mais manual.
- Em Rust, profiling continua essencial; ownership nao elimina gargalo de cache, branch ou layout.
- Em Go, o runtime participa mais da historia, mas hot paths e comportamento de memoria ainda precisam de medicao.
- Em Python, muito do custo fica escondido no interpretador e em extensoes nativas, mas o metodo de medir continua valendo.

C++ e um terreno muito bom para isso porque:

- layout aparece;
- abstracoes podem ser observadas no perfil;
- custo do hardware conversa diretamente com o design da linguagem e das bibliotecas.

## 20. Erros comuns e anti-padroes

1. **Olhar so tempo total e concluir cedo demais**.
2. **Interpretar um counter isolado como prova absoluta**.
3. **Usar `callgrind` como se representasse exatamente o sistema real**.
4. **Perfilar binario sem simbolos e perder contexto util**.
5. **Mudar layout ou padding sem confirmar hot path e sintomas**.
6. **Achar que a ferramenta substitui entendimento de arquitetura e dados**.

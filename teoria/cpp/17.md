# Aula 17 - Interoperabilidade com C, Rust e outras linguagens

---

## Objetivo da Aula

Entender como C++ cruza fronteiras de linguagem com C, Rust e outros ecossistemas, quais problemas ABI e ownership criam, e como desenhar interfaces mais estaveis para FFI. Ao final, voce deve conseguir reconhecer por que interoperar nao e apenas "dar include" ou "linkar a biblioteca", mas negociar layout, nome, lifetime, erro e contrato binario. Ao final, voce devera: expor uma funcao C++ com tipos simples e chama-la de outra linguagem (ou simular); declarar quem aloca/libera em cada direcao; e justificar tipos opacos e erro como codigo.

### Como ler esta aula (tres niveis)

- **Fundamental:** C como ABI comum, quem aloca libera.
- **Intermediario:** opacos, callbacks, erro como codigo.
- **Aprofundamento (opcional):** estabilidade de ABI (ponte 13b retoma).

## 2. Por que C costuma ser lingua franca?

Muitas integracoes binarias passam por interface estilo C porque C oferece:

- ABI mais simples;
- simbolos mais previsiveis;
- ausencia de sobrecarga;
- layout mais controlavel em tipos simples;
- interoperabilidade ampla entre toolchains.

### 2.1 Consequencia pratica

Mesmo quando a implementacao interna e C++, a fronteira externa frequentemente vira:

- API C

---

## 3. Name mangling e `extern "C"`

C++ faz name mangling para suportar recursos como:

- sobrecarga;
- namespaces;
- templates.

Isso altera o simbolo binario exportado.

Para expor uma funcao com convencao C, usamos:

```cpp
extern "C" int soma(int a, int b);
```

### 3.1 O que isso faz?

- pede ligacao estilo C para aquele simbolo;
- evita mangling C++ naquele ponto.

### 3.2 O que isso nao faz?

Nao transforma automaticamente tudo em "interoperabilidade segura".

Ainda restam:

- ownership;
- layout;
- excecoes;
- strings;
- alocacao;
- erros.

---

## 4. O que nao deve atravessar FFI com facilidade

Evite expor diretamente na fronteira:

- `std::string`
- `std::vector`
- templates
- excecoes C++
- classes com layout nao estabilizado
- referencias C++
- `std::function`

### 4.1 Por que?

Porque essas entidades:

- dependem de ABI de toolchain;
- podem variar entre compiladores;
- podem carregar contratos dificeis de reproduzir em outra linguagem.

---

## 5. O que costuma atravessar melhor

Tipos mais seguros na fronteira:

- `int32_t`, `uint64_t`
- `double`
- ponteiros opacos
- buffers com ponteiro + tamanho
- structs POD simples, com muito criterio
- codigos de erro inteiros ou enums simples

### 5.1 Ponteiro opaco

Padrao comum:

- do lado de fora, voce ve `struct Handle;`
- do lado de dentro, o C++ conhece a implementacao real

Isso ajuda a esconder:

- layout;
- membros privados;
- detalhes internos.

## 6. Exemplo C chamando implementacao C++

### 6.1 Header publico `math_c_api.h`

```cpp
#ifndef MATH_C_API_H
#define MATH_C_API_H

#ifdef __cplusplus
extern "C" {
#endif

int soma_ints(int a, int b);

#ifdef __cplusplus
}
#endif

#endif
```

### 6.2 Implementacao `math_c_api.cpp`

```cpp
#include "math_c_api.h"

extern "C" int soma_ints(int a, int b) {
    return a + b;
}
```

### 6.3 Uso em C `main.c`

```c
#include <stdio.h>

#include "math_c_api.h"

int main(void) {
    printf("%d\n", soma_ints(2, 3));
    return 0;
}
```

## 7. Ownership na fronteira

Pergunta obrigatoria:

- quem aloca?
- quem libera?

Se isso nao estiver claro, o sistema vira armadilha.

### 7.1 Padrao ruim

- C++ aloca internamente
- outra linguagem tenta liberar do proprio jeito

### 7.2 Padrao mais seguro

Expor funcoes pareadas:

- `obj_create()`
- `obj_destroy()`

ou usar buffer fornecido pelo chamador quando fizer sentido.

---

## 8. Excecoes nao devem atravessar fronteira C

Se uma funcao exportada estilo C lancar excecao atraves da fronteira, o resultado pode ser desastroso.

### 8.1 Regra pratica

Na fronteira externa:

- capture excecoes internamente;
- converta para codigo de erro ou resultado estruturado.

Exemplo conceitual:

```cpp
extern "C" int api_operacao(...) {
    try {
        return 0;
    } catch (...) {
        return -1;
    }
}
```

## 9. Interoperabilidade com Rust

Rust conversa muito bem com interfaces C-style.

Na pratica, o caminho comum e:

- C++ interno
- camada C pequena e estavel
- Rust chama a camada C

### 9.1 Por que esse caminho e comum?

Porque evita expor diretamente a complexidade ABI de C++.

### 9.2 O que precisa alinhar?

- ownership;
- nulabilidade;
- tamanho de buffer;
- quem libera memoria;
- codigos de erro;
- thread safety.

---

## 10. Interoperabilidade com Python, Go e outras linguagens

Quase sempre a mesma moral reaparece:

- crie fronteira pequena;
- use tipos simples;
- nao exponha detalhes internos do C++;
- documente ownership e erros;
- estabilize ABI.

### 10.1 O que muda?

Cada linguagem hospedeira tera sua ponte especifica:

- CPython extension ou C API
- cgo em Go
- FFI frameworks de outras linguagens

Mas a parte dificil continua:

- contrato nativo.

## 11. Exemplo com handle opaco

### 11.1 Header publico

```cpp
#ifndef COUNTER_API_H
#define COUNTER_API_H

#ifdef __cplusplus
extern "C" {
#endif

typedef struct CounterHandle CounterHandle;

CounterHandle* counter_create(int initial_value);
void counter_destroy(CounterHandle* handle);
int counter_increment(CounterHandle* handle);
int counter_get(const CounterHandle* handle);

#ifdef __cplusplus
}
#endif

#endif
```

### 11.2 Implementacao C++

```cpp
#include "counter_api.h"

class CounterImpl {
public:
    explicit CounterImpl(int initial_value) : value(initial_value) {}

    int increment() {
        return ++value;
    }

    int get() const {
        return value;
    }

private:
    int value;
};

struct CounterHandle {
    CounterImpl impl;
};

extern "C" CounterHandle* counter_create(int initial_value) {
    return new CounterHandle{{initial_value}};
}

extern "C" void counter_destroy(CounterHandle* handle) {
    delete handle;
}

extern "C" int counter_increment(CounterHandle* handle) {
    if (handle == nullptr) {
        return -1;
    }
    return handle->impl.increment();
}

extern "C" int counter_get(const CounterHandle* handle) {
    if (handle == nullptr) {
        return -1;
    }
    return handle->impl.get();
}
```

---

## 12. O que esse exemplo mostra?

### 12.1 Tipo opaco na API

O consumidor externo nao ve o layout de `CounterImpl`.

### 12.2 Ownership explicito

Temos:

- `counter_create`
- `counter_destroy`

### 12.3 Fronteira simples

Argumentos e retornos usam tipos C-like:

- ponteiro;
- `int`

### 12.4 Implementacao interna continua C++

Ou seja:

- podemos usar classes e encapsulamento por dentro;
- expomos interface estavel por fora.

---

## 13. O que acontece em memoria e ABI?

Na fronteira, so o contrato binario visivel importa.

Se voce esconder o tipo real atras de ponteiro opaco:

- evita expor layout interno;
- reduz acoplamento binario;
- facilita evolucao interna da implementacao.

### 13.1 Ponto central

FFI robusta quase sempre implica:

- superficie pequena;
- ownership claro;
- ABI simples;
- poucos tipos expostos.

---

## 14. Comparacao com C, Rust, Go e Python

- Em C, essa fronteira e o proprio idioma natural da linguagem.
- Em Rust, o mais comum e abracar a camada C-ABI como ponto de contato.
- Em Go, cgo costuma conversar melhor com API simples estilo C.
- Em Python, binding nativo tambem se beneficia de interface pequena e previsivel.

C++ e excelente motor interno, mas nem sempre a melhor lingua franca binaria direta.

## 16. Erros comuns e anti-padroes

1. **Expor `std::string` ou `std::vector` diretamente na FFI**.
2. **Deixar excecao atravessar fronteira C**.
3. **Nao documentar quem aloca e quem libera**.
4. **Expor layout de classe C++ como se fosse estavel entre toolchains**.
5. **Misturar compiladores e flags sem pensar em ABI**.
6. **Criar superficie de API grande demais antes de estabilizar o contrato**.

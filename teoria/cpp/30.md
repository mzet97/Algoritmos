# Aula 30 - SIMD, vetorizacao, `-march`, auto-vectorization e criterio para otimizar loops criticos em C++

---

## Nesta aula

Entender o que SIMD e vetorizacao realmente significam em C++, quando o compilador consegue transformar um loop escalar em execucao vetorial, quando isso falha, e em quais situacoes faz sentido confiar na auto-vetorizacao, reorganizar layout ou descer para intrinsics. Você vai aprender a ler o relatorio de vetorizacao e dizer por que sim/nao; medir o ganho com baseline e dispersao; e decidir com numero se intrinsics pagam.

## 2. O que e SIMD?

- **SIMD**: Single Instruction, Multiple Data.

Ideia central:

- uma instrucao pode operar sobre varios elementos de uma vez.

Exemplos conceituais:

- somar varios `float` em paralelo;
- multiplicar varios `int` ou `double`;
- aplicar a mesma operacao a um bloco contiguo de dados.

### 2.1 O que isso nao significa?

Nao significa:

- "qualquer loop fica magico e rapido"

SIMD ajuda melhor quando ha:

- dados homogeneos;
- acesso regular;
- poucas dependencias entre iteracoes;
- pouco controle imprevisivel;
- layout favoravel.

---

## 3. Vetorizacao

- **Vetorizacao**: transformacao de um loop escalar em execucao vetorial.

Ela pode acontecer de dois jeitos principais:

- automaticamente pelo compilador;
- manualmente pelo programador via intrinsics.

### 3.1 Auto-vectorization

O compilador tenta provar que:

- iteracoes sao independentes;
- aliasing nao impede transformacao;
- alinhamento e acesso sao aceitaveis;
- o ganho potencial compensa.

### 3.2 Vetorizacao manual

Quando o programador usa intrinsics ou tecnicas mais explicitas para controlar a operacao vetorial.

---

## 4. Por que o compilador nao vetoriza tudo?

Porque ele precisa ser conservador.

Coisas que atrapalham:

- aliasing incerto;
- ponteiros opacos;
- branches imprevisiveis;
- dependencias entre iteracoes;
- acesso com stride ruim;
- chamada de funcao no meio do loop;
- layout desfavoravel.

### 4.1 Regra pratica

O compilador vetoriza melhor codigo:

- simples;
- regular;
- contiguo;
- previsivel.

---

## 5. Loop amigavel a vetorizacao

Exemplo conceitual:

```cpp
for (std::size_t i = 0; i < n; i++) {
    out[i] = a[i] + b[i];
}
```

Isso tende a ser bom candidato porque:

- mesma operacao em cada iteracao;
- arrays contiguos;
- sem branch;
- sem dependencia entre iteracoes.

---

## 6. Loop hostil a vetorizacao

Exemplo conceitual:

```cpp
for (std::size_t i = 0; i < n; i++) {
    if (a[i] > limit) {
        out[i] = x[i] + y[i];
    } else {
        out[i] = x[i] - y[i];
    }
}
```

Aqui entram dificuldades como:

- branch;
- possivel imprevisibilidade dos dados;
- menor regularidade.

### 6.1 Ainda pode vetorizar?

As vezes sim, dependendo de:

- arquitetura;
- compilador;
- tecnica de masked operations;
- forma do codigo.

Mas ja nao e tao simples quanto o caso escalar regular.

---

## 7. Layout e vetorizacao conversam diretamente

Da Aula 28, voce traz:

- cache lines;
- contiguidade;
- AoS vs SoA;
- layout e localidade.

Agora o ponto fica ainda mais forte:

- loop vetorial gosta de ler blocos regulares de memoria.

### 7.1 SoA pode ajudar muito

Se o loop trabalha sobre:

- um campo de cada vez

SoA pode ser mais vetorizavel do que AoS.

### 7.2 Quando AoS pode atrapalhar?

Quando cada elemento traz campos que:

- o loop nem usa;
- poluem cache;
- quebram regularidade do acesso.

---

## 8. `-O2`, `-O3` e `-march`

### 8.1 `-O2`

Boa base geral.

Ativa varias otimizacoes sem ser tao agressivo.

### 8.2 `-O3`

Pode aplicar transformacoes mais agressivas.

Em certos loops numericos, pode ajudar mais.

Em outros casos:

- ganho pequeno;
- codigo maior;
- possivel piora de i-cache ou previsibilidade.

### 8.3 `-march=native`

Permite ao compilador usar recursos da CPU local.

Isso pode liberar:

- instrucoes vetoriais mais fortes;
- melhores escolhas de codigo;
- tuning especifico para a maquina.

### 8.4 Cuidado

`-march=native` melhora performance local, mas reduz portabilidade binaria.

## 9. Exemplo completo da aula

Este exemplo compara:

- `saxpy_scalar`
- `saxpy_branchy`
- `saxpy_restrict`

para discutir vetorizacao, aliasing e regularidade.

```cpp
#include <chrono>
#include <cstddef>
#include <iostream>
#include <vector>

void saxpy_scalar(const float* x, const float* y, float* out, float a, std::size_t n) {
    for (std::size_t i = 0; i < n; i++) {
        out[i] = a * x[i] + y[i];
    }
}

void saxpy_branchy(const float* x, const float* y, float* out, float a, std::size_t n) {
    for (std::size_t i = 0; i < n; i++) {
        if (x[i] > y[i]) {
            out[i] = a * x[i] + y[i];
        } else {
            out[i] = x[i] - y[i];
        }
    }
}

void saxpy_restrict(const float* __restrict x,
                    const float* __restrict y,
                    float* __restrict out,
                    float a,
                    std::size_t n) {
    for (std::size_t i = 0; i < n; i++) {
        out[i] = a * x[i] + y[i];
    }
}

template <typename F>
long long timed_us(F f) {
    auto start = std::chrono::steady_clock::now();
    f();
    auto end = std::chrono::steady_clock::now();
    return std::chrono::duration_cast<std::chrono::microseconds>(end - start).count();
}

int main() {
    constexpr std::size_t n = 8'000'000;
    std::vector<float> x(n, 1.25f);
    std::vector<float> y(n, 2.50f);
    std::vector<float> out(n, 0.0f);

    auto t1 = timed_us([&] {
        saxpy_scalar(x.data(), y.data(), out.data(), 2.0f, n);
    });

    auto t2 = timed_us([&] {
        saxpy_branchy(x.data(), y.data(), out.data(), 2.0f, n);
    });

    auto t3 = timed_us([&] {
        saxpy_restrict(x.data(), y.data(), out.data(), 2.0f, n);
    });

    std::cout << "scalar_us=" << t1 << "\n";
    std::cout << "branchy_us=" << t2 << "\n";
    std::cout << "restrict_us=" << t3 << "\n";
    std::cout << "out0=" << out[0] << "\n";
    return 0;
}
```

---

## 10. O que esse exemplo mostra?

### 10.1 `saxpy_scalar`

Loop simples, regular e classico para auto-vetorizacao.

### 10.2 `saxpy_branchy`

Introduce controle e possivel imprevisibilidade.

Pode reduzir o quanto o compilador consegue otimizar ou mudar a forma da vetorizacao.

### 10.3 `saxpy_restrict`

Tenta ajudar o compilador a assumir:

- `x`, `y` e `out` nao se sobrepoem

Isso pode facilitar otimizacao e vetorizacao.

### 10.4 Ponto importante

`restrict` nao e varinha magica.

Ele so ajuda se a promessa for verdadeira.

---

## 11. Aliasing e `restrict`

O compilador e conservador quando suspeita que ponteiros possam apontar para regioes sobrepostas.

Se houver aliasing possivel:

- ele pode evitar certas transformacoes.

### 11.1 O que `restrict` comunica?

Que aqueles ponteiros, dentro daquele contrato, representam regioes independentes.

### 11.2 Cuidado

Mentir com `restrict` pode introduzir comportamento incorreto.

## 12. Relatorios de vetorizacao

Uma das formas mais praticas de aprender e pedir ao compilador para contar o que fez.

Com `g++`, por exemplo:

```bash
g++ -std=c++20 -O3 -march=native -fopt-info-vec aula30.cpp -o aula30
g++ -std=c++20 -O3 -march=native -fopt-info-vec-missed aula30.cpp -o aula30
```

### 12.1 O que isso ajuda a ver?

- quais loops foram vetorizados;
- quais nao foram;
- pistas de por que falharam.

### 12.2 Isso substitui medicao?

Nao.

Relatorio do compilador ajuda a entender transformacao.

Performance final ainda precisa ser medida.

---

## 13. Auto-vectorization nao substitui profiling

Mesmo que um loop tenha sido vetorizado:

- talvez nao seja o verdadeiro gargalo;
- talvez o gargalo seja memoria, nao ALU;
- talvez o layout continue ruim;
- talvez a contencao multicore domine.

### 13.1 Regra de ouro

Primeiro:

- descubra hot path

Depois:

- investigue se vetorizar ali faz sentido.

---

## 14. Intrinsics

Intrinsics sao uma forma mais explicita de usar instrucoes vetoriais.

Exemplo de ecossistema:

- SSE
- AVX
- AVX2
- AVX-512

### 14.1 Quando pensar nisso?

- loop muito quente;
- auto-vetorizacao insuficiente;
- equipe entende custo de manutencao;
- portabilidade controlada;
- ganho potencial real.

### 14.2 Quando evitar?

- antes de medir;
- por vaidade tecnica;
- em codigo sem gargalo claro;
- quando layout e algoritmo ainda estao ruins.

---

## 15. Exemplo conceitual de intrinsics

Nao e para memorizar tudo agora.

E apenas para visualizar o grau de explicitude:

```cpp
#include <immintrin.h>

void add8(const float* a, const float* b, float* out) {
    __m256 va = _mm256_loadu_ps(a);
    __m256 vb = _mm256_loadu_ps(b);
    __m256 vc = _mm256_add_ps(va, vb);
    _mm256_storeu_ps(out, vc);
}
```

### 15.1 O que isso mostra?

- o programador controla mais;
- a complexidade sobe;
- a dependencia de ISA fica explicita;
- a manutencao e a portabilidade ficam mais delicadas.

---

## 16. Quando vetorizacao falha por culpa dos dados

Mesmo com loop bonito, pode haver limite por:

- bandwidth de memoria;
- working set grande demais;
- stride ruim;
- layout ruim;
- cargas desalinhadas;
- prefetch insuficiente;
- cache miss dominante.

### 16.1 Licao

SIMD nao cura:

- localidade ruim

Muitas vezes, a melhor otimizacao primeiro e:

- reorganizar dados

e nao:

- escrever intrinsics.

---

## 17. Comparacao com C, Rust, Go e Python

- Em C, a historia fisica e muito parecida; o programador pode descer para intrinsics com controle semelhante.
- Em Rust, vetorizacao e intrinsics existem, com outra camada de tipos e ecossistema.
- Em Go, o controle fino sobre vetorizacao e diferente e normalmente menos central para o programador comum.
- Em Python, o ganho vetorial normalmente entra via bibliotecas nativas como NumPy, nao em loops Python puros.

C++ fica num ponto forte porque:

- o compilador pode auto-vetorizar bem;
- o programador pode intervir quando necessario;
- layout e aliasing ficam suficientemente visiveis para raciocinio tecnico serio.

## 20. Erros comuns e anti-padroes

1. **Tentar vetorizar antes de descobrir o hot path real**.
2. **Assumir que `-O3` sempre melhora tudo**.
3. **Usar `-march=native` sem pensar em portabilidade**.
4. **Ignorar aliasing e achar que o compilador deveria "adivinhar" tudo**.
5. **Escrever intrinsics quando o verdadeiro problema era layout ou memoria**.
6. **Concluir que um loop vetorizado automaticamente ja esta otimo sem medir counters e tempo real**.

# Aula 26 - PIMPL, estabilidade binaria, headers mais leves e contratos de biblioteca

---

## Objetivo da Aula

Entender como PIMPL ajuda a reduzir dependencia de headers, esconder detalhes de implementacao e estabilizar parte da superficie binaria de uma biblioteca C++, e por que isso importa quando build time, ABI e distribuicao de componentes entram no jogo. Ao final, voce deve conseguir olhar para uma classe de biblioteca e perguntar quais detalhes realmente precisam estar no header, quais podem ficar opacos e como isso afeta recompilacao, compatibilidade e manutencao.

---

## 1. Ponte com a aula anterior

Na Aula 25, vimos:

- type erasure;
- `std::function`;
- SBO;
- custo de abstracoes de chamada;
- desenho de APIs flexiveis.

Agora vamos para outro custo estrutural de C++:

- custo fisico de headers e da exposicao de implementacao

Em C++, aquilo que voce coloca no header afeta:

- quem precisa recompilar;
- o quanto do seu layout fica exposto;
- o quanto da ABI pode quebrar;
- o acoplamento entre biblioteca e usuario.

Pergunta central:

- como esconder implementacao sem destruir a usabilidade da API?

---

## 2. O problema dos headers pesados

Imagine uma classe publica assim:

```cpp
class ImageProcessor {
public:
    void load(const std::string& path);
    void process();

private:
    std::vector<float> pixels_;
    std::unordered_map<std::string, int> metadata_;
    std::mutex mutex_;
    ThirdPartyHugeType heavy_;
};
```

Esse header pode forcar inclusao de:

- `<string>`
- `<vector>`
- `<unordered_map>`
- `<mutex>`
- headers pesados de terceiros

### 2.1 Consequencias

- mais tempo de compilacao;
- mais acoplamento textual;
- mais recompilacao em cascata;
- mais detalhes internos expostos;
- maior sensibilidade de layout e ABI.

---

## 3. O que e PIMPL?

- **PIMPL**: Pointer to IMPLementation.

Ideia central:

- o header publico declara a classe;
- detalhes reais ficam em uma struct/classe `Impl` definida no `.cpp`;
- a classe publica guarda apenas um ponteiro para essa implementacao.

### 3.1 O que isso compra?

- esconde detalhes internos;
- reduz includes no header;
- reduz acoplamento de build;
- pode estabilizar melhor o layout publico da classe.

---

## 4. Exemplo conceitual sem PIMPL

```cpp
class Logger {
public:
    void log(std::string_view msg);

private:
    std::vector<std::string> entries_;
    std::mutex mutex_;
};
```

Se voce mudar:

- `std::vector<std::string>` para outra estrutura;
- ordem dos campos;
- membros internos;

isso pode afetar:

- compilacao de dependentes;
- layout da classe;
- compatibilidade binaria.

---

## 5. Exemplo conceitual com PIMPL

Header:

```cpp
class Logger {
public:
    Logger();
    ~Logger();

    Logger(Logger&&) noexcept;
    Logger& operator=(Logger&&) noexcept;

    Logger(const Logger&) = delete;
    Logger& operator=(const Logger&) = delete;

    void log(std::string_view msg);

private:
    struct Impl;
    std::unique_ptr<Impl> impl_;
};
```

Source:

```cpp
struct Logger::Impl {
    std::vector<std::string> entries;
    std::mutex mutex;
};
```

### 5.1 O que mudou?

O header agora precisa conhecer bem menos sobre os detalhes internos.

O usuario sabe:

- existe `Logger`;
- existe sua API;
- existe um ponteiro para implementacao.

Mas nao ve:

- estrutura concreta dos dados internos.

---

## 6. Exemplo completo da aula

Arquivo unico para fins didaticos:

```cpp
#include <iostream>
#include <memory>
#include <string>
#include <string_view>
#include <utility>
#include <vector>

class ConfigStore {
public:
    ConfigStore();
    ~ConfigStore();

    ConfigStore(ConfigStore&&) noexcept;
    ConfigStore& operator=(ConfigStore&&) noexcept;

    ConfigStore(const ConfigStore&) = delete;
    ConfigStore& operator=(const ConfigStore&) = delete;

    void set(std::string key, std::string value);
    std::string_view get(std::string_view key) const;

private:
    struct Impl;
    std::unique_ptr<Impl> impl_;
};

struct ConfigStore::Impl {
    std::vector<std::pair<std::string, std::string>> items;
    std::string scratch;
};

ConfigStore::ConfigStore() : impl_(std::make_unique<Impl>()) {}
ConfigStore::~ConfigStore() = default;

ConfigStore::ConfigStore(ConfigStore&&) noexcept = default;
ConfigStore& ConfigStore::operator=(ConfigStore&&) noexcept = default;

void ConfigStore::set(std::string key, std::string value) {
    for (auto& [k, v] : impl_->items) {
        if (k == key) {
            v = std::move(value);
            return;
        }
    }

    impl_->items.push_back({std::move(key), std::move(value)});
}

std::string_view ConfigStore::get(std::string_view key) const {
    for (const auto& [k, v] : impl_->items) {
        if (k == key) {
            return v;
        }
    }

    return {};
}

int main() {
    ConfigStore cfg;
    cfg.set("host", "localhost");
    cfg.set("port", "8080");

    std::cout << "host=" << cfg.get("host") << "\n";
    std::cout << "port=" << cfg.get("port") << "\n";
    return 0;
}
```

---

## 7. O que esse exemplo mostra?

### 7.1 Header publico menor

A interface publica precisa conhecer:

- `std::unique_ptr`
- nomes dos metodos
- declaracao antecipada de `Impl`

Ela nao precisa expor diretamente:

- `std::vector<std::pair<std::string, std::string>>`
- outros detalhes internos

### 7.2 Implementacao escondida

`Impl` vive fora da interface publica concreta.

### 7.3 Move faz sentido, copia foi proibida

`std::unique_ptr` representa ownership exclusivo.

Entao, por padrao de design:

- mover e natural;
- copiar exige semantica explicita, e aqui foi proibido.

---

## 8. Por que PIMPL ajuda build time?

Em C++, dependencia textual pesa muito.

Se o header publico inclui muitos detalhes, qualquer alteracao interna pode forcar:

- recompilar varios usuarios da biblioteca

Com PIMPL, varias mudancas internas ficam confinadas ao `.cpp`.

### 8.1 Exemplos de mudancas internas menos invasivas

- trocar `std::vector` por outra estrutura;
- adicionar campo interno;
- reordenar membros internos;
- incluir dependencia pesada de terceiros;
- trocar estrategia de cache interna.

---

## 9. PIMPL e ABI

Este ponto precisa de cuidado.

PIMPL pode ajudar bastante a estabilizar o layout exposto da classe publica, porque o objeto publico tende a conter essencialmente:

- um ponteiro

ou algo muito proximo disso.

### 9.1 O que isso tende a proteger melhor?

- tamanho da classe publica;
- layout dos campos publicamente visiveis;
- exposicao de tipos internos;
- necessidade de recompilar usuarios por mudancas internas.

### 9.2 O que PIMPL nao resolve sozinho?

- toda compatibilidade binaria do universo;
- mudanca arbitraria de assinatura publica;
- regras de excecao atraves de fronteiras;
- mudancas de convencao de compilador/stdlib;
- compatibilidade entre toolchains diferentes.

---

## 10. O custo de PIMPL

Nada vem de graca.

PIMPL normalmente introduz:

- indirecao extra;
- alocacao dinamica da `Impl`;
- possivel pior localidade;
- mais cuidado com semantica especial;
- mais boilerplate.

### 10.1 Em que isso pode importar?

- hot path extremo;
- objetos minusculos criados em massa;
- estruturas muito sensiveis a localidade;
- cenarios onde um ponteiro extra pesa.

### 10.2 Em que costuma valer a pena?

- bibliotecas publicas;
- componentes grandes;
- tipos com dependencias pesadas;
- APIs distribuidas para terceiros;
- sistemas com compilacao cara.

---

## 11. Destrutor e tipo incompleto

Esse e um ponto tecnico importante.

No header, `Impl` e tipo incompleto.

`std::unique_ptr<Impl>` consegue existir com tipo incompleto em varios contextos, mas a destruicao precisa ocorrer onde `Impl` ja esteja completa.

Por isso, um padrao comum e:

- declarar destrutor no header;
- defini-lo no `.cpp`.

Exemplo:

```cpp
class Widget {
public:
    ~Widget();

private:
    struct Impl;
    std::unique_ptr<Impl> impl_;
};
```

E no `.cpp`:

```cpp
Widget::~Widget() = default;
```

### 11.1 Por que isso ajuda?

Porque nesse ponto o compilador ja conhece a definicao completa de `Impl`.

---

## 12. PIMPL e regras especiais de classe

Como ha `std::unique_ptr`, convem pensar explicitamente em:

- destrutor;
- move constructor;
- move assignment;
- copia proibida ou implementada de forma explicita.

### 12.1 Regra pratica

PIMPL quase sempre merece revisao consciente da:

- regra dos 5

mesmo que parte seja `= default`.

---

## 13. Forward declarations

PIMPL quase sempre anda junto com:

- declaracoes antecipadas

Isso ajuda a reduzir includes no header.

### 13.1 Mas cuidado

Forward declaration serve quando o header so precisa conhecer:

- que o tipo existe

Nao serve quando precisa conhecer:

- layout completo;
- tamanho;
- definicoes inline que dependem do tipo concreto.

---

## 14. PIMPL e contratos de biblioteca

Uma biblioteca madura precisa decidir:

- o que faz parte do contrato publico?;
- o que e detalhe interno?;

PIMPL e uma ferramenta forte para reforcar essa fronteira.

### 14.1 Exemplo de contrato bom

Usuario sabe:

- como construir;
- quais metodos chamar;
- quais erros esperar;
- qual semantica de lifetime existe.

Usuario nao precisa saber:

- qual container interno guarda dados;
- quantos mutexes existem;
- qual dependencia third-party esta escondida.

---

## 15. Quando PIMPL e exagero?

Nem toda classe precisa disso.

Pode ser exagero quando:

- tipo e pequeno e interno ao projeto;
- performance/localidade pesam mais que encapsulamento fisico;
- nao existe distribuicao binaria relevante;
- build time nao e dor real;
- o header ja e simples.

### 15.1 Regra saudavel

Use PIMPL quando ele resolver problema real de:

- acoplamento;
- ABI;
- dependencia;
- compilacao;
- encapsulamento fisico.

---

## 16. Comparacao com C, Rust, Go e Python

- Em C, a ideia de tipo opaco com ponteiro para struct privada e extremamente comum e conceitualmente parecida.
- Em Rust, encapsulamento de implementacao segue outras regras de modulo e crate, sem o mesmo modelo textual de headers.
- Em Go, o modelo de pacote e compilacao evita boa parte dessa dor especifica de headers.
- Em Python, detalhes internos podem ser escondidos por modulo/classe, mas o problema de ABI e diferente.

C++ herda parte da dor de:

- compilacao textual;
- headers;
- ABI delicada;

entao PIMPL vira ferramenta muito pratica de engenharia.

---

## 17. Relacao com alocacao e custo real

Na Aula 24, discutimos heap e estrategias de alocacao.

Aqui isso reaparece:

- PIMPL costuma implicar uma alocacao para `Impl`;
- isso pode ser irrelevante ou importante dependendo do contexto;
- se o objeto for muito criado/destruido, o custo pode aparecer.

### 17.1 Conclusao

PIMPL melhora encapsulamento fisico e build, mas nao e gratis em:

- heap;
- indirecao;
- localidade.

---

## 18. Relacao com distribuicao de bibliotecas

Se voce entrega:

- DLLs;
- shared libraries;
- SDKs nativos;

o cuidado com superficie binaria cresce muito.

PIMPL pode ajudar a tornar a interface publica:

- menos fragil;
- menos vazadora de detalhes;
- menos sensivel a mudancas internas frequentes.

Mas continua sendo necessario pensar em:

- versao de compilador;
- stdlib;
- flags;
- excecoes;
- alocacao atraves de fronteiras;
- ownership entre modulos.

## 20. Erros comuns e anti-padroes

1. **Usar PIMPL sem motivo real so porque parece sofisticado**.
2. **Esquecer o custo de heap e indirecao introduzido pela `Impl`**.
3. **Definir destrutor no lugar errado quando o tipo ainda esta incompleto**.
4. **Achar que PIMPL sozinho garante compatibilidade binaria total**.
5. **Esconder implementacao, mas continuar expondo dependencias pesadas desnecessarias no header**.
6. **Aplicar PIMPL em tipos minimos de hot path onde localidade e critica sem medir o impacto**.
